# Transaction Durability and Recovery Through redb

The engine does not implement its own WAL, page redo, checkpoints, segment retention, or root-slot selection. The pinned [redb backend](redb-storage.md) owns persistent atomicity and recovery. Never layer an independent engine WAL around it or write database-file bytes behind redb.

The engine maps one successful invocation's final data, index, catalog, audit, and durable outcome update into one redb write transaction. Choose a durable redb commit mode explicitly. A successful client commit response requires redb to report success under that mode. An ambiguous commit error is UNKNOWN until redb recovery/current state establishes the outcome; do not report ABORTED based on a lost response.

Invocation read snapshots and private write overlays are engine-managed; redb owns its snapshot/page lifetime and file recovery. See [redb transaction mapping](redb-storage.md) for ordering and cancellation semantics.

Required validation uses the pinned redb release: crash/reopen around commits, aborted writes, atomic updates to rows/indexes/catalog/outcomes, read-snapshot retention, file errors/corruption, and every enabled durability mode. [`process_exit_after_durable_commit_preserves_reconcilable_outcome`](../engine/tests/commit.rs) exits a child process immediately after a durable commit and reconciles its outcome after reopen. [`process_exit_after_atomic_row_index_commit_preserves_publication`](../engine/tests/commit.rs) verifies the row, index locator, catalog dependency, audit record, outcome, and commit sequence together after a child exits immediately after publication. These tests exercise process exit after successful commit only; they do not prove filesystem power-loss behavior or recovery from an error returned inside `redb::WriteTransaction::commit`. There are no engine WAL/checkpoint record encodings in this design.
