# IPC Protocol

## Transport and Authority

This document specifies internal process IPC. External clients use the separate [network protocol](client-protocol.md) terminated by the [gateway](client-gateway.md); its service role translates an allowlist of admission/control operations and cannot tunnel arbitrary internal messages. Internal executor/planner connections start with copied, framed messages over a Unix socket. Each execution/planning connection is provisioned by the supervisor and bound server-side to one invocation context and role. Client admission is a separate authenticated control interface; it does not inherit an invocation role from a message field. The worker cannot authenticate as another principal by changing a message field.

Use connection-scoped handles with server-side ownership and lifetime checks. Handle possession or guessability alone must not bypass authorization. Do not pass database descriptors or accept arbitrary descriptor transfer.

Numeric operator/page/request-count ceilings below are reference defaults supplied by the trusted workload-budget profile in [workload profile](workload-profile.md#configurable-bounds-and-production-sizing), unless explicitly marked as a format invariant. V1's 1 MiB frame payload is a hard envelope; effective per-request byte and row ceilings may be configured below it, and cumulative query work may exceed one frame by paging/chunking. Count fields' representable ranges are format limits; current smaller count ceilings are profile defaults unless a versioned payload explicitly reserves them. Raising a profile value must not bypass per-invocation/global budgets, cancellation, or authorization.

## Frame Envelope v1

Unix-stream frames use a fixed 20-byte header followed by a copied payload. Header fields are big-endian and ordered as: four-byte magic `PRDI`, u16 frame version (`1`), u16 operation code, u64 nonzero request ID, and u32 payload length. Operation code zero is reserved and rejected. A payload is at most 1,048,576 bytes; reject larger lengths before allocating or reading the payload. The header has no client-controlled service-role, principal, invocation, handle, or descriptor fields. Channel provisioning binds the service role and execution context out of band. Operation payload schemas are independently versioned and validated by the selected channel handler.

Readers accept arbitrary stream fragmentation and leave following coalesced frames available for the next read. EOF is clean only between frames; EOF within a header or payload is a truncated-frame error. Unknown frame versions and malformed headers fail before payload allocation. Frame payloads contain encoded fields, never native struct memory.

The Rust and C frame codecs use shared v1 validation status values: invalid magic `2`, unsupported version `3`, invalid operation `4`, unknown operation `5`, invalid request ID `6`, payload too large `7`, and truncated frame `8`. C-only argument and output-capacity results remain local API statuses; Rust transport I/O failures do not map to a frame-validation status.

The C v1 frame codec uses the same generated header constants and generated operation-tag case list as Rust. `prdb_ipc_frame_encode_v1` writes into caller-owned storage, supports a required-size query, and leaves a short output buffer untouched. `prdb_ipc_frame_decode_v1` decodes one frame prefix and borrows its payload from the input, so coalesced frames can be processed successively without allocation. Both reject zero/unknown operations, zero request IDs, unsupported versions, oversized payloads, malformed arguments, and truncated input before publishing a decoded result. Native `prdb_ipc_frame_v1` values are local C views and are never wire encodings.

### Version-1 Operation Tags and Service Roles

Operation tags are fixed independently of their payload schemas. The channel's service role is assigned during trusted connection provisioning and is never selected by a frame field. `Operation::from_code` rejects unknown tags; framing rejects them before payload allocation. A role/operation mismatch is denied before the selected handler runs. Database-principal authorization remains a separate StorageManager check.

`GatewayClientError` (`0x1412`) is a supervisor-to-gateway response event only. Its bounded UTF-8 JSON payload uses the public client ERROR `{ "code": string, "message": string }` schema. Version 1 accepts only these canonical byte strings: `invalid_request` / `Request is invalid.`, `invalid_state` / `Request is not valid in the current session state.`, `unauthenticated` / `Authentication is required.`, `resource_limit` / `Request exceeds a configured limit.`, and `unavailable` / `Requested resource is unavailable.` A gateway rejects any other payload and closes the client connection; raw errors and principal or token details do not cross this boundary. A gateway MUST reject this operation as an inbound client request.

The storage-side Supervisor handler accepts `0x1301` finalize and `0x1302` abort on a channel bound out of band to one active invocation. Both requests carry only `u16 version = 1`; finalize responds with version, status 0, and the committed sequence `u64`, while abort responds with version and status 0. The handler consumes the invocation on either decision, rejects further terminal requests, and aborts if the supervisor channel closes before a decision. Worker or planner EOF alone does not finalize. `0x1304` status requests carry version and invocation ID[16]; the connection's authenticated principal is bound out of band. The response starts with version and status: 0 UNKNOWN; 1 ACTIVE; 2 COMMITTING; 3 COMMITTED; 4 ABORTED. ACTIVE/COMMITTING append observed time `i64`, start time `i64`, deadline-present `u8`, optional deadline `i64`, and cancellation-requested `u8`. COMMITTED/ABORTED append observed time `i64`, commit sequence `u64`, and retention deadline `i64`. UNKNOWN covers absent or non-owned invocations. `0x1303` cancellation carries version, invocation ID[16], and nonzero reason code `u16`; the authenticated administrator is bound out of band and storage rechecks database-admin authority and persists the audit event. Its response status is 0 ACCEPTED, 1 TOO_LATE, 2 TERMINAL followed by outcome code (1 COMMITTED, 2 ABORTED), commit sequence `u64`, and retention deadline `i64`, or 3 UNKNOWN.

Executor `0x1113` cancellation checks require an empty request payload. The response is `u16 version = 1` and `u8 cancelled`, where zero means the invocation remains active and within its deadline, and one means cancellation or expiry has been detected; storage aborts the invocation before reporting one. SDK query runners should poll between bounded work batches and stop when cancelled.

Executor `0x1114` accepts a v1 request containing the version, resolved relation handle, logical index ID, non-NULL key-value count, result-column count, scalar-value records, and selected column IDs. A NULL equality uses the reference scan path. The generated response records are exact `{version:u8=1,status:u8=0}` for `unavailable`, exact `{version:u8=1,status:u8=1}` for `no_match`, or the prefix `{version:u8=1,status:u8=2}` followed by one executor batch-row record for `match`. The row contains an opaque executor handle and sanitized cells in requested-column order. Storage checks the pinned schema and index, reconciles snapshot candidates with staged writes, and applies row/cell authorization. A hidden or conditionally readable key returns `unavailable` before the key is inspected.

Executor `0x1115` accepts a v1 request with a resolved relation handle, logical index ID, one-byte lower-bound flag record, optional lower scalar record, one-byte upper-bound flag record, optional upper scalar record, a generated `u16be` result-column count record, and selected column IDs. Each scalar record contains a type code (`u8`), value length (`u32be`), and exactly that many value bytes. Each flag is 0 absent, 1 inclusive, or 2 exclusive; at least one bound is required. Range scans use only the leading index key. The response uses a shared generated schema: `unavailable` is the exact two-byte record `{version:u8=1, status:u8=0}`; a rows response begins with `{version:u8=1, status:u8=1, row_count:u16be}` followed by that many rows. Each row contains a `u16` cell count and sanitized cell records in requested-column order; raw row IDs and row handles are not exposed. Results are capped at 1,024 rows and the IPC payload limit. A result that does not fit returns `unavailable` without a partial page. Storage checks the pinned schema, index and key readability, reconciles snapshot candidates with staged writes, and applies row/cell authorization. Executor `0x1116` accepts a request beginning with `version:u16be=1`, then the resolved relation handle, logical index ID, a `u8` prefix-value count from 2 through 8, that many typed scalar records in the index's leading-column order, a generated `u16be` result-column count, and selected column IDs. Every value must be non-NULL and match the corresponding pinned leading index column type and parameters. The response has the same v1 `unavailable` or bounded sanitized-rows shape as `0x1115`, with no partial rows. Storage returns `unavailable` before key matching if any indexed column is not statically readable and unconditionally allowed, then reconciles snapshot entries with staged writes and reapplies row/cell authorization.

The batch operations are additive v1 payload schemas. `0x1117` accepts one relation handle, index ID, a `u16` probe count (1–128), then probes in ordinal order. Each probe contains a `u8` key-value count (1–8) and that many non-NULL typed scalar records; one value is an exact leading-key equality probe, and two to eight values are a leading-prefix probe. The request ends with the common result-column selection. Its response starts with version and status; status 0 is `unavailable` with no trailing bytes. Status 1 carries the probe count followed by one result group per input ordinal. A group contains a `u16` row count (0–1,024) and sanitized rows in the same form as `0x1115`; zero rows means no match. The aggregate response is capped at 1 MiB and 16,384 candidate rows. If any group exceeds its row cap or the response cannot fit, storage returns `unavailable` with no partial groups. Storage validates every probe's types and index-prefix shape, checks key readability before inspecting any key, reconciles each result with the pinned snapshot and private-write overlay, and reapplies row/cell authorization. Result groups preserve duplicate input keys and their probe ordinals; the SDK retains outer-row order and applies residual join predicates itself. The same operation supports independent point-lookup sets for a validated OR-of-equalities or SQL `IN` filter, subject to that operator's candidate/materialization limits and no-partial-output fallback rules.

`0x1118` carries one relation handle, a `u16` row count (1–4,096), then that many full-shape insert cell lists using the `0x1110` cell encoding. Success returns version, status 0, and one opaque row handle per input row in order. `0x1119` carries a `u16` row count (1–4,096), then for each row a row handle, a `u16` patch count and unique ordinal/value patches in the `0x1111` encoding. `0x111a` carries a `u16` row count (1–4,096) and that many row handles. Update/delete success returns version and status 0. Each batch request and response is capped by the 1 MiB frame limit; the count cap is reduced as needed to fit. Storage validates and stages each request atomically: malformed input, authorization/policy failure, stale handle, constraint failure, cancellation, or resource exhaustion stages no member of that batch and returns failure; the invocation still follows the existing terminal statement-error rule. Successful mutations consume all row handles for the affected rows. The SDK may split a SQL statement into bounded batch requests; if a later chunk fails, the invocation aborts and no earlier chunk can commit. Single-row operations remain supported and retain their existing payloads and response shapes.

The administrative-control channel is bound to an already authenticated actor; its service role does not confer database privileges. Gateway operations go to the supervisor service and cannot be forwarded as arbitrary internal operation codes. The protected bootstrap socket accepts only its credential-delivery and acknowledgement operations. Executor and planner roles are distinct: only the planner receives estimate operations, and neither role can finalize or administer.

### Gateway Submission Service Payloads

Each gateway-service channel is provisioned for one client connection and one HELLO-selected mode. The gateway-to-supervisor stream is dedicated to the paired TCP connection; the supervisor creates and owns one `ClientConnectionSession` for that stream. The paired TCP/Unix streams represent the v1 gateway generation, connection, and session context, so v1 carries no reusable session identifier in request payloads. A gateway restart closes the service streams and invalidates their sessions; clients must reconnect and authenticate again. A future multiplexed or reusable channel version must carry trusted generation/connection/session identifiers. The gateway copies the client request ID into the IPC frame and permits only one outstanding client operation on the channel. The service revalidates storage authority and derives staging ownership from the authenticated session.

`0x140a` is the first operation on a new per-client service stream and carries the strict HELLO JSON payload; it establishes mode and connection-local limits but no identity. `0x140b` carries the client PING JSON payload. `0x1401`, `0x1403`, `0x1405`, `0x1407`, and `0x1408` carry the corresponding bounded client JSON payload without its TCP frame header. `0x1404` begins with one byte selecting client kind 4 (artifact) or 5 (parameters), followed by the unchanged binary chunk payload. `0x1406` carries the client START JSON payload. Responses preserve the operation and request ID and contain the client RESPONSE JSON payload.

After the correlated START response, the supervisor may send `0x1410` frames containing arbitrary provisional application bytes, followed by one `0x1411` event only after a storage terminal decision has been confirmed. Event frames use the START request ID. The gateway assigns TCP response sequence numbers starting at one and maps the events to RESULT_DATA and TERMINAL. These events are server-to-gateway only and are not admitted as gateway requests.

START has an additional trusted in-process result: the supervisor-side dispatcher retains the admitted `SupervisorInvocation` and owner-checked immutable `SealedSubmission` handle for launch code while returning the sequence-zero `accepted` response. Those Rust objects are never serialized over gateway IPC. A failed START returns an error and does not expose staged bytes or a storage transaction. Result relay and terminal messages remain separate supervisor-generated events. The storage-side Supervisor terminal handler refuses finalization until the trusted storage owner has drained planner/executor channels and observed a successful worker exit; worker failure durably aborts the invocation.

The server provisions one service stream and `ClientConnectionSession` per client connection. Request IDs must increase for that session. Clean EOF, malformed framing, a role/payload error, or a failed response write closes the context: unstarted staging is discarded, while started work is signalled for storage cancellation. After START, trusted supervisor code owns the invocation event; it may resume servicing that session only after execution/result handling returns control. The runner must separately monitor client disconnect while execution is active.

## Administrative Control

Authenticated clients submit bounded schema/user/permission DDL or structured equivalents on a dedicated control channel. Storage validates both definitions and current actor authority. Administrative operations may be atomically batched, but cannot be mixed with executor DML/native code. Request IDs, budgets, durable outcomes, and status lookup apply to DDL too.

Credential issuance/revocation uses protected control API fields, not SQL literals or executor messages. Separate database principals/roles from service roles assigned to executor, optimizer, and supervisor channels. Credentials never cross into the executor. See [schema DDL](ddl-schema.md), [identity DDL](ddl-identity.md), and [permission DDL](ddl-permissions.md).

## Discovery and Observability

Provide bounded `list_schemas`, `list_relations`, and `describe_columns` operations with snapshot-bound continuation tokens as defined in [metadata discovery](metadata-discovery.md). Built-in `information_schema` scans use the same visibility rules. Privileged object inspection stays on the control channel; secrets/verifiers never appear in responses.

Live status/monitoring APIs follow [operational metadata](operational-metadata.md) and are explicitly outside invocation MVCC snapshots. Own-invocation status is not authority to enumerate other users or global metrics. Durable outcome lookup may return UNKNOWN/EXPIRED; it must not invent an abort after a lost commit reply. Administrative cursors recheck current authority between pages.

## Relation Resolution and Handles

Structured SQL requests name relations. The optimizer resolves those names through authorized storage metadata, but must not embed its connection-local handles in returned plans. Plans carry logical relation/schema references, which the executor resolves independently on its storage connection. Resolution rechecks the invocation grant and pinned schema; a plan reference grants no authority.

The executor role supports authorized schema discovery and relation resolution for direct SDK access as well as plan execution. It does not receive physical access-path statistics or the optimizer's estimation role. Cursors and row handles remain connection-local. Snapshot/schema mismatch fails the request rather than silently rebinding a plan to another relation.

The storage engine provides an `ExecutorMetadataConnection` resolver session with opaque relation handles. An IPC handler must own one such session per provisioned executor connection, revalidate each handle through the invocation's pinned catalog before use, and drop it on connection close. These handles are references only; the scan and mutation operations still perform their own grant, policy, and snapshot checks. Optimizer-local handles are never accepted by executor handlers.

The Rust executor dispatcher implements `resolve_relation` (`0x1101`), `open_scan` (`0x1102`), `next_batch` (`0x1103`), `close_cursor` (`0x1104`), and the mutation operations (`0x1110`–`0x1112`). Each payload schema uses version 1. The resolve request is `u16 version`, `u16 schema_name_bytes`, `u16 relation_name_bytes`, and the two nonempty UTF-8 names. Its response is `u16 version`, `u8 status`; status 0 is followed by a 16-byte relation ID, 16-byte relation handle, u16-length UTF-8 relation name, u16 column count, then column records. A column record is `column_id[16]`, zero-based ordinal `u32`, nullable `u8`, scalar type code `u8`, four type-parameter bytes, and a u16-length UTF-8 name. Type codes 1–11 are Boolean, SmallInt, Integer, BigInt, Decimal, Text, Varchar, Bytea, Uuid, Date, TimestampTz. Decimal parameters are precision/scale followed by two zero bytes; Varchar parameters are a big-endian u32 maximum character count; other parameters are zero. Status 1 means unavailable, covering hidden and absent names. Schema metadata is returned in catalog ordinal order.

The C SDK bridges `stage_insert` (`0x1110`), `stage_update` (`0x1111`), and `stage_delete` (`0x1112`). INSERT accepts up to 4,096 full-shape VALUE/NULL/DEFAULT inputs, encodes into a caller-owned buffer bounded by the IPC limit, and accepts only a version-1 response containing a kind-8 row handle. UPDATE accepts up to 4,096 unique in-range ordinals with VALUE/NULL data. UPDATE and DELETE validate the version/status-0 acknowledgement. These SDK helpers only serialize IPC; storage remains the enforcement point for invocation scope, snapshot, grants, policies, row versions, constraints, and handle lifetime.

The planner dispatcher implements `describe_relation` (`0x1201`), `estimate_scan` (`0x1202`), and `describe_plan_relation` (`0x1204`) with version-1 payloads. `describe_relation` uses the same qualified-name request as executor resolution; a successful response contains status 0, relation ID, planner-only handle[16], relation name, u16 column count, and column records in the format above. Status 1 means unavailable. `estimate_scan` carries version, planner handle[16], u16 column count, and column IDs[16]; zero requests the full declared shape. Its response is status 1 for UNKNOWN, or status 0, visible-row count `u64`, u16 column count, then one triple of `readable_values`, `nulls`, and `redacted` `u64` counts per requested column. `describe_plan_relation` accepts the qualified-name request and returns either status 1 unavailable or status 0, schema ID[16], schema version `u64`, table write epoch `u64`, relation ID[16], relation name, u16 column count, and the declared column records. An optional u16 count of approved unique paths follows, with each path encoded as logical index ID[16], key-column count, and ordered column IDs[16]. A separate optional `52 01` suffix carries a u16 count of approved non-unique range paths with the same path record shape. Either path group is omitted when empty. Storage includes paths only when all indexed cells are statically readable under the pinned authorization projection; index IDs cannot appear in both groups. The plan description contains no planner handle and creates no executor capability. Executor `resolve_plan_relation` (`0x1105`) accepts the same request and returns the identity and declared columns from the executor's pinned, authorized catalog, without planner-only access-path metadata, a handle, or a capability; executor scans still require `resolve_relation` (`0x1101`). Planning handles use kind 9 and are connection-local; executor handles and row handles are not accepted. The stream loop caps each planner connection at 256 requests. `SupervisorInvocation::serve_worker_channels` serves planner and executor streams concurrently against the same invocation and drains both before returning. Clean EOF closes only the planning session; malformed frames or protocol violations abort the invocation. For filtered ordinary unordered single-table SELECT, the optimizer may send a bound-predicate `EstimateScan` request; only exact zero matches select the no-scan plan hint, while nonzero and UNKNOWN estimates preserve ordinary execution. Broader selectivity costing and shared planner task scheduling remain future work.

Planner batch metadata operations are additive v1 schemas on the planner-to-storage channel. `describe_plan_relations` (`0x1209`) accepts `version:u16be=1`, `count:u16be` (1–64), then that many qualified names encoded as `schema_length:u16be`, `relation_length:u16be`, and nonempty UTF-8 name bytes. Its response contains version and the same count, followed by one `u32be entry_length` and one complete entry per input ordinal. A status-0 entry contains planner handle[16] followed by the successful `describe_plan_relation` body fields (schema/relation identity, epoch, declared columns, and approved paths, without a nested version/status); status 1 means unavailable and carries no handle or body. Handles are scoped to the planner connection that served the batch and are valid for `estimate_scans` on that connection only. `estimate_scans` (`0x120a`) accepts version, `count:u16be` (1–16), then entries containing planner handle[16], `column_count:u16be`, and that many column IDs. Its response contains version and count, then length-delimited entries using the existing `estimate_scan` response shape: status 0 plus counts, or status 1 UNKNOWN. UNKNOWN remains per-entry and does not discard other estimates; each entry consumes one unit of the existing 16-estimate allowance. Both requests and responses are capped by the 1 MiB frame limit; count must also fit the encoded payload. Malformed framing, invalid handles/columns, duplicate request IDs, or trailing bytes reject the whole request, while hidden or absent relations and unsupported/exhausted estimates retain their existing per-entry non-disclosing results. The batch does not widen the planner connection's 256-frame limit; one batch consumes one frame.

The shared operation registry reserves `optimize_select` (`0x1203`) for the separately provisioned `OptimizerSubmission` role. Its request payload is the bounded canonical structured SELECT v1 or v2 payload (maximum 64 KiB); v2 is reserved for the specified SELECT `IN` node and v1 remains unchanged. The response is `u16 version=1`, `u8 status`, and, only for status 0, `u32 plan_length` plus canonical validated plan v1 or v2 bytes (maximum 64 KiB), matching the request generation. Statuses are 1 invalid request, 2 unavailable relation, 3 rejected query/plan, and 4 internal failure; non-success responses contain no trailing fields. Request/response codecs and the `prdb-optimizer` process loop implement the protocol over separate submission and planner streams. The process requests stable authorized metadata through `describe_plan_relation` or `describe_plan_relations` and returns only a validated plan or a non-disclosing status. The supervisor starts the confined optimizer alongside the executor, serves both planner streams, and exposes the allowlisted optimizer callback to the executor through ABI v4/v5. Process-level sandbox acceptance is described in [planner/compiler](planner-compiler.md) and [supervisor](supervisor.md). The optimizer uses exact-zero predicate estimates for filtered ordinary unordered single-table SELECT; broader predicate selectivity costing and shared planner scheduling remain future work.

`open_scan` request: version, relation handle[16], u16 column count, then that many column IDs[16]; count zero requests the full declared shape. Its response is version and cursor[16]. `next_batch` request: version, cursor[16], u16 maximum candidate rows (1–128), u32 maximum response bytes (8–1,048,576). Its response is version, `u8 finished` (0 means continuation follows; 1 means end), optional cursor[16], u16 visible row count, then rows. The visible row count must not exceed the request's maximum candidate rows, and the encoded response length must not exceed its maximum response bytes; the SDK rejects an over-limit response without publishing a decoded batch. Each row begins with a versionless generated row record containing the opaque row handle[16] and u16 cell count, followed by that many cells. Each cell begins with a generated one-byte state tag: 0 is VALUE followed by scalar type code, u32 value length, and canonical bytes; 1 is NULL; 2 is REDACTED and carries no source bytes or length. Scalar values use big-endian fixed-width integers, booleans 0/1, UTF-8 Text/Varchar, raw Bytea/Uuid bytes, and signed two's-complement Decimal/Date/TimestampTz bytes. `close_cursor` request is version and cursor[16]; its acknowledgement is version and status 0. No row ID or storage address appears in a batch.

Mutation requests use the same version and scalar value encoding. `stage_insert` carries version, relation handle[16], u16 value count, then full-shape VALUE/NULL/DEFAULT cells; state 0 is VALUE followed by type, length, and bytes, state 1 is NULL, and state 2 is DEFAULT. Its response is version and a new opaque row handle[16]. `stage_update` carries version, row handle[16], u16 patch count, then zero-based ordinal `u32` and VALUE/NULL cell for each unique patch. `stage_delete` carries version and row handle[16]. Update/delete acknowledgements are version and status 0. REDACTED is response-only. Storage resolves the handle within its connection, derives schema, grants, policies, constraints, and indexes from the pinned catalog, and consumes all handles for a row after a successful mutation. INSERT requires every declared column; generated identities must be DEFAULT and cannot be overridden.

The executor stream loop accepts at most 512 frames per connection and rejects reused request IDs. This bounds connection state while leaving room for multiple sequential SQL statements in one invocation; individual SQL operators retain their stricter 256-request budgets. Relation and row handles and scan cursors use server-side, connection-local state. At most 4,096 row handles may be issued per connection. An unsupported column, invalid cursor, oversized response, or malformed request aborts the bound invocation. Clean EOF ends only the executor session and does not commit or abort; the supervisor must independently observe worker completion and request finalization or abort through its trusted storage channel. Predicate pushdown is not part of this initial dispatcher. `SupervisorInvocation::serve_worker_channels` provisions both worker storage streams and invokes their handlers with the same invocation context.

## Conceptual Operations

```text
resolve_relation(logical_relation_ref) -> table_handle, authorized_schema
open_scan(table_handle, requested_columns, restricted_predicate) -> cursor
next_batch(cursor, max_bytes) -> authorized_batch | end
close_cursor(cursor) -> acknowledgement
stage_insert(table_handle, field_values) -> provisional_row_handle
stage_inserts(table_handle, rows[1..4096]) -> provisional_row_handles[rows]
stage_update(row_handle, field_patch) -> acknowledgement
stage_updates(rows[1..4096]) -> acknowledgement
stage_delete(row_handle) -> acknowledgement
stage_deletes(row_handles[1..4096]) -> acknowledgement
scan_index_ranges(relation, index, probes[1..128], columns) -> grouped_authorized_rows[probes]
```

The v1 mutation batch payloads use a common `version:u16be=1`, `count:u16be` header (count 1–4096), followed by `count` records encoded as `record_length:u32be` and one complete scalar mutation request body without an outer frame. `stage_inserts` records each carry the relation handle and full-shape values; all records must name the same relation. Its response is version, count, then one opaque row handle per input ordinal. `stage_updates` records carry one row handle and its unique ordinal/value patches; `stage_deletes` records carry one row handle. The latter two return the existing mutation acknowledgement. The entire request is decoded and validated before staging begins. Any member failure aborts the invocation, including already accepted chunks of the same statement, so no prefix can commit. SDKs split work into payload-bounded chunks; each chunk consumes one request-budget unit, while the transaction remains all-or-error across chunks.

Requested limits are capped by the server. Predicates use a bounded, validated expression language; native callbacks are forbidden. Exact expression support and wire encoding remain undecided.

## Mutation Ordering and Transaction Control

All operations bind to the invocation's MVCC transaction. Server-side row handles identify snapshot/private versions, never raw addresses or permission to update the latest row. Mutation messages cannot override the transaction, base version, grant, or policy checks. Updates carry field patches so the executor need not receive hidden unchanged fields.

Serialize each invocation's mutation stream and each cursor's advancement. Initially reject overlapping statement/request streams; use request IDs and handle generations to reject duplicates and stale responses. Bound write-set bytes and outstanding work. No transparent mutation replay after disconnect.

Only the supervisor control role may explicitly finalize/abort a transaction; storage also aborts autonomously on errors, limits, or disconnection. User library return is a request to the supervisor, not commit authority. Provide an authenticated client status endpoint keyed by opaque invocation ID for lost-reply reconciliation. Commit, abort, durable outcomes, and cancellation races follow [concurrency and MVCC](concurrency-mvcc.md). Storage enforces these role distinctions even if SDK definitions expose all message types.

## Planning Channel

There are two distinct planning interfaces. An executor-to-planner submission channel carries bounded structured queries, parameters, physical plans, and errors. The supervisor binds it to the admitted execution context. This allows the SDK SQL code inside query.so to request optimization without receiving the planner's storage-estimation role. The planner validates all input, and request counts/size and planning work are bounded.

The executor-to-optimizer request uses `optimize_select`; its peer receives only the `OptimizerSubmission` role. Do not reuse the optimizer's separate `Planner`-to-storage channel or its `describe_relation` / `estimate_scan` operations on this endpoint.

Provision a separate planner-to-storage channel bound to the same execution authority, with a planning role and independent estimation budget. Role checks prevent workers from directly invoking storage estimation/maintenance operations and prevent the planner from acquiring unrestricted scan access.

```text
describe_relation(logical_relation_ref) -> planning_table_handle, authorized_schema_and_access_paths
estimate_scan(planning_table_handle, columns) -> scoped_estimate
estimate_predicate(qualified_relation, bound_predicate_ir) -> visible_and_matching_rows | unknown
```

Estimates describe population, uncertainty, and context-scoped validity, or return unknown/unsupported. The bounded predicate request uses the planner-only EstimateScan operation with prefix marker `52 05`, a qualified relation name, predicate bytes, and a trailing big-endian `u32` predicate length. Storage re-resolves the relation and predicate columns against the invocation snapshot. An exact predicate response is marker `52 06` followed by big-endian `u64 visible_rows` and `u64 matching_rows`; unknown uses the existing versioned unknown-estimate response. The bounded join-cardinality request uses marker `52 08`, a maximum row count, one through eight paired left/right column IDs, and two qualified relation names; the response is marker `52 09` plus a big-endian `u64` joined-pair count, or the existing unknown response. Storage re-resolves both relations and columns in the pinned planner context and returns exact results only when both populations and join keys are authorized for this bounded estimate. Predicate, population, and join estimates share the per-planner-connection request allowance. Do not export global statistics, physical counts, private costs, raw samples, or global refresh epochs. Expressions use bounded trusted built-ins, never native callbacks. No planner-accessible unrestricted statistics-refresh operation exists. See [statistics service](statistics-service.md).

Unknown estimates permit heuristic planning only while the invocation and planning request remain active. Cancellation, expired deadlines, and fatal protocol errors do not permit continued work or broader access. Planning handles and pending requests expire with the execution context. Connection teardown and cancellation must release estimation resources as well as cursors.

## Batch Representation

```text
scoped row handles
column values containing only authorized payloads
per-column cell states: VALUE | NULL | REDACTED
```

Invisible rows are omitted. Redacted variable-length values must not retain source bytes or original lengths. Initialize padding and avoid serializing unused buffer capacity. Returned metadata must not disclose physical storage addresses or hidden row counts.

## Validation and Errors

Version IPC independently of the native host ABI and structured query/plan formats, as described in the [SDK contract](client-sdk.md). Define maximum frame sizes, collection lengths, nesting, outstanding requests, cursors, and response sizes before implementation. Validate framing before allocation and reject malformed states, stale handles, and cross-context references. Host ABI structures are not wire encodings and must not be sent by copying native memory layouts.

Errors should distinguish invalid requests, denied operations, expired contexts, cancellation, and resource limits without exposing hidden values or invisible row identities. Precise error equivalence and inference behavior require further design.

Define cursor advancement and retry behavior explicitly; the prototype fails the invocation on a required channel disconnect instead of supporting transparent replay. Statement success closes its resources and leaves the transaction active; any statement error aborts the whole transaction. Cancellation accepted before redb commit begins invalidates all handles and discards private writes; after redb commit begins, report pending/terminal outcome rather than promising rollback; reclaim resources only after in-flight tasks release their pins. After a durable commit, cancellation cannot roll back data. Invocation-wide budget exhaustion is terminal before commit.

## Validation and Future Work

Fuzz decoding and state transitions; exercise oversized frames, forged cursors, premature disconnects, and backpressure. Test that denied data never appears in serialized bytes.

The copied socket transport is the initial baseline; serialize directly into final sanitized batch buffers and use bounded vectored sends when useful. [Memory storage](memory-storage.md) specifies the optional sealed-memfd batch extension, required ownership/sealing checks, and adversarial validation before enabling it. Descriptor transfer remains forbidden except for a future explicitly negotiated sanitized-batch capability. Raw storage mappings and writable worker/storage shared memory remain forbidden.
