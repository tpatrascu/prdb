# Statistics Collection and Planning Estimates

## Decision and Rationale

The optimizer needs cardinality, selectivity, value-width, distinct-count, correlation, and access-path information to choose useful plans. It does not need unrestricted scans or direct access to database files to obtain that information. Separate collection from consumption: trusted storage code collects statistics, while the isolated planner requests authorized estimates.

Introduce a logical statistics service inside the storage manager for the baseline. It owns collection, a protected catalog, scoped estimation, and refresh scheduling. Moving collection into a separate trusted process is a future option, not a prerequisite. Such a collector would hold sensitive data and remain part of the confidentiality boundary.

## Two Statistics Domains

| Domain | Contents and use | Planner access |
| --- | --- | --- |
| Internal physical statistics | Global counts, pages, histograms, frequent values, samples, index properties, correlations | No direct access |
| Authorized-view estimates | Estimates derived from the execution's visible rows and readable cells, plus explicitly public schema/configuration | Bounded estimation API |

Global statistics are optional in the first prototype. They can later support storage maintenance and internal access-path decisions, subject to the architecture's timing-channel limitations. Do not return global counts, costs, catalog epochs, or plan recommendations indirectly through the scoped API unless their disclosure has been explicitly authorized.

## Collection

Use fixed, trusted Rust routines over storage snapshots; never load the C SDK into this trusted component. Do not invoke planner-supplied code, user-defined comparators, or native functions on private samples. Bound scan work, memory, catalog size, and refresh frequency. Schedule expensive maintenance separately from per-query planning; a planner cannot trigger an unrestricted `ANALYZE` operation.

Initially compute small authorized summaries on demand within a planning budget. If computation is too expensive, return `unknown` and let the optimizer use fixed heuristics. Later add scoped caches, incremental collection, or sampling. Sampling must account for row visibility and cell redaction; a global sample cannot simply be relabeled as representative of an authorized population.

The first committed-snapshot collector stores only a global row population for one logical table. It reads row keys from one committed redb snapshot and inspects at most 16,385 keys to distinguish an exact population up to 16,384 from an oversized one. It never reads row values or transaction-private overlays. One shared per-database maintenance permit admits at most one collection at a time; another request returns `Busy` without waiting. The scan holds a read snapshot but no catalog or commit lock, then releases the snapshot before one small durable write to the protected `stats_v1` table. Operational commits remain independently admitted while the scan runs.

The gateway service schedules one table refresh per configured statistics-maintenance interval, defaulting to 15 minutes in the supervisor. It walks the table catalog with a round-robin key cursor, reads at most one table definition per tick, and wraps at the end rather than materializing all table IDs. A table dropped between selection and collection is skipped. Busy admission skips that tick and later tables continue on subsequent ticks. This scheduler is separate from per-query planning and from outcome pruning; each admitted collection retains the same 16,384-row bound and single shared maintenance permit. Shutdown stops future ticks without leaving a detached collector task.

The collector stores a versioned `CPR1` record under `statistics:committed-population:v1:` followed by the 16-byte table ID. Its 21-byte value contains the source engine commit sequence as little-endian `u64`, a status byte, and a little-endian `u64` count. Status 1 is exact and carries a count from 0 through 16,384; status 0 is unknown and requires a zero count. Invalid encodings fail closed. The public maintenance outcome returns only exact versus unknown and does not return counts, table IDs, or commit sequences. A trusted freshness check reads a record and engine commit sequence from one redb snapshot; the record is reusable only when its source sequence equals that snapshot sequence. The scheduled refresher skips a redundant scan for a fresh exact or `Unknown` record and refreshes missing or stale records. An over-budget pass durably replaces any older record with `Unknown`, never a partial count. The stats table is derived and rebuildable; records are not exposed through a dedicated planner/executor operation or ordinary catalog discovery. The planner's existing bounded population estimate may reuse a record only from the invocation's pinned snapshot, when literal row policies prove that every row is visible and the transaction has no private row writes. The record must be exact and within the requested population bound. The storage service returns only that authorized-view count through the existing estimate response; stale, missing, malformed, over-bound, unknown, or overlay-bearing cases use the bounded snapshot estimate or return `Unknown`. The explicit maintenance call is also scheduled by the gateway service.

## Planner Interface

Conceptual planning-channel operations:

```text
describe_relation(logical_relation_ref) -> planning_table_handle, authorized_schema_and_access_paths
estimate_scan(planning_table_handle, columns, predicate_ir) -> estimate
```

Planning table handles belong only to the optimizer connection and cannot be passed as executor scan handles. The connection supplies the context; requests cannot choose a principal or arbitrary policy version. Access-path descriptions expose approved logical capabilities, not physical page counts or private index contents. An estimate may contain:

- Estimated visible output rows and authorized output bytes.
- Estimated readable/null/redacted fractions for requested fields.
- Selectivity or distinct-count estimates with an explicit population definition.
- Method and uncertainty information, or `unknown`/`unsupported`.
- An opaque context-scoped validity token with no global catalog history.

Provide only fields justified by authorized data or public configuration. Histograms and raw samples are not part of the initial external API. Estimates must not conceal privileged data in errors, logs, response metadata, or returned physical plans.

### Initial On-Demand Summary

`InvocationTransaction::estimate_authorized_scan(table_id, projection)` returns either an exact authorized-view summary or `Unknown`. Exact summaries contain the visible-row count and, in requested-column order, VALUE/NULL/REDACTED cell counts. They contain no row values, widths, row IDs, partial counts, or predicate selectivity. Collection reads the invocation's pinned snapshot plus its private overlay and applies the same trusted row/cell projection as an authorized scan.

Each planner connection may request at most 16 estimates. The count is cumulative for the lifetime of its planner stream and survives metadata-session detach/reattach between requests. After the estimate allowance is exhausted, the storage interface returns `Unknown` without aborting the invocation, so the optimizer can continue with fixed heuristics. Each estimate is separately bounded to 16,384 candidate rows and returns `Unknown` without partial counts when that bound is reached or the request's context/schema cannot be validated. To keep the completion result independent of invisible-row volume, it only releases exact counts when applicable table SELECT policies have literal Boolean predicates and no `WITH CHECK` expressions. If at least one applicable ALLOW policy is literal TRUE and no RESTRICT policy is literal FALSE, it scans the full population; if no ALLOW policy is literal TRUE or a RESTRICT policy is literal FALSE, it returns an exact empty summary without scanning rows. At least one requested column must be granted. Any value-dependent or otherwise unsupported policy returns `Unknown` before scanning, even when another policy is a constant deny, because execution may still evaluate the unsupported policy. Exact summaries may be reused only under the planner-session cache contract below. Cancellation and deadline expiry remain terminal rather than becoming `Unknown`.

Exact bounded join-cardinality estimates may also be reused within the planner session. Their cache key includes ordered left/right relation IDs, schema ID and version, ordered left/right join-key column IDs, and the requested per-input row bound. As with the other exact estimate caches, a hit consumes the shared allowance, each successful private overlay mutation invalidates the entry, and no cache is shared across planner sessions or invocations.

The trusted transaction layer now has a separate bounded predicate estimator for authorized populations of at most 16,384 rows, matching the per-estimate candidate budget. It reads snapshot row IDs in pages no larger than the storage scan-page limit, stops after the bound plus one candidate, and computes the exact visible and matching counts during that one bounded candidate pass. It returns no partial count. It accepts only a bound Boolean predicate with validated column IDs, ordinals, and types; comparisons over Boolean, integer, DECIMAL, DATE, UUID, TIMESTAMPTZ, BYTEA, and text literals, and same-typed scalar columns of Boolean, SMALLINT, INTEGER, BIGINT, DECIMAL, TEXT, VARCHAR, BYTEA, UUID, DATE, or TIMESTAMPTZ are supported, along with bounded AND/OR/NOT. Column-to-column comparisons require identical scalar types; DECIMAL precision and scale must match. Variable-width TEXT, VARCHAR, and BYTEA cells are limited to 4 KiB per value for estimation. cross-type coercions remain unsupported by the optimizer request format. It returns `(visible_rows, matching_rows)` only when the authorized population is exact and every referenced cell is readable. A redacted cell, unsupported value/operator, invalid projection, population above 16,384 rows, or incomplete row set returns `Unknown` without partial counts. SQL NULL comparisons follow three-valued semantics and count as non-matches. The estimator reads only sanitized authorized cells and includes the invocation's private overlay. The planner session may reuse exact predicate results for the same relation identity and schema version, encoded predicate, and candidate bound; exact bounded population probes for the same relation/schema identity and row bound; and exact column summaries for the same relation/schema identity and ordered requested column IDs. Each planner session is tied to one invocation's principal, effective grants and policies, and pinned snapshot; every successful private overlay mutation advances a generation that invalidates all cached entries. Unknown results are not cached, every request including a cache hit consumes the shared 16-request allowance, and entries are never reused across planner sessions or invocations. Planner IPC carries a bounded bound-predicate estimate request and returns either the two counts or `Unknown`; it re-resolves the qualified relation in the invocation context. For filtered ordinary unordered single-table SELECT, the optimizer requests this estimate for the bound plan predicate. Only an exact zero-match result selects the validated empty-view hint. For nonzero exact estimates, the optimizer uses total `visible_rows` to select a sequential scan for populations of one through four. For larger populations, it uses `matching_rows` to remove a range hint when at least half of the visible rows match; a unique point probe is retained. This half-selectivity rule is a bounded heuristic from direct-API TEXT comparisons: five-run 130-row profiles favored range at 43%, were near crossover at 49%, and favored scan plus filter at 62%; five-run 514-row profiles had median-of-run p50s of 4.966 ms range versus 5.746 ms scan at 43%, 5.769 versus 5.565 ms at 49%, and 7.626 versus 6.037 ms at 62%. Five 2,050-row runs at 43% measured 21.579 ms range versus 25.323 ms scan plus filter. These compare the access paths alone and are host-local. Predicate estimation itself measured 26.103 ms median-of-run p50s at 2,050 rows, so its per-query cost can exceed the access-path savings; planner-visible estimate overhead and end-to-end plan latency remain open. This is not a general cost model. Unknown estimates preserve the ordinary plan. Ordered SELECT and other statement kinds do not request predicate estimates.

For ordinary single-table SELECT planning, the optimizer explicitly opts in to a no-scan empty-population proof in its relation metadata request. Storage may attach the proof when the pinned policy shape proves no rows can be visible. Only an opted-in proof attempt consumes the same cumulative 16-request planner allowance as a scan estimate; other relation metadata lookups do not consume it. An exhausted allowance or unsupported policy omits the proof. This metadata contains no row values or counts, and the optimizer may use it only to elide an otherwise validated SELECT scan. It does not authorize an operation or change executor checks.

Ordinary unordered single-table SELECT may opt into a bounded authorized-population probe for populations of 0–4, which reads at most five row keys. Join planning may request a count up to 4,096 rows, reading at most 4,097 row keys. Both probes return an exact row count only when a literal policy shape proves that row inclusion does not depend on stored values and the pinned snapshot plus private overlay contains no more than the requested maximum. Neither decodes row values. Larger populations, value-dependent or unsupported policies, an oversized overlay, or exhausted estimate allowance return `Unknown` without a partial count. This probe shares the planner connection's cumulative 16-request estimate allowance. Exact zero may be used with the empty-view proof above; an exact population from one through four may inform only the bounded scan-versus-index heuristic documented in [planner and compiler](planner-compiler.md). For a two-relation join, the optimizer requests one population estimate per relation. Exact zero or two known inputs of at most four rows retain hash join. Exactly one known 1–4-row input may orient an indexed nested-loop join when an eligible opposite-side index exists. When both known populations exceed four, the smaller input may drive indexed nested-loop if it has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash join. Five-run confined 4×128 and 8×128 profiles support these population-skew cases, while the 64×64 profile retains hash join.

For joins where both exact populations are at most 4,096, one side has 9–16 rows and the other is at least eight times larger, or the outer side has 17 rows and the indexed side is at least seven times larger, storage may compute an exact bounded INNER JOIN pair count. It reads both authorized projections from the pinned snapshot plus private overlay, requires row visibility to be independent of stored values, and requires every join-key cell to be statically readable for every candidate. Composite keys support one through eight columns; NULL components do not match. The operation is bounded to 4,096 rows per side, 8 MiB of decoded row data, 4 KiB per encoded key, and the shared estimate allowance. Unsupported types, redacted values, incomplete populations, unsupported policy shapes, size-limit failures, or exhaustion return `Unknown` without partial counts. The result is scoped to the planner session and invalidated by each private write; unknown results are not cached.

The optimizer uses this count only for the moderate skew region: if the exact joined-pair count is at most four pairs per row on the smaller outer side, an eligible opposite-side index may drive nested-loop probes. Higher fanout retains hash join. Other joins keep the measured population rules above; `Unknown` preserves existing heuristic selection. This fanout gate is a bounded heuristic, not a general cost model. Five-run confined 9×128 mixed-load profiles found indexed nested-loop faster than hash by median-of-run medians at one match per outer row (180.1 ms versus 295.6 ms), two matches (182.7 ms versus 309.4 ms), three matches (181.5 ms versus 301.9 ms), and four matches (183.7 ms versus 307.4 ms); with five matches per outer row, all five optimizer plans selected hash. Five 16×128 runs also favored indexed nested-loop at one match per outer row (243.5 ms versus 305.7 ms), as did five 17×128 runs (257.3 ms versus 298.9 ms). Five exact-boundary 17×119 runs also favored indexed nested-loop (259.6 ms versus 313.8 ms). Each run overlapped 192 operational reads and 192 commits. These measurements validate the cutoff for these host-local fixtures only, not as a deployment performance target. Predicate estimation remains bounded to 16,384 rows and must not inspect a cell unless authorization proves the referenced cell readable for every candidate row; redacted or unsupported cases fall back without changing execution's redaction and error semantics.

The confined acceptance measures two nonuniform 17×128 fanout distributions. When one outer key matches 16 indexed rows and the remaining 16 outer keys are unmatched, the exact 16-pair estimate falls below the four-pairs-per-outer threshold; kind 17 returns all 16 rows and matches hash. Five fresh-database runs overlapped 192 operational reads and commits each; median-of-run p50 was 257.8 ms indexed and 299.1 ms hash. When that one key matches all 128 indexed rows, the exact estimate exceeds the threshold and all five optimizer plans retain kind-4 hash; all 128 result rows are validated, with median-of-run p50 hash latency of 341.9 ms. Each run again overlapped 192 reads and commits. These host-local cases check two hot-key distributions and do not establish general cost-based planning.

## Cell-Specific Semantics

For a department manager, visible employee count may cover the department, but salary distributions may use only readable salaries of direct reports. State both populations explicitly. A readable-salary distribution must never stand in for the full department's salary distribution.

An internal summary of readable cells is advisory metadata, not permission to execute `SUM(salary)` while silently dropping redacted inputs. Estimation must preserve the query's redaction/error semantics. Predicates requiring redacted values cannot be evaluated against those values during estimation. Return an authorization outcome only if established by trusted validation; otherwise report an unknown estimate and leave definitive checks to execution. A sample showing no redactions is not proof of full authorization.

Multicolumn and future join estimates require authorization for all contributing inputs and explicit joint populations. Separate marginal summaries do not justify assumptions about hidden correlations.

## Disclosure and Trust

Assume the optimizer can encode anything it receives into a physical plan or diagnostic, which the user query library can then disclose through results. It does not generate native artifacts in the baseline. Consequently its statistics authority must not exceed the execution's data authority. Estimates derived from inaccessible cells are disclosures even if they are approximate, rounded, or returned only as costs. Repeated chosen predicates can turn such an API into a data-probing oracle.

The baseline allows summaries computable from the current authorized view. The narrowly reusable committed row count is eligible only when the pinned snapshot, policy shape, and empty private overlay prove it equals that view. Other global or historical statistics remain unavailable to the optimizer and would require an explicitly broader trust model and a reviewed disclosure policy; process separation by itself would not make them safe. This design does not claim full timing or cache noninterference. Rate limits bound work, not disclosure.

## Operational Priority

Keep collection and expensive estimates off the operational critical path when bounded heuristics suffice. Analytical estimates may use larger admitted budgets but cannot starve WAL/commit or expose global distributions. Evaluate plan quality and collection overhead with mixed operational/analytical workloads; a table-wide histogram is not a reason to change the row-oriented primary storage layout.

## Concurrent Collection

Estimate against the invocation's MVCC snapshot plus its successful private writes. Include a transaction-local write generation in estimate/cache validity and reject reuse after mutations. Never expose one invocation's private writes to another. Background collectors use their own registered committed snapshots, no private overlays, and publish catalog updates atomically.

Background collectors and any future asynchronous estimation tasks hold their own storage-managed snapshot/version pins. Release them on completion or drained cancellation so reclamation cannot race an in-flight scan. The current planner estimate request runs synchronously on its provisioned stream using the invocation-pinned snapshot; there is no detached estimation task or separate estimate pin to drain. Apply independent work budgets and avoid holding catalog locks while scanning or sending replies. See [concurrency and MVCC](concurrency-mvcc.md).

## Catalog Integration

Logical object/type/schema identities come from the [data dictionary](data-dictionary.md). Protected statistics catalogs remain a separate derived store: entries reference source object versions, sampling method, and validity domain and are never ordinary metadata-discovery rows. Statistics storage/format may be discarded and rebuilt during [offline upgrades](catalog-lifecycle.md), but invalid estimates must not be reused. Live collection progress belongs to [operational metadata](operational-metadata.md), not optimizer-visible cardinalities or global counters.

## Freshness, Caches, and Failure

Bind summaries to the principal, effective grant, policy and policy-input snapshot, data snapshot, private-write generation, schema version, requested expression, and population. Reuse across contexts requires proof of equivalent visibility and validity; initially do not share scoped entries across principals.

Stale values can contain data no longer authorized under the current snapshot. Do not reuse historical statistics merely because inaccurate estimates are acceptable. Initial estimates use the pinned authorized snapshot; incompatible entries are recomputed or treated as unavailable.

Statistics never establish authorization or correctness. Missing or unsupported estimates, or exhaustion of an estimation-specific allowance, may fall back to fixed heuristics while the planning request remains active. Invocation/request cancellation, deadline expiry, or overall planning budget exhaustion terminates the affected work; fallback must not bypass cancellation or widen access. Keep validity of permissions separate from uncertainty in cardinality.

## Validation and Research Questions

- Compare scoped summaries with a reference authorized scan, including nulls and redactions.
- Change only hidden values or add invisible rows: normalized estimate content must remain unchanged when the authorized view and public inputs are unchanged. Test timing/resource behavior separately as a known limitation.
- Attempt repeated predicate probes, cross-principal cache reuse, stale-policy reuse, and statistics access through worker channels.
- Test planning work limits, cancellation, unsupported expressions, and heuristic fallback.
- Measure planning overhead and plan quality under highly selective policies before adding richer statistics.

Open choices include collection algorithms, safe sampling, cache equivalence proofs, policy-aware cardinality estimation, and whether an explicitly privileged planning mode is ever desirable.

## Background

PostgreSQL separates statistics collection through [`ANALYZE`](https://www.postgresql.org/docs/18/sql-analyze.html) from planner consumption. Its [planner statistics security documentation](https://www.postgresql.org/docs/18/planner-stats-security.html) explains how stored values can leak through user-defined operators. PostgreSQL permits some generic statistics independently of access privileges; this design deliberately adopts a stricter disclosure boundary for true cell-specific permissions.
