# Storage Manager

## Responsibilities and Trust

The Rust storage manager is the sole database authority and the only process that opens the embedded [redb backend](redb-storage.md). It owns SQL semantics, typed row/catalog records, invocation transactions, authorization, constraints, private overlays, logical indexes, outcomes, and budgets. redb owns physical B+trees, page allocation, copy-on-write, physical reclamation, and crash recovery.

The executor is hostile. Authorization does not depend on a plan, index path, or SDK validation. No native client code runs inside storage. The supervisor provisions identities and requests finalization; only storage decides and durably records transaction outcomes.

## Access and Authorization

Resolve logical table/column IDs through the versioned catalog. At admission, pin a redb read transaction and authenticated schema/policy context. Each statement reads the pinned view overlaid with that invocation's staged writes. Before producing results, storage applies row visibility, predicate/cell authorization, and redaction semantics; encode only authorized values into bounded output.

Writes are private field patches until finalization. Storage checks readable/writable changed cells, row policies, constraints, and hidden unchanged-field preservation. At commit it revalidates row versions and authority epochs against the latest redb state. Indexes are access paths only; every candidate still passes visibility and permission checks.

`InvocationTransaction::scan_catalog_authorized_rows` loads the table schema, admitted principal's role closure, data grants, and applicable policies from the pinned catalog, builds the projection internally, and scans the snapshot plus private overlay. The caller supplies only a stable table ID, invocation-local continuation, and bounded candidate count; caller-built grants and policy lists cannot authorize this path. Returned rows are filtered by row policies and each cell is VALUE, NULL, or REDACTED according to the pinned grants and cell policies. The executor connection wraps continuations in one-use kind-7 tokens, revalidates the relation handle before every page, applies a requested-column subset after full-row policy evaluation, and emits kind-8 opaque row handles instead of row IDs. Executor pages cap work at 128 candidate rows and encoded responses at the caller's bounded byte limit.

Executor mutations accept only connection-local relation/row handles and typed full-shape insert values or unique ordinal patches. Storage reloads schema, grants, policies, checks, foreign keys, and indexes from the pinned catalog before staging writes; referenced policy fields and generated identity fields are immutable to updates. INSERT distinguishes VALUE, NULL, and DEFAULT; generated UUID identities are allocated only for DEFAULT and are collision-checked against the serialized final table contents. Successful updates and deletes invalidate outstanding handles for that row. These handlers stage private writes only; finalization remains supervisor-owned.

`ExecutorMetadataConnection::open_relation_scan` revalidates a resolved user-relation handle and issues a connection-local 16-byte cursor with its own kind byte and CSPRNG bytes. `next_relation_scan_page` consumes each cursor once, revalidates the relation handle, derives catalog authorization again, and returns a fresh continuation when more rows may remain. Cross-connection, replayed, modified, and wrong-kind cursors are rejected. Closing a cursor releases the active row-scan slot; closing its relation handle also invalidates an associated scan. Built-in `information_schema` relations are not physical row scans and are rejected by this path.

## Commit and Concurrent Invocations

Allow concurrent redb read transactions and concurrent engine staging. Do not hold a redb write transaction across user execution or individual SQL statements. At successful library return, the supervisor requests finalization; storage obtains the serialized writer, validates all conflicts/constraints/authority, applies data/index/catalog/audit/outcome changes in one redb write transaction, and commits using the selected durable mode.

Any statement error aborts the whole invocation. Cancellation accepted before redb commit begins prevents publication. Once commit begins, report pending/too-late until storage establishes the durable outcome. On ambiguous failures, recover/reconcile; never infer ABORTED from a missing reply. See [MVCC](concurrency-mvcc.md) and [redb mapping](redb-storage.md).

## Catalog and Metadata

The engine owns the [data dictionary](data-dictionary.md), [catalog payloads](catalog-payloads.md), DDL, users, roles, grants, and true row-dependent cell policies. These logical records live in redb tables, not redb's inaccessible physical system tables. Public metadata and planning estimates remain permission-filtered. Required administrative audit records commit atomically with changes. After service authentication, `StorageManager::get_invocation_status` returns owner-scoped live ACTIVE/COMMITTING state, including whether cancellation was requested, and falls back to retained durable outcomes after completion or restart. `StorageManager::list_own_invocations` returns bounded pages of only that owner's live entries; each continuation is owner- and owner-generation-bound and fails if one of that owner's live entries changes between pages. `StorageManager::list_runtime_invocations` provides current database administrators bounded pages of all live invocation entries after revalidating their authority on every request. Its cursor is bound to the administrator and process-local registry generation; no global count is returned. `StorageManager::cancel_invocation` durably audits requests and serializes acceptance against the transition to COMMITTING; the admin runtime page returns its live reason code. Cancellation requests have a separate configurable per-actor rolling-minute cap, defaulting to 30. Unknown, cross-owner, and expired point lookups are indistinguishable. Registry state is best-effort, process-local, and shared by live manager handles for one redb `Database` object. Other global-monitoring surfaces remain control-service work.

The first scoped statistics path, `InvocationTransaction::estimate_authorized_scan`, applies the invocation's pinned projection to its snapshot and private overlay, then returns only visible-row and per-column VALUE/NULL/REDACTED counts. It is bounded to 16,384 candidate rows and returns `Unknown` without partial counts when a value-dependent table policy prevents proving row inclusion or when validation/work limits fail. The planner operation is defined in IPC, but no planner-to-storage handler or planning handle is implemented yet.

`InvocationTransaction::list_authorized_relations` reads the pinned schema catalog and lists only tables within that schema for which the invocation has schema USAGE and an effective table-level SELECT/INSERT/UPDATE/DELETE or column-level SELECT/INSERT/UPDATE grant. Write-only grants therefore permit declared relation discovery. The bounded result contains stable relation IDs and names; the method does not scan rows, evaluate row policies, or expose defaults, policy text, ownership, grant provenance, schema versions, or hidden totals. SQL `information_schema` virtual scans remain unimplemented.

`InvocationTransaction::describe_authorized_columns` applies the same discovery checks and returns all declared column IDs, names, ordinals, scalar types, and nullability for an admitted relation, with no defaults or policy details. Its page variant returns at most 128 ordinal-ordered columns and at most 1 MiB, with an invocation-local continuation. Neither method returns partial shape when its response limit is exceeded; serialized IPC cursors and SQL `information_schema` scans remain future work.

`InvocationTransaction::resolve_authorized_relation` resolves an exact relation name through the filtered relation pages and then independently rechecks access before returning its stable ID, name, and declared columns. Hidden and nonexistent names produce the same unavailable result. The bounded description is not a row-access capability; later reads reauthorize their own requests. `open_executor_metadata_connection` issues at most 256 16-byte opaque relation handles over a session's lifetime. The session binds each handle to the qualified name and stable relation ID, re-resolves it before use, and invalidates it on close or drop. The IPC handler must own one session per executor connection; the engine primitive does not replace per-operation authorization. SQL `information_schema` request dispatch and administrative discovery remain future work.

`InvocationTransaction::list_authorized_schemas` returns schema IDs and names for schemas with schema USAGE plus the reserved public `information_schema` namespace, in bounded pages ordered by stable schema ID. Its continuation is limited to the invocation that created it and does not disclose hidden schema totals. `scan_information_schema_schemata` projects these pages to `schema_name` rows while preserving the same filtering, bounds, ordering, and continuation. `scan_information_schema_tables_in_schema` resolves one exact visible schema and projects its bounded relation pages to `table_schema`, `table_name`, and `table_type = BASE TABLE`; hidden and nonexistent user schema names share the unavailable result, while a visible empty schema yields an empty page. The public `information_schema` schema exposes its three fixed virtual relations with `table_type = VIEW`. `scan_information_schema_tables` walks those schema pages and relation pages in schema-ID/relation-ID order, with a distinct invocation-local cursor; an empty visible schema can return an empty page while advancing. SQL binding/execution for the virtual relations remains future work.

`scan_information_schema_columns_for_relation` resolves one visible schema/relation pair and projects the authorized declared columns into the initial `information_schema.columns` shape. For user schemas it pages through the existing column-description API; the public built-in relations use fixed static definitions. Both paths use one-based ordinals and YES/NO nullability, and include only applicable VARCHAR length and integer/decimal precision/scale values. Each projected page counts its extra schema, relation, and type-description bytes against the 1 MiB metadata page cap. `scan_information_schema_columns` walks those relation pages in schema-ID/relation-ID order using a separate invocation-local cursor that retains the current schema, relation, and column continuations. An empty relation page can advance the scan. The built-in self-description shapes are `schemata(schema_name TEXT NOT NULL)`, `tables(table_schema TEXT NOT NULL, table_name TEXT NOT NULL, table_type TEXT NOT NULL)`, and `columns(table_schema TEXT NOT NULL, table_name TEXT NOT NULL, column_name TEXT NOT NULL, ordinal_position INTEGER NOT NULL, data_type TEXT NOT NULL, is_nullable TEXT NOT NULL, character_maximum_length INTEGER NULL, numeric_precision INTEGER NULL, numeric_scale INTEGER NULL)`. SQL binding/execution remains future work.

Schema, relation, column, all-schema table, and all-relation column continuation tokens have a fixed 16-byte wire form with a cursor-kind byte and 15 OS-random bytes. One-use server-side state binds them to the invocation and authorization inputs. Modified, replayed, cross-invocation, or cross-kind tokens fail closed.

`InvocationTransaction::resolve_authorized_schema` performs exact, case-sensitive lookup over the same filtered pages. Hidden and nonexistent schema names both return no result; the returned ID is only a logical reference and grants no authority.

`InvocationTransaction::load_catalog_schema_usage_grants` derives only persisted schema USAGE grants for the admitted principal and pinned role closure. It guards the membership, grant, schema, and grantor records it reads so a later authority change invalidates a pending write.

`InvocationTransaction::list_catalog_authorized_schemas` uses those pinned records to construct the metadata context internally and return bounded visible schema pages for the admitted invocation. The caller supplies neither identity nor grants.

`InvocationTransaction::load_catalog_relation_discovery_grants` loads schema USAGE and relation data grants for one schema from the pinned catalog, validates column targets, and guards the authority records. `list_catalog_authorized_relations` constructs its context from that result before returning bounded visible relation pages. The caller supplies only the schema reference and page continuation.

`InvocationTransaction::resolve_catalog_authorized_relation` resolves schema and relation names from the invocation's pinned catalog, deriving schema and relation grants internally. It returns only the declared shape after an independent authority check; subsequent reads authorize again.

The trusted identity DDL route supports `DROP USER/ROLE ... RESTRICT` after bounded scans find no object owner/parent, membership, grant, policy-target, or dependency references. A user's active credentials are revoked in the same serialized commit that removes its principal and named object and inserts its permanent identity tombstone. The final catalog validators reject concurrent dangling references, and deletion cannot leave the database without a login-enabled administrator credential.

Token issue, revoke, and inventory requests use a monotonic 60-second sliding window per authenticated actor, with a default cap of 30 requests. Administrative cancellation has a separate per-actor limiter with the same default. Live manager handles for one redb `Database` object share each limiter; each actor-history map is capped at 4,096 entries and expired histories are pruned. If a map is full, requests for new actors fail closed. Invalid token-authentication attempts require gateway-level throttling because the storage API does not receive a client source identity.

## Resource and Process Boundaries

Bound active redb snapshots, transaction age, private overlay bytes, scans, output, and finalization work. `StorageInstance::open` acquires the exclusive local instance lock and validates a recovered READY image before a trusted service constructs `StorageManager`; it can then create a manager from that already validated image without repeating the startup scan. Direct `StorageManager` construction also validates READY state, but does not acquire the filesystem lock. Neither path authenticates a service connection. `bootstrap::initialize` creates an INITIALIZING instance, and `bootstrap::resume` rotates its bootstrap token after interrupted handoff. Both retain the instance lock until acknowledgement or drop. `begin_token_authenticated_invocation` verifies the versioned random-token profile using trusted UTC time and pins the verifier, user, and role-membership records for commit revalidation. `issue_token` uses the system CSPRNG, returns its secret once, and stores only its verifier; `revoke_token` uses the authorized identity DDL path. `list_tokens` reads a single snapshot and returns nonsecret metadata only, allowing self-inventory or cross-user inventory with `MANAGE_USERS`/database-admin authority. The identity-based admission method is only for a trusted caller that has already authenticated the user. The manager also requires a positive configured active-invocation limit and age, shares the snapshot cap across cloned handles, and reserves a slot before pinning the redb snapshot. Managed transactions observe accepted cancellation and expire at read/write/finalization checkpoints; services must poll `check_deadline` while work is idle so terminal transactions release their snapshot and admission slot. A long analytical reader can retain redb pages and delay reclamation; scheduling must protect operational transactions. Do not hold redb guards while waiting for network or executor output.

Only the gateway handles client TCP. Only the supervisor launches and owns executor processes. The executor receives local scoped IPC and sanitized values, never redb handles/descriptors. The optimizer receives authorized schema and scoped estimates, never raw database tables.

## Validation

Test redb snapshot/overlay semantics, concurrent staging and serialized finalization, same-row conflicts, distinct-row commits, write skew, atomic row/index/catalog/outcome updates, policy changes racing commit, hidden-field preservation, restart/outcome reconciliation, malformed IPC, long-reader pressure, and identical authorization behavior for scans and index lookups.
