# Storage Manager

## Responsibilities and Trust

The Rust storage manager is the sole database authority and the only process that opens the embedded [redb backend](redb-storage.md). It owns SQL semantics, typed row/catalog records, invocation transactions, authorization, constraints, private overlays, logical indexes, outcomes, and budgets. redb owns physical B+trees, page allocation, copy-on-write, physical reclamation, and crash recovery.

The executor is hostile. Authorization does not depend on a plan, index path, or SDK validation. No native client code runs inside storage. The supervisor provisions identities and requests finalization; only storage decides and durably records transaction outcomes.

## Access and Authorization

Resolve logical table/column IDs through the versioned catalog. At admission, pin a redb read transaction and authenticated schema/policy context. Each statement reads the pinned view overlaid with that invocation's staged writes. Before producing results, storage applies row visibility, predicate/cell authorization, and redaction semantics; encode only authorized values into bounded output.

Writes are private field patches until finalization. Storage checks readable/writable changed cells, row policies, constraints, and hidden unchanged-field preservation. At commit it revalidates row versions and authority epochs against the latest redb state. Indexes are access paths only; every candidate still passes visibility and permission checks.

`InvocationTransaction::scan_catalog_authorized_rows` loads the table schema, admitted principal's role closure, data grants, and applicable policies from the pinned catalog, builds the projection internally, and scans the snapshot plus private overlay. The caller supplies only a stable table ID, invocation-local continuation, and bounded candidate count; caller-built grants and policy lists cannot authorize this path. Returned rows are filtered by row policies and each cell is VALUE, NULL, or REDACTED according to the pinned grants and cell policies. The executor connection wraps continuations in one-use kind-7 tokens, revalidates the relation handle before every page, applies a requested-column subset after full-row policy evaluation, and emits kind-8 opaque row handles instead of row IDs. Executor pages cap work at 128 candidate rows and encoded responses at the caller's bounded byte limit.

Executor mutations accept only connection-local relation/row handles and typed full-shape insert values or unique ordinal patches. Storage reloads schema, grants, policies, checks, foreign keys, and indexes from the pinned catalog before staging writes; referenced policy fields and generated identity fields are immutable to updates. INSERT distinguishes VALUE, NULL, and DEFAULT; generated UUID identities are allocated only for DEFAULT and are collision-checked against the serialized final table contents. Successful updates and deletes invalidate outstanding handles for that row. These handlers stage private writes only; the Supervisor-role terminal handler alone commits or aborts an active invocation.

`ExecutorMetadataConnection::open_relation_scan` revalidates a resolved relation handle and issues a connection-local 16-byte cursor with its own kind byte and CSPRNG bytes. Physical user-relation scans revalidate the relation handle and derive catalog authorization on each page. The initial virtual executor scan supports `information_schema.schemata`, using the invocation's filtered schema scanner; its rows receive opaque read-only handles that cannot be staged for mutation. `information_schema.tables` and `information_schema.columns` are not yet available through this executor scan path. Cross-connection, replayed, modified, and wrong-kind cursors are rejected. Closing a cursor releases its active physical or virtual scan state; closing its relation handle also invalidates an associated scan.

`StorageManager::authenticate_query_session` verifies a database token and the principal's current login/role closure on one read snapshot without creating an invocation or durable outcome. It returns a non-secret identity context and a server-generated opaque connection ID. The context creates staging owners bound to that connection ID and authenticated principal; clients cannot supply principal IDs. Execution START must revalidate the token through `admit_supervisor_invocation`; successful AUTH does not freeze later authority changes.

`admit_supervisor_invocation_with_deadline_and_scope` adds the sealed submission's requested execution deadline to the storage manager's configured maximum age and intersects its decoded `PSC1` requested capability set with grants loaded from the pinned token-authenticated catalog. This only narrows effective authority; a client cannot create grants by requesting capabilities. The supervisor must poll `SupervisorInvocation::check_deadline` while planner and executor channels are idle; expiration durably aborts an admitted invocation and releases its snapshot. The client session's `start_submission` decodes requested scope and invokes token-bound admission only inside the one-shot sealed staging transition.

## Commit and Concurrent Invocations

Allow concurrent redb read transactions and concurrent engine staging. Do not hold a redb write transaction across user execution or individual SQL statements. At successful library return, the supervisor requests finalization; storage obtains the serialized writer, validates all conflicts/constraints/authority, applies data/index/catalog/audit/outcome changes in one redb write transaction, and commits using the selected durable mode.

Any statement error aborts the whole invocation. Cancellation accepted before redb commit begins prevents publication. Once commit begins, report pending/too-late until storage establishes the durable outcome. On ambiguous failures, recover/reconcile; never infer ABORTED from a missing reply. See [MVCC](concurrency-mvcc.md) and [redb mapping](redb-storage.md).

## Catalog and Metadata

The engine owns the [data dictionary](data-dictionary.md), [catalog payloads](catalog-payloads.md), DDL, users, roles, grants, and true row-dependent cell policies. These logical records live in redb tables, not redb's inaccessible physical system tables. Public metadata and planning estimates remain permission-filtered. Required administrative audit records commit atomically with changes. After service authentication, `StorageManager::get_invocation_status` returns owner-scoped live ACTIVE/COMMITTING state, including whether cancellation was requested, and falls back to retained durable outcomes after completion or restart. `StorageManager::get_administrative_invocation_status` revalidates current database-administrator authority before returning any invocation's live state or retained terminal outcome. `StorageManager::list_own_invocations` returns bounded pages of only that owner's live entries; each continuation is owner- and owner-generation-bound and fails if one of that owner's live entries changes between pages. `StorageManager::list_runtime_invocations` provides current database administrators bounded pages of all live invocation entries after revalidating their authority on every request. Its cursor is bound to the administrator and process-local registry generation; no global count is returned. `StorageManager::cancel_invocation` durably audits requests and serializes acceptance against the transition to COMMITTING; the admin runtime page returns its live reason code. Cancellation requests have a separate configurable per-actor rolling-minute cap, defaulting to 30. Unknown, cross-owner, and expired point lookups are indistinguishable. Registry state is best-effort, process-local, and shared by live manager handles for one redb `Database` object. Other global-monitoring surfaces remain control-service work.

The first scoped statistics path, `InvocationTransaction::estimate_authorized_scan`, applies the invocation's pinned projection to its snapshot and private overlay, then returns only visible-row and per-column VALUE/NULL/REDACTED counts. It is bounded to 16,384 candidate rows and returns `Unknown` without partial counts when a value-dependent table policy prevents proving row inclusion or when validation/work limits fail. `planner_ipc` dispatches relation description and estimates through a planner-only kind-9 handle and never accepts executor row handles. Supervisor provisioning of the planner stream remains unimplemented.

`InvocationTransaction::list_authorized_relations` scans the pinned table catalog for relations whose stored schema ID matches the requested schema, then lists only those for which the invocation has schema USAGE and an effective table-level SELECT/INSERT/UPDATE/DELETE or column-level SELECT/INSERT/UPDATE grant. This matches the catalog representation: schema records do not maintain a relation ID list. Write-only grants therefore permit declared relation discovery. The bounded result contains stable relation IDs and names; the method does not scan rows, evaluate row policies, or expose defaults, policy text, ownership, grant provenance, schema versions, or hidden totals. The executor scan path now exposes filtered `information_schema.schemata`; SQL-backed `tables` and `columns` virtual scans remain future work.

`InvocationTransaction::describe_authorized_columns` applies the same discovery checks and returns all declared column IDs, names, ordinals, scalar types, and nullability for an admitted relation, with no defaults or policy details. Its page variant returns at most 128 ordinal-ordered columns and at most 1 MiB, with an invocation-local continuation. Neither method returns partial shape when its response limit is exceeded; virtual `information_schema.columns` has not yet been connected to executor IPC or SQL execution.

`InvocationTransaction::resolve_authorized_relation` resolves an exact relation name through the filtered relation pages and then independently rechecks access before returning its stable ID, name, and declared columns. Hidden and nonexistent names produce the same unavailable result. The bounded description is not a row-access capability; later reads reauthorize their own requests. `open_executor_metadata_connection` issues at most 256 16-byte opaque relation handles over a session's lifetime. The session binds each handle to the qualified name and stable relation ID, re-resolves user relations before use, and invalidates it on close or drop. The IPC handler owns one session per executor connection. The initial SQL executor scan supports only the `information_schema.schemata` virtual relation; the other virtual scans and administrative discovery remain future work.

`InvocationTransaction::list_authorized_schemas` returns schema IDs and names for schemas with schema USAGE plus the reserved public `information_schema` namespace, in bounded pages ordered by stable schema ID. Its continuation is limited to the invocation that created it and does not disclose hidden schema totals. `scan_information_schema_schemata` projects these pages to `schema_name` rows while preserving the same filtering, bounds, ordering, and continuation. The executor `open_scan`/`next_batch` path exposes these filtered rows as read-only virtual relation cells. `scan_information_schema_tables_in_schema` resolves one exact visible schema and projects its bounded relation pages to `table_schema`, `table_name`, and `table_type = BASE TABLE`; hidden and nonexistent user schema names share the unavailable result, while a visible empty schema yields an empty page. The public `information_schema` schema exposes its three fixed virtual relations with `table_type = VIEW`. `scan_information_schema_tables` walks those schema pages and relation pages in schema-ID/relation-ID order, with a distinct invocation-local cursor; an empty visible schema can return an empty page while advancing. SQL binding/execution for the `tables` and `columns` virtual relations remains future work.

`scan_information_schema_columns_for_relation` resolves one visible schema/relation pair and projects the authorized declared columns into the initial `information_schema.columns` shape. For user schemas it pages through the existing column-description API; the public built-in relations use fixed static definitions. Both paths use one-based ordinals and YES/NO nullability, and include only applicable VARCHAR length and integer/decimal precision/scale values. Each projected page counts its extra schema, relation, and type-description bytes against the 1 MiB metadata page cap. `scan_information_schema_columns` walks those relation pages in schema-ID/relation-ID order using a separate invocation-local cursor that retains the current schema, relation, and column continuations. An empty relation page can advance the scan. The built-in self-description shapes are `schemata(schema_name TEXT NOT NULL)`, `tables(table_schema TEXT NOT NULL, table_name TEXT NOT NULL, table_type TEXT NOT NULL)`, and `columns(table_schema TEXT NOT NULL, table_name TEXT NOT NULL, column_name TEXT NOT NULL, ordinal_position INTEGER NOT NULL, data_type TEXT NOT NULL, is_nullable TEXT NOT NULL, character_maximum_length INTEGER NULL, numeric_precision INTEGER NULL, numeric_scale INTEGER NULL)`. SQL binding/execution remains future work.

Schema, relation, column, all-schema table, and all-relation column continuation tokens have a fixed 16-byte wire form with a cursor-kind byte and 15 OS-random bytes. One-use server-side state binds them to the invocation and authorization inputs. Modified, replayed, cross-invocation, or cross-kind tokens fail closed.

`InvocationTransaction::resolve_authorized_schema` performs exact, case-sensitive lookup over the same filtered pages. Hidden and nonexistent schema names both return no result; the returned ID is only a logical reference and grants no authority.

`StorageManager::create_schema` creates one empty schema and its family-2 object atomically. It accepts normalized lowercase ASCII identifiers (128 bytes maximum) and a live user or role as initial owner. The authenticated actor must hold inherited database-scoped `CREATE_SCHEMA` or belong to `database_admin`; the owner assignment itself grants no table data privileges. Storage validates the schema/object pair, rejects an existing schema name or reused ID, and commits audit and outcome with the records. The v1 `schemas.create` control operation exposes this path through connection-owned PREPARE/START. Quoted mixed-case identifiers remain unsupported.

`StorageManager::drop_schema` removes the schema record and owned object in one authorized DDL commit. The owner (including inherited membership in an owning role) or a database administrator may request the operation. Reserved system schemas and schemas with child objects or remaining dependency edges are rejected with `SchemaNotEmpty`; the dependency and child scan is bounded by `MAX_CATALOG_FAMILY_SCAN`. Storage repeats the emptiness scan inside the serialized redb write transaction so a concurrent table creation cannot leave an orphan. The `schemas.drop` control operation uses connection-owned PREPARE/START and returns the removed schema ID and commit sequence.

`StorageManager::set_schema_owner` transfers a non-system schema to a live user or role. The current owner or a database administrator authorizes the change. Storage increments the schema object's version and replaces its owner atomically, preserving the schema record and child objects. A schema owner may create tables and manage the schema but receives no table data privileges. The `schemas.set_owner` control operation uses connection-owned PREPARE/START.

`StorageManager::rename_schema` updates a non-system schema object's normalized name and version atomically. The owner or a database administrator authorizes the change. The stable schema ID, schema record, and child objects remain unchanged; schema-name uniqueness is checked in the serialized catalog writer. The `schemas.rename` control operation uses connection-owned PREPARE/START.

Table-drop requests also reject targets in built-in system schemas.

`StorageManager::drop_table` removes a table and its owned typed definitions, expressions, grants, dependency edges, rows, and physical index entries in one DDL commit. The owner or database administrator authorizes the request. External incoming dependencies are rejected after authorization. Removing an owned foreign key also advances the referenced table's write epoch once per affected table in the same commit, invalidating writers pinned to the prior constraint graph. Cleanup is bounded by 65,536 rows, 65,536 physical index entries, and 64 MiB combined row tuple payload plus physical index key and locator bytes. Row versions and catalog values are checked again during commit. The `tables.drop` control operation uses connection-owned PREPARE/START and returns the removed table ID and commit sequence.

`StorageManager::drop_column` applies RESTRICT checks to expressions, constraints, indexes, and policies that reference the target. It removes the column and its owned default expression, compacts sibling ordinals, advances the table schema version and write epoch, and rewrites stored tuples and surviving index memberships under the table DDL fence. The old row versions and index memberships are revalidated at publication. The operation is bounded to 65,536 rows and 64 MiB of combined old and rewritten tuple payloads; oversized changes abort without publication. The `tables.drop_column` PREPARE/START operation returns the table ID, column ID, and commit sequence.

`StorageManager::create_table` accepts `CreateTableRequest` with a schema ID, normalized table name, and ordered `TableColumnDefinition` values. It supports built-in scalar types, UUID generated identity metadata, typed literal/NULL defaults, and the trusted current-principal UUID default. Defaults publish family-7 expression records and column-to-expression kind-2 dependencies in the same commit as the family-2 objects, family-5 table record, family-6 ordered column records, kind-1 owned-child dependencies, audit event, and durable outcome. The expression form and type profile are checked again at commit. Table names are checked for uniqueness within the schema under the serialized catalog writer. The actor must hold schema CREATE, be the schema owner (including inherited membership in an owning role), or be a database administrator. New tables receive no data grants. The authenticated `tables.create` control operation owns PREPARE/START state per connection and returns the generated table and ordered column IDs; it does not parse SQL or define inline constraints.

`InvocationTransaction::load_catalog_schema_usage_grants` derives only persisted schema USAGE grants for the admitted principal and pinned role closure. It guards the membership, grant, schema, and grantor records it reads so a later authority change invalidates a pending write.

`InvocationTransaction::list_catalog_authorized_schemas` uses those pinned records to construct the metadata context internally and return bounded visible schema pages for the admitted invocation. The caller supplies neither identity nor grants.

`InvocationTransaction::load_catalog_relation_discovery_grants` loads schema USAGE and relation data grants for one schema from the pinned catalog, validates column targets, and guards the authority records. `list_catalog_authorized_relations` constructs its context from that result before returning bounded visible relation pages. The caller supplies only the schema reference and page continuation.

`InvocationTransaction::resolve_catalog_authorized_relation` resolves schema and relation names from the invocation's pinned catalog, deriving schema and relation grants internally. It returns only the declared shape after an independent authority check; subsequent reads authorize again.

The trusted identity DDL route creates LOGIN users and non-login roles with normalized lowercase ASCII names and generated stable IDs, publishing each family-10 principal and matching family-2 object together with its audit and outcome. Creation grants no data privileges; users receive credentials through separate token issuance, and roles receive memberships through separate membership DDL. Membership grant/revoke updates the family-11 membership and family-15 dependency edge atomically and increments the member's authority epoch; final graph, endpoint-kind, cycle, and usable-administrator checks run through the authorized membership commit path. The route also supports `DROP USER/ROLE ... RESTRICT` after bounded scans find no object owner/parent, membership, grant, policy-target, or dependency references. A user's active credentials are revoked in the same serialized commit that removes its principal and named object and inserts its permanent identity tombstone. The final catalog validators reject concurrent dangling references, and deletion cannot leave the database without a login-enabled administrator credential.

The administrative system-privilege lifecycle grants or revokes database-scoped `MANAGE_USERS`, `MANAGE_ROLES`, and `CREATE_SCHEMA` for a live principal. Each change atomically updates the family-12 privilege record, its family-15 dependency edge, the grantee's authority epoch, audit event, and durable operation outcome. Only a current database administrator can change these grants; duplicate grants and missing revokes are rejected.

`rename_identity` renames a live user or role through the authorized identity DDL path. It updates the family-10 principal name and authority epoch together with the family-2 object name and object version. Authorization is selected from the principal kind (`MANAGE_USERS` for users, `MANAGE_ROLES` for roles), with database administrators allowed to rename either kind.

`set_user_login_enabled` changes a LOGIN user's enabled state and authority epoch. Disabling LOGIN scans the bounded credential family and revokes every outstanding verifier in the same authorized commit; enabling LOGIN never unrevokes credentials. The commit path retains the final login-enabled administrator check.

`drop_identity` removes a user or role only when the authorized identity DDL validator confirms no object ownership/parent, membership, grant, policy, or dependency references remain. It atomically deletes the principal and named object and adds a permanent tombstone; user token verifiers are revoked in that same commit.

Token issue, revoke, and inventory requests use a monotonic 60-second sliding window per authenticated actor, with a default cap of 30 requests. Administrative cancellation has a separate per-actor limiter with the same default. Live manager handles for one redb `Database` object share each limiter; each actor-history map is capped at 4,096 entries and expired histories are pruned. If a map is full, requests for new actors fail closed. The [gateway](client-gateway.md) separately reserves and limits failed token-authentication attempts per source IP because storage does not receive a network source identity; IP is never used as database authority.

## Resource and Process Boundaries

Bound active redb snapshots, transaction age, private overlay bytes, scans, output, and finalization work. `StorageInstance::open` acquires the exclusive local instance lock and validates a recovered READY image before a trusted service constructs `StorageManager`; it can then create a manager from that already validated image without repeating the startup scan. Direct `StorageManager` construction also validates READY state, but does not acquire the filesystem lock. Neither path authenticates a service connection. `bootstrap::initialize` creates an INITIALIZING instance, and `bootstrap::resume` rotates its bootstrap token after interrupted handoff. Both retain the instance lock until acknowledgement or drop. `begin_token_authenticated_invocation` verifies the versioned random-token profile using trusted UTC time and pins the verifier, user, and role-membership records for commit revalidation. `admit_supervisor_invocation` wraps that transaction in one supervisor-owned context with the authenticated principal and role closure bound outside IPC payloads; it routes planner, executor, terminal, status, and cancellation channels, and durably aborts if the owner drops an unfinalized invocation. Planner and executor channels may serve concurrently: the owner serializes access to the shared invocation for each request while preserving opaque handles and scan state within each channel. Terminal finalization is rejected while a planner or executor channel remains open, and new worker channels are rejected after a terminal decision starts. The supervisor can call `SupervisorInvocation::check_deadline` while workers are idle to enforce accepted cancellation and transaction age, releasing the snapshot and admission slot on abort. After both worker channels drain, `SupervisorInvocation::observe_worker_exit` polls and reaps the process while continuing deadline checks; a failed exit or inspection error durably aborts, and the supervisor may request commit only after a successful exit. `start_and_launch_executor` owns worker setup, confinement hooks, and spawn ordering; the supervisor service owns that orchestration and its host-specific runtime paths. `issue_token` uses the system CSPRNG, returns its secret once, and stores only its verifier; `revoke_token` uses the authorized identity DDL path. `list_tokens` reads a single snapshot and returns nonsecret metadata only, allowing self-inventory or cross-user inventory with `MANAGE_USERS`/database-admin authority. The identity-based admission method is only for a trusted caller that has already authenticated the user. The manager also requires a positive configured active-invocation limit and age, shares the snapshot cap across cloned handles, and reserves a slot before pinning the redb snapshot. A long analytical reader can retain redb pages and delay reclamation; scheduling must protect operational transactions. Do not hold redb guards while waiting for network or executor output.

Only the gateway handles client TCP. Only the supervisor launches and owns executor processes. The executor receives local scoped IPC and sanitized values, never redb handles/descriptors. The optimizer receives authorized schema and scoped estimates, never raw database tables.

The supervisor may pass preprovisioned planner and executor `UnixStream`s to `SupervisorInvocation::serve_worker_channels`. Storage serves both channels concurrently, polls cancellation and age every 100 ms while either handler is idle, shuts down the sibling channel after a handler failure, aborts if a handler panics, and returns after both handlers drain. `serve_terminal` refuses to commit until worker observation has waited for and reaped the associated process successfully; while observing, no new worker channel can open. For sandboxed workers, the supervisor uses cgroup-aware observation, which kills descendants and requires the cgroup to be empty before returning success. The observer continues polling cancellation and age. A nonzero exit is a durable abort and closes the invocation against later worker or terminal requests. `start_and_launch_executor` provides only the supervised process boundary; actual host-level security acceptance remains conditional on the delegated-cgroup and TinyCC integration fixtures.

## Validation

`StorageManager::rename_table` updates the table object's normalized name and version and increments the table write epoch in one authorized commit. The owner or a database administrator may rename a non-system table. Final schema-local name uniqueness is checked in the serialized writer; table identity, tuple schema version, rows, and index memberships remain unchanged. The `tables.rename` control operation uses connection-owned PREPARE/START and returns the table ID and commit sequence.

`StorageManager::set_table_owner` transfers a non-system table to an existing live user or role. The current owner or a database administrator authorizes the change. Storage atomically updates the table object's owner and object version and increments its write epoch while preserving tuple schema version, rows, indexes, and grants. The new owner gains table-level DDL authority but no data privileges. The `tables.set_owner` control operation uses connection-owned PREPARE/START.

`StorageManager::rename_column` updates the family 6 column name and matching family 2 object name/version while incrementing the table write epoch in one authorized commit. The owner or a database administrator may rename a column on a non-system table. Column identity, ordinal, type, defaults, nullability, dependencies, and tuple schema version remain unchanged. Final table-local name uniqueness is checked in the serialized writer. The `tables.rename_column` control operation uses connection-owned PREPARE/START.

`StorageManager::set_column_nullable` changes a column's nullable flag in an authorized constraint DDL commit. The owner or a database administrator may alter a column on a non-system table. It increments the table write epoch while preserving the tuple schema version. Setting nullable to false creates the internal NOT NULL constraint and validates current rows under the exclusive table fence, bounded to 65,536 rows and 64 MiB of row-record bytes. Setting nullable to true removes the matching internal constraint when present. The `tables.alter_column_nullability` control operation uses connection-owned PREPARE/START.

`StorageManager::alter_column_default` sets, replaces, or drops the current insert default on a non-generated column. It checks the declared scalar type and type default mask, then uses the authorized constraint DDL commit path to atomically update the family 6 default reference, family 7 expression, family 2 expression object, family 15 dependency, table write epoch, audit event, and durable outcome. Replaced/dropped expression records and dependency edges are removed atomically. The tuple schema version and add-column default reference remain unchanged; existing rows are not rewritten. The `tables.set_column_default` and `tables.drop_column_default` operations use connection-owned PREPARE/START.

Standalone index creation, removal, and rebuild increment the affected table's write epoch without changing its tuple schema version. The epoch update commits atomically with the index definition and physical memberships, so writers pinned to an older index set conflict after publication. Combined schema rewrites already advance the table epoch and do not add a second increment.

`StorageManager::add_table_column` appends one non-generated column to a non-system table. The owner or database administrator authorizes the DDL. NOT NULL requires a typed non-null literal; nullable columns may omit a default and backfill NULL. `CURRENT_PRINCIPAL_ID` is disallowed for backfill. Storage publishes the new family 6 definition, family 2 object, owned-child dependency, immutable add-column default expression/reference when present, table schema version/write epoch, audit, and outcome atomically. It rewrites rows and refreshes existing index definitions and locators under the table DDL fence, preserving stable row IDs. The combined row rewrite is bounded to 65,536 rows and 64 MiB of old plus rewritten tuple payloads.

Test redb snapshot/overlay semantics, concurrent staging and serialized finalization, same-row conflicts, distinct-row commits, write skew, atomic row/index/catalog/outcome updates, policy changes racing commit, hidden-field preservation, restart/outcome reconciliation, malformed IPC, long-reader pressure, and identical authorization behavior for scans and index lookups.
