# Client SDK and Query Library Contract

## Required Model

For a hand-written native query program, the user compiles it into a loadable shared library using the SDK; the client submits that artifact and parameters, and a disposable confined executor loads it and invokes its entry point. For ordinary SQL (`prdb-client interactive-sql`), the client instead submits SQL text, parameters, and scope directly with `submission_kind: "sql_text"` and builds no artifact at all; the confined executor calls the SDK's own fixed SQL batch entry points directly, with no client-supplied code loaded. The SDK includes basic SQL support and public definitions for interacting with database components; either way, the SQL engine itself is the same fixed, server-selected code.

The user program may call SQL, process authorized results, or use lower-level scoped storage APIs. SQL is a convenience layer, not an authorization boundary. Compilation does not require database access or live statistics; optimization happens when SDK SQL calls run against an admitted execution context. See [`engine/examples/queries`](../engine/examples/queries/README.md) for three complete hand-written programs (one calling SQL, one using only direct storage calls, one mixing both) and the full `prdb-packager`/`prdb-client submit` build-and-submit walkthrough.

## SDK Contents

| Surface | SDK contents | Runtime authority |
| --- | --- | --- |
| Query entry point / executor | Versioned C ABI, host function table, parameters, result emission, errors, cancellation | Current invocation only |
| Storage manager | Schema/value types, redaction states, opaque handles, scan/cursor/mutation request definitions and stubs | Scoped reads and staged writes validated by storage |
| Optimizer | Structured request encoding, physical-plan definitions and initial decoder, bounded planning submission | Plans for the current context |
| SQL | Parser, expression semantics, physical-plan interpreter, result API | Same storage authority as user code |
| Client submission/network | TCP framing, authentication, artifact upload, compatibility manifest, START, provisional results, outcome/status/cancellation | Client-only gateway connection; caller-authenticated admission |
| Administration | Schema/user/role/policy DDL, token lifecycle, and SDK repository operations | Separate authenticated control channel; never an executor capability |
| Statistics and other services | Versioned public protocol definitions and role annotations | Definitions confer no access; scoped estimation remains optimizer-only; global catalogs are private |

Generate language bindings from one protocol/schema source when selected. Do not expose process-local storage structures, raw page layouts, private catalogs, or server object pointers. Public definitions are contracts, not copies of server implementations. Services still validate messages from clients that ignore or modify the SDK.

## Client Network Boundary

Use the [network protocol](client-protocol.md) through the dedicated [gateway](client-gateway.md) for external submission and result delivery. Ship the transport/authentication client separately from the C SQL/runtime shared library linked into query.so. It may be implemented as a Rust client library/helper with bindings; that choice does not change TinyCC query compilation. The query runtime receives no network sockets or admission credentials.

The client uploads/seals bytes before START, records the reserved invocation ID, and treats result frames as provisional until a supervisor-originated storage-confirmed terminal outcome. Network errors require authenticated status lookup, not automatic invocation replay. Multiple connections can run concurrent invocations; the initial TCP connection carries one operation/result stream at a time. Cancellation/status during streaming uses another authenticated connection.

## Packaging Baseline

Ship headers/bindings and a prebuilt position-independent SQL/runtime shared library for each supported target, native ABI, and SDK release. Compile user code and dynamically link it to the selected local library to produce query.so; do not rebuild the database services on each query edit. Packages contain query.so and its compatibility metadata; the client uploads query.so but never `sql.so`. The server resolves the exact SDK release from its instance repository.

Give each SQL shared library the versioned SONAME for the declared SDK release. The package manifest identifies the SDK release, target/profile, and ABI; the query ELF's DT_NEEDED set must include that SONAME and match the manifest. The client links against its locally installed copy matching its persistent per-instance release selection, but submits only query.so, not the SDK shared library. START resolves the exact release from the instance's administrator-managed [SDK library repository](sdk-library-repository.md), pins the immutable release, and stages it alongside query.so in the worker's private read/execute-only artifact directory. The query uses only a fixed `$ORIGIN` RUNPATH to resolve the staged dependency; arbitrary RPATH/RUNPATH and loader overrides remain forbidden. The repository entry cannot be removed while referenced by an active invocation.

The repository is a supervisor-managed immutable file store, not a loaded-code cache. The supervisor never loads the SDK library. The clean executor loads query.so and its dependencies only after confinement is established; SDK constructors and code are untrusted native code and run under the same sandbox. The SDK library may share kernel file-page cache across workers, while each invocation retains its own process, address space, mutable globals, and SQL state. Standard runtime dependencies must still be declared and supported; this is not a promise of a completely self-contained binary.

### Artifact Manifest v1

Manifest version 1 is canonical binary `PMF1`. Its 28-byte header is: magic[4], target OS:u8 (`1` Linux), target architecture:u8 (`1` x86_64), native ABI:u8 (`1` through `6`), flags:u8 (zero), client protocol major:u16 BE (`1`), minor:u16 BE (`0`), SDK release:u32 BE (nonzero), dependency count:u16 BE (0 through 32), then five u16 BE byte lengths for CPU baseline, runtime profile, compiler identity, descriptor symbol, and entry-point symbol. The body contains those five ASCII strings in that order, followed by dependency records of length:u16 BE and name bytes. The exact end of the last record must equal the manifest length.

The C SDK exposes `prdb_sdk_manifest_encode_v1` for client-side PMF1 production; it derives the required descriptor/entry symbol pair from the selected native ABI, accepts only bounded fields and sorted unique dependencies, and does not modify an undersized output buffer. Its inputs are borrowed and the caller owns the output buffer. Rust exposes `manifest_v1_from_elf` to inspect a compiled artifact's bounded ELF dynamic table and required ABI exports without loading it, derive and sort its dependency names, and combine them with caller-supplied compatibility profile strings. Dynamic symbol bounds are verified from either SysV `DT_HASH` chains or GNU `DT_GNU_HASH` buckets and terminated chains. `encode_manifest_v1` and `decode_manifest_v1` provide canonical PMF1 handling and validation.

The Rust packager publishes a complete private staging directory with Linux `renameat2(RENAME_NOREPLACE)` so an existing package is never replaced and partial output is not exposed. The destination filesystem must support this operation; filesystems such as the workspace's NFSv4.2 mount may return `EINVAL`, in which case packaging fails with `AtomicPublishUnsupported` and removes the staging directory. Packages link to the selected shared SDK and contain only the query DLL, manifest, scope, and query digest. The shared SDK is an administrator-managed repository release and is neither published in the package nor uploaded with a query.

CPU and runtime profiles are nonempty identifier strings of at most 64 bytes and must exactly match the trusted service's configured compatibility profile. The SDK release must match the service's configured repository entry and ABI contract; a client selection does not let it install a release or target. ABI v1 through v6 requires the corresponding `prdb_query_descriptor_vN` and `prdb_query_main_vN` symbol pair; SEAL checks that both names are defined, externally visible entries in ELF64 `DT_SYMTAB` with descriptor type OBJECT and entry-point type FUNC. ABI v4 adds the fixed-operation optimizer callback while retaining the v3 host table as its prefix. ABI v5 retains the complete v4 host table and adds a bounded optimizer callback with an operation argument; the executor still enforces the provisioned optimizer role allowlist. ABI v6 retains the v5 host table and adds an invocation-scoped opaque spill callback with bounded create, append, seal, read-at, and destroy operations. The callback carries no path or identity fields and fails the statement on broker or quota errors. Compiler identity is printable ASCII, bounded to 128 bytes, and diagnostic only. Dependencies are at most 128 bytes each, use an ASCII SONAME basename, and appear in strict bytewise order without duplicates. The validator checks query dependencies against the service's configured allowlist and parses ELF64 dynamic tables without loading or executing either file. Repository SDK releases carry the versioned SONAME, have no RPATH/RUNPATH, and depend only on configured runtime libraries. Digests protect repository integrity and package transfer consistency but do not authenticate or establish safety. The query's only permitted RUNPATH is exact `$ORIGIN` for the private staged directory; the loader may resolve only provisioned dependencies there or in the configured runtime profile. DT_RPATH, other DT_RUNPATH values, DT_AUDIT, DT_DEPAUDIT, DT_FILTER, and DT_AUXILIARY are rejected. Malformed ELF and non-Linux-x86_64 ET_DYN files fail closed.

Treat the manifest as untrusted. Pin immutable artifact bytes for admission/loading, bound size, and reject incompatible targets. Hashes identify artifacts; they do not establish trust or permission. Do not execute constructors or load the artifact in a trusted service to inspect it.

### Requested Capability Scope v1

`requested_scope` version 1 is canonical binary `PSC1`: four magic bytes, a big-endian u16 capability count from 1 through 200, then that many strictly increasing records. Each record starts with operation:u8 and target-kind:u8, followed by a 16-byte object ID for schema/table targets or two 16-byte IDs for a column target (`table_id`, then `column_id`). Operations are USAGE=1, SELECT=2, INSERT=3, UPDATE=4, DELETE=5; targets are schema=1, table=2, column=3. USAGE is valid only for schemas; data operations are valid only for tables and columns. IDs must be nonzero. Duplicate, unsorted, truncated, trailing, unknown, and empty records are invalid. The largest encoding is 6,806 bytes, within the 8 KiB transport bound.

The C SDK exposes `prdb_sdk_scope_encode_v1` to build PSC1 records. It validates target/operation combinations, nonzero identifiers, strict ordering and count bounds; it supports size queries and never writes a partial result when output capacity is short. Inputs are borrowed and output bytes are caller-owned.

The requested set is only a ceiling. At START storage intersects it with the current token-authenticated principal's catalog-derived grants in the pinned invocation context. It cannot create a grant, bypass a policy, or widen access after START. Every schema, relation, column, row, estimate, and mutation authorization path uses the narrowed scope. SEAL validates the encoding before making the upload immutable; START decodes it again before storage admission. Unsupported scope versions are rejected.

The Rust `RequestedScopeBuilder` consumes permission-filtered `VisibleSchema`, `VisibleRelation`, and `VisibleColumn` records from metadata discovery. Selecting a relation operation produces a table capability; selecting a column operation produces a column capability. Both automatically include that schema's USAGE capability. It emits canonical PSC1 ordering, collapses repeated identical selections, and enforces the 200-capability limit atomically. It cannot discover objects itself or establish authority: callers must obtain records through the authorized discovery APIs, and storage validates every submitted ID and grant independently.

## Administrative Identity Creation SQL

`AdminClient::execute_create_identity_sql` accepts one `CREATE USER name LOGIN|NOLOGIN` or `CREATE ROLE name` statement and dispatches the existing authenticated identity operation. `AdminClient::execute_create_identity_if_not_exists_sql` accepts the matching `CREATE USER|ROLE IF NOT EXISTS` forms and returns `None` for an existing identity only after confirming database-administrator authority; it leaves login state unchanged and commits no DDL outcome. An absent identity follows the ordinary typed create path. A created user has no credential until a separate token-issue operation succeeds. Rename, drop, and membership SQL remain outside this bounded SQL helper; their typed AdminClient operations remain available.

## Administrative CREATE INDEX SQL

`AdminClient::execute_create_index_sql` accepts one bounded `CREATE [UNIQUE] INDEX name ON schema.table [USING BTREE] (column, ...)` statement. It resolves schema, relation, and ordered column names through authenticated metadata, then calls the existing typed index-create operation on the same control connection. `execute_rename_index_sql` accepts `ALTER INDEX schema.name RENAME TO new_name`, resolves the existing index through authenticated metadata, and dispatches `indexes.rename` by stable ID. Rename preserves the physical definition and index ID; storage checks the new name for schema-level collisions and records the catalog change and DDL outcome atomically. Storage remains authoritative for DDL permission, uniqueness, and catalog validation. `execute_drop_index_sql` accepts `DROP INDEX schema.name RESTRICT`, enumerates visible relations and their name-bearing index metadata, and dispatches the existing typed index-drop operation by generated ID. Missing or ambiguous names reject before mutation.

## Buffer Lifetime and Workload

Borrow SDK result values from immutable authorized batches until explicit batch release; do not allocate/copy every cell by default. The C API must make ownership and invalidation visible, and copied input validation remains necessary at the trust boundary. Follow [memory storage](memory-storage.md); no API exposes disk-page pointers or ring buffers.

The first SDK value view is [`prdb_sdk_value_v1`](../engine/include/prdb_sdk_value_v1.h). It is a sized/versioned C record with a 32-bit state and type code, a borrowed byte pointer, and a 64-bit length. States are VALUE (0), NULL (1), and REDACTED (2); NULL and REDACTED have type code zero and no bytes. VALUE type codes 1 through 11 match the executor batch scalar codes, with fixed-width integers encoded big-endian, UUID as 16 bytes, Boolean as one byte containing zero or one, and text/varchar as UTF-8. Bytea is uninterpreted bytes. Empty text/bytea may use a null pointer with zero length. Values are capped at 1 MiB. DATE payloads must be signed days since 1970-01-01 in the range -719,162 through 2,932,896; TIMESTAMPTZ payloads must be signed UTC microseconds since the Unix epoch in the range -62,135,596,800,000,000 through 253,402,300,799,999,999. The view never owns or frees its byte pointer; it stays valid only while its source batch remains borrowed. The validator checks record size/version, state/type, lengths, fixed widths, Boolean encoding, UTF-8 validity, and temporal ranges. SQL parameter binding uses the same validator before accepting values. It cannot make an invalid native pointer safe to dereference. Use the owned-batch lifecycle above when the caller cannot retain the transport response buffer.

Typed accessors expose Boolean, SmallInt, Integer, BigInt, Date, and TimestampTz values in host C scalar types. Signed integers convert from canonical two's-complement big-endian bytes without relying on implementation-defined unsigned-to-signed casts. The byte accessor returns the original borrowed payload and its length for text, varchar, bytea, decimal, UUID, or any other VALUE type. Access on NULL or REDACTED returns `NO_VALUE`; requesting the wrong scalar type returns `TYPE_MISMATCH`. Callers inspect the state separately to distinguish NULL from REDACTED. These helpers validate the record before reading, but the source bytes must still remain valid and unchanged for the duration of the call and any borrowed view use.

[`prdb_sdk_batch_v1`](../engine/include/prdb_sdk_batch_v1.h) opens the version-1 executor `next_batch` payload in place. Opening validates the complete payload, including its 1 MiB bound, optional continuation cursor kind, at most 128 rows, row-handle kind, at most 4096 cells per row, each cell representation, and exact end-of-payload. Row and cell iterators yield borrowed handles/value bytes without copying. The application retains the response buffer unchanged until all views and iterators are discarded. A finished batch has no continuation cursor; otherwise it exposes the opaque 16-byte cursor for the next request. Row handles and cursors are opaque connection-scoped tokens, not row IDs or addresses.

The same header exposes `prdb_sdk_index_range_v1` for the bounded executor `scan_index_range` response. It validates the v1 status, at most 16,384 rows (the current implementation envelope; storage applies the lower invocation-pinned candidate allowance), each sanitized cell, and exact payload end before publishing a borrowed range view. An `unavailable` response returns `PRDB_SDK_BATCH_UNAVAILABLE` so callers can use the authorized reference scan. Range row/cell iterators expose no row handle; values borrow the unchanged response buffer just like ordinary batch values.

[`prdb_sdk_owned_batch_v1`](../engine/include/prdb_sdk_owned_batch_v1.h) provides an optional owned-result lifecycle when the caller cannot retain the transport response buffer. The caller zero-initializes the wrapper, then `prdb_sdk_owned_batch_copy_v1` copies and validates one complete payload snapshot of at most 1 MiB. It rejects an already active wrapper and leaves it empty on invalid or unsupported payloads. `prdb_sdk_owned_batch_open_v1` creates the same borrowed batch/row/cell views over that SDK-owned immutable copy. `prdb_sdk_owned_batch_release_v1` frees the copy and clears the wrapper; every pointer, iterator, and view opened from it becomes invalid at release. Releasing an empty wrapper is safe, and the wrapper may be reused after release. The payload bytes returned through the owned wrapper are read-only by contract and must not be changed by callers.

The executor SDK exposes `prdb_sdk_executor_stage_insert_v1`, `prdb_sdk_executor_stage_update_v1`, and `prdb_sdk_executor_stage_delete_v1`. INSERT takes the full schema-order cell shape, with VALUE/NULL/DEFAULT states, writes into a caller-owned bounded request buffer, and returns only a validated kind-8 row handle. UPDATE accepts unique in-range column ordinals with VALUE/NULL data; DELETE takes a kind-8 handle. Both mutation acknowledgements must match version 1 and status 0. Batched counterparts use IPC `0x1118`–`0x111a` for multiple rows per request and preserve row order for INSERT handles. Each batch is bounded by count and frame bytes and stages atomically; statement-level failure still aborts all earlier private chunks. `ScanIndexRanges` (`0x1117`) batches independent scalar or leading-prefix index keys and returns sanitized rows grouped by input ordinal. These functions serialize and validate IPC only; storage revalidates invocation, snapshot, grants, policies, constraints, and row authority.

The SDK serves operational invocations first and also supports bounded analytical work. SQL analytical operators follow the [workload roadmap](workload-profile.md), run over authorized batches, and must not treat redaction as SQL null or omit denied inputs silently.

The SQL DML AST API in [`prdb_sdk_sql_dml_v1.h`](../engine/include/prdb_sdk_sql_dml_v1.h) parses positional single- and multi-row INSERT values (`$n`, `NULL`, `DEFAULT`, up to 127 same-arity rows, capped at 4,096 cells, with optional column lists), bounded UPDATE assignments, and mandatory-WHERE DELETE statements using Boolean predicates. [`prdb_sdk_sql_execute_insert_v1`](../engine/include/prdb_sdk_sql_exec_v1.h) binds typed parameters against independently checked planner/executor shapes and submits one full-row storage mutation; `prdb_sdk_sql_execute_insert_batch_v1` stages every multi-row/column-listed INSERT row in the invocation overlay and latches statement failure if any row fails. [`prdb_sdk_sql_execute_update_v1`](../engine/include/prdb_sdk_sql_exec_v1.h) and [`prdb_sdk_sql_execute_delete_v1`](../engine/include/prdb_sdk_sql_exec_v1.h) scan authorized batches into bounded row-handle lists, close the scan, then stage patches or deletes. These APIs grant no authority: storage validates each mutation under the invocation's scope. SQL write execution has host callback fixture evidence; live multi-process SQL write evidence remains future work.

## Administrative SDK

The bounded SQL expression binder supports `IS [NOT] TRUE`, `FALSE`, and `UNKNOWN` on BOOLEAN-valued expressions in CHECK and policy expressions, including parenthesized expressions. It lowers the tests to existing EIR1 null, equality, AND, and NOT nodes, preserving the two-valued SQL boolean-test result without a protocol or stored-expression version change.

Expose typed definitions/builders and text submission for [schema DDL](ddl-schema.md), [users/roles](ddl-identity.md), and [permission DDL](ddl-permissions.md). Administration occurs in the client over a separate authenticated control-mode gateway connection; user query libraries cannot inherit that connection or its tokens. Storage validates every definition and privilege independently. Do not embed credentials in compiled artifacts or logged SQL. Data SQL functions reject DDL in an invocation, even when its principal also has administrative privileges.

`AdminClient::execute_create_table_sql` accepts table-level `FOREIGN KEY (...) REFERENCES schema.table (...)` clauses and column-level `REFERENCES schema.table (column)` clauses, resolving existing target columns through authenticated metadata. It binds each FK to an ordered visible PRIMARY KEY or UNIQUE constraint and submits all table and FK definitions through one typed `tables.create` operation; storage atomically checks REFERENCES authority and publishes the referenced-table epoch change. `AdminClient::execute_add_foreign_key_sql` resolves source and target columns through authenticated metadata and binds the target to an ordered visible PRIMARY KEY or UNIQUE constraint before calling the typed foreign-key operation. `execute_drop_constraint_sql` accepts a generated PRIMARY KEY, UNIQUE, CHECK, or FOREIGN KEY ID, confirms that the constraint belongs to the selected source table, and invokes the matching typed drop operation. Constraint names are not available in the current catalog.

## Metadata SDK Surfaces

Provide typed discovery records and bounded paging for [metadata discovery](metadata-discovery.md), including SQL access to its built-in metadata relations. Keep administrative definition inspection and [live monitoring](operational-metadata.md) in the client control API, not executor host callbacks. Expose neither raw dictionary records nor physical roots/paths. Durable status has an explicit unknown/expired outcome so clients cannot mistake missing retained history for safe retry.

## Contract Versions

Negotiate the client TCP protocol and gateway-service protocol independently from the native entry-point/host ABI, internal IPC, and structured-request/physical-plan formats. The SQL SDK API and SDK release version also have explicit compatibility rules. A matching SDK version alone is not sufficient. Reject unsupported versions at their boundary; do not infer compatibility from language or compiler provenance. The manifest advertises compatibility, while runtime endpoints validate it independently.

## Entry-Point Contract

The Linux x86_64 entry-point ABI v1 is defined by [`prdb_query_abi_v1.h`](../engine/include/prdb_query_abi_v1.h), v2 by [`prdb_query_abi_v2.h`](../engine/include/prdb_query_abi_v2.h), v3 by [`prdb_query_abi_v3.h`](../engine/include/prdb_query_abi_v3.h), v4 by [`prdb_query_abi_v4.h`](../engine/include/prdb_query_abi_v4.h), v5 by [`prdb_query_abi_v5.h`](../engine/include/prdb_query_abi_v5.h), and v6 by [`prdb_query_abi_v6.h`](../engine/include/prdb_query_abi_v6.h); Rust mirrors these contracts in `query_abi`. The executor prefers a v6 descriptor, then v5, v4, v3, v2, and v1, and rejects an invalid preferred descriptor rather than falling back. V3 adds a callback that latches SQL statement failure in trusted executor memory. V4 embeds a v3 host record and adds a dedicated bounded optimizer request callback fixed to SELECT. V5 embeds the complete v4 host record and adds an operation-selected optimizer callback; the trusted host authorizes each operation on the optimizer channel, which allows the SDK to submit DELETE without changing v4 behavior. After the entry point returns, any latched statement failure forces a nonzero worker exit even when C code caught the SQL status. The supervisor observes that exit and aborts the invocation. V2 and v3 remain available for earlier query libraries; v1 carries only parameters. PMF1 packaging, encoding, ELF export inspection, and decoding support ABI v1 through v6 and require the exact descriptor and entry symbols for the declared version. The SQL SDK submits supported explicit-projection SELECTs through ABI v4, validates Scan/Filter/Project/Limit plans and executor-resolved relation identity, and runs bounded filtered scans. ABI v5 provides the operation-aware callback required by the DELETE SDK path. The maintained combined SQL fixture exercises a parameterized filtered SELECT through ABI v4; live confined acceptance still depends on the configured delegated-cgroup host.

`prdb_invocation_v1` carries borrowed parameter and SQL data pointers with `uint64_t` byte lengths, each capped at 1 MiB by admission. Each pointer may be NULL exactly when its length is zero; otherwise it points to the complete immutable bytes and remains valid only for the entry-point call. The entry point returns zero for success and nonzero for failure. The host and library records use fixed-width fields and natural C alignment; on the supported x86_64 target, host table size/alignment are 64/8, invocation size/alignment are 40/8 with parameter pointer/length at offsets 8/16 and SQL data pointer/length at offsets 24/32, and descriptor size/alignment are 16/4. A query return code is not itself a transaction commit decision.

Use C-compatible fixed-layout structures, explicit sizes/versions, opaque handles, and explicit buffer ownership. No Rust containers, Go-managed objects, language exceptions, or panics may cross the ABI. Native pointers refer only to executor memory. Calls to other processes use validated serialization.

The executor SDK exposes `prdb_sdk_executor_check_cancelled_v1` as a cooperative checkpoint for SQL and other bounded query loops. It returns success with `cancelled_out` set to 0 while the invocation remains active, or 1 after storage detects cancellation or deadline expiry and aborts the transaction. Callers should poll between bounded work batches and stop promptly on 1. The worker host and supervisor retain process-level cancellation handling for code that does not poll.

`prdb_sdk_executor_scan_index_range_v1` submits executor operation `0x1115` with a checked relation handle, logical index ID, optional non-NULL typed bounds, and packed selected-column IDs. The request buffer is caller-owned and bounded by the IPC payload limit. A successful response is validated with `prdb_sdk_index_range_open_v1`; its row/cell views borrow the response and carry no row handles. `PRDB_SDK_EXECUTOR_UNAVAILABLE` means the caller must fall back to the authorized reference scan. This low-level SDK operation grants no additional read or mutation authority.

Constructors execute under confinement before entry-point checks can finish. The entire artifact, bundled SDK, and dependency code are untrusted. Host callbacks cannot constrain arbitrary machine code within the process; server-side roles and the OS sandbox enforce authority.

Allow sequential SQL/storage operations under one MVCC snapshot plus private writes and cumulative budgets. Initially permit one active statement/request stream and single-threaded SDK calls. All statement errors abort the entire transaction; no savepoints or per-statement commits exist. Successful library return requests finalization, but success requires storage-confirmed durable commit. Cancellation/failure accepted before redb commit begins aborts staged writes; after commit begins the outcome may be pending/uncertain and must be reconciled. After commit it cannot undo data. Results remain provisional until commit confirmation, which is not a correctness attestation. Use authenticated invocation-status lookup after lost replies; never automatically rerun a library with an unknown outcome. Exit the process rather than relying on safe unloading of arbitrary code.

## Concurrent Invocation Contract

Multiple clients and executors may run concurrently. Each invocation is one snapshot-isolated transaction; it sees its own staged writes but not others' uncommitted changes. Optimistic row conflicts abort the entire invocation. Snapshot isolation is not serializable. Status lookup, known-abort retries, cancellation, and version retention follow [concurrency and MVCC](concurrency-mvcc.md).

Read-only grants reject mutation calls. Public protocol definitions for commit do not grant the executor the supervisor's finalization role. No arbitrary timestamp selection or hidden historical reads are exposed.

## Language and Compilation Decision

Use C for user queries and SDK SQL/runtime code. TinyCC compiles user queries; the prebuilt SQL SDK shared library is built once per release with the pinned Clang/LLVM toolchain, since that build is not on the per-query latency path. Rust implements the database engine, including the executor host, supervisor, optimizer, storage, transactions, and authorization. This is an established choice, not an experiment among language candidates. See [toolchain implications](toolchain.md) for the component split and release gates.

Distribute a pinned TinyCC toolchain and prebuilt C SDK shared libraries; compile only user source per edit. Keep administrative helpers separate from executor runtime code. TinyCC runs in a bounded client subprocess and emits query.so without executing it. Engine Rust compilation is never part of the per-query path.

The `prdb-packager` Rust client helper implements this compile-and-package step on Linux x86_64. It accepts one source file (at most 1 MiB), the local shared SQL SDK library selected by the client's persistent per-instance setting, an include directory, a canonical PSC1 requested-scope file (at most 8 KiB), and diagnostic compiler identity. Release, target, ABI, CPU baseline, and runtime profile are derived from and checked against that setting. TinyCC compiles user code with a cleared environment and bounded resources; a fixed shared-link step links it to the selected SONAME, strips non-dynamic symbols, and emits query.so with exact `$ORIGIN` RUNPATH and a non-executable stack. Required dynamic ABI exports remain available. The helper bounds diagnostics, validates the output ELF and required query ABI exports without loading it, and rejects artifacts above 64 MiB. Its stdout and stderr are drained so output cannot fill a pipe. The package contains `query.so`, its digest sidecar, manifest, and scope; the SDK library is not packaged or uploaded. Library digests are integrity checks rather than proof of publisher identity or code safety.

On success, the helper creates a new package directory containing `query.so`, canonical `manifest.pmf1`, validated `requested_scope.psc1`, and a lowercase-hex SHA-256 sidecar for query.so. Files are mode 0600 and the directory is mode 0700. The directory is published by an atomic no-replace rename, so an existing package is never overwritten and incomplete staging data is removed on ordinary errors. The helper does not execute the query or SDK library, grant the requested scope, or provide authorization credentials to TinyCC.

The Rust `SubmissionClient` implements the query-mode TCP path. It verifies package file permissions, PMF1/PSC1 encodings, and the artifact digest before sending PREPARE. It uploads artifact and parameter bytes in bounded contiguous chunks, checks each acknowledged offset, then SEALs and returns the reserved invocation ID. The connection remains available for START and status calls. `start` first writes a caller-selected `PDBR1 <invocation-id>` receipt with mode 0600, synchronizes it and its parent directory, and refuses to overwrite an existing receipt; only then does it send START. START is never retried automatically. A lost or malformed START reply returns an uncertain-outcome error carrying the invocation ID; the caller reconnects and uses authenticated STATUS. Result bytes remain provisional until the supervisor's terminal event reports `committed`. The bearer secret input buffer is zeroized, as are its encoded AUTH payload copies. This client uses the specified plaintext TCP transport and does not add TLS.

The `prdb-client` command exposes `scope`, `submit`, the authenticated control-mode `admin-sql` command for bounded DDL (including administrator-only `IF NOT EXISTS` no-ops for schemas, tables, indexes, and added columns), `status`, owner-scoped `cancel`, and administrator-authorized `admin-cancel`. The `admin-sql` command reads a bounded SQL file or stdin, validates the supported DDL locally before credential access, and submits only typed operations over the authenticated control channel; it supports `CREATE SCHEMA [IF NOT EXISTS] name AUTHORIZATION 'uuid'` using an explicit hexadecimal UUID owner, `ALTER SCHEMA name RENAME TO new_name`, `DROP SCHEMA name RESTRICT`, `ALTER TABLE schema.table RENAME TO name`, `DROP TABLE schema.table RESTRICT`, and bounded `CREATE TABLE` syntax. `ALTER SCHEMA ... OWNER TO` and `ALTER TABLE ... OWNER TO` resolve named destinations within the target schema/table owner or effective ALTER authority before using typed owner-transfer operations; their contract is in [administrative SQL input](admin-sql.md). `scope` discovers schemas, relations, and columns through the authenticated metadata API, resolves the supplied exact names only within that principal's visible set, and writes canonical PSC1 to a mode-0600 no-overwrite file. It can request schema USAGE, relation-level operations, or selected column operations; all data selections automatically include schema USAGE. The resulting scope is only a request ceiling and START still authorizes each capability. Submission takes a numeric IP socket address, a private credential file, a prepared package directory, a no-overwrite START receipt path, and optional bounded parameter file, deadline, and workload class. It writes provisional data bytes to stdout and reports the terminal outcome on stderr; success exit status requires a committed terminal event. Status and cancellation authenticate on new connections; owner-scoped cancellation uses query mode, while `admin-cancel` uses control mode and requires current database-administrator authority. Cancellation reports `accepted`, `too_late`, a terminal outcome, or `unknown`, and the acknowledgement is not itself a transaction terminal event. START is issued once only, and uncertain results include the invocation ID for later status reconciliation.

`client_credentials` reads and writes a canonical `PDB-CREDENTIALS-1` file containing a lowercase token ID and lowercase hex token secret on separate lines. Files must be regular, owned by the effective user, and mode 0600; reads reject symbolic links and noncanonical contents. Creation writes a private same-directory temporary file, synchronizes it, then publishes it with a no-overwrite hard link and synchronizes the parent directory. Removal applies the same ownership and mode checks and synchronizes the parent. The secret is zeroized in temporary buffers; the file is plaintext bearer material protected by its owner-only mode.

`MetadataClient` implements authenticated control-mode reads for grant-visible schemas, relations, and declared columns. `AdminClient` exposes the same bounded page methods for principals that need schema-owner or database-administrator visibility, plus `list_indexes_page` for logical index IDs, ordered column IDs, and uniqueness, `list_constraints_page` for constraint IDs, kinds, source columns, and visible foreign-key targets (available to schema/table owners, database administrators, and effective table-scoped ALTER grantees), `list_grants_page` for direct table/column grants with grantor IDs, `list_policies_page` for secret-free policy summaries with recipient redaction, and `list_dependencies_page` for direct dependency edges whose two endpoints are visible. Dependency reads omit hidden-endpoint edges before encoding and do not expose hidden counts or names. Page methods accept a limit from 1 through 128 and an optional opaque connection-local cursor. MetadataClient complete-list methods follow pages automatically using a default page size of 64. Both clients validate IDs, ordering, ordinals, type spellings, continuation syntax, and response shape before constructing typed discovery records. Administrative visibility applies only to these control reads and does not grant query capabilities; START still rechecks every requested capability against current catalog grants. The control clients zeroize bearer-secret input and AUTH payload copies and share the plaintext TCP profile with `SubmissionClient`.

`prdb-client discover` prints only records returned by the authenticated metadata API. Without filters it lists visible schemas; `--schema NAME` also lists visible relations in that schema; `--relation NAME` requires `--schema` and adds that relation's visible columns. Output is tab-separated and starts each record with `schema`, `relation`, or `column`; IDs are lowercase hex, columns are in declared ordinal order, and their type/nullability fields preserve the discovered schema. An invisible schema or relation is reported as unavailable by name without falling back to administrative catalog access.

`AdminClient` is a separate authenticated control-mode API for typed administrative operations. It exposes user and role creation, rename, drop, login enable/disable, role membership grant/revoke, database-scoped system privilege grant/revoke, schema create/rename/drop/owner transfer, table create/rename/drop/owner transfer, invocation cancellation, column add/rename/drop, nullability changes, column-default set/drop, unique and primary-key create/drop, CHECK create/drop, foreign-key create/drop, token issue/revoke/inventory, and ordinary-index create/rebuild/rename/drop. `execute_add_key_constraint_sql` accepts qualified `ALTER TABLE schema.table ADD [CONSTRAINT name] PRIMARY KEY (columns...)` and `ADD [CONSTRAINT name] UNIQUE (columns...)` forms. `execute_add_foreign_key_sql` accepts a qualified `ADD [CONSTRAINT name] FOREIGN KEY (...) REFERENCES ...` form; all names are retained on the resulting catalog objects and can be used by DROP CONSTRAINT. `execute_drop_column_sql` accepts qualified `ALTER TABLE schema.table DROP COLUMN column RESTRICT`, resolves the column through authenticated metadata, and submits `tables.drop_column`. `execute_rename_column_sql` accepts qualified `ALTER TABLE schema.table RENAME COLUMN old_name TO new_name`, resolves the column through authenticated metadata, and submits `tables.rename_column`. `execute_add_column_sql` accepts one qualified `ALTER TABLE schema.table ADD COLUMN name type [NOT NULL] [DEFAULT literal]` definition, resolves the table through authenticated metadata, and uses `tables.add_column`; a non-null column requires a non-null typed literal default. `execute_alter_column_nullability_sql` accepts qualified `ALTER TABLE schema.table ALTER COLUMN column SET NOT NULL` and `DROP NOT NULL` forms, resolves the column through authenticated metadata, and submits `tables.alter_column_nullability`. `execute_alter_column_default_sql` accepts `SET DEFAULT` with a typed scalar literal or `DROP DEFAULT`, resolves the declared column type/nullability through authenticated metadata, and submits `tables.set_column_default` or `tables.drop_column_default`; current rows remain unchanged. `execute_add_check_constraint_sql` accepts qualified `ALTER TABLE schema.table ADD [CONSTRAINT name] CHECK (expression)` with Boolean column references, `IS [NOT] NULL` on supported scalar expressions, `NOT`, `AND`, `OR`, parentheses, and `=`, `!=`, `<>`, `<`, `<=`, `>`, and `>=` comparisons. `IS [NOT] DISTINCT FROM` accepts a supported scalar expression on each side, including expressions that evaluate to NULL. `IN`/`NOT IN` accepts one to 64 supported scalar expressions, and `BETWEEN`/`NOT BETWEEN` accepts two supported scalar expressions as bounds; both predicates apply to any supported scalar expression. It resolves identifiers and scalar types through authenticated metadata, contextually types literals, and submits the typed EIR1 CHECK operation. Type mismatches and lossy DECIMAL rescaling reject. It resolves relation and column names through authenticated metadata reads on the same control connection, then uses the existing typed constraint PREPARE/START operation; storage independently enforces table authority, nullability, uniqueness, and catalog invariants. A supplied ALTER CHECK name is normalized and persisted; `execute_create_table_sql` accepts the bounded SQL subset `CREATE TABLE schema.table (column type [GENERATED ALWAYS AS IDENTITY] [NOT NULL] [DEFAULT literal] [CONSTRAINT name CHECK (expression)], ..., [PRIMARY KEY (column, ...),] [UNIQUE (column, ...),] [CONSTRAINT name CHECK (expression),] ...)` with an optional final semicolon. `NOT NULL` and `DEFAULT` may appear in either order. The optional table-level primary key may appear once, makes its columns NOT NULL, and atomically creates its constraint and owned unique index with the table. Any number of distinct table-level UNIQUE and CHECK constraints may follow; a CHECK clause may begin with `CONSTRAINT name`, and names must be unique within the statement; each UNIQUE creates an owned unique index atomically, allows nullable columns, and treats NULL tuples as distinct. CHECK accepts Boolean column references, `IS [NOT] NULL` on supported scalar expressions, `NOT`, `AND`, `OR`, parentheses, and the bounded typed comparisons supported by ALTER CHECK. `IS [NOT] DISTINCT FROM` accepts a supported scalar expression on each side, including expressions that evaluate to NULL. `IN`/`NOT IN` accepts one to 64 supported scalar expressions, and `BETWEEN`/`NOT BETWEEN` accepts two supported scalar expressions as bounds; both predicates apply to any supported scalar expression. Comparison literals use the opposite operand type, including exact DECIMAL scaling. CHECK expressions bind to column IDs and publish atomically with the table. The identity clause is valid only for UUID, implies NOT NULL, and cannot be combined with a default; storage still generates values only for DEFAULT inserts and rejects explicit identity overrides. It requires schema-qualified unquoted normalized identifiers of at most 128 bytes, at least one column, and supported scalar type names with bounded DECIMAL/VARCHAR parameters. Omitted nullability means nullable. Column modifiers may include `DEFAULT` with a type-compatible boolean, signed integer, exact DECIMAL, quoted text/VARCHAR, `X'hex'` BYTEA, quoted UUID, engine-epoch DATE/TIMESTAMPTZ integer, SQL NULL, or UUID `CURRENT_PRINCIPAL_ID()` literal. DECIMAL scale reduction and precision overflow are rejected. It resolves the schema and referenced relations through the same authenticated control connection and submits the existing typed `tables.create` operation, so storage independently enforces authority and catalog invariants. Final table-level FOREIGN KEY clauses may reference an existing schema-qualified table’s ordered PRIMARY KEY or UNIQUE columns; the client binds the target constraint ID and storage atomically validates REFERENCES authority, types, and cross-table catalog updates. This SQL entry point accepts column-level PRIMARY KEY and UNIQUE as one-column table constraints and column-level CHECK expressions over that column; a column-level primary key implies NOT NULL. CREATE TABLE self-references, quoted identifiers, multiple statements, or other DDL; use typed AdminClient methods where available. Named PRIMARY KEY, UNIQUE, CHECK, and FOREIGN KEY constraints are supported in CREATE TABLE and retained in metadata; SQL DROP CONSTRAINT resolves any explicitly named constraint. Table creation accepts typed column definitions, scalar values for literal defaults, SQL NULL defaults, and the UUID current-principal default; it returns ordered generated column IDs. Column addition enforces the protocol's backfill rules for NULL and non-null defaults. CHECK creation encodes a row-local expression as canonical EIR1 hex and accepts an empty dependency list for expressions with no column references. Constraint and foreign-key creation return their generated catalog IDs; key creation also returns its backing index ID. System privilege values are a closed enum for `manage_users`, `manage_roles`, and `create_schema`. User creation creates an identity without a credential; issue a token separately. Token issuance returns its bearer secret once in `AdminTokenResult`, which does not print the secret and zeroizes it when dropped. A lost or malformed issue response is uncertain and the plaintext cannot be recovered; explicitly revoke/reissue after reconciling. The client validates nonzero IDs, canonical lowercase names, column/default type compatibility, and ordered distinct index and constraint columns before sending requests, and follows the server's connection-owned PREPARE/START flow. It sends no administrative credentials to query artifacts. If START loses its reply or returns an invalid response, the client returns `AdministrativeOutcomeUncertain` with the operation ID and never retries; callers reconnect and use `AdminClient::status` to reconcile the operation.

`prdb-client token-issue` issues a credential through the authenticated `AdminClient` control channel and saves the returned secret to a new private credential file; it never prints the secret. The command requires a positive TTL in seconds and computes the absolute expiration timestamp locally. If issuance commits but file publication fails, the CLI reports the operation and token IDs and instructs the caller to revoke the unrecoverable token before retrying. Rotation is explicit: save a replacement file, verify it with a fresh authenticated request, then revoke the old token with `token-revoke`. The CLI never revokes the previous token automatically.

`prdb-client credential-remove --credentials FILE` removes an owned mode-0600 credential file and synchronizes its parent directory. This deletes only the local file; it does not revoke the server-side token. Use `token-revoke` when server-side invalidation is required.

`AdminClient::list_tokens_page` and `prdb-client token-list` return up to 64 token metadata records for a selected user, ordered by token ID. `--after-token-id` resumes after an ID returned by `next_after_token_id`. Storage allows users to inspect their own tokens and requires current `MANAGE_USERS` or database-administrator authority for another user’s inventory. The response includes labels, issue/expiry times, and revocation state; verifier and bearer-secret bytes are never returned.

`prdb-client dependency-list` reads one bounded page from `AdminClient::list_dependencies_page` for `--object-id`, with optional `--limit` (default 64, range 1–128) and `--cursor`. It prints JSON containing direct dependency edge IDs/kinds and `next_cursor`; pass that cursor back unchanged for the next page. The command uses a private credential file and emits only the endpoint-filtered records returned by storage.

`AdminClient::list_runtime_invocations_page` and `prdb-client runtime-list` read administrator invocation registry pages of up to 128 records. The CLI defaults to 64 and accepts optional `--limit` (1–128) and `--cursor`; it prints one JSON page. Pages include `observed_at_us`, `consistency: "best_effort"`, invocation/principal IDs, an opaque `transaction_id` unique among live transactions, workload class (`operational` or `analytical`), state, optional start/deadline timestamps, `age_us` as elapsed time at that page's observation, current `staged_rows` and `staged_value_bytes` (row payload bytes, excluding row IDs and index metadata), `snapshot_pin_count` (0 or 1, the number of invocation-owned redb read snapshots retained), `pinned_snapshot_count` and `oldest_snapshot_pin_age_us` (a best-effort aggregate of active invocation-owned redb read snapshots, not a retained-page or memory estimate), `invocations_admitted_total` (successful admission count), `invocation_conflicts_total` (invocation commits rejected with a conflict), `admin_cancellations_accepted_total` (first transition after an accepted audit), `admin_cancellations_denied_total` (requests with a durably committed denied AUD1 audit), `invocation_policy_denials_total` (managed invocation executor requests rejected with explicit `AuthorizationError::Denied`), and `invocation_staged_value_bytes_total` (cumulative encoded payload bytes accepted by successful managed overlay puts, including replacements; deletes and failed writes add nothing). `invocation_commit_latency_buckets` is a six-count array in fixed ranges `<=1,000us`, `(1,000us,5,000us]`, `(5,000us,10,000us]`, `(10,000us,50,000us]`, `(50,000us,100,000us]`, and `>100,000us`, counting managed commit calls through either success or error return. `invocation_redb_write_acquisition_buckets` uses the same ranges for managed commits reaching `Database::begin_write()`; it measures acquisition-call latency including API setup, not pure lock wait, and excludes earlier validation failures. Unauthorized, rate-limited, and unaudited late cancellation requests do not increment the denied counter; failed audits increment neither cancellation counter. Hidden rows/cells, unavailable relations, malformed requests, and policy evaluation failures do not increment policy denials. These counters are process-local, saturate, and reset when the registry is recreated. The page also contains cancellation state/reason, an opaque process-local `next_cursor`, and a per-page best-effort `fence_waits` snapshot. Fence wait entries identify writer or DDL waits, elapsed duration, opaque wait/blocker IDs, and up to eight table resource IDs with explicit truncation flags; at most 16 waits are returned. Every page rechecks administrator authority; registry changes or restart may invalidate the invocation cursor. History, counter, and wait summaries are independently sampled on each page.

Runtime-list protocol version 5 reports `gateway_result_bytes_relayed_total`, the supervisor-process total of result payload bytes completely written to gateway channels. Version 6 adds `gateway_result_bytes_sent_to_clients_total`, the gateway-process total of result payload bytes completely written to client streams. Both saturate and reset with their process, exclude frame headers, and do not prove that a remote client application read or persisted the payload.

`AdminClient::list_runtime_invocations_page` requests runtime-list version 7. Earlier versions remain available to compatible clients: version 2 adds durable-outcome maintenance counters, version 3 adds identifier-free supervisor staging/START usage, version 4 adds oldest queued START age, and version 5 adds the supervisor result-relay byte total. Version 6 also reports the gateway result bytes written to external client streams; version 7 reports storage write-transaction acquisition latency buckets. Storage, supervisor, and gateway snapshots are best effort and independently sampled.

`AdminClient::list_own_invocations_page` requests owner-list operation version 2 and returns only the authenticated principal's live invocations, including each invocation's current staged row count and row-payload bytes. The server retains version 1's prior response shape for older clients. The decoder accepts older rows that omit both gauges; a response containing only one gauge is invalid.

The admin CLI also exposes user and role create/rename/drop, user login enable/disable, and role membership grant/revoke through typed `AdminClient` operations. User creation returns an identity only; use `token-issue` separately to create a credential. These commands require the corresponding storage authority and print generated identity IDs and operation/commit metadata, never bearer secrets. Schema create/rename/drop and table create/rename/drop use the same authenticated control channel. Schema creation requires an explicit nonzero `--owner-id`; the caller must have schema-management authority. Table creation requires `--schema-id`, `--name`, and at least one column in the form `name:type:nullability[:identity]`, with columns separated by semicolons. Supported types are `boolean`, `smallint`, `integer`, `bigint`, `decimal(P,S)`, `text`, `varchar(N)`, `bytea`, `uuid`, `date`, and `timestamptz`; `P` is 1 through 38, `S` is no greater than `P`, and `N` is positive. Nullability is `nullable` or `not-null`. In this CLI version, a non-null column must use the `identity` modifier, which is valid only for a non-null UUID column; literal/default expressions are not accepted by table-create. `column-add` accepts one nullable column with the same type names, while `column-rename` and `column-drop` require both table and column IDs. `column-nullability` sets the nullable flag. `column-default-set` takes an explicit type and value: `null` encodes SQL NULL; `current-principal-id` is valid for UUID; booleans use `true` or `false`; integer types use decimal integer text; DECIMAL uses a base-ten value with no more fractional digits than its declared scale; TEXT/VARCHAR use the supplied text; BYTEA uses even-length lowercase `hex:` bytes; UUID uses 32 lowercase hex digits; DATE uses days since 1970-01-01; and TIMESTAMPTZ uses microseconds since the Unix epoch. `column-default-drop` removes the default. `index-create` takes a table ID, normalized name, ordered comma-separated column IDs, and an optional uniqueness flag defaulting to false. `index-rebuild` takes an index ID and the replacement ordered column IDs/profile; `index-drop` takes an index ID. Storage remains responsible for current authority, dependency, backfill, and uniqueness validation. Typed AdminClient and storage requests remain authoritative for range, schema, and permission checks. The CLI validates the syntax before sending typed requests and prints generated IDs and operation/commit metadata.

`table-owner-set` accepts nonzero `--table-id` and `--owner-id` values and submits `tables.set_owner` through the authenticated ADMIN channel. The current table owner or a database administrator may transfer a non-system table to a live user or role. The client prints the operation ID and committed sequence; storage remains authoritative for the transfer and does not grant data privileges to the new owner. `schema-owner-set` accepts nonzero `--schema-id` and `--owner-id` values and submits `schemas.set_owner`; the current schema owner or a database administrator may transfer a non-system schema to a live user or role. Both commands print the operation ID and committed sequence, and storage remains authoritative for ownership changes and does not grant data privileges to the new owner.

The CLI also exposes `unique-create` and `primary-key-create` with a table ID and ordered, distinct comma-separated column IDs, plus `unique-drop` and `primary-key-drop` with the generated constraint ID. Storage checks primary-key nullability and all catalog, authority, dependency, and backfill rules.

The system-privilege-grant and system-privilege-revoke commands take a nonzero --grantee-id and one closed --privilege value: manage_users, manage_roles, or create_schema. These commands use the authenticated ADMIN channel; only a current database administrator can change these grants.

The AdminClient object grant/revoke methods and object-grant/object-revoke CLI commands accept a grantee, schema/table object, one closed object privilege, and either object or column target scope. They use the authenticated ADMIN channel; storage checks current ownership, inherited MANAGE_GRANTS, or database-administrator authority. REFERENCES grants may target a whole table or individual columns and are required before foreign-key creation.

AdminClient policy create/drop methods and policy-create/policy-drop CLI commands use the authenticated ADMIN channel. Policy creation supplies a row/cell kind, operation, ALLOW/RESTRICT effect, nonempty user/role recipient set, optional cell target columns, and the EIR1 USING/WITH CHECK expressions required by that operation. Storage binds expressions to the current table schema and enforces owner or MANAGE_POLICIES authority; the CLI never exposes policy bodies through metadata reads. `execute_drop_policy_sql` accepts `DROP ROW|CELL POLICY name ON schema.table RESTRICT`, resolves the name only inside the selected table for a caller with policy DDL authority, and submits the existing typed `policies.drop` operation.

The foreign-key-create CLI command takes a source table ID, ordered and distinct source column IDs, and a target unique or primary-key constraint ID; foreign-key-drop takes the generated foreign-key ID. The authenticated storage path checks column correspondence, types, both tables' authority, existing rows, and dependency rules. Creation also requires a pre-existing REFERENCES grant on the target table or columns; `object-grant` and `object-revoke` provide that grant lifecycle.

The check-create CLI command accepts canonical lowercase hex containing one EIR1 row-local expression, plus an explicit dependency-column list; the list may be empty for a constant expression. check-drop takes the generated constraint ID. The client decodes EIR1 before sending it, and storage validates field bindings, Boolean result type, current rows, and authority.

The versioned C ABI is the interoperability boundary, not permission to use unspecified Rust layouts. C can corrupt the Rust executor host, so all trusted services remain outside that process. Other query languages/compilers are outside the initial supported SDK; artifact provenance never bypasses validation.

## Benchmark and Acceptance Plan

Measure cold and warm compile-plus-link time, one-line-edit turnaround, artifact size, load/startup time, and compile-to-first-result latency. Include SQL wrapper queries, small native loops, and mixed SQL/native work. Measure execution throughput too; reduced compile time may trade off generated-code quality.

Measure the selected TinyCC build and separate SDK release-build time from per-query compilation. Do not assume GCC-style optimization options produce equivalent results with TinyCC. The package helper is implemented, but exact TinyCC build distribution, dependency packaging, and the deployed runtime profile still need to be pinned; the local process resource limits do not replace a compiler sandbox.

Validate cross-version rejection, malformed manifests, missing symbols, hostile constructors, dependency lookup restrictions, library crashes, protocol forgery, sequential-call budgets, and preservation of redaction states. Confirm SDK provenance never bypasses authorization.

Select exact TinyCC/Rust versions, the deployed CPU/runtime compatibility profile and dependency allowlist, plus remaining administrative operation schemas.
