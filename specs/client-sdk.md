# Client SDK and Query Library Contract

## Required Model

The user writes a native query program in their client and compiles it into a loadable shared library using the SDK. The client submits that artifact and parameters. A disposable confined executor loads it and invokes its entry point. The SDK includes basic SQL support and public definitions for interacting with database components.

The user program may call SQL, process authorized results, or use lower-level scoped storage APIs. SQL is a convenience layer, not an authorization boundary. Compilation does not require database access or live statistics; optimization happens when SDK SQL calls run against an admitted execution context.

## SDK Contents

| Surface | SDK contents | Runtime authority |
| --- | --- | --- |
| Query entry point / executor | Versioned C ABI, host function table, parameters, result emission, errors, cancellation | Current invocation only |
| Storage manager | Schema/value types, redaction states, opaque handles, scan/cursor/mutation request definitions and stubs | Scoped reads and staged writes validated by storage |
| Optimizer | Structured request encoding, physical-plan definitions and initial decoder, bounded planning submission | Plans for the current context |
| SQL | Parser, expression semantics, physical-plan interpreter, result API | Same storage authority as user code |
| Client submission/network | TCP framing, authentication, artifact upload, compatibility manifest, START, provisional results, outcome/status/cancellation | Client-only gateway connection; caller-authenticated admission |
| Administration | Schema/user/role/policy DDL builders and token lifecycle calls | Separate authenticated control channel; never an executor capability |
| Statistics and other services | Versioned public protocol definitions and role annotations | Definitions confer no access; scoped estimation remains optimizer-only; global catalogs are private |

Generate language bindings from one protocol/schema source when selected. Do not expose process-local storage structures, raw page layouts, private catalogs, or server object pointers. Public definitions are contracts, not copies of server implementations. Services still validate messages from clients that ignore or modify the SDK.

## Client Network Boundary

Use the [network protocol](client-protocol.md) through the dedicated [gateway](client-gateway.md) for external submission and result delivery. Ship the transport/authentication client separately from the C SQL/runtime archive linked into query.so. It may be implemented as a Rust client library/helper with bindings; that choice does not change TinyCC query compilation. The query runtime receives no network sockets or admission credentials.

The client uploads/seals bytes before START, records the reserved invocation ID, and treats result frames as provisional until a supervisor-originated storage-confirmed terminal outcome. Network errors require authenticated status lookup, not automatic invocation replay. Multiple connections can run concurrent invocations; the initial TCP connection carries one operation/result stream at a time. Cancellation/status during streaming uses another authenticated connection.

## Packaging Baseline

Ship headers/bindings and prebuilt position-independent SQL/runtime libraries for supported Linux targets. Compile only user code and link the prebuilt SDK into query.so. Do not rebuild the SQL parser, interpreter, or database services on each query edit. Initially avoid whole-program optimization across the SDK boundary.

A separate SQL shared dependency is an optional packaging alternative, with explicit ABI/dependency matching. The baseline favors a statically linked SDK archive inside the dynamically loaded user artifact. Standard runtime dependencies must still be declared and supported; this is not a promise of a completely self-contained binary.

### Artifact Manifest v1

Manifest version 1 is canonical binary `PMF1`. Its 28-byte header is: magic[4], target OS:u8 (`1` Linux), target architecture:u8 (`1` x86_64), native ABI:u8 (`1` through `4`), flags:u8 (zero), client protocol major:u16 BE (`1`), minor:u16 BE (`0`), SDK release:u32 BE (nonzero), dependency count:u16 BE (0 through 32), then five u16 BE byte lengths for CPU baseline, runtime profile, compiler identity, descriptor symbol, and entry-point symbol. The body contains those five ASCII strings in that order, followed by dependency records of length:u16 BE and name bytes. The exact end of the last record must equal the manifest length.

The C SDK exposes `prdb_sdk_manifest_encode_v1` for client-side PMF1 production; it derives the required descriptor/entry symbol pair from the selected native ABI, accepts only bounded fields and sorted unique dependencies, and does not modify an undersized output buffer. Its inputs are borrowed and the caller owns the output buffer. Rust exposes `manifest_v1_from_elf` to inspect a compiled artifact's bounded ELF dynamic table and required ABI exports without loading it, derive and sort its dependency names, and combine them with caller-supplied compatibility profile strings. `encode_manifest_v1` and `decode_manifest_v1` provide canonical PMF1 handling and validation.

CPU and runtime profiles are nonempty identifier strings of at most 64 bytes and must exactly match the trusted service's configured compatibility profile. The SDK release must match that profile. ABI v1/v2/v3/v4 requires the corresponding `prdb_query_descriptor_vN` and `prdb_query_main_vN` symbol pair; SEAL checks that both names are defined, externally visible entries in ELF64 `DT_SYMTAB` with descriptor type OBJECT and entry-point type FUNC. ABI v4 adds the optimizer request callback to the host record while retaining the v3 host table as its prefix. Compiler identity is printable ASCII, bounded to 128 bytes, and diagnostic only. Dependencies are at most 128 bytes each, use an ASCII SONAME basename, and appear in strict bytewise order without duplicates. The validator checks each declared dependency against the service's configured allowlist and parses the ELF64 PT_DYNAMIC table without loading or executing the artifact; its actual DT_NEEDED set must exactly match the manifest. The supported TinyCC ELF profile must include a bounded SysV `DT_HASH` table for dynamic-symbol enumeration. DT_RPATH, DT_RUNPATH, DT_AUDIT, DT_DEPAUDIT, DT_FILTER, and DT_AUXILIARY are rejected. Malformed ELF, non-Linux-x86_64 ET_DYN files, unknown fields, and trailing data fail closed.

Treat the manifest as untrusted. Pin immutable artifact bytes for admission/loading, bound size, and reject incompatible targets. Hashes identify artifacts; they do not establish trust or permission. Do not execute constructors or load the artifact in a trusted service to inspect it.

### Requested Capability Scope v1

`requested_scope` version 1 is canonical binary `PSC1`: four magic bytes, a big-endian u16 capability count from 1 through 200, then that many strictly increasing records. Each record starts with operation:u8 and target-kind:u8, followed by a 16-byte object ID for schema/table targets or two 16-byte IDs for a column target (`table_id`, then `column_id`). Operations are USAGE=1, SELECT=2, INSERT=3, UPDATE=4, DELETE=5; targets are schema=1, table=2, column=3. USAGE is valid only for schemas; data operations are valid only for tables and columns. IDs must be nonzero. Duplicate, unsorted, truncated, trailing, unknown, and empty records are invalid. The largest encoding is 6,806 bytes, within the 8 KiB transport bound.

The C SDK exposes `prdb_sdk_scope_encode_v1` to build PSC1 records. It validates target/operation combinations, nonzero identifiers, strict ordering and count bounds; it supports size queries and never writes a partial result when output capacity is short. Inputs are borrowed and output bytes are caller-owned.

The requested set is only a ceiling. At START storage intersects it with the current token-authenticated principal's catalog-derived grants in the pinned invocation context. It cannot create a grant, bypass a policy, or widen access after START. Every schema, relation, column, row, estimate, and mutation authorization path uses the narrowed scope. SEAL validates the encoding before making the upload immutable; START decodes it again before storage admission. Unsupported scope versions are rejected.

The Rust `RequestedScopeBuilder` consumes permission-filtered `VisibleSchema`, `VisibleRelation`, and `VisibleColumn` records from metadata discovery. Selecting a relation operation produces a table capability; selecting a column operation produces a column capability. Both automatically include that schema's USAGE capability. It emits canonical PSC1 ordering, collapses repeated identical selections, and enforces the 200-capability limit atomically. It cannot discover objects itself or establish authority: callers must obtain records through the authorized discovery APIs, and storage validates every submitted ID and grant independently.

## Buffer Lifetime and Workload

Borrow SDK result values from immutable authorized batches until explicit batch release; do not allocate/copy every cell by default. The C API must make ownership and invalidation visible, and copied input validation remains necessary at the trust boundary. Follow [memory storage](memory-storage.md); no API exposes disk-page pointers or ring buffers.

The first SDK value view is [`prdb_sdk_value_v1`](../engine/include/prdb_sdk_value_v1.h). It is a sized/versioned C record with a 32-bit state and type code, a borrowed byte pointer, and a 64-bit length. States are VALUE (0), NULL (1), and REDACTED (2); NULL and REDACTED have type code zero and no bytes. VALUE type codes 1 through 11 match the executor batch scalar codes, with fixed-width integers encoded big-endian, UUID as 16 bytes, Boolean as one byte containing zero or one, and text/varchar as UTF-8. Bytea is uninterpreted bytes. Empty text/bytea may use a null pointer with zero length. Values are capped at 1 MiB. The view never owns or frees its byte pointer; it stays valid only while its source batch remains borrowed. The validator checks record size/version, state/type, lengths, fixed widths, Boolean encoding, and UTF-8 validity. It cannot make an invalid native pointer safe to dereference. Use the owned-batch lifecycle above when the caller cannot retain the transport response buffer.

Typed accessors expose Boolean, SmallInt, Integer, BigInt, Date, and TimestampTz values in host C scalar types. Signed integers convert from canonical two's-complement big-endian bytes without relying on implementation-defined unsigned-to-signed casts. The byte accessor returns the original borrowed payload and its length for text, varchar, bytea, decimal, UUID, or any other VALUE type. Access on NULL or REDACTED returns `NO_VALUE`; requesting the wrong scalar type returns `TYPE_MISMATCH`. Callers inspect the state separately to distinguish NULL from REDACTED. These helpers validate the record before reading, but the source bytes must still remain valid and unchanged for the duration of the call and any borrowed view use.

[`prdb_sdk_batch_v1`](../engine/include/prdb_sdk_batch_v1.h) opens the version-1 executor `next_batch` payload in place. Opening validates the complete payload, including its 1 MiB bound, optional continuation cursor kind, at most 128 rows, row-handle kind, at most 4096 cells per row, each cell representation, and exact end-of-payload. Row and cell iterators yield borrowed handles/value bytes without copying. The application retains the response buffer unchanged until all views and iterators are discarded. A finished batch has no continuation cursor; otherwise it exposes the opaque 16-byte cursor for the next request. Row handles and cursors are opaque connection-scoped tokens, not row IDs or addresses.

[`prdb_sdk_owned_batch_v1`](../engine/include/prdb_sdk_owned_batch_v1.h) provides an optional owned-result lifecycle when the caller cannot retain the transport response buffer. The caller zero-initializes the wrapper, then `prdb_sdk_owned_batch_copy_v1` copies and validates one complete payload snapshot of at most 1 MiB. It rejects an already active wrapper and leaves it empty on invalid or unsupported payloads. `prdb_sdk_owned_batch_open_v1` creates the same borrowed batch/row/cell views over that SDK-owned immutable copy. `prdb_sdk_owned_batch_release_v1` frees the copy and clears the wrapper; every pointer, iterator, and view opened from it becomes invalid at release. Releasing an empty wrapper is safe, and the wrapper may be reused after release. The payload bytes returned through the owned wrapper are read-only by contract and must not be changed by callers.

The executor SDK exposes `prdb_sdk_executor_stage_insert_v1`, `prdb_sdk_executor_stage_update_v1`, and `prdb_sdk_executor_stage_delete_v1`. INSERT takes the full schema-order cell shape, with VALUE/NULL/DEFAULT states, writes into a caller-owned bounded request buffer, and returns only a validated kind-8 row handle. UPDATE accepts unique in-range column ordinals with VALUE/NULL data; DELETE takes a kind-8 handle. Both mutation acknowledgements must match version 1 and status 0. These functions serialize IPC only; storage revalidates invocation, snapshot, grants, policies, constraints, and row authority.

The SDK serves operational invocations first and also supports bounded analytical work. SQL analytical operators follow the [workload roadmap](workload-profile.md), run over authorized batches, and must not treat redaction as SQL null or omit denied inputs silently.

The SQL DML AST API in [`prdb_sdk_sql_dml_v1.h`](../engine/include/prdb_sdk_sql_dml_v1.h) parses positional single-row INSERT values (`$n`, `NULL`, `DEFAULT`), bounded UPDATE assignments, and mandatory-WHERE DELETE statements using v2 predicates. [`prdb_sdk_sql_execute_insert_v1`](../engine/include/prdb_sdk_sql_exec_v2.h) binds typed parameters against independently checked planner/executor shapes and submits one full-row storage mutation. [`prdb_sdk_sql_execute_update_v1`](../engine/include/prdb_sdk_sql_exec_v2.h) and [`prdb_sdk_sql_execute_delete_v1`](../engine/include/prdb_sdk_sql_exec_v2.h) scan authorized batches into bounded row-handle lists, close the scan, then stage patches or deletes. These APIs grant no authority: storage validates each mutation under the invocation's scope. SQL write execution has host callback fixture evidence; live multi-process SQL write evidence remains future work.

## Administrative SDK

Expose typed definitions/builders and text submission for [schema DDL](ddl-schema.md), [users/roles](ddl-identity.md), and [permission DDL](ddl-permissions.md). Administration occurs in the client over a separate authenticated control-mode gateway connection; user query libraries cannot inherit that connection or its tokens. Storage validates every definition and privilege independently. Do not embed credentials in compiled artifacts or logged SQL. Data SQL functions reject DDL in an invocation, even when its principal also has administrative privileges.

## Metadata SDK Surfaces

Provide typed discovery records and bounded paging for [metadata discovery](metadata-discovery.md), including SQL access to its built-in metadata relations. Keep administrative definition inspection and [live monitoring](operational-metadata.md) in the client control API, not executor host callbacks. Expose neither raw dictionary records nor physical roots/paths. Durable status has an explicit unknown/expired outcome so clients cannot mistake missing retained history for safe retry.

## Contract Versions

Negotiate the client TCP protocol and gateway-service protocol independently from the native entry-point/host ABI, internal IPC, and structured-request/physical-plan formats. The SQL SDK API and SDK release version also have explicit compatibility rules. A matching SDK version alone is not sufficient. Reject unsupported versions at their boundary; do not infer compatibility from language or compiler provenance. The manifest advertises compatibility, while runtime endpoints validate it independently.

## Entry-Point Contract

The Linux x86_64 entry-point ABI v1 is defined by [`prdb_query_abi_v1.h`](../engine/include/prdb_query_abi_v1.h), v2 by [`prdb_query_abi_v2.h`](../engine/include/prdb_query_abi_v2.h), v3 by [`prdb_query_abi_v3.h`](../engine/include/prdb_query_abi_v3.h), and v4 by [`prdb_query_abi_v4.h`](../engine/include/prdb_query_abi_v4.h); Rust mirrors these contracts in `query_abi`. The executor prefers a v4 descriptor, then v3, v2, and v1, and rejects an invalid preferred descriptor rather than falling back. V3 adds a callback that latches SQL statement failure in trusted executor memory. V4 embeds a v3 host record and adds a dedicated bounded optimizer request callback with no caller-selected operation code; existing v3 SDK functions can use its `v3` field. After the entry point returns, any latched statement failure forces a nonzero worker exit even when C code caught the SQL status. The supervisor observes that exit and aborts the invocation. V2 and v3 remain available for earlier query libraries; v1 carries only parameters. The SDK encodes the current explicit-projection/no-WHERE SELECT subset and independently validates Scan/Filter/Project/Limit optimizer plans. Plan execution and independent relation resolution remain future work.

`prdb_invocation_v1` carries a borrowed parameter pointer and a `uint64_t` byte length, capped at 1 MiB by admission. The pointer may be NULL exactly when the length is zero; otherwise it points to the complete immutable parameter bytes and remains valid only for the entry-point call. The entry point returns zero for success and nonzero for failure. The host and library records use fixed-width fields and natural C alignment; on the supported x86_64 target, host table size/alignment are 8/4, invocation size/alignment are 24/8 with pointer and length at offsets 8 and 16, and descriptor size/alignment are 16/4. A query return code is not itself a transaction commit decision.

Use C-compatible fixed-layout structures, explicit sizes/versions, opaque handles, and explicit buffer ownership. No Rust containers, Go-managed objects, language exceptions, or panics may cross the ABI. Native pointers refer only to executor memory. Calls to other processes use validated serialization.

The executor SDK exposes `prdb_sdk_executor_check_cancelled_v1` as a cooperative checkpoint for SQL and other bounded query loops. It returns success with `cancelled_out` set to 0 while the invocation remains active, or 1 after storage detects cancellation or deadline expiry and aborts the transaction. Callers should poll between bounded work batches and stop promptly on 1. The worker host and supervisor retain process-level cancellation handling for code that does not poll.

Constructors execute under confinement before entry-point checks can finish. The entire artifact, bundled SDK, and dependency code are untrusted. Host callbacks cannot constrain arbitrary machine code within the process; server-side roles and the OS sandbox enforce authority.

Allow sequential SQL/storage operations under one MVCC snapshot plus private writes and cumulative budgets. Initially permit one active statement/request stream and single-threaded SDK calls. All statement errors abort the entire transaction; no savepoints or per-statement commits exist. Successful library return requests finalization, but success requires storage-confirmed durable commit. Cancellation/failure accepted before redb commit begins aborts staged writes; after commit begins the outcome may be pending/uncertain and must be reconciled. After commit it cannot undo data. Results remain provisional until commit confirmation, which is not a correctness attestation. Use authenticated invocation-status lookup after lost replies; never automatically rerun a library with an unknown outcome. Exit the process rather than relying on safe unloading of arbitrary code.

## Concurrent Invocation Contract

Multiple clients and executors may run concurrently. Each invocation is one snapshot-isolated transaction; it sees its own staged writes but not others' uncommitted changes. Optimistic row conflicts abort the entire invocation. Snapshot isolation is not serializable. Status lookup, known-abort retries, cancellation, and version retention follow [concurrency and MVCC](concurrency-mvcc.md).

Read-only grants reject mutation calls. Public protocol definitions for commit do not grant the executor the supervisor's finalization role. No arbitrary timestamp selection or hidden historical reads are exposed.

## Language and Compilation Decision

Use C and TinyCC for user queries and SDK SQL/runtime code. Rust implements the database engine, including the executor host, supervisor, optimizer, storage, transactions, and authorization. This is an established choice, not an experiment among language candidates. See [toolchain implications](toolchain.md) for the component split and release gates.

Distribute a pinned TinyCC toolchain and prebuilt C SDK archive; compile only user source per edit. Keep administrative helpers separate from executor runtime code. TinyCC runs in a bounded client subprocess and emits query.so without executing it. Engine Rust compilation is never part of the per-query path.

The `prdb-packager` Rust client helper implements this compile-and-package step on Linux x86_64. It accepts one source file (at most 1 MiB), a prebuilt SDK archive (at most 128 MiB), an include directory, a canonical PSC1 requested-scope file (at most 8 KiB), and explicit ABI, SDK release, CPU baseline, runtime profile, and diagnostic compiler identity fields. TinyCC receives a cleared environment and is invoked with `-Wall -Wextra -Werror -shared`; it runs with 65 seconds of CPU, a 60-second wall limit, 2 GiB address space, 64 MiB output-file limit, no core dumps, and 64 file descriptors. The helper bounds captured diagnostics to 8 KiB, validates the output ELF and required ABI exports without loading it, and rejects artifacts above 64 MiB. The compiler's stdout and stderr are drained so output cannot fill a pipe.

On success, the helper creates a new package directory containing `query.so`, canonical `manifest.pmf1`, validated `requested_scope.psc1`, and lowercase-hex `artifact.sha256`. Files are mode 0600 and the directory is mode 0700. The directory is published by an atomic no-replace rename, so an existing package is never overwritten and incomplete staging data is removed on ordinary errors. The helper does not execute the artifact, grant the requested scope, or provide authorization credentials to TinyCC.

The Rust `SubmissionClient` implements the query-mode TCP path. It verifies package file permissions, PMF1/PSC1 encodings, and the artifact digest before sending PREPARE. It uploads artifact and parameter bytes in bounded contiguous chunks, checks each acknowledged offset, then SEALs and returns the reserved invocation ID. The connection remains available for START and status calls. `start` first writes a caller-selected `PDBR1 <invocation-id>` receipt with mode 0600, synchronizes it and its parent directory, and refuses to overwrite an existing receipt; only then does it send START. START is never retried automatically. A lost or malformed START reply returns an uncertain-outcome error carrying the invocation ID; the caller reconnects and uses authenticated STATUS. Result bytes remain provisional until the supervisor's terminal event reports `committed`. The bearer secret input buffer is zeroized, as are its encoded AUTH payload copies. This client uses the specified plaintext TCP transport and does not add TLS.

The `prdb-client` command exposes `scope`, `submit`, `status`, owner-scoped `cancel`, and administrator-authorized `admin-cancel`. `scope` discovers schemas, relations, and columns through the authenticated metadata API, resolves the supplied exact names only within that principal's visible set, and writes canonical PSC1 to a mode-0600 no-overwrite file. It can request schema USAGE, relation-level operations, or selected column operations; all data selections automatically include schema USAGE. The resulting scope is only a request ceiling and START still authorizes each capability. Submission takes a numeric IP socket address, a private credential file, a prepared package directory, a no-overwrite START receipt path, and optional bounded parameter file, deadline, and workload class. It writes provisional data bytes to stdout and reports the terminal outcome on stderr; success exit status requires a committed terminal event. Status and cancellation authenticate on new connections; owner-scoped cancellation uses query mode, while `admin-cancel` uses control mode and requires current database-administrator authority. Cancellation reports `accepted`, `too_late`, a terminal outcome, or `unknown`, and the acknowledgement is not itself a transaction terminal event. START is issued once only, and uncertain results include the invocation ID for later status reconciliation.

`client_credentials` reads and writes a canonical `PDB-CREDENTIALS-1` file containing a lowercase token ID and lowercase hex token secret on separate lines. Files must be regular, owned by the effective user, and mode 0600; reads reject symbolic links and noncanonical contents. Creation writes a private same-directory temporary file, synchronizes it, then publishes it with a no-overwrite hard link and synchronizes the parent directory. Removal applies the same ownership and mode checks and synchronizes the parent. The secret is zeroized in temporary buffers; the file is plaintext bearer material protected by its owner-only mode.

`MetadataClient` implements the authenticated control-mode reads for visible schemas, relations, and declared columns. Its `list_*_page` methods accept a page limit from 1 through 128 and an optional opaque cursor; complete-list methods follow the pages automatically using a default page size of 64. The client validates IDs, ordering, ordinals, type spellings, continuation syntax, and response shape before constructing the typed discovery records used by `RequestedScopeBuilder`. A caller can use these records to select query capabilities; START still rechecks every requested capability against current catalog grants. The control client zeroizes the bearer-secret input and AUTH payload copies and shares the plaintext TCP profile with `SubmissionClient`.

`AdminClient` is a separate authenticated control-mode API for typed administrative operations. It exposes user and role creation, rename, drop, login enable/disable, role membership grant/revoke, database-scoped system privilege grant/revoke, schema create/rename/drop/owner transfer, table create/rename/drop/owner transfer, invocation cancellation, column add/rename/drop, nullability changes, column-default set/drop, unique and primary-key create/drop, CHECK create/drop, foreign-key create/drop, token issue/revoke, and ordinary-index create/rebuild/drop. Table creation accepts typed column definitions, scalar values for literal defaults, SQL NULL defaults, and the UUID current-principal default; it returns ordered generated column IDs. Column addition enforces the protocol's backfill rules for NULL and non-null defaults. CHECK creation encodes a row-local expression as canonical EIR1 hex and accepts an empty dependency list for expressions with no column references. Constraint and foreign-key creation return their generated catalog IDs; key creation also returns its backing index ID. System privilege values are a closed enum for `manage_users`, `manage_roles`, and `create_schema`. User creation creates an identity without a credential; issue a token separately. Token issuance returns its bearer secret once in `AdminTokenResult`, which does not print the secret and zeroizes it when dropped. A lost or malformed issue response is uncertain and the plaintext cannot be recovered; explicitly revoke/reissue after reconciling. The client validates nonzero IDs, canonical lowercase names, column/default type compatibility, and ordered distinct index and constraint columns before sending requests, and follows the server's connection-owned PREPARE/START flow. It sends no administrative credentials to query artifacts. If START loses its reply or returns an invalid response, the client returns `AdministrativeOutcomeUncertain` with the operation ID and never retries; callers reconnect and use `AdminClient::status` to reconcile the operation.

`prdb-client token-issue` issues a credential through the authenticated `AdminClient` control channel and saves the returned secret to a new private credential file; it never prints the secret. The command requires a positive TTL in seconds and computes the absolute expiration timestamp locally. If issuance commits but file publication fails, the CLI reports the operation and token IDs and instructs the caller to revoke the unrecoverable token before retrying. Rotation is explicit: save a replacement file, verify it with a fresh authenticated request, then revoke the old token with `token-revoke`. The CLI never revokes the previous token automatically.

The admin CLI also exposes user and role create/rename/drop, user login enable/disable, and role membership grant/revoke through typed `AdminClient` operations. User creation returns an identity only; use `token-issue` separately to create a credential. These commands require the corresponding storage authority and print generated identity IDs and operation/commit metadata, never bearer secrets. Schema create/rename/drop and table create/rename/drop use the same authenticated control channel. Schema creation requires an explicit nonzero `--owner-id`; the caller must have schema-management authority. Table creation requires `--schema-id`, `--name`, and at least one column in the form `name:type:nullability[:identity]`, with columns separated by semicolons. Supported types are `boolean`, `smallint`, `integer`, `bigint`, `decimal(P,S)`, `text`, `varchar(N)`, `bytea`, `uuid`, `date`, and `timestamptz`; `P` is 1 through 38, `S` is no greater than `P`, and `N` is positive. Nullability is `nullable` or `not-null`. In this CLI version, a non-null column must use the `identity` modifier, which is valid only for a non-null UUID column; literal/default expressions are not accepted by table-create. `column-add` accepts one nullable column with the same type names, while `column-rename` and `column-drop` require both table and column IDs. `column-nullability` sets the nullable flag. `column-default-set` takes an explicit type and value: `null` encodes SQL NULL; `current-principal-id` is valid for UUID; booleans use `true` or `false`; integer types use decimal integer text; DECIMAL uses a base-ten value with no more fractional digits than its declared scale; TEXT/VARCHAR use the supplied text; BYTEA uses even-length lowercase `hex:` bytes; UUID uses 32 lowercase hex digits; DATE uses days since 1970-01-01; and TIMESTAMPTZ uses microseconds since the Unix epoch. `column-default-drop` removes the default. `index-create` takes a table ID, normalized name, ordered comma-separated column IDs, and an optional uniqueness flag defaulting to false. `index-rebuild` takes an index ID and the replacement ordered column IDs/profile; `index-drop` takes an index ID. Storage remains responsible for current authority, dependency, backfill, and uniqueness validation. Typed AdminClient and storage requests remain authoritative for range, schema, and permission checks. The CLI validates the syntax before sending typed requests and prints generated IDs and operation/commit metadata.

`table-owner-set` accepts nonzero `--table-id` and `--owner-id` values and submits `tables.set_owner` through the authenticated ADMIN channel. The current table owner or a database administrator may transfer a non-system table to a live user or role. The client prints the operation ID and committed sequence; storage remains authoritative for the transfer and does not grant data privileges to the new owner. `schema-owner-set` accepts nonzero `--schema-id` and `--owner-id` values and submits `schemas.set_owner`; the current schema owner or a database administrator may transfer a non-system schema to a live user or role. Both commands print the operation ID and committed sequence, and storage remains authoritative for ownership changes and does not grant data privileges to the new owner.

The CLI also exposes `unique-create` and `primary-key-create` with a table ID and ordered, distinct comma-separated column IDs, plus `unique-drop` and `primary-key-drop` with the generated constraint ID. Storage checks primary-key nullability and all catalog, authority, dependency, and backfill rules.

The system-privilege-grant and system-privilege-revoke commands take a nonzero --grantee-id and one closed --privilege value: manage_users, manage_roles, or create_schema. These commands use the authenticated ADMIN channel; only a current database administrator can change these grants.

The AdminClient object grant/revoke methods and object-grant/object-revoke CLI commands accept a grantee, schema/table object, one closed object privilege, and either object or column target scope. They use the authenticated ADMIN channel; storage checks current ownership, inherited MANAGE_GRANTS, or database-administrator authority. REFERENCES grants may target a whole table or individual columns and are required before foreign-key creation.

AdminClient policy create/drop methods and policy-create/policy-drop CLI commands use the authenticated ADMIN channel. Policy creation supplies a row/cell kind, operation, ALLOW/RESTRICT effect, nonempty user/role recipient set, optional cell target columns, and the EIR1 USING/WITH CHECK expressions required by that operation. Storage binds expressions to the current table schema and enforces owner or MANAGE_POLICIES authority; the CLI never exposes policy bodies through metadata reads.

The foreign-key-create CLI command takes a source table ID, ordered and distinct source column IDs, and a target unique or primary-key constraint ID; foreign-key-drop takes the generated foreign-key ID. The authenticated storage path checks column correspondence, types, both tables' authority, existing rows, and dependency rules. Creation also requires a pre-existing REFERENCES grant on the target table or columns; `object-grant` and `object-revoke` provide that grant lifecycle.

The check-create CLI command accepts canonical lowercase hex containing one EIR1 row-local expression, plus an explicit dependency-column list; the list may be empty for a constant expression. check-drop takes the generated constraint ID. The client decodes EIR1 before sending it, and storage validates field bindings, Boolean result type, current rows, and authority.

The versioned C ABI is the interoperability boundary, not permission to use unspecified Rust layouts. C can corrupt the Rust executor host, so all trusted services remain outside that process. Other query languages/compilers are outside the initial supported SDK; artifact provenance never bypasses validation.

## Benchmark and Acceptance Plan

Measure cold and warm compile-plus-link time, one-line-edit turnaround, artifact size, load/startup time, and compile-to-first-result latency. Include SQL wrapper queries, small native loops, and mixed SQL/native work. Measure execution throughput too; reduced compile time may trade off generated-code quality.

Measure the selected TinyCC build and separate SDK release-build time from per-query compilation. Do not assume GCC-style optimization options produce equivalent results with TinyCC. The package helper is implemented, but exact TinyCC build distribution, dependency packaging, and the deployed runtime profile still need to be pinned; the local process resource limits do not replace a compiler sandbox.

Validate cross-version rejection, malformed manifests, missing symbols, hostile constructors, dependency lookup restrictions, library crashes, protocol forgery, sequential-call budgets, and preservation of redaction states. Confirm SDK provenance never bypasses authorization.
