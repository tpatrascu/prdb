# Client Network Protocol v1: Plain TCP

## Scope

This is the external client protocol v1, terminated by the [gateway](client-gateway.md). It is not HTTP, HTTP/3, or executor IPC. It supports authenticated submissions, streamed arbitrary query output, status/cancellation, and a separate administrative connection mode. It is unencrypted; loopback is the default. Keep protected bootstrap on its local setup channel. The separate interactive SQL protocol v2 contract, which adds connection-independent transactions and per-package effective actors, is specified in [interactive SQL](interactive-sql.md); v1 remains one invocation per transaction and never silently accepts v2 semantics. Query submissions require repository-mode negotiation. Older optional SQL-library upload fields and chunks are rejected; clients do not fall back to them.

The client submission SDK implements this protocol outside query.so. The C SQL/runtime inside query.so uses only provisioned local host services. Neither TCP sockets nor client credentials enter the executor.

## Frame Encoding

TCP is treated as a byte stream: reads may contain part of a frame or several frames. Each frame has this 32-byte header, integers unsigned little-endian:

| Offset | Bytes | Field |
| --- | --- | --- |
| 0 | 4 | ASCII `PDBN` |
| 4 | 2 | Protocol major=1 |
| 6 | 2 | Protocol minor=0 |
| 8 | 2 | Message kind |
| 10 | 2 | Flags=0 |
| 12 | 4 | Payload byte length, excluding header |
| 16 | 8 | Request ID |
| 24 | 8 | Response sequence |

Hard payload maximum is 1 MiB; JSON control payloads are limited to 64 KiB and chunk data to 256 KiB. Negotiation may lower limits, never raise these maxima. Validate header/version/length before allocation. No compression, optional frame flags, or generic descriptor transport exists in v1. Invalid framing closes the connection after a bounded error if possible; do not scan arbitrary bytes for a resynchronization magic.

Clients allocate strictly increasing nonzero request IDs per connection and set response sequence=0. Responses echo the ID. All ordinary requests have one response at sequence 0. START produces a stream described below. No request pipelining/multiplexing on one connection initially; different clients/connections execute concurrently. Status and cancellation during a streamed invocation use another authenticated connection.

Control payloads are UTF-8 JSON objects, with duplicate/unknown keys rejected, nesting depth at most 16, and no nonfinite numbers. Encode u64 counters/offsets as canonical decimal strings to avoid JSON numeric precision loss. Opaque IDs are 32 lowercase hexadecimal characters; hashes are 64. Binary credential/scope/manifest fields use canonical padded base64 where specified. These representation rules are independent of on-disk formats.

## Messages and Connection Modes

| Kind | Direction | Operation |
| --- | --- | --- |
| 1 | Client | HELLO |
| 2 | Client | AUTH |
| 3 | Client | PREPARE |
| 4 | Client | ARTIFACT_CHUNK |
| 5 | Client | PARAMETER_CHUNK |
| 6 | Client | SEAL |
| 7 | Client | START |
| 8 | Client | STATUS |
| 9 | Client | CANCEL |
| 10 | Client | ADMIN |
| 11 | Client | PING |
| 100 | Server | RESPONSE, JSON operation-specific result |
| 101 | Server | ERROR, JSON bounded code/message |
| 102 | Server | RESULT_DATA, raw application bytes |
| 103 | Server | TERMINAL, JSON invocation outcome |

HELLO is the first request: `{ "mode": "query" | "control", "client_name": string }`, with client_name at most 128 UTF-8 bytes. Repository-enabled query clients add `"sdk_library_mode":"repository"`. The server must echo that exact mode in RESPONSE; a peer that rejects or omits the capability cannot be used by the repository client, which closes without retrying the legacy profile. RESPONSE also reports selected version, mode, limit values, and `transport: "plaintext_tcp"`. Only version 1.0 is supported; reject unsupported versions, never silently negotiate weaker security. Before authentication allow only HELLO, AUTH, and PING under strict time/size/rate bounds.

AUTH supplies `{ "token_id": id, "token_secret": base64 }`; decoded secret is bounded to 4 KiB and its actual algorithm/length is checked by the separate credential profile. RESPONSE contains a nonsecret session ID and `authenticated: true`. The session ID is server-generated and binds supervisor staging to this connection and the principal resolved from storage. Invalid credentials use one generic failure category and disclose no principal/token existence. No user-supplied principal field is accepted. The gateway does not log or reflect credential bytes. A connection has one identity and mode; switching requires a new connection.

The gateway session state accepts HELLO as the first request, then authenticates through storage and applies the request allowlist for the selected mode. Before HELLO no other request is permitted; after HELLO but before AUTH only AUTH and PING are permitted. Query sessions may use PREPARE, chunks, SEAL, START, STATUS, CANCEL, and PING. Control sessions may use STATUS, CANCEL, ADMIN, and PING. A query staging owner is derived from the storage-authenticated session, not request fields. The gateway retains the bearer secret only for the connection lifetime, zeroizes its in-memory copy on disconnect, and asks storage to revalidate token, login, and current role closure before each execution or control request. PING does not require revalidation.

The initial control-payload decoder implements the exact flat string-object shapes for HELLO and AUTH. It rejects duplicate keys (including escaped-equivalent names), unknown or non-string fields, malformed JSON escapes, trailing bytes, noncanonical token IDs, and noncanonical or wrong-sized base64 secrets. Other request payload schemas remain unimplemented until their allowlisted operation increments.

Query mode supports PREPARE through START, STATUS, CANCEL, and PING. Control mode supports STATUS, CANCEL, ADMIN, and PING. Mode selection never grants administrative privileges. Every new execution/admin/status/cancel operation revalidates credential/current authority; an initially valid AUTH does not freeze permissions for the connection lifetime.

## Submission and Upload

PREPARE contains `manifest_version` (u32 JSON integer), `manifest` (base64), `artifact_bytes` (u64 string), `artifact_sha256`, `parameter_bytes` (u64 string), `parameter_sha256`, `scope_version` (u32), `requested_scope` (base64), `deadline_ms` (u64 string), and the required `"sdk_library_mode":"repository"` capability. SQL-library byte and digest fields are invalid. Clients upload only the query artifact and parameters; SQL-library chunks are invalid for every session. The profile must match the HELLO capability; profile mismatch or an old peer fails closed, with no retry or fallback. Manifest and requested-scope decoders are separately versioned SDK/admission contracts; reject unimplemented versions before accepting upload. Manifest version 1 uses canonical binary `PMF1`; requested-scope version 1 uses canonical `PSC1`, both defined in the [SDK contract](client-sdk.md). SEAL checks `PMF1` compatibility against the configured service profile and compares its declared dependencies to the query ELF64 `DT_NEEDED` set. Repository-profile SDK resolution validates the repository library as data and never loads it in the gateway or supervisor. Raw manifest is at most 16 KiB and scope at most 8 KiB, within the control-frame bound. Parameters are opaque application bytes, not admission credentials. Application-specific parameter encodings remain defined by their client contract; generic `submit` transports parameter bytes without interpreting them.

Baseline upper bounds: artifact 64 MiB, parameters 1 MiB, one live submission per query connection. Configured quotas may be lower. SDK libraries are installed and versioned by database administrators through the control API and are never submitted with a query. PREPARE allocates an authenticated supervisor-owned staging reservation and returns `invocation_id` and admitted upload limits. It creates no MVCC snapshot and launches no executor. The ID is known to the client before execution can have effects.

Chunk payloads are binary: invocation ID[16], offset u64 little-endian, then 1–256 KiB data bytes. ARTIFACT_CHUNK (kind 4) and PARAMETER_CHUNK (kind 5) track independent offsets. SQL_LIBRARY_CHUNK (kind 12) is reserved and rejected. Require the exact next contiguous offset; reject duplicates, gaps, overflow, or bytes beyond the declaration. Acknowledgement reports the next offset. Zero-length parameters require no chunks and use the SHA-256 digest of empty bytes. Authenticate and bound staging globally and per principal; declared lengths do not authorize unlimited allocation.

SEAL `{ "invocation_id": id }` verifies all declared byte counts/digests and manifest compatibility, then makes staged bytes immutable. RESPONSE reports `state: "prepared"`. Hash agreement does not establish artifact safety. No untrusted library is loaded during validation.

The Rust query submission client negotiates repository mode in HELLO, verifies local package files and their digests, sends PREPARE, uploads query and parameter chunks at the acknowledged contiguous offsets, then SEALs. It never sends SDK library bytes. The client returns the reserved invocation ID while retaining the connection for START. Before transmitting START it writes a no-overwrite `PDBR1 <invocation-id>` receipt at a caller-selected path, mode 0600, and synchronizes the file and parent directory. It never retries START. If its reply is uncertain, the client uses a new authenticated connection for STATUS. RESULT_DATA remains provisional in the client API until the matching TERMINAL frame reports `committed`.

START `{ "invocation_id": id }` is permitted once for that sealed reservation, on its owning query connection. The supervisor revalidates admission and atomically transitions it to execution, then returns RESPONSE sequence 0 with `state: "accepted"`. Execution may start before that response is received. Repeated START is rejected, not replayed; this live-reservation guard is not durable submission deduplication. A rejected pre-execution start returns ERROR, releases any temporary admission snapshot, and creates no durable outcome or other transaction effects.

Disconnect before START discards staging. After any START transmission with an uncertain reply, use STATUS; never automatically repeat START or submit a fresh invocation. Reservations are not durable across supervisor restart, and missing status cannot establish safe retry. Upload-resume and detached execution are outside v1.

## Results and Transaction Outcomes

After accepted START, RESULT_DATA frames use the START request ID and consecutive sequences starting at 1; TERMINAL takes the next sequence and ends the stream. Each data payload is untrusted application output chosen by the query library. Output media/schema conventions may be defined by the application; they are not raw storage batch structures. The transport does not claim arbitrary output is a truthful SQL result.

Only the supervisor can supply the invocation's terminal envelope. TERMINAL fields are `invocation_id`, `outcome` (`committed`, `aborted`, or `unknown`), and `reason_code` (bounded public category). Unknown requires subsequent reconciliation. `committed` requires storage's durable decision; `aborted` requires a definitive abort decision. Neither application bytes containing those words, TCP EOF, nor upload/START acknowledgements establish an outcome. Durable ABORTED status follows the WAL/outcome contract.

Every RESULT_DATA frame is provisional until COMMITTED. An aborted invocation invalidates all provisional data as successful transaction output. On EOF, timeout, or incomplete framing, retain the ID and reconcile through STATUS. A committed invocation may have incomplete/lost results; v1 has no retained result replay. After a terminal frame the connection may prepare a new invocation with a new ID and increasing request IDs.

## Control Operations and Administration

STATUS `{ "invocation_id": id }` returns an authorized state: `prepared`, `active`, `committing`, `committed`, `aborted`, `unknown`, or `expired`. Prepared is ephemeral and means no execution has started. Query mode is owner-scoped. Control mode can reconcile the caller's own live or retained outcome, including an ADMIN mutation outcome; looking up another owner's live or retained terminal state requires current database-administrator authority. Committed/aborted recovery status comes from storage, not gateway memory.

CANCEL `{ "invocation_id": id }` returns `accepted`, `too_late`, or an authorized terminal state. Query mode cancels only the caller's prepared or active invocation. Control mode revalidates current database-administrator authority and records an administrative cancellation audit before reporting its decision. Cancellation accepted before COMMIT submission prevents commit; after submission, report too_late/pending resolution. Cancelling prepared staging removes it without starting a transaction. Status/cancellation acknowledgements are not synthetic transaction terminal events.

ADMIN is a control-mode operation with one of these exact envelopes:

- Read-only: `{ "phase": "read", "operation_version": u32, "operation": string, "arguments": object }`.
- Prepare mutation: `{ "phase": "prepare", "operation_version": u32, "operation": string, "arguments": object }`; response contains `operation_id` and `state: "prepared"`. No mutation has run.
- Start mutation: `{ "phase": "start", "operation_id": id }`; this may execute only once on the owning connection, after current-authority revalidation. Response contains the ID, outcome (`committed`, `aborted`, or `unknown`), and operation-specific result if justified by that outcome. It is a single bounded response, not an executor result stream.

STATUS/CANCEL use their existing `invocation_id` field for either an invocation ID or an administrative operation ID; IDs share one opaque namespace. Reserve one prepared operation per control connection. Lost replies follow the same authenticated durable-outcome reconciliation rule; never replay an uncertain administrative mutation. Disconnect discards unstarted reservations and requests cancellation of started work subject to the commit barrier.

The operation allowlist covers schema/table/identity/permission DDL submission, credential lifecycle, and authorized metadata/runtime inspection under their existing specs. Each named operation requires an explicit bounded argument/result schema and authority check; unknown or not-yet-specified operations fail unsupported, not generic dispatch into internal IPC. The server classifies reads versus mutations and rejects attempts to run a mutation with phase=read. DDL uses one statement or bounded atomic batch. Credential issuance returns its secret only once in its operation response; lost delivery requires an explicit authorized revoke/reissue flow, not recovery of plaintext from status. Bootstrap retains its separate local handoff protocol.

The first implemented read operation is `tokens.list`, with arguments `{ "user_id": id, "after_token_id"?: id }`. It requires ownership of the token inventory or current `MANAGE_USERS`/database-administrator authority. Results contain at most 64 records ordered by token ID and a `next_after_token_id` cursor or `null`. Each record contains `token_id`, `label`, `issued_at_us`, `expires_at_us`, `revoked`, and `revoked_at_us`; verifier and bearer-secret material are never returned. The client sends the cursor as `after_token_id` to fetch the next page.

`metadata.identities.resolve` accepts `{ "name": normalized_name, "kind": "user"|"role"|"either" }` and returns `{ "identity_id": id|null }`. It resolves at most one identity and requires the matching `MANAGE_USERS` or `MANAGE_ROLES` authority, or database-administrator membership. `either` checks the resolved principal kind and only returns it when the caller may manage that kind; otherwise it returns `null`. Unauthorized and absent names both return `null`; no identity enumeration or principal details are exposed. Mutations using the returned stable ID revalidate authority and catalog state independently.

`metadata.policy_identities.resolve` accepts `{ "schema_id": id, "table_id": id, "name": normalized_name, "kind": "user"|"role" }` and returns `{ "identity_id": id|null }`. It resolves only one named identity for policy binding and requires ownership of the schema/table, scoped `MANAGE_POLICIES`, or database-administrator membership. Unauthorized and absent names both return `null`; no identity enumeration or principal details are exposed. `policies.create` independently revalidates actor authority and catalog state.

`metadata.grant_identities.resolve` accepts `{ "schema_name": normalized_name, "table_name"?: normalized_name, "name": normalized_name, "kind": "user"|"role" }` and returns `{ "schema_id": id|null, "object_id": id|null, "identity_id": id|null }`. Omitting `table_name` targets the schema; supplying it targets one table in that schema. The server resolves the target and one recipient in the same authenticated request and returns IDs only to the target owner, an inherited `MANAGE_GRANTS` holder, or a database administrator. Unauthorized and absent targets or identities share the all-null response; no identity enumeration or principal details are exposed. `objects.grant` and `objects.revoke` independently revalidate authority and catalog state.

`metadata.policies.resolve` accepts `{ "schema_id": id, "table_id": id, "name": normalized_name, "kind": "row"|"cell"|"any" }` and returns `{ "policy_id": id|null }`. It resolves a policy name only within that table and requires the same database-admin, ownership, or scoped `MANAGE_POLICIES` authority used by policy DDL. `any` is used by replacement to resolve a same-name row or cell policy. Unauthorized and absent names both return `null`. `policies.drop` independently revalidates authority and catalog state before atomically removing the policy.

`metadata.schemas.list` is an authenticated control-mode read. An empty `arguments` object requests the bounded complete response `{ "schemas": [{ "schema_id": id, "name": string }] }`; the SDK uses paged arguments `{ "limit": positive_decimal_string, "cursor"?: string }`. Page limits are 1–128. Paged responses include `next_cursor`, which is a lowercase-hex opaque cursor string or `null`. Schemas are ordered by stable schema ID. Ordinary control callers receive schemas visible through USAGE, while database administrators, schema owners, table owners, and principals with inherited table-scoped INDEX grants may also discover the schema names required for their authorized DDL. The public `information_schema` namespace remains visible. The captured result is capped at 4,096 records and 1 MiB of IDs plus UTF-8 names. This operation grants no table access; later scope requests and invocation admission independently recheck catalog grants, and this read does not require database-administrator authority.

`metadata.relations.list` accepts `{ "schema_id": id }` for a bounded complete response, or adds `limit` and optional `cursor` for pages. It returns `{ "relations": [{ "relation_id": id, "name": string }] }` in stable relation-ID order for relations visible through schema USAGE and table/column data grants. Authenticated control callers who own the schema/table or hold scoped `MANAGE_POLICIES` may also discover the target table's name for policy DDL. Table owners and inherited table-scoped INDEX grantees may discover their target relation for index DDL without schema USAGE. The reserved `information_schema` schema returns its three fixed public relations. An absent or hidden schema returns the same empty array as an authorized schema with no discoverable relations. The captured result is capped at 4,096 records and 1 MiB of IDs plus UTF-8 names. Stable IDs and names grant no table access.

`metadata.columns.list` accepts `{ "schema_id": id, "relation_id": id }` for a bounded complete response, or adds `limit` and optional `cursor` for pages. It returns `{ "columns": [{ "column_id": id, "name": string, "ordinal": integer, "scalar_type": string, "nullable": boolean }] }` for the declared shape of an authorized relation. Policy DDL authorities may inspect declared columns for a table they administer after schema USAGE; a table owner or inherited `MANAGE_GRANTS` holder may inspect the target table shape without schema USAGE or data grants to bind object-grant SQL. This does not expose row data or grant query access. Ordinals are zero-based tuple positions; `scalar_type` uses the canonical type spelling accepted by `tables.create` (including `decimal(p,s)` and `varchar(n)`). The public built-in relations return their fixed declared shapes. Hidden or absent user relations return the same empty array as an authorized relation with no columns. The captured result is capped at 4,096 records and 1 MiB of IDs, names, and scalar-type spellings. This metadata does not reveal defaults, policies, ownership, grant provenance, or data values.

`metadata.indexes.list` accepts `{ "schema_id": id, "table_id": id, "limit": positive_decimal_string, "cursor"?: string }` and is available to a database administrator or schema owner (including inherited ownership), and to the owner or inherited INDEX grantee of the target table. It returns `{ "indexes": [{ "index_id": id, "name": string, "column_ids": [id, ...], "unique": boolean }] }` in stable index-ID order. Column IDs preserve index key order. Hidden or absent tables return an empty array. The captured result is capped at 4,096 records and 1 MiB of IDs, names, and flags; physical storage IDs, roots, membership entries, counts, and key samples are omitted.

`metadata.constraints.list` accepts `{ "schema_id": id, "table_id": id, "limit": positive_decimal_string, "cursor"?: string }` and requires current database-administrator or schema-owner authority. It returns `{ "constraints": [{ "constraint_id": id, "name": string, "kind": string, "column_ids": [id, ...], "referenced_table_id": id | null, "referenced_column_ids": [id, ...] }] }` in stable constraint-ID order. `name` is the current catalog object name, including generated names for unnamed constraints. Kinds are `not_null`, `primary_key`, `unique`, `check`, and `foreign_key`; CHECK expression bodies are omitted. For a foreign key, target table and ordered target columns appear only when the caller also has administrative visibility over the target schema; otherwise the target ID is `null` and the target column list is empty. Hidden or absent source tables return an empty array. The result is capped at 4,096 records and 1 MiB including names, IDs, and kind names.

`metadata.grants.list` accepts `{ "schema_id": id, "table_id": id, "limit": positive_decimal_string, "cursor"?: string }` and requires current database-administrator or schema-owner authority. It returns direct grants on that table in grantee-ID, privilege-code, target-scope, and target-ID order. Each row contains `grantee_id`, `grantor_id`, `privilege`, `target_scope` (`object` or `column`), and `target_id`; principal names and inherited grants are omitted. Supported table privileges are `select`, `insert`, `update`, `delete`, `references`, `alter`, `index`, `manage_policies`, and `manage_grants`; only data privileges may use column scope, and object-scoped targets equal the table ID. Hidden or absent source tables return an empty array. The result is capped at 4,096 records and 1 MiB.

`metadata.policies.list` accepts `{ "schema_id": id, "table_id": id, "limit": positive_decimal_string, "cursor"?: string }` and requires current database-administrator or schema-owner authority. It returns policy IDs, `kind` (`row` or `cell`), operation (`select`, `insert`, `update`, or `delete`), effect (`allow` or `restrict`), and cell target `column_ids` in policy-ID order. Database administrators receive `recipients`, an ordered array of `{ "kind": "user" | "role", "principal_id": id }`; schema owners receive `recipients: null` because those principal endpoints may be outside their visibility. Row policies have an empty column list. Expression IDs and USING/WITH CHECK bodies are never returned. Hidden or absent source tables return an empty array. The result is capped at 4,096 records and 1 MiB.

`metadata.dependencies.list` accepts `{ "object_id": id, "limit": positive_decimal_string, "cursor"?: string }` and requires current database-administrator or schema-owner authority over the anchor object. It returns direct adjacent catalog edges in `(dependent_id, referenced_id, kind)` order as `{ "dependencies": [{ "dependent_id": id, "referenced_id": id, "kind": string }] }`. Kinds are `owned_child`, `expression_reference`, `foreign_key_target`, `backing_index`, and `authority`; the operation does not traverse transitively. An edge is included only when both endpoints are currently administratively visible. Edges with hidden endpoints are omitted before encoding, and neither hidden counts nor endpoint names are returned. Hidden or absent anchors return an empty array. The captured result is capped at 4,096 records and 1 MiB. Continuations use the same one-use connection-local cursor and current-authority revalidation as the other metadata pages.

Metadata page cursors are one-use, connection-local opaque 16-byte lowercase-hex tokens. A cursor binds the operation, filter IDs, page limit, authenticated principal, role closure, and one bounded result captured from a single request-scoped catalog snapshot. The session caches at most one metadata result; starting a new metadata query replaces it. Pages remain stable through catalog renames, while a changed principal/role closure, wrong query/filter/limit, replay, cross-connection use, or 60 seconds of cursor inactivity invalidates the continuation. Pages obey the control-frame limit. The SDK's complete-list methods follow these cursors; callers using a page method pass `next_cursor` unchanged.

`runtime.invocations.list` is a database-administrator-only read with `{ "limit": positive_decimal_string, "cursor"?: string }` arguments. The limit is at most 128. Results contain an observation time, `consistency: "best_effort"`, and at most the requested number of invocation records ordered by invocation ID. Each record contains its invocation and principal IDs, an opaque nonzero `transaction_id` unique among live transactions, `workload_profile_id`, state, start/deadline times where applicable, `age_us` measured at the page observation time, `staged_rows`, `staged_value_bytes` (row payload bytes, excluding row IDs and index metadata), `snapshot_pin_count` (0 or 1, the number of invocation-owned redb read snapshots retained), and cancellation state/reason. The page also includes `pinned_snapshot_count` and `oldest_snapshot_pin_age_us`, a best-effort summary of live invocation-owned redb read snapshots; it does not estimate retained page bytes, cache size, or total memory. `invocations_admitted_total`, `invocation_conflicts_total`, `admin_cancellations_accepted_total`, `admin_cancellations_denied_total`, `invocation_policy_denials_total`, and `invocation_staged_value_bytes_total` are process-local counters that saturate at `u64::MAX` and reset when the process-local registry is recreated. The counters count successful admissions, invocation commits rejected with `CommitError::Conflict`, first cancellation transitions after a durable accepted audit, cancellation requests after a durable `Denied` AUD1 audit, and managed invocation executor requests rejected with explicit `AuthorizationError::Denied`, respectively. The staged-value byte counter adds each successful managed overlay put’s encoded payload length, including replacements; deletes and failed writes add nothing. `invocation_commit_latency_buckets` is a six-element array of noncumulative, process-local saturating counts in this order: `<=1,000us`, `(1,000us,5,000us]`, `(5,000us,10,000us]`, `(10,000us,50,000us]`, `(50,000us,100,000us]`, and `>100,000us`; it records managed commit API calls from entry through return, whether they succeed or fail. Unauthorized, rate-limited, and unaudited late cancellation requests do not increment the denied counter; failed audit commits increment neither cancellation counter. Hidden rows/cells, unavailable relations, malformed requests, and policy evaluation failures do not increment policy denials. The page includes a best-effort `fence_waits` snapshot of at most 16 active DDL or writer waits. Each wait has an opaque `wait_id`, `category` (`writer` or `ddl`), `waited_us`, up to eight table `resource_ids`, and up to eight opaque `blocker_ids`; `resources_truncated` and `blockers_truncated` mark shortened lists, while `fence_waits_truncated` marks omitted wait records. History, counter, and wait fields are sampled on each page and do not use the invocation cursor. The optional `next_cursor` is an opaque lowercase-hex, process-local cursor bound to the administrator and current invocation-registry generation; clients pass it back unchanged. Every page rechecks current administrator authority. A registry change, including write-set usage or transaction admission/release, or process restart can invalidate the cursor, requiring a new first-page request.

Runtime-list operation versions 1–7 preserve their versioned response fields. Version 5 adds the supervisor-process `gateway_result_bytes_relayed_total` count. Version 6 retains that field and adds `gateway_result_bytes_sent_to_clients_total`, supplied by the gateway only on a successful administrator runtime response. It counts result payload bytes after a full TCP frame write, excludes client-frame headers and failed/partial writes, saturates at `u64::MAX`, and resets with the gateway process. A completed socket write does not establish remote application receipt or persistence. Version 7 adds `invocation_redb_write_acquisition_buckets`, a six-count array over the commit-latency bucket ranges. The storage process times managed commit calls immediately around `redb::Database::begin_write()`; this measures acquisition-call latency, including internal setup, rather than a pure lock wait. Calls rejected before reaching that API are excluded. Counts saturate and reset with the storage registry.

`runtime.invocations.own.list` is available to any authenticated control-mode session and accepts `{ "limit": positive_decimal_string, "cursor"?: string }`, with a maximum page size of 128. It returns only the authenticated principal's live invocations, ordered by invocation ID, with `invocation_id`, `state` (`active` or `committing`), `started_at_us`, nullable `deadline_at_us`, and `cancellation_requested`. The response includes `observed_at_us`, `consistency: "best_effort"`, and an optional owner-bound process-local cursor. A change to that owner's invocation entries or phases invalidates the cursor; other owners' changes do not. Terminal outcomes remain available through point status. This page contains no principal, transaction, workload, write-set, or global counters. `prdb-client invocation-list` exposes the page to an authenticated owner; database-administrator authority does not widen this owner-scoped listing.

Operation version 1 retains the established response shape through `invocation_commit_latency_buckets` and `fence_waits`. Version 2 adds `outcome_maintenance_passes_total`, `outcome_maintenance_failures_total`, and `outcomes_pruned_total`, which count bounded durable-outcome pruning calls, failed calls, and removed outcomes. Version 3 adds an identifier-free `supervisor_queue` object with `pending_submissions`, `starting_submissions`, `started_submissions`, `queued_operational_starts`, `queued_analytical_starts`, and `reserved_submission_bytes`. Version 4 adds `oldest_queued_start_wait_us`; version 5 adds the supervisor-process `gateway_result_bytes_relayed_total`; version 6 adds the gateway-process `gateway_result_bytes_sent_to_clients_total`; version 7 adds the storage-process `invocation_redb_write_acquisition_buckets`. This six-count array uses the `invocation_commit_latency_buckets` ranges and measures the managed commit path's elapsed time immediately around `redb::Database::begin_write()`, including API setup rather than only lock wait. Attempts rejected before this call are excluded. Version 8 adds the six-count `operational_start_wait_buckets` and `analytical_start_wait_buckets` arrays to `supervisor_queue`, using the same elapsed-time ranges as the commit latency buckets. These bounded histograms count completed queued starts by workload class and are identifier-free. Each later version retains all earlier fields. Process-local counters saturate at `u64::MAX` and reset with their owning process or registry. Queue counts and reservations are sampled from the supervisor staging registry and contain no principal or invocation IDs. Earlier response shapes remain available to earlier-version requests; unsupported versions are rejected.

Every accepted ADMIN START consumes its connection-owned PREPARE reservation before invoking storage, including when the storage action returns an error before a durable outcome exists. The operation ID cannot be started again; a definitive error closes the connection, so the client reconnects and checks STATUS. Storage may report `unknown` when no outcome was committed or `aborted` when it durably recorded a failed operation. The client may issue a new PREPARE with a new operation ID after confirming the original operation did not commit. A lost or otherwise uncertain START reply is reconciled with STATUS and is never replayed automatically.

`users.create` is a supported identity mutation. PREPARE uses `phase: "prepare"`, `operation_version: 1`, `operation: "users.create"`, and `{ "name": normalized_name }`; names are 1–128 bytes and use lowercase ASCII letters, digits, and underscores, starting with a letter or underscore. START consumes the connection-owned reservation and calls the audited storage identity path, which checks current `MANAGE_USERS`/database-administrator authority and publishes the LOGIN principal and matching user object with its DDL audit and durable outcome in one commit. New users receive no data privileges and no credential; issue a token separately. Success returns the operation ID, committed outcome, generated `user_id`, and commit sequence. The client sends STATUS with the operation ID to reconcile a lost reply. START is never replayed automatically.

`users.create_no_login` uses the same PREPARE/START envelope and `{ "name": normalized_name }` argument, but atomically publishes the user with LOGIN disabled. It applies the same `MANAGE_USERS`/database-administrator check, audit, generated `user_id` response, and durable outcome behavior as `users.create`. The user cannot authenticate or receive a token until a separately authorized LOGIN change succeeds.

`roles.create` uses the same PREPARE/START envelope and normalized `name` argument. START checks current `MANAGE_ROLES`/database-administrator authority and atomically publishes a non-login role principal and matching role object with audit and durable outcome. The role receives no memberships or privileges. Success returns the operation ID, committed outcome, generated `role_id`, and commit sequence.

`schemas.create` uses PREPARE/START with `{ "name": normalized_name, "owner_id": id }`; omitting `owner_id` assigns ownership to the authenticated actor. Names use the normalized lowercase ASCII profile. START requires inherited database-scoped `CREATE_SCHEMA` or database-administrator membership, verifies that the owner is a live user or role, and atomically publishes an empty schema and its owned object with audit and durable outcome. Success returns the operation ID, committed outcome, generated `schema_id`, and commit sequence. Schema ownership does not grant data privileges. `schemas.drop` uses PREPARE/START with `{ "schema_id": id }`; the owner (including inherited membership in an owning role) or a database administrator may drop it. System schemas, schemas with child objects, or schemas with remaining catalog dependencies are rejected. The serialized writer rechecks emptiness before deleting the schema and its object record atomically. Success returns the operation ID, committed outcome, `schema_id`, and commit sequence.

`schemas.set_owner` uses PREPARE/START with `{ "schema_id": id, "owner_id": id }`. The current schema owner or a database administrator may transfer a non-system schema to a live user or role. The owner object and version update atomically; the schema record and its contents remain unchanged. The new schema owner may create tables and manage the schema, but receives no table data privileges. Success returns the operation ID, committed outcome, `schema_id`, `owner_id`, and commit sequence.

`schemas.rename` uses PREPARE/START with `{ "schema_id": id, "name": normalized_name }`. The schema owner or a database administrator may rename a non-system schema. START updates the schema object's name and version while preserving its stable ID and schema contents; final schema-name uniqueness is checked in the serialized writer. Success returns the operation ID, committed outcome, `schema_id`, new `name`, and commit sequence.

`tables.drop` uses PREPARE/START with `{ "table_id": id }`; the table owner (including inherited membership in an owning role) or a database administrator may drop it. Incoming catalog dependencies reject the operation. Storage atomically removes the table and its owned definitions, rows, and physical indexes. The row cleanup limit is 65,536 rows and 64 MiB of row payloads per commit. Success returns the operation ID, committed outcome, `table_id`, and commit sequence.

`foreign_keys.drop` uses PREPARE/START with `{ "foreign_key_id": id }`. The source table owner or a database administrator may remove the constraint. Storage atomically removes the foreign-key definition, object, and target-constraint dependency, advances the source and referenced table write epochs (once for a self-reference), and records the audit and durable outcome. Success returns the operation ID, committed outcome, `foreign_key_id`, and commit sequence.

`foreign_keys.create` version 1 uses PREPARE/START with `{ "source_table_id": id, "source_column_ids": [id, ...], "target_constraint_id": id }`; version 2 adds optional normalized `name`. Source columns are ordered to match the referenced PRIMARY KEY or UNIQUE columns; the array must be non-empty and contain distinct IDs. Storage generates the FK ID, requires source ALTER and target REFERENCES authority, checks types and existing rows under fences on both tables, and atomically publishes the definition, object (retaining the optional name), dependency, audit, outcome, and table write-epoch increments. Duplicate names are rejected after authority checks. Success returns the operation ID, committed outcome, generated `foreign_key_id`, and commit sequence.

`constraints.create_unique` version 1 uses PREPARE/START with `{ "table_id": id, "column_ids": [id, ...] }`; version 2 adds optional normalized `name`. The non-empty, ordered column list must contain distinct IDs. Storage generates the constraint and backing-index IDs, requires table ownership or inherited ALTER, validates/backfills the unique index against persisted rows under the table DDL fence, and atomically publishes the constraint (retaining the optional name), index, dependency, audit, outcome, and table write-epoch increment. Duplicate names are rejected after table authority checks. NULL key tuples follow the UNIQUE NULLS DISTINCT behavior. Success returns the operation ID, committed outcome, generated `constraint_id` and `index_id`, and commit sequence.

`constraints.create_primary_key` version 1 uses PREPARE/START with the same argument shape; version 2 adds optional normalized `name`. All listed columns must already be non-nullable. Storage generates the constraint and backing-index IDs, validates and backfills the owned unique index under the table DDL fence, and atomically publishes the PRIMARY KEY (retaining the optional name) and its catalog dependencies. Duplicate names are rejected after table authority checks. Existing rows that violate the key reject publication with an ABORTED outcome. Success returns the generated `constraint_id` and `index_id` with the commit sequence.

`constraints.create_check` version 1 uses PREPARE/START with `{ "table_id": id, "expression_eir1": lowercase_hex, "dependency_column_ids": [id, ...] }`. Version 2 adds required normalized `name`; named CHECK objects retain it in the catalog, and duplicate table-local names are rejected after table DDL authorization with a durable ABORTED outcome. The EIR1 bytes encode a deterministic row-local expression and are bounded by the control-frame and expression limits. Storage binds its fields and declared dependencies to the table schema, requires a Boolean result, validates persisted rows under the table DDL fence, and atomically publishes the CHECK, expression, dependency edges, audit, outcome, and table write-epoch increment. Success returns `constraint_id`, `expression_id`, and commit sequence. `constraints.drop_check` takes `{ "constraint_id": id }` and atomically removes the CHECK, its expression and dependency edges, and advances the table write epoch.

`constraints.drop_primary_key` and `constraints.drop_unique` use PREPARE/START with `{ "constraint_id": id }`. Storage removes the key constraint and its owned index records and memberships atomically, advances the table write epoch, and rejects removal while a foreign key references the constraint. Success returns the constraint ID and commit sequence.

`indexes.create` uses PREPARE/START with `{ "table_id": id, "name": normalized_name, "column_ids": [id, ...], "unique": boolean }`. The ordered column list is non-empty and distinct. The table owner (including inherited membership in an owning role), a database administrator, or a principal with `INDEX` authority may create the index. START validates authority against current catalog state, backfills rows, checks duplicate keys when `unique` is true, and atomically publishes the index and schema ownership records with audit, outcome, and table write-epoch advance. Success returns the operation ID, committed outcome, generated `index_id`, and commit sequence.

`indexes.rebuild` uses PREPARE/START with `{ "index_id": id, "column_ids": [id, ...], "unique": boolean }`. It applies the same authority rule as index creation, validates old memberships, rebuilds from current rows using the requested ordered columns and uniqueness, then atomically publishes the new definition and memberships while advancing the table write epoch. A request with the same definition is still a rebuild: storage verifies and republishes its memberships, records audit/outcome, and advances the table write epoch. Older snapshots retain their prior definition and memberships. Success returns the operation ID, committed outcome, `index_id`, and commit sequence.

`indexes.drop` uses PREPARE/START with `{ "index_id": id }` and the same authority rule. It atomically removes the index definition, schema ownership records, and both membership directions, and advances the table write epoch. A drop that would leave a dependent constraint invalid is rejected. Success returns the operation ID, committed outcome, `index_id`, and commit sequence.

`tables.drop_column` uses PREPARE/START with `{ "table_id": id, "column_id": id }`; the table owner (including inherited membership in an owning role) or a database administrator may request it. The operation applies RESTRICT semantics to constraints, expressions, indexes, and policies that reference the column. It rewrites stored tuples and surviving index keys atomically, advances the table schema version and write epoch, and removes the column and its owned default expression. The scan is limited to 65,536 rows and 64 MiB of combined old and rewritten tuple payloads. Success returns the operation ID, committed outcome, `table_id`, `column_id`, and commit sequence.

`tables.create` operation version 1 uses PREPARE/START with `{ "schema_id": id, "name": normalized_name, "columns": [...], "primary_key_columns": [name, ...], "unique_constraints": [[name, ...], ...] }`; both key fields are optional. Version 2 adds parallel `foreign_key_source_columns`, `foreign_key_target_constraint_ids`, and `foreign_key_target_columns` arrays. Version 3 adds `check_constraint_names`, aligned with `check_expressions_eir1`; an empty string denotes an unnamed CHECK and a non-empty entry is a normalized catalog name. Version 4 adds `primary_key_name`, `unique_constraint_names`, and `foreign_key_names`; names are normalized catalog names, with empty strings for unnamed constraints, and the arrays align with their corresponding key/FK definitions. All names in one table must be distinct. For each foreign key, the target constraint ID is a nonzero lowercase ID and target-column names are empty for a referenced existing key; a zero ID is permitted only with non-empty same-statement target-column names, which must resolve to a key declared by the new table. Version 1 remains valid for table definitions without self-references and continues to encode external foreign keys with the source-column and target-constraint arrays. Versions 1 and 2 remain valid for unnamed CHECK constraints. Version 4 carries named PRIMARY KEY, UNIQUE, and FOREIGN KEY constraints; version 3 remains valid for CREATE TABLE definitions without those names.  The non-empty `columns` array contains 1–4096 objects with required `name`, `type`, `nullable`, and `generated_uuid_identity` fields; the last two are JSON booleans. An optional `default` is an object: `{ "kind": "literal", "value": "..." }` uses a type-specific canonical string, `{ "kind": "null" }` supplies SQL NULL, and `{ "kind": "current_principal_id" }` supplies the authenticated principal UUID (UUID columns only). Boolean literals are `true`/`false`; integer, date (days from 1970-01-01), and timestamptz (UTC microseconds from 1970-01-01) values are canonical decimal integers; decimal literals have exactly the declared scale; UUID literals are 32 lowercase hex digits; bytea literals are lowercase hex; text and varchar literals are their string contents. A generated UUID identity cannot also have a default. Type strings are `boolean`, `smallint`, `integer`, `bigint`, `decimal(p,s)`, `text`, `varchar(n)`, `bytea`, `uuid`, `date`, or `timestamptz`, with canonical positive decimal parameters. Names are normalized lowercase ASCII identifiers. A supplied primary-key name array is non-empty, ordered, and distinct; each name must identify a declared non-nullable column. The optional `unique_constraints` array contains distinct, non-empty ordered column-name arrays; every name must identify a declared column, and NULL-containing tuples remain distinct. START requires inherited schema `CREATE`, schema ownership (including inherited membership in an owning role), or database-administrator membership, and rejects reserved system schemas. It atomically publishes the table, ordered columns, default expressions, optional PRIMARY KEY/UNIQUE constraints and their owned unique indexes, audit, and durable outcome. New tables receive no data grants. Success returns the operation ID, committed outcome, generated `table_id`, ordered `column_ids`, and commit sequence.

`tables.add_column` uses PREPARE/START with `{ "table_id": id, "column": { "name": normalized_name, "type": type, "nullable": boolean, "generated_uuid_identity": false, "default": ... } }`; `default` is optional and supports typed `literal` or `null` forms, but not `current_principal_id`. A NOT NULL column requires a non-null literal; a nullable column without a default backfills NULL. The table owner or a database administrator may add a column to a non-system table. The operation appends the column, advances schema version and write epoch, rewrites existing rows, and updates index definitions and locators atomically. The rewrite is limited to 65,536 rows and 64 MiB of old and rewritten tuple payloads. Success returns the operation ID, committed outcome, `table_id`, `column_id`, schema version, and commit sequence.

`users.rename` and `roles.rename` use PREPARE/START with `{ "user_id": id, "name": normalized_name }` or `{ "role_id": id, "name": normalized_name }`. START requires the corresponding `MANAGE_USERS` or `MANAGE_ROLES` privilege, or current database-administrator authority. It atomically updates the principal name and authority epoch, matching named object and object version, audit, and durable outcome.

`users.login` uses PREPARE/START with `{ "user_id": id, "enabled": "true" | "false" }`. START requires `MANAGE_USERS` or current database-administrator authority and changes the LOGIN flag and authority epoch atomically. Disabling LOGIN also revokes all outstanding user tokens in the same commit; enabling LOGIN does not restore revoked tokens.

`users.drop` and `roles.drop` use PREPARE/START with `{ "user_id": id }` or `{ "role_id": id }`. START requires the matching management privilege or current database-administrator authority and applies RESTRICT semantics: any remaining catalog dependency rejects the drop. A user drop atomically revokes outstanding credentials, removes the principal and named object, and writes a permanent identity tombstone.

`roles.grant` and `roles.revoke` use the same PREPARE/START envelope with `{ "member_id": id, "role_id": id }` arguments. START checks current membership authority, atomically updates the membership record, matching dependency edge, member authority epoch, audit, and durable outcome. It rejects nonexistent/wrong-kind endpoints, duplicate or missing membership changes, cycles, and changes that would remove the last usable database-administrator credential. Memberships target users or roles and always grant the complete role; no admin option exists.

`privileges.grant` and `privileges.revoke` use PREPARE/START with `{ "grantee_id": id, "privilege": "manage_users" | "manage_roles" | "create_schema" }`. START requires current database-administrator authority and atomically updates the database-scoped system privilege, its matching dependency edge, the grantee's authority epoch, audit, and durable outcome. Grants are rejected if already present; revokes are rejected if absent. The affected grantee must be a live principal.

`objects.grant` and `objects.revoke` use PREPARE/START with the common fields `{ "grantee_id": id, "object_id": id, "privilege": name, "target_scope": scope }`. For `object` or single-column scope, include `target_id`; object scope requires it equal `object_id`. For `target_scope: "columns"`, include `target_ids` containing 2–64 distinct column IDs and omit `target_id`. `target_scope: "all_columns"` takes no target ID and expands table `SELECT`, `INSERT`, `UPDATE`, or `REFERENCES` to every column present when storage processes the operation. The closed lowercase privilege set is `usage`, `select`, `insert`, `update`, `delete`, `references`, `create`, `alter`, `index`, `manage_policies`, and `manage_grants`; object-kind and table/column scope combinations are validated by storage. Column, columns, and all_columns scopes are valid only for table data privileges. START checks current object ownership, inherited `MANAGE_GRANTS`, or database-administrator authority, validates the live grantee and every target column, then atomically changes the complete direct grant set, each authority dependency that changes between first/last grant to a target, the grantee authority epoch once, audit, and durable outcome. Duplicate grants, duplicate target IDs, or any absent revoke reject the whole request without partial publication.

`policies.create` uses PREPARE/START with `table_id`, normalized `name`, `kind` (`row` or `cell`), `policy_operation` (`select`, `insert`, `update`, or `delete`), `effect` (`allow` or `restrict`), `recipients` (a nonempty array of `user:<lowercase-id>` or `role:<lowercase-id>` strings), `target_column_ids` (an ID array), and nullable `using_expression_eir1`/`with_check_expression_eir1` fields. Expressions are canonical EIR1 hex. SELECT/DELETE require USING, INSERT requires WITH CHECK, and UPDATE requires both; cell policies require one or more target columns and reject DELETE, while row policies reject target columns. START revalidates current table schema, recipient principal kinds, column bindings, Boolean expressions, ownership or `MANAGE_POLICIES` authority, and commits the policy, expression, target, dependency, table epoch, audit, and outcome records atomically. Success returns the generated `policy_id` and commit sequence. `policies.replace` accepts the same definition plus `replaced_policy_id`; it atomically removes that same-table policy, including its expressions, targets, and dependencies, then publishes the new definition under one authority recheck and one table epoch advance. It can replace between row and cell kinds. `policies.drop` takes `{ "policy_id": id }`; it removes the policy and its expressions and targets and advances the affected table epoch in one authorized commit. All operations follow PREPARE/START ownership and uncertain START reconciliation rules.

`tokens.revoke` is a supported mutation. PREPARE uses `phase: "prepare"`, `operation_version: 1`, `operation: "tokens.revoke"`, and `{ "token_id": id }` arguments. It reserves one opaque operation ID on the authenticated control connection and returns `{ "operation_id": id, "state": "prepared" }`; it does not look up or revoke the target. START uses `{ "phase": "start", "operation_id": id }` on that same connection. The server revalidates the session, consumes the reservation once, and delegates to the audited storage token-revocation API, which checks `MANAGE_USERS`. Success returns the operation ID, `outcome: "committed"`, and a commit sequence. Unknown, already revoked, and unauthorized targets share the storage operation's non-disclosing failure. Disconnect discards the unstarted reservation; an uncertain start is reconciled with STATUS and is never replayed automatically.

`tokens.issue` uses the same prepare/start ownership rule. PREPARE arguments are `{ "user_id": id, "label": string, "expires_at_us": positive_decimal_string }`; label length is 1–128 UTF-8 bytes. START delegates to the audited storage credential issuance path. Its single success response includes the operation ID, committed outcome, token ID, one-time canonical padded base64 token secret, and commit sequence. The secret is never included in STATUS, later reads, storage records, or audit events. A lost issue response requires explicit revoke/reissue; the server cannot recover the plaintext secret.

PING has `{}` payload and returns `{ "alive": true }`; it is not a health/durability or authorization proof. ERROR has `code` and a sanitized message of at most 256 UTF-8 bytes. Initial code categories: invalid_frame, unsupported_version, unauthenticated, unavailable, invalid_state, invalid_request, resource_limit, cancelled, internal_error. Do not expose raw exceptions, SQL parameters, private names, paths, token details, or competing principals.

ERROR is response kind 101, uses the failed request ID and response sequence zero, and has `{ "code": string, "message": string }`. The gateway closes the client connection after an ERROR response. Its message is selected from fixed public text by category and never copies an internal exception.

`tables.rename` uses PREPARE/START with `{ "table_id": id, "name": normalized_name }`. The table owner or a database administrator may rename a non-system table. START checks the final schema-local name set while serialized, keeps the table ID and tuple schema version, and increments the write epoch and object version. Success returns the operation ID, committed outcome, `table_id`, and commit sequence.

`tables.set_owner` uses PREPARE/START with `{ "table_id": id, "owner_id": id }`. The current table owner or a database administrator may transfer a non-system table to a live user or role. START changes the table object's owner and object version and increments the table write epoch; tuple schema version, rows, indexes, and grants remain unchanged. Ownership permits table-level DDL but grants no data privileges. Success returns the operation ID, committed outcome, `table_id`, `owner_id`, and commit sequence.

`tables.rename_column` uses PREPARE/START with `{ "table_id": id, "column_id": id, "name": normalized_name }`. The table owner or a database administrator may rename a column on a non-system table. START updates the family 6 column name and matching family 2 object name, increments the column object version and table write epoch, and checks final table-local name uniqueness while serialized. Success returns the operation ID, committed outcome, `table_id`, `column_id`, new `name`, and commit sequence.

`tables.alter_column_nullability` uses PREPARE/START with `{ "table_id": id, "column_id": id, "nullable": "true" | "false" }`. The table owner or a database administrator may change nullability on a non-system table. Setting `nullable` to "false" validates persisted rows under the table DDL fence and returns a constraint violation if any value is NULL; setting it to "true" drops the matching internal NOT NULL constraint when present. Success returns the operation ID, committed outcome, table and column IDs, the resulting nullable value, and commit sequence.

`tables.set_column_default` uses PREPARE/START with `{ "table_id": id, "column_id": id, "type": type, "default": { ... } }`. The type and default encoding follow `tables.create`; supported forms are typed `literal`, `null`, and UUID `current_principal_id`. The table owner or a database administrator may set or replace a default on a non-system, non-generated column. Existing rows are unchanged. `tables.drop_column_default` takes only `{ "table_id": id, "column_id": id }` and removes the current default. Both preserve tuple schema version, increment write epoch, and return operation ID, committed outcome, table ID, column ID, and commit sequence. Identical sets and drops of absent defaults fail.

## Validation and Extension

Test partial/coalesced frames, oversized lengths, malformed JSON/base64, duplicate IDs/keys, incorrect sequences, cross-session submissions, revoked credentials between upload/start, slow uploads without snapshot pins, upload substitution, forged worker terminal bytes, reconnect/status, and gateway death around commit. The Linux x86_64 sandbox acceptance path uploads a PMF1/PSC1 package through `SubmissionClient` over TCP, runs it through the gateway service and supervisor IPC, receives provisional SQL output and a committed terminal event, then confirms the durable owner-scoped outcome. Its restricted-principal variant checks that the same invocation's metadata API and confined SQL both expose only the granted empty schema plus public metadata. A separate process-level test kills the gateway after an accepted START, verifies the supervisor durably records ABORTED, stops and restarts the supervisor on the same instance, then retrieves that owner-scoped status through a new gateway. It does not retry START or claim successful execution after disconnect. Test multiple concurrent connections while retaining one stream per connection.

This framing can be implemented behind other transports, or another gateway may map the same admission/result operations to its own transport. Future TLS/HTTP/3 and multiplexing require separate explicit versions/capabilities and equivalent failure semantics. They must not change transaction identity, internal process roles, or the client's prohibition on automatic replay.
