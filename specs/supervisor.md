# Supervisor

## Responsibilities and Trust

Implement the supervisor in Rust. Client network connections terminate in the separate [gateway](client-gateway.md); the supervisor exposes bounded private admission/result IPC, not a public listener. It is trusted to establish execution identity, arrange confinement, provision scoped channels, and manage process lifetimes. It may initially run alongside the storage manager. It must not execute user native code or load client-built query libraries, including for inspection.

The Linux x86_64 `prdb-supervisor` executable owns the READY instance lock and current `StorageManager`, and exposes the service only over a mode-0600 Unix socket restricted by peer UID. It requires an explicit compatibility profile (CPU baseline, runtime profile, SDK release, and dependency allowlist), executor and scratch paths, runtime filesystem allowlists, delegated cgroup parent, worker resource ceilings, and admission limits. The operational cgroup ceiling is required; an optional complete set of analytical CPU, memory, and process-count flags configures a separate analytical ceiling. If omitted, analytical submissions use the operational ceiling. It validates and opens a READY instance before binding. On an ambiguous durable commit error it drops the listener, reopens and revalidates storage while retaining the instance lock, then binds again. Each START callback relays provisional worker output and sends a terminal result only after storage confirms it. The profile and sandbox paths are deployment inputs; this executable does not infer or ship a host runtime profile. Graceful shutdown removes only the exact service socket inode it created; an existing or subsequently replaced path is left untouched.

## Execution Context

Arrange a storage-managed context containing:

- Authenticated principal and invocation-specific grant.
- MVCC data/schema snapshot, private write set, and policy version/context, including policy inputs.
- Opaque invocation/transaction ID for authenticated outcome lookup.
- Deadline, resource budgets, and cancellation state.
- Connection identity and lifecycle ownership.

Identity comes from a trusted admission path, never a worker-supplied user ID. Initial client authentication uses database-issued revocable tokens through the [plaintext TCP gateway](client-protocol.md), with loopback binding by default; bootstrap remains on a restricted local setup socket. Storage validates token state. Gateway-provided principal IDs are not proof of authentication. See [users and roles](ddl-identity.md). Credentials never enter executor parameters or artifacts. Verify login/token state at each admission and record the identity/credential epochs for write-commit validation. Creating a context must not permit authority greater than the admitted caller's permissions.

## Lifecycle

1. Authenticate staging through gateway-service IPC and accept bounded client-built artifact, manifest, and parameter bytes into supervisor-owned storage. Reserve an invocation ID before execution; upload alone creates no MVCC snapshot. Check compatibility, lengths/digests, and seal immutable artifact bytes without loading the library. On explicit START, revalidate authentication and authority before admission.
2. Allocate an invocation context, pinned MVCC snapshot and private write set, effective grant, deadline, and cumulative budgets. Provision separate executor-storage and optimizer-storage channels; the latter has the estimation role.
3. Provision a context-bound executor-to-optimizer submission channel and bounded output channel. The SDK's published definitions do not grant roles or widen the invocation grant.
4. Launch the executor using the Linux sandbox specification before loading query.so or any dependencies. Invoke the user entry point; SDK SQL calls submit structured queries to the optimizer and execute returned plans.
5. Monitor planning, execution, and bounded result output. Relay executor bytes as provisional data to the gateway; only supervisor envelopes backed by storage decisions carry terminal outcomes. No executor output buffer connects directly to the client.
6. On successful library return, stop new worker requests and request atomic commit through the supervisor-only storage control channel. On any statement/execution error, request abort. Finalize resources after storage resolves the transaction and in-flight tasks drain. Report success only after durable commit; partial output is provisional, and a lost reply requires authenticated outcome lookup. Success does not attest to result correctness.

Use a fresh worker per user-library invocation in the prototype. Sequential SDK calls share its MVCC snapshot, private writes, and cumulative budgets; a statement error aborts the whole transaction. After accepted cancellation or disconnect, keep executor channels available for up to 500 ms so a cooperative SDK poll can receive the positive cancellation response and exit; then kill and reap any remaining worker processes. Hard invocation deadlines remain enforced during this grace period. Avoid cross-principal process reuse and inherited storage memory. Sandbox establishment must finish before any untrusted executable, library constructor, or entry point runs.

The initial supervisor staging store is memory-resident and process-local. It reserves declared artifact and parameter sizes before accepting chunks, enforces the protocol maxima of 64 MiB and 1 MiB plus configured global/per-principal quotas, permits one live reservation per authenticated query connection, and caps chunks at 256 KiB with exact contiguous offsets. It retains the requested workload class and deadline with the sealed metadata; the deadline must be positive and no greater than the configured admission ceiling (15 minutes by default). PREPARE creates no storage transaction. SEAL verifies lengths and SHA-256 digests, validates `PSC1` requested scope and `PMF1` manifest v1 against the configured compatibility profile, parses the pinned ELF64 artifact's dynamic dependencies and required ABI exports without loading it, and requires exact agreement between the `DT_NEEDED` and manifest dependency sets. START is one-shot: the caller revalidates authority, then storage intersects the decoded requested scope with current catalog grants in the pinned invocation before launching a worker. Outcome retention is a configured duration converted to an absolute deadline from the trusted clock for each START or ADMIN request; it is not a process-start timestamp. The trusted START callback owns execution and terminal resolution; after it returns, the service releases that invocation's sealed artifact/parameter reservation and quota before servicing another request on the same connection. Disconnect discards pre-start staging and signals started work for cancellation. Unstarted reservations expire after five minutes by default, with a configurable shorter or longer TTL. The gateway service runs the staging reaper each accept-loop iteration, scanning at most 256 reservations per pass and rotating through the ordered reservation set so large stores are eventually covered. It also starts outcome pruning immediately and then every 60 seconds by default, scanning at most 1,024 outcomes per immediate transaction with a durable resume cursor. Storage errors that quarantine the database trigger the normal close/reopen/revalidate cycle; malformed maintenance state stops the service. The store limits live reservations to 1,024 by default.

Staging STATUS is owner-scoped and reports uploading, sealing, prepared, starting, or started state; unknown and foreign IDs share the unavailable response. CANCEL on an unstarted reservation releases its reserved bytes and creates no transaction. If cancellation races with SEAL, the reservation is discarded when bounded validation finishes. Starting or started work uses invocation cancellation through storage.

## Budgets and Failures

Bound CPU, memory, process count, wall time, output bytes, and storage work attributable to the whole invocation, including all sequential SQL and direct storage calls. Worker limits alone do not bound expensive requests handled by storage. Bound planning and statistics estimation independently; user compilation occurs in the client. Cancellation closes planning channels and pending estimates as well as worker resources; private background statistics maintenance has separate admission and budgets.

Reject execution if required sandbox features cannot be established. Worker crashes must fail only that execution; disconnects and supervisor cancellation must trigger storage cleanup. Before redb write-transaction commit begins, required channel loss, cancellation, expired deadlines, and invocation-wide resource exhaustion abort the transaction; they cannot be converted into heuristic planning or a fresh context by user code.

`StagingStore::start_with_sandbox_preflight` probes the configured cgroup parent and rejects a host that lacks any required profile capability before invoking its storage-admission callback. A preflight rejection leaves the sealed reservation prepared and creates no snapshot. `start_with_worker_cgroup` additionally creates and configures the invocation's CPU, memory, and process-limited cgroup before it consumes the one-shot START transition. Capability or cgroup setup failure leaves the sealed reservation prepared and does not call storage admission. Its callback owns the cgroup and remains responsible for installing the other confinement controls and spawning the executor. If the reservation is cancelled while cgroup setup runs, START rechecks ownership and state before invoking the callback; the unused cgroup is dropped. Neither helper is a complete worker launcher or evidence that confinement is active.

`start_and_launch_executor` is the reusable launch orchestration: after cgroup setup it stages the sealed artifact in a private read/execute-only directory, places parameters in a sealed memfd, creates separate planner and executor Unix socket pairs, prepares the Landlock policy and ordered pre-exec hooks, calls the supplied storage-admission callback, and only then spawns `prdb-executor` with the worker endpoints. The executor-aware gateway service routes network START through this path and returns the running process with its storage invocation to the trusted supervisor callback. Admission failure cleans the prepared launch resources; spawn failure returns an error and relies on the admitted transaction owner's drop path to abort. The supervisor observes both storage channels concurrently, relays bounded worker bytes as provisional output, then couples child reaping and cgroup cleanup to `SupervisorInvocation::observe_worker_exit_in_cgroup`; it does not request commit unless observation succeeds. The versioned host table exposes only its scoped planner and executor callbacks; result bytes cannot choose the terminal decision.

If `StorageManager::requires_reopen_after_commit_error` becomes true, `serve_gateway_service_listener` stops accepting connections, joins its per-connection workers so they release manager borrows, drops the listener, and returns `GatewayServiceListenerError::StorageReopenRequired`. `run_gateway_service_with_recovery` owns this lifecycle: it drops the manager, calls `StorageInstance::reopen` while retaining the instance lock, validates the recovered image, builds a fresh manager, and asks the bind callback for a new private listener. The `StorageInstance` keeps its redb handle at a stable address so quarantine state follows it across owner moves and can be cleared for the closed handle only after validation succeeds. A recovery or validation failure leaves the service unavailable; do not replay requests from connections served by the old manager.

## Workload Admission

Assign bounded operational/analytical resource classes under the caller's allowance. Reserve progress for WAL/commit, point reads, cancellation, and reclamation; limit analytical prefetch, cache pollution, snapshot age, and output. Client labels cannot bypass quotas. Follow [workload profile](workload-profile.md) and keep I/O-backend capability fallback separate from fail-closed sandbox requirements.

## Administrative Admission

Route DDL and credential operations from a separate authenticated gateway control-mode connection over the supervisor's administrative service, separate from executor channels. The gateway service role cannot finalize transactions or bypass actor validation. Authorize schema, user/role, and permission actions independently; storage rechecks administrative actor authority at commit. Database role names are not IPC service-role assignments. Support bootstrap, token rotation/revocation, user disable, and protected outcome lookup as defined in identity DDL.

## Startup and Operational Metadata

Do not admit invocations before storage completes [bootstrap/recovery validation](catalog-lifecycle.md) and publishes READY. Runtime construction through `StorageManager` repeats the recovered-image integrity validation before it opens an admission path. This integrity check is not client authentication. Coordinate offline upgrade admission/drain requirements without loading user code during migration.

Expose own-invocation status and administrator-only runtime inspection through [operational metadata](operational-metadata.md). Reconcile lost replies against [durable outcome records](physical-metadata.md); absence of a live executor does not prove rollback. Required administrative audit records/outbox entries commit with their state changes, while optional telemetry cannot reverse a durable data commit.

## Concurrency and Outcome Races

Admit multiple invocations concurrently with global and per-principal limits, bounded queues, and fairness between scans, writes, and planning. Bound transaction age and retained history; abort rather than silently refreshing old snapshots. Do not hold storage locks while waiting on worker output.

Cancellation accepted before redb commit begins aborts; after commit begins it may be too late and requires outcome reconciliation. Durable commits cannot be undone. Never report rollback merely because a reply or supervisor connection was lost. Use the state machine and recovery/status contract in [concurrency and MVCC](concurrency-mvcc.md). No automatic replay of arbitrary user code is permitted.

## Validation and Open Questions

Test launch failures, timeout, client/gateway disconnect, slow network output, forged worker terminal messages, upload revocation before START, worker descendants, cancellation during an outstanding read, output flooding, and cleanup after planner failure.

Open choices: authentication wire/cryptographic details, deployment privileges and packaged runtime profile, and whether supervisor/storage separation is needed after the prototype.
