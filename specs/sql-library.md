# SDK Basic SQL Library

## Requirement and Placement

The SQL SDK includes a reusable basic SQL implementation that query code can call. The client uses its persistent per-instance SDK release selection and a matching local `libprdb_sql.so.<release>` to link `query.so`; it uploads only `query.so`, its manifest, and the ordinary scope/parameter data. It does not upload an SDK library with each query. The database administrator installs compatible shared libraries in the instance [SDK library repository](sdk-library-repository.md). At START the supervisor resolves the exact release declared by the query manifest and stages that immutable repository library beside query.so in the private worker artifact directory. The query's exact `$ORIGIN` RUNPATH resolves this dependency. Only the executor loads either library and only after confinement; neither supervisor nor storage loads native SDK code. The repository digest and ELF metadata protect repository integrity and compatibility, not code safety. Treat the SQL library, constructors, and query library as compromised code running under the same worker sandbox. SQL remains SDK functionality rather than trusted storage code or a separate server-selected query entry point. Expose a versioned C API; Rust engine services validate requests independently.

The library implements SQL parsing, expression semantics, and physical-plan execution. The separate planner/optimizer selects physical plans using authorized metadata and scoped estimates. This preserves the existing optimizer process boundary while keeping the SQL frontend and execution runtime in the library.

## Proposed Initial SQL Subset

Support a single-table read/write subset from the initial implementation:

- `SELECT` with explicit columns, literals, and aliases, including filtered built-in `information_schema` relations defined in [metadata discovery](metadata-discovery.md).
- `FROM` naming one authorized table.
- `WHERE` with supported comparisons, Boolean operators, and `IS NULL`.
- Typed parameters and `LIMIT` for reads.
- `INSERT ... VALUES`, `UPDATE ... SET ... WHERE`, and `DELETE ... WHERE` with the same bounded expression subset.
- Generated identities and explicitly writable user-supplied keys, subject to schema constraints and permission policies.

For example: `SELECT name FROM employees WHERE department_id = $1 LIMIT 100`.

[Schema DDL](ddl-schema.md) defines initial scalar types and identifier rules. ABI v1 is the first deliberately narrow parser slice; the separately versioned APIs below add the required analytical operators and define their current expression, coercion, and wire behavior. Reject syntax not listed for a specific version. General subqueries, explicit transaction-control statements, and user-defined SQL functions remain deferred. Schema/user/permission DDL is supported through the separate administrative SDK channel and is rejected inside user invocations. `AdminClient::execute_create_table_sql` parses one bounded CREATE TABLE subset locally and translates it to the existing typed control request; SQL text is not sent to the query gateway or trusted storage.

SQL ABI v1 accepts this deliberately narrow grammar:

```text
select       := SELECT projection FROM identifier
                [WHERE predicate]
                [LIMIT unsigned_integer] [;]
projection   := * | identifier (',' identifier)*
comparison   := '=' | '!=' | '<>' | '<' | '<=' | '>' | '>='
predicate   := identifier comparison parameter
             | identifier IS [NOT] NULL
parameter    := '$' unsigned_integer
identifier   := ASCII letter or '_' followed by ASCII letters, digits, or '_'
```

Keywords are case-insensitive; identifier spelling is preserved as source bytes for later binding. Whitespace is ASCII space, tab, CR, or LF. SQL input is bounded to 65,536 bytes, each identifier to 128 bytes, projection to 64 columns, parameter indices to 1–65,535, and LIMIT to 0–1,000,000. LIMIT 0 is valid. ABI v1 accepts at most one predicate. Comparison predicates take only a positional parameter on the right side; `IS [NOT] NULL` predicates take no parameter. Parameter values are bound separately. Comments, quoted identifiers, aliases, schema qualification, literals, Boolean combinations, multiple statements, and other statement kinds are rejected (a non-SELECT statement reports UNSUPPORTED). The AST stores source offsets/lengths into the caller-owned immutable SQL buffer and allocates no strings. The predicate operator field uses `PRDB_SDK_SQL_COMPARE_IS_NULL` or `PRDB_SDK_SQL_COMPARE_IS_NOT_NULL` for null tests, and leaves `parameter_index` zero for them; those codes are predicate operators and are not valid inputs to the scalar comparison evaluator.

SQL ABI v2 adds a separate sized `prdb_sdk_select_v2` record without changing v1 layouts. Its predicate grammar is `OR := AND (OR AND)*`, `AND := unary (AND unary)*`, `unary := NOT unary | primary`, and `primary := '(' OR ')' | predicate`; each predicate is one comparison against `$n` or `IS [NOT] NULL`. AND binds more tightly than OR; unary NOT binds most tightly, and parentheses override precedence. The AST stores nodes in postorder with zero-based child indices and a root index, and preserves each predicate column as a borrowed SQL source span. At most 64 nodes and 32 levels of NOT/parenthesis nesting are accepted. The parser returns `LIMIT_EXCEEDED` when either bound is exceeded.

The initial DML parser supports `INSERT INTO relation VALUES (value, ...)`, `UPDATE relation SET column = value [, ...] WHERE predicate`, and `DELETE FROM relation WHERE predicate`, each with an optional final semicolon. INSERT values are a one-based typed parameter `$n`, `NULL`, or `DEFAULT`; positional values follow declared schema order and must contain exactly one entry per declared column when executed. The separately versioned INSERT v3 parser also accepts an explicit list of unique column names; its VALUES width must equal that list, and execution supplies DEFAULT for omitted columns. UPDATE values are `$n` or `NULL`, the mandatory WHERE clause uses the bounded v2 predicate grammar, and at most 64 unique case-insensitive assignment columns are accepted. DELETE also requires a WHERE clause and uses that same bounded predicate grammar. Literals, expressions in SET, UPDATE DEFAULT, UPDATE/DELETE without WHERE, and RETURNING are rejected. INSERT v1 remains single-row-only, and INSERT v2 retains its schema-order grammar; the v2 executor additively accepts the v3 column-list AST while preserving positional behavior. The sized ASTs store source spans and up to 4,096 INSERT cells or 64 UPDATE assignments into caller-owned SQL bytes. They write output only on success, reject trailing statements, and use the shared 65,536-byte SQL and 1–65,535 parameter-index bounds. Parameter type and Decimal metadata validation, full-shape checking, and mutation execution remain separate operations.

`prdb_sdk_planner_decode_relation_v1` decodes the planner's version-1 `describe_relation` response into a borrowed relation description and a column shape accepted by `prdb_sdk_sql_bind_select_v2`. It validates response framing, identifiers, column order, type parameters, and the planner-only handle kind; unavailable relations are reported without distinguishing hidden from absent. The handle remains planner-only. The SQL client must resolve the relation again on its executor connection and must not pass the planner handle to storage.

`prdb_sdk_planner_describe_relation_v1` submits the qualified schema and relation names through host operation `0x1201`, then decodes the response with that same validator. It uses the invocation's planner channel and keeps the resulting kind-9 handle scoped to planner work. The explicit schema follows the same admitted-schema requirement as executor resolution.

`prdb_sdk_executor_v1.h` provides bounded host-callback helpers for executor `resolve_relation`, `open_scan`, `next_batch`, `close_cursor`, and `check_cancelled`. Resolve takes separate explicit schema and relation identifiers, validates the executor response using handle kind 6, and returns a declared column shape suitable for SQL binding. The schema argument must come from the invocation's admitted schema context; the executor helper does not invent a default schema. Open requests the full declared shape, next validates the returned batch and continuation cursor, and close validates its acknowledgement. `prdb_sdk_executor_check_cancelled_v1` reports cancellation or deadline expiry. SQL scan runners poll before each batch and fail the statement without publishing partial results when storage reports cancellation.

`prdb_sdk_optimizer_decode_plan_v1` in [`prdb_sdk_optimizer_plan_v1.h`](../engine/include/prdb_sdk_optimizer_plan_v1.h) independently decodes optimizer plan v1 for the initial `Scan -> Project -> optional Limit` pipeline. `prdb_sdk_optimizer_decode_plan_with_filter_v1` additionally accepts the optional Filter node after validating its bounded prefix tree, references against scan columns, compatible comparison types, Boolean operators, and Boolean root. Both validate nonzero schema/relation/column IDs and epochs, identifier and scalar-type encodings, sorted unique scan columns, projection membership, node order, bounds, and complete consumption. Relation names and the validated raw predicate borrow the encoded plan; fixed-size scan and projection records are copied into the output. The decoded logical IDs do not authorize access; the SQL library must resolve the relation again through executor storage before using it. Executor IPC operation `resolve_plan_relation` (`0x1105`) returns the invocation-pinned authorized identity and declared shape without granting access. `prdb_sdk_optimizer_validate_executor_relation_v1` independently decodes the plan, asks executor storage for that identity, and checks schema/relation IDs, versions, epochs, relation name, and every scanned column definition. `prdb_sdk_optimizer_validate_select_plan_v1` also checks that relation, projection names/order, and LIMIT match the submitted SELECT AST. `prdb_sdk_optimizer_acquire_plan_relation_v1` performs stable identity checks before resolving an ordinary executor handle. `prdb_sdk_optimizer_open_plan_scan_v1` uses the checked handle to open a full scan and treats `LIMIT 0` as an empty result without opening a cursor. The plan batch consumer evaluates a validated Filter prefix tree against scanned cells using the shared SQL comparison and three-valued truth helpers before applying projection and LIMIT; false and UNKNOWN rows do not count toward LIMIT. Projected values borrow the current batch only during the callback. `prdb_sdk_optimizer_execute_unfiltered_plan_v1` drives unfiltered or filtered scans for at most 125 pages so two requests per page plus SQL-plan verification, setup, and an early cursor close fit the 256-request executor stream budget, polls cancellation between pages, stops at LIMIT, and closes an early cursor. `prdb_sdk_optimizer_execute_select_ast_v1` connects a parsed SELECT AST to ABI v4 optimizer submission and this executor runner. `prdb_sdk_optimizer_execute_select_ast_to_result_v1` emits each projected row as one provisional SQLR v1 record. The compatibility encoder without parameters returns unsupported for predicates. `prdb_sdk_optimizer_encode_select_with_parameters_v1` serializes bounded parameterized comparisons, direct-column IS [NOT] NULL tests, and Boolean AND/OR/NOT trees; unsupported parameter types return unsupported. The parameterized SQL AST bridge submits supported WHERE comparisons, null tests, and Boolean AND/OR/NOT trees, then validates the returned Filter, column identity, operator, and parameter values against the original AST before execution. Unsupported value types stay on the established SQL path. Direct plan execution evaluates bounded Filter nodes; optimizer/plan/execution failures latch statement failure.

`prdb_sdk_sql_execute_select_v2` requires the version-3 host ABI. It composes parsing, planner description, independent executor resolution, shape comparison, SQL binding, typed parameter validation, authorized full-shape scan pages, bound predicate evaluation, LIMIT, and cursor cleanup. It uses bounded caller-owned response and scratch buffers and returns each matching sanitized source row synchronously to a callback with its projection binding. Row bytes expire when the callback returns. The runner shares a 126-page scan ceiling between cancellation checks and batch fetches. After scan completion and cursor cleanup it polls cancellation once more, including when the terminal batch produced no matching rows. At the page limit it fails before another check or fetch and closes the active cursor; resolve/open, 126 check/fetch pairs, and close use at most 255 executor requests. On a normally completed 126-page scan, the final poll also keeps the total at 255. Every nonzero status, including a result-callback failure after provisional rows were delivered, invokes the trusted host's sticky statement-failure callback. The executor forces a failing process exit after the query entry point returns, even if C code catches the SQL status, so the supervisor aborts the invocation.

`prdb_sdk_sql_run_batch_v1` accepts a bounded list of statement slices produced by a SQL lexer/parser and invokes a caller-supplied statement runner in order under the same host invocation. It does not split SQL text on semicolons. A package is limited to 64 statements, 1 MiB per SQL slice, 1 MiB per parameter block, and 64 MiB cumulative SQL and parameter bytes. Result callbacks are framed as SQLB v1 records with event (`START`, `DATA`, `COMPLETE`, or `FAILED`), zero-based statement ordinal, and payload length; DATA payload bytes carry the existing SQL result records. If an execution or result callback fails, the batch latches statement failure and stops before later statements, so the enclosing query package must abort. `client_sql::generate_query_batch_source` uses the interactive SQL lexer to produce a bounded C wrapper with numeric SQL byte arrays. Its statement runner calls `prdb_sdk_sql_run_statement_v1`, which dispatches row SELECT, single-key and composite grouped SELECT, v8 single-key INNER JOIN, v20 alias-aware filtered INNER JOIN, INSERT v3, UPDATE v1, and DELETE v1 forms to their bounded SDK execution APIs; grouped and joined SELECTs emit the corresponding SQLR result shape. Transaction control and DDL remain outside query packages. The trusted client lexer determines statement boundaries, while SDK parsers and storage authorization remain authoritative for SQL validity and permissions.

`prdb_sdk_sql_execute_insert_v1` executes the initial single-row INSERT grammar through the version-3 host ABI. It independently obtains planner and executor relation descriptions, requires matching relation IDs/names/declared column shapes, requires one input per declared column, binds each parameter to the exact declared scalar type and Decimal precision/scale, then calls the executor's bounded `stage_insert` bridge. NULL and DEFAULT pass through as distinct states for storage to validate and materialize. The returned row handle is provisional and connection-local. Every failure after valid host setup invokes the sticky statement-failure callback, so a query library cannot catch a later error and commit the invocation. This function uses caller-owned response, request, shape, and insert-value buffers; callers must keep them valid and non-overlapping for the call.

`prdb_sdk_sql_parse_insert_v2` adds `INSERT INTO relation VALUES (...), (...), ...` while preserving the v1 record and parser behavior. It accepts 1–127 rows, requires the same positive number of schema-order cells per row, and caps the flattened AST at 4,096 cells. `prdb_sdk_sql_parse_insert_v3` preserves that row/value grammar and adds an optional unique, case-insensitive explicit column list, represented by source spans in its own versioned AST. `prdb_sdk_sql_execute_insert_v2` consumes the v3 AST, validates planner and executor relation shapes, maps listed names against the resolved executor shape, rejects missing/duplicate/unknown names and mismatched widths, and initializes omitted fields as DEFAULT before binding listed values. Storage therefore materializes declared defaults, implicit NULL, or generated identities using its normal trusted path. It polls cancellation before each row and stages rows sequentially in the same invocation overlay. The 127-row cap keeps resolve, per-row cancellation checks, and per-row staging within 255 executor requests. A failure latches statement failure, which aborts the invocation and all earlier private row stages; `inserted_count_out` is published only after every stage succeeds. No per-statement commit occurs.

`prdb_sdk_sql_execute_update_v1` executes bounded UPDATE statements through the version-3 host ABI. It validates planner and executor shapes independently, binds unique SET ordinals and typed values, validates predicate parameters before scanning, evaluates the WHERE tree on sanitized full-shape rows, and materializes up to 128 matching row handles in caller storage. It closes any live scan cursor before staging a patch set for each target. Exceeding target or request budgets fails the statement before staging; a storage error during staging latches failure, so any earlier private patches are discarded when the invocation aborts. The function reports a provisional updated-row count. Its supported SET values are only parameters or NULL, and its predicates use the existing bounded comparison/NULL subset. The enabled `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` acceptance verifies UPDATE against live executor/storage processes, including visibility of a staged update to a following SELECT.

`prdb_sdk_sql_execute_delete_v1` runs the mandatory-WHERE DELETE subset through the same version-3 host boundary. It independently checks planner and executor relation shapes, binds and validates predicate parameters, scans authorized full-shape batches, evaluates the predicate on sanitized rows, and materializes at most the caller's target capacity (maximum 128) of opaque handles. It closes a live scan before staging any delete. Exceeding the materialization or 256-request connection budget fails before deletion; a staging failure latches failure so the invocation aborts any earlier private deletes. The reported deleted-row count is provisional. The enabled delegated-cgroup sandbox acceptance verifies DELETE against live executor/storage processes, including that a following SELECT sees no deleted rows; its final durable COMMITTED outcome is also checked after terminal delivery fails.

`prdb_sdk_sql_bind_select_v2` binds the v2 AST against one already-resolved authorized relation name and its declared column shape. Unquoted relation and column names match case-insensitively by ASCII folding to lowercase, as defined by schema DDL. The binding result maps explicit projection names and predicate leaves to zero-based column ordinals and carries each predicate column's type and Decimal precision/scale, plus the declared relation column count. `SELECT *` retains a star marker and no explicit ordinal list. Missing and ambiguous referenced columns fail the bind; malformed type metadata fails closed. Relation resolution, including the admitted default schema and hidden-versus-absent behavior, occurs before this helper. The binding is descriptive metadata only and grants no row access.

## Scalar Comparison Semantics

The C SDK's initial scalar evaluator follows the trusted policy evaluator's type and ordering rules. VALUE comparisons require identical scalar type codes; Decimal additionally requires equal declared scales, which the binder obtains from the pinned column/parameter types. Since NULL and REDACTED value views carry no type code, static type compatibility must be checked by the binder before evaluation. Fixed-width signed scalars compare as signed two's-complement values. Text and Varchar compare lexicographically by Unicode scalar value (equivalent to bytewise order for valid UTF-8), Bytea and Uuid compare lexicographically by bytes, and Boolean orders FALSE before TRUE. Numeric coercions, mixed Text/Varchar comparison, and collation-specific ordering are not implicit.

Comparison with SQL NULL yields UNKNOWN. REDACTED is not SQL NULL: any comparison or `IS NULL` requiring a REDACTED operand returns an evaluation error. `IS NULL` returns TRUE only for NULL and FALSE for VALUE. Boolean AND/OR/NOT use SQL three-valued truth tables; evaluation is left to right and short-circuits only on decisive FALSE for AND or TRUE for OR. Once a reached operand is REDACTED or malformed, evaluation fails rather than treating it as UNKNOWN. These rules do not authorize filtering hidden storage data: SQL operates only on sanitized executor batches.

The C SDK provides scalar comparison, `IS NULL`, Boolean-to-truth conversion, and pure AND/OR/NOT truth-table helpers in [`prdb_sdk_sql_v1.h`](../engine/include/prdb_sdk_sql_v1.h). `prdb_sdk_sql_eval_select_predicate_v1` connects one v1 parsed predicate to a sanitized row-cell view and, for comparisons, its separately bound parameter view. It checks VALUE types against the resolved column type, applies the declared Decimal scale, returns SQL truth values including UNKNOWN for NULL comparisons, and propagates REDACTED errors. V2 `prdb_sdk_sql_eval_select_predicate_v2` traverses the bounded v2 tree left to right, resolving reached leaves by source span through the caller callback. `prdb_sdk_sql_eval_bound_select_predicate_v2` instead consumes a successful v2 binding and asks its callback for the bound zero-based column ordinal; type and Decimal metadata come from that binding. `prdb_sdk_sql_eval_bound_select_row_v2` indexes one complete-shape row from an already decoded executor batch into caller-provided bounded scratch, then evaluates through the binding. Both evaluators skip the right branch of AND after FALSE and OR after TRUE; UNKNOWN requires evaluating the right branch. They validate the predicate tree before invoking callbacks and return callback errors unchanged. Storage must independently validate handles and enforce row and cell authorization for each batch access.

The first typed-parameter binding helper takes the parsed SELECT record, a caller-owned one-based array of `prdb_sdk_value_v1` views, and the resolved column type (plus Decimal precision and scale when applicable). Decimal metadata must satisfy `1 <= p <= 38` and `0 <= s <= p`; a value's signed coefficient magnitude must not exceed `10^p - 1`. It selects the AST's `$n` entry, validates its record and bytes, rejects REDACTED values and type mismatches, and returns a borrowed copy of the selected view. SQL NULL is accepted and retains the expected type only in the binder context; the value record itself carries no type for NULL. No implicit coercions occur. The parameter array and underlying bytes remain caller-owned and immutable for the call and any later evaluation.

## Query Flow

1. The client builds query.so with the SDK and submits the artifact plus parameters. The supervisor creates its context and launches the confined executor.
2. The host invokes the user library entry point with host services and parameters. User code calls the SDK SQL API with SQL text and typed parameters; calls may be computed at runtime.
3. The library parses the request into a bounded structured representation and sends it through a host-provided planning submission channel.
4. The isolated planner validates the representation, resolves authorized schema/types, and constructs a physical plan using its own scoped statistics channel.
5. The library validates the returned plan format, resolves logical relation/schema references on its own storage channel, and executes supported operators using host-provided storage callbacks over scoped IPC. Optimizer-local handles are never reusable executor capabilities.
6. The SQL library returns result batches/errors to user code, which may process authorized values and emit results through bounded host callbacks. The invocation reports an explicit completion/error outcome.

Interpret SQL physical plans initially. The enclosing user query library is already native code compiled by the client; this does not require the server to compile SQL plans. Server-side native plan generation is outside the baseline. Keep parameter values bound to execution; they cannot modify identity or grants.

## Operational and Analytical Execution

Favor low-overhead point/range operations and small writes. Analytical operators consume borrowed authorized columnar transport batches from the row-oriented storage engine; no raw page or private-statistics access is implied. Bound hash/sort/aggregation memory and fail explicitly when budgets are exceeded until a secure scratch/spill design exists. Validate SQL null, overflow, and redaction behavior before each new operator is enabled; COUNT(*) covers visible rows only.

The first sort primitive orders at most 128 already-authorized row keys by one declared scalar column. NULL sorts first in both ascending and descending order; equal values retain input order. A REDACTED key is an evaluation error, and invalid or mismatched typed values fail rather than being omitted. The helper returns only a stable permutation of caller row indexes, writes no partial permutation on failure, and performs no allocation. SQL `ORDER BY` must apply this ordering before `LIMIT`; parsing and row materialization are separate increments.

The bounded grouping kernel accepts at most 128 already-authorized values for one declared scalar key and computes stable `COUNT(*)` groups. Equal typed values share a group, all NULL keys form one group, and group output order follows each key's first input row. A REDACTED grouping key is an evaluation error; malformed or mismatched values fail without publishing partial groups. The v4 SELECT runner scans the authorized relation, evaluates `WHERE`, and retains at most 128 matching keys and 1 MiB of copied key bytes in caller-owned memory. It closes the scan before emitting groups, counts every matching visible row (including rows with NULL keys), and applies `LIMIT` to stable group output. Scan, filter, key-buffer, or grouping errors fail before any group callback; a callback error fails the statement and may follow earlier callbacks. A zero limit binds the relation but skips the scan.

The `prdb_sdk_sql_group_count_composite_v1` operator primitive groups up to 128 already-authorized row-major key tuples with one to eight columns. Each column supplies its own declared scalar type and Decimal scale. Tuples match only when every component compares equal; NULL components compare equal to NULL, and a NULL/non-NULL pair differs. Groups remain in first-seen order. REDACTED, malformed, or mismatched cells and insufficient output capacity fail without changing caller outputs. The v13 runner below supplies packed tuples to this kernel; the v13 SQLR writer emits all bound group-key fields and the selected aggregate in one result record.

The bounded `prdb_sdk_sql_minmax_v1` kernel computes MIN or MAX over at most 128 authorized typed scalar values using the shared exact comparator. It supports the declared scalar types, including Decimal at the caller-supplied declared scale; NULL inputs are ignored, while empty or all-NULL input returns a canonical NULL value view. Any REDACTED, malformed, or mismatched operand fails without changing the output view, even if another value would determine the extremum. Ties keep the first input representation.

The bounded `prdb_sdk_sql_sum_v1` kernel accepts at most 128 authorized SMALLINT, INTEGER, BIGINT, or DECIMAL values of one declared type. Integer inputs produce BIGINT; DECIMAL(p,s) inputs produce DECIMAL(38,s). Each non-NULL Decimal coefficient must fit the declared input precision. NULLs are ignored; empty or all-NULL input returns canonical NULL. REDACTED, malformed, or mismatched operands fail the operation. Accumulation is exact within the bounded input count, and NUMERIC_OVERFLOW is reported only when the final sum is outside the result type's range, so intermediate cancellation does not depend on row order. The output view and its caller-owned bytes remain unchanged on failure. This kernel is an operator primitive; grouped SUM parsing, execution, and SQLR encoding remain separate work.

The bounded `prdb_sdk_sql_avg_v1` kernel accepts the same 128-row numeric input set and null/redaction rules. It returns DECIMAL(38,r). Integer inputs use `r=6`; DECIMAL(p,s) inputs use `r=min(max(6,s+6),38-(p-s))`, reserving enough integer digits to represent the input type's range. The exact rational average is rounded to nearest with ties to even at scale `r`. Empty/all-NULL input returns canonical NULL and still reports the derived result scale. Accumulation and scaled division use fixed-width caller-independent scratch sized for the input cap; output value, bytes, and scale remain untouched on failure.

The bounded `prdb_sdk_sql_inner_join_pairs_v1` operator primitive receives two arrays of already-authorized scalar join keys and returns stable left-major `(left_row,right_row)` pairs for equal, non-NULL values. Both inputs use the same declared scalar type; Decimal inputs must have the same declared scale, matching the current SQL scalar comparator. REDACTED, malformed, or mismatched keys fail the operation. Each input is limited to 128 rows and the output to at most 16,384 pairs. The primitive preflights all comparisons and required output capacity before writing any pair. The separately versioned v8 parser, binder, runner, and SQLR result writer below use this primitive for single-key `INNER JOIN` execution; later versions add composite keys, aliases, self-joins, and filtered joins.

The separately versioned `prdb_sdk_sql_inner_join_pairs_composite_v2` operator receives row-major tuples with two to eight equality keys. Each key position has one shared declared type and Decimal scale for both inputs. A row pair matches only when every component compares TRUE; any NULL component prevents a match. All supplied cells are validated, so REDACTED, malformed, or type-mismatched join operands fail even if another component is NULL. It keeps the v1 limits of 128 rows per side and 16,384 result pairs, preserves stable left-major order, and writes neither pairs nor the output count until comparison and capacity validation succeeds.

The separately versioned v8 parser and binder accept qualified projections from two named relations with one `INNER JOIN ... ON left.key = right.key` predicate and optional LIMIT. The join condition must qualify its first key with the first relation and its second key with the joined relation. Projection and join-key references bind against two independently supplied relation shapes. Join keys must have the same declared type and Decimal scale. `prdb_sdk_sql_execute_inner_join_v8` obtains planner and executor descriptions independently for both relations, verifies each pair of shapes, and scans the two authorized relations sequentially. It shares a 121-page ceiling across both scans, polling cancellation before each batch; reaching the page ceiling fails before another fetch and closes the active cursor. It retains at most 128 rows per side and at most 1 MiB of copied join-key and projected-value bytes; it closes both scans before matching or emitting joined rows. After pair generation it polls cancellation before the first callback, including when there are no matching pairs, and then polls every 2,048 output pairs. At 121 full pages and the maximum 16,384 pairs, setup, scans, the pre-output poll, and output polls use at most 254 executor requests within the 256-request ceiling. The bounded inner-join kernel determines stable left-major match order, NULL keys do not match, and REDACTED join keys fail before callbacks. LIMIT applies to joined rows. Callback failure latches statement failure, so provisional rows must be discarded with the invocation. `prdb_sdk_sql_encode_join_result_v1` and its writer encode the callback's projected values as one SQLR v1 record, using the bound side and ordinal to recover each declared column's name and type metadata. Projection order and duplicate names are preserved, as are VALUE, NULL, and REDACTED states; VALUE type mismatches and invalid bindings fail with zero reported output length. The writer emits host-sized provisional chunks. The maintained confined acceptance executes the v8 runner and the v19 aliased composite and self-join runners against SELECT-authorized relations in one invocation and verifies the relayed SQLR frames before durable commit. The v8 parser and runner continue to reject aliased syntax; v19 adds the separately versioned alias parser, binder, and runner. Self-joins require distinct aliases; WHERE and outer joins remain unsupported.

The separately versioned v16 parser and binder accept two to eight qualified INNER JOIN equality predicates joined by `AND`, with the same two-relation qualified projection form and optional LIMIT. Every left operand must bind to the first relation and every right operand to the joined relation; each pair must have matching scalar type and Decimal scale. The v16 runner independently describes and resolves both authorized relations, verifies planner/executor shape agreement, scans and closes each side sequentially, retains at most 128 rows per side and 1 MiB of copied join-key and projected-value bytes, then evaluates row-major tuples with the composite join kernel. It closes both scans before callbacks, preserves stable left-major results, and applies LIMIT after matching. The runner shares a 121-page ceiling across both scans; each page polls cancellation before fetching. After pair evaluation, it polls before the first callback and every 2,048 emitted pairs. Its own resolve/open/close, scan, and cancellation requests stay within the executor's 256-request ceiling; reaching the page limit fails the statement before another batch request. Cancellation or another error during callbacks may follow provisional output and fails the statement. The runner returns the embedded v8 binding to callbacks, so the v8 SQLR writer encodes the qualified projections without changing result wire format. The maintained confined fixture exercises a two-key join and checks the emitted SQLR rows. V8's parser, AST, binder, runner, and result APIs remain frozen.

The initial grouped SELECT grammar is `SELECT key, COUNT(*) FROM relation [WHERE predicate] GROUP BY key [LIMIT n]`. Its v4 AST preserves the v1–v3 records and stores the group-key span and COUNT(*) marker; binding resolves the key against the complete relation shape. The grouping key must be the only non-aggregate projection and must match the sole GROUP BY key case-insensitively. The v4 runner reports each bound key and `COUNT(*)` through a synchronous group callback. It scans at most 124 pages: each page uses one cancellation check and one batch request, then a final poll after scan completion and cursor cleanup checks cancellation raised during the terminal batch even when WHERE leaves no groups. Callback output also checks cancellation before the first group and every 32 emitted groups before publishing the next. At 124 full pages with four output polls, the final scan poll keeps the maximum within 255 executor requests of the 256-request budget; the page-limit path closes an early cursor within the same budget. `prdb_sdk_sql_encode_group_count_result_v1` writes a standalone SQLR v1 record with the declared group-key name/type followed by a `count` BIGINT field; the positive count uses canonical eight-byte big-endian value bytes. NULL group keys retain their declared type and NULL state. ## Metadata Queries

Treat the fixed `information_schema` relations as read-only virtual storage scans. `prdb_sdk_sql_execute_select_v2` receives the admitted schema separately from the unqualified relation in the SQL text, so a metadata query supplies `information_schema` as that schema and names `schemata`, `tables`, or `columns` in `FROM`. The Rust storage manager filters metadata before sending rows; the C SDK evaluates SQL predicates only over those authorized rows and cannot broaden discovery. These scans share the invocation catalog snapshot and do not expose private definitions, credential records, or live operational state. General user-created SQL views remain deferred.

## Transactional Execution

All statements participate in the invocation's storage-managed MVCC transaction. Reads see the committed snapshot plus successful prior writes. Mutation plans use a fixed statement input view; close the prior result stream before starting another statement. Initially materialize a bounded target/value list, close the mutation input scan, then stage writes so the scan cannot revisit its own updates. Exceeding the budget aborts the invocation. Storage independently validates every row and cell and keeps all changes private until commit.

Any SQL/storage error aborts the invocation transaction in the baseline; catching an SDK error cannot make earlier writes committable. No savepoints or per-statement autocommit. Successful library return asks the supervisor to finalize, but only storage can decide commit. Mutation counts and result batches are provisional until durable commit. General `RETURNING` remains deferred. Storage enforces the constraints defined in schema DDL, including commit-time unique and foreign-key validation.

## Authorization and Results

Execute against the authorized view: invisible rows are absent and cells are `VALUE`, `NULL`, or `REDACTED`. Projection may return redaction markers. Supported predicates requiring redacted inputs fail rather than treating redaction as null or false. SQL null logic remains distinct from redaction. Define evaluation order and error behavior before optimization rules are added.

SQL result encoding must preserve redaction as a distinct state. User code must treat statement batches as provisional until statement success, because an error may arise after partial output. A statement error invalidates its stream and aborts the invocation transaction; user code cannot recover and commit earlier writes. Separately, the external client treats all emitted invocation output as provisional until confirmed durable commit. Neither boundary proves the honesty of arbitrary user code. Limits and pagination must not become authorization proofs or justify hidden-value pushdown.

`prdb_sdk_sql_encode_result_row_v1` encodes one projected row as a standalone `SQLR` record. All integers are unsigned big-endian unless identified as raw value bytes. The fixed header is magic `SQLR`, `u16 version = 1`, and `u16 column_count` (1–4096). Each column then contains `u16 name_length` (1–128), the declared ASCII column name bytes, `u32 type_code`, `u8 decimal_precision`, `u8 decimal_scale`, `u8 state`, `u32 value_length`, and `value_length` bytes. The name and type metadata are taken from the executor's authorized declared shape; the row value is selected by the SQL binding ordinal. VALUE, NULL, and REDACTED use the v1 value-state codes 0, 1, and 2. NULL and REDACTED retain the declared type metadata and have zero value bytes. VALUE bytes use the canonical executor scalar encoding. Decimal precision/scale are included only for DECIMAL and are zero for other types. Projection order and duplicates are preserved; `SELECT *` uses declared relation order. One encoded record is capped at 1 MiB. The caller supplies output and cell scratch buffers; on any error the reported output length is zero. `prdb_sdk_sql_write_result_row_v1` uses the v3 host callback to emit that record in chunks no larger than 16 KiB; an error can follow earlier provisional chunks and must be propagated from the SQL row callback. `prdb_sdk_sql_encode_join_result_v1` uses the v8 binding's source side and ordinal to select metadata from the corresponding authorized relation shape and pairs it with the runner's projected value. It applies the same record format, size cap, value-state rules, and projection-order behavior; its writer emits host-sized provisional chunks. The client may receive any byte fragments of a row record and concatenates result-data payloads before decoding complete `SQLR` records. Neither SDK function makes result bytes durable.

## Lifecycle and Validation

Load only the submitted query artifact and declared supported runtime dependencies; arbitrary filesystem plugin discovery is not part of the prototype. ABI/version mismatch fails the request. Prefer process exit to unloading a library with live callbacks or buffers. Bound parsing, AST size, planning requests, memory, and output.

Validate syntax/type errors, unsupported statements, parameter binding, null/redaction behavior, malformed plans, ABI mismatch, constructor-time confinement, cancellation, and partial-output failure. Compare interpreter results against small authorized-view fixtures. None of these correctness checks replace malicious-worker containment tests.

Allow sequential SQL calls within one user invocation under the same MVCC snapshot, private write set, and cumulative budgets. Reentrant/nested execution and concurrent statements are deferred; start with one active statement at a time and one disposable executor per user invocation.

## Open Decisions

This initial SELECT implementation does not settle the rest of the SQL dialect, types, coercions, AST extension/compatibility rules, full filter-plan decoding/execution coverage, or mutation expression support. The baseline abort-on-statement-error rule is enforced by the v3 host failure latch; savepoints are future work.
