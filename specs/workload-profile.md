# Operational Workload and Analytical Queries

## Primary Objective

This is an operational database: prioritize short transactions, point lookups, small range reads, frequent inserts/updates/deletes, predictable commit latency, and recovery correctness. Analytical queries are supported on the same authorized MVCC data, but do not drive the primary storage layout or receive permission exemptions.

Use redb key/value tables and logical indexes under the operational scheduler. Do not build a custom heap, buffer manager, or WAL. Do not introduce a mandatory column store, warehouse ingestion pipeline, materialized analytics replica, or distributed execution layer. Those require separate future decisions.

## Analytical Scope

The first storage milestone retains the existing single-table SQL subset and can perform bounded scans and native computation over authorized batches. Supporting SQL analytics is an explicit follow-on deliverable: inner equijoins, GROUP BY, COUNT/SUM/MIN/MAX/AVG, ORDER BY, and HAVING. These are required roadmap capabilities, not claims that the initial parser implements them. Window functions, recursive queries, and distributed analytics are deferred.

Execute analytical operators in the untrusted executor over sanitized batches. SQL aggregates use declared null semantics and fail when they require redacted values; they do not silently omit denied cells. COUNT(*) counts only visible rows. No privileged aggregates over hidden data are implied. Hash joins/sorts have bounded memory. Until the SQL-9 spill implementation is accepted, operators reject excess work; they never spill implicitly or without the controls below.

### Secure query spill

The SQL-9 secure spill implementation permits bounded external-memory execution for supported ORDER BY, hash JOIN, and GROUP BY COUNT(*) shapes. The confined local acceptance passes with explicit spill budgets; production enablement still requires validation of the configured scratch filesystem and service-wide saturation behavior. Spill applies only to invocations admitted as analytical; operational invocations retain current in-memory bounds and never consume spill capacity. Spill is an extension of those SQL operators; it does not grant the executor database-file access or permit storage, authorization, planner statistics, or catalog work to spill through this interface. Operators retain a bounded in-memory working set and use spill only for intermediate records that would otherwise exceed that operator's memory budget. If spill is disabled, a quota is exhausted, or scratch I/O fails, the statement fails and the enclosing invocation cannot commit.

Spill data consists only of values and metadata already returned in sanitized, authorized executor batches. Storage applies row visibility and cell permissions before the SQL SDK can append a record. A REDACTED value has no payload and remains an evaluation error wherever the SQL operator requires its value; spill must not turn REDACTED into NULL, omit the row, or expose an underlying value. Spill records preserve declared scalar type/Decimal metadata, NULL and VALUE states, and any stable input ordinal needed to reproduce the operator's specified ordering and grouping semantics. Spill must not include raw redb bytes, page/index data, hidden-row counts, or private planner/statistics state.

The executor receives no spill path or spill-file descriptor. A trusted spill broker owned by the supervisor performs all filesystem operations and exposes a bounded, versioned byte-stream API over a dedicated worker channel. The broker derives the invocation, package, workload class, and effective actor from its provisioned channel; caller-supplied identities never select a quota or namespace. Stream handles are unpredictable, scoped to that channel, and unusable from another invocation or package. Each package gets an isolated spill namespace, including packages that use different RUNAS actors in one explicit transaction. The broker treats stream bytes as opaque and does not grant data or transaction authority.

The broker stores spill bytes unencrypted on a disk-backed filesystem. Encryption at rest is not part of this contract; host administrators and processes with authority over the service scratch filesystem are within the host trust boundary. Protect spill from other invocations and untrusted host users with a service-owned scratch parent, private per-invocation directories, restrictive ownership/modes, descriptor-relative no-follow file creation, and no worker path traversal access. Create files exclusively, reject links and caller-selected paths, and unlink each file as soon as its broker-owned descriptor is established. Never pass those descriptors to the worker. Do not place spill on a memory-backed filesystem and do not fall back to one when disk-backed scratch is unavailable.

Spill is opt-in through explicit positive limits. There are no implicit production defaults and no unlimited mode. The supervisor accepts the complete configuration set `--spill-parent`, `--spill-max-bytes`, `--spill-max-io-bytes`, `--spill-max-streams`, `--spill-max-operations`, `--spill-max-response-bytes`, and `--spill-max-service-bytes`. All flags must be supplied together with positive values; omitting all disables spill, while a partial set rejects startup. `--spill-max-bytes` bounds live physically allocated bytes per invocation; `--spill-max-io-bytes` bounds cumulative broker read plus write payload bytes per invocation; the other per-invocation limits bound streams, calls, and one broker response; `--spill-max-service-bytes` is the shared live-allocation ceiling across active analytical invocations. Concurrent growth reservations share one service-wide accounting gate, so a reservation is charged before filesystem I/O begins and simultaneous appenders cannot reserve the same remaining capacity. The service-wide limit must be configured below the scratch filesystem capacity to reserve space for other service needs. Account for allocated filesystem blocks, rounding reservations to the filesystem allocation unit, rather than only logical file length; reserve capacity before acknowledging growth and release it on truncation/deletion/close. Configuration that cannot enforce actual disk allocation bounds disables spill or prevents service startup; an enabled configuration using tmpfs or ramfs rejects supervisor startup before the service admits requests. A memory cgroup is not a disk quota. Spill remains disabled if configuration is absent or zero.

The stream API creates an empty stream, appends bounded bytes, seals it against further writes, reads a bounded range, and destroys it. Appends are contiguous and cannot create holes. Sealed streams are immutable. The broker bounds each request frame to the executor IPC request maximum (1 MiB); an append payload is at most that limit minus its 16-byte stream handle. The response limit applies to read-at bytes returned by one operation, not to append payloads. The cumulative I/O limit accounts for both appended and read bytes. Every request validates the stream handle, offset, length, aggregate budgets, invocation deadline, and cancellation state. Check cancellation between chunks and before each blocking disk operation. Do not block the supervisor's admission, result-relay, cancellation, or commit-control loops on spill I/O. The current implementation serves each admitted analytical worker on a dedicated channel thread; analytical admission bounds the number of such threads and each channel processes one request at a time. Per-stream I/O locks keep filesystem work outside the broker-wide accounting lock, and a deterministic test confirms a blocked append does not stop another package from creating a stream. Sustained fairness under service-wide disk saturation remains open for deployment validation.

The broker deletes stream contents when the package ends, whether it succeeds, fails, is cancelled, times out, disconnects, or crashes. The broker closes and removes the package namespace when its dedicated worker channel reaches EOF or errors; supervisor cleanup may repeat that close safely. Closing the broker's last descriptor after process failure must release unlinked files. A cleanup or accounting inconsistency fails closed, prevents further spill admission, and is surfaced to supervisor recovery; it never permits a transaction to commit on the assumption that cleanup succeeded. Spill data is temporary and nondurable: it is never used to recover a database transaction or establish a commit outcome. A broker restart invalidates every stream and fails active spill-dependent packages; undecided transactions follow the normal abort/recovery rules.

Spill preserves SQL values, errors, and explicit `ORDER BY` results for the authorized view. Since SQL without `ORDER BY` does not promise row order, spilled hash JOIN output follows partition order; callers that require deterministic order must specify `ORDER BY`. Any spill quota, allocation, I/O, codec, cancellation, or broker failure is a statement failure and latches invocation failure. Output already emitted remains provisional and must not be treated as committed; the invocation aborts if the statement does not complete. No partial durable writes are allowed. The security goal is cross-invocation isolation and bounded resource use, not secrecy from the same query process: compromised native query code already has access to the values authorized for its effective actor.

The current SDK sort kernel accepts at most 128 authorized keys for one declared scalar column. It places NULL before non-NULL values in either direction, preserves input order among ties, rejects REDACTED or malformed keys, and writes no partial index permutation on failure. SQL `ORDER BY` supports one source-column key through the v3 parser/binder. ABI v6 analytical invocations with the spill callback use a stable external merge sort of fixed 1024-byte encoded row records; rows whose encoded representation exceeds that limit fail before sorted output. The legacy ABI or spill-disabled path remains bounded to 128 matching rows and 1 MiB of row bytes. Both paths close the scan before sorted results are delivered and apply `LIMIT` after sorting. Multiple ORDER BY keys remain deferred.

The grouped v4-v7 runners compute stable COUNT, SUM, MIN, MAX, or AVG groups for at most 128 matching authorized rows and 1 MiB of copied key and operand bytes for one scalar key. `WHERE` is evaluated before grouping; equal values group together, NULL values form one group, and groups follow first appearance order. `COUNT(*)` counts every matching visible row, including NULL-key rows. The runner closes the scan before group callbacks and applies `LIMIT` after aggregation. The v9 runner adds one selected-aggregate comparison against a positional parameter: SQL NULL yields UNKNOWN and omits the group, while missing, mistyped, malformed, or REDACTED parameters fail before scanning. The v10 runner adds stable sorting by the selected group key or aggregate, with NULL first in both directions. V11 permits explicit `NULLS FIRST` or `NULLS LAST`, independent of sort direction; omission retains NULLS FIRST. V12 permits lexicographic ordering by the distinct group key and selected aggregate, each with independent direction and NULL placement, for at most two keys. The runners apply `LIMIT` after sorting and validate comparisons/sort keys before callbacks. Scan, filter, key validation, aggregate, comparison, sorting, and materialization errors produce no group callbacks. The runner reports groups through its synchronous SDK callback and the SQLR v1 grouped writer. In addition, ABI v6 can spill unordered `COUNT(*) GROUP BY` queries with no `WHERE`, `HAVING`, or `ORDER BY` by externally sorting fixed 1024-byte key records and folding equal keys in one streaming pass; this path sorts groups by key and applies `LIMIT` after grouping. Other grouped shapes retain the bounded v24 behavior. Multiple grouping keys, more than two grouped sort keys, general Boolean HAVING expressions, HAVING-only projections, and arbitrary ORDER BY expressions remain unsupported.

The SDK also has bounded MIN/MAX, SUM, and AVG kernels and versioned grouped SELECT runners. The v5 runner accepts `MIN(column)` and `MAX(column)`, scans and filters at most 128 matching authorized rows, and caps combined copied group-key and aggregate bytes at 1 MiB. It closes the scan and validates all groups before callbacks; NULL operands are ignored, all-NULL groups return NULL, and REDACTED, malformed, or mismatched operands fail before output. SQLR output uses the declared group-key field followed by a `min` or `max` field with the aggregate column's declared type metadata; writing uses bounded provisional chunks. V6 parsing and binding accept `SUM(column)` for numeric columns, and the v6 runner applies the same row and copied-byte bounds. SUM widens integer inputs to BIGINT and DECIMAL(p,s) to DECIMAL(38,s), applies exact final-result overflow checks, and emits a SQLR `sum` field using the result type metadata. V7 accepts numeric `AVG(column)` and executes it under the same row and copied-byte bounds; the result is DECIMAL(38,r), with exact averages rounded to nearest, ties to even. The runner validates all groups before callbacks and emits an `avg` SQLR field with the derived scale, including for all-NULL groups. The maintained confined SQL artifact exercises grouped MIN, SUM, and AVG through the result relay.

The SDK has a bounded inner equijoin pair kernel for already-authorized key arrays: up to 128 values per side and at most 16,384 result pairs. It emits stable left-major matches, treats NULL as non-matching, and fails on REDACTED, malformed, or mismatched values.

The separately versioned composite join pair kernel accepts two to eight row-major key columns with one declared type and Decimal scale per position. Every component must compare TRUE for a match, so a NULL component makes the tuple non-matching. It validates all operands before emitting output, preserves stable left-major ordering, and retains the 128-row/16,384-pair bounds. The original bounded SQL join runner accepts one predicate; the ABI v6 spill dispatch supports the composite form described below.

ABI v6 SQL JOIN dispatch now uses the secure spill profile for supported alias-aware composite and filtered JOIN statements, and normalizes the supported single-key JOIN form to the same operator. The runner hash-partitions authorized row records into eight partitions per input, opens at most sixteen broker streams, and compares bounded 128-by-128 blocks within a partition, including skewed partitions. Encoded input records are limited to 4096 bytes. The v25 parser and binder add one qualified projected ORDER BY key; ABI v6 dispatch spools joined projection records of at most 1024 bytes, sorts them with the stable external row sorter, then applies LIMIT. The temporary spool can overlap the 16 JOIN partition streams, so this combined path requires at least 17 simultaneous streams per invocation. Larger packed joined records fail before SQLR output. Spill-disabled ABI v6 statements retain the bounded unordered runner; combined JOIN ORDER BY requires the spill broker. Confined coverage verifies integer ordering, Decimal NULLS FIRST, nullable BIGINT ordering, Decimal NULL and parameterized filters before ordering, LIMIT after sorting, REDACTED Decimal key failure, and oversized joined-record rejection before SQLR output. Broader scalar and workload combinations still need wider acceptance coverage.

The SQL-10 implementation adds an index nested-loop strategy for INNER JOIN while retaining hash join as the general path. It probes an authorized unique or non-unique index by exact equality on the inner relation's leading key column for each non-NULL outer key. All scalar types supported by the versioned index-range value codec and ordered SQL index encoder are eligible; variable-length values remain subject to request and row-size bounds. Remaining composite predicates and qualified WHERE filters run in the executor. Every probe runs through trusted storage IPC and returns sanitized, authorized rows from the invocation snapshot plus staged-write overlay. The index is usable only when its indexed key is statically readable and unconditionally allowed for that invocation. The runner caps each statement at 128 outer rows, 16,384 joined pairs, 16,384 cumulative inner candidates, 1 MiB of copied outer/inner key and projected-value bytes, the 1 MiB IPC response maximum per lookup, and the shared 256 executor requests. The existing per-range 1,024-candidate and storage key/payload bounds also apply. Exceeding a bound fails the statement and prevents commit. The optimizer selects the indexed path only when a valid authorized path exists, otherwise the existing bounded/hash implementation applies. Join planning requests authorized populations up to 128 rows per side: exact empty or two known inputs of at most four rows retain hash join; exactly one known 1–4-row input may be the outer side for an eligible opposite-side index; a smaller input of at most eight rows may drive the index when the other known population is at least 16 times larger. For moderate skew, one side of 9–16 rows and an opposite side at least eight times larger may use an exact authorized join-pair estimate; indexed nested-loop is selected only at no more than four output pairs per outer row. Unknown estimates preserve right-index preference with left fallback. Existing population rules have local confined timing evidence; the moderate fanout threshold still needs mixed-load validation. General cost-based strategy selection, populations above 128, broader predicate/selectivity estimates, and index-prefix support remain later increments.

The v8 parser/binder and runner accept one INNER JOIN with relation-qualified projections and one equijoin predicate over two separately authorized relation shapes. The runner resolves both relations independently, scans sequentially, and closes both before result callbacks. It bounds each side to 128 rows and combined copied key/projection bytes to 1 MiB, then emits joined projection values in stable left-major match order. NULL keys do not match; REDACTED keys fail before callbacks. The joined-row SQLR v1 encoder/writer derives metadata from each projection's bound relation side and ordinal and emits bounded provisional chunks. The maintained confined acceptance exercises two distinct SELECT-authorized storage relations through the result relay and durable commit.

The v16 parser/binder and runner support two to eight qualified equality predicates for an INNER JOIN and bind each pair against independently described and authorized relation shapes. The runner scans each side sequentially, closes both cursors before result callbacks, copies at most 128 rows per side and 1 MiB of join keys plus projected values, and evaluates all key tuples through the composite join kernel. It shares a 121-page budget across both scans and checks cancellation before each page, after pair evaluation, and every 2,048 emitted pairs; setup, scan, close, and cancellation calls remain within the executor's 256-request ceiling. Reaching the page budget fails before another fetch. NULL key components do not match; malformed, redacted, or mistyped keys fail the statement. Results preserve stable left-major pair order and apply LIMIT after matching. V16 keeps v8's projection and relation semantics, reuses its SQLR writer through the embedded v8 binding, and preserves v8 compatibility. The maintained confined fixture verifies two-key matching and exact SQLR rows; the dedicated executor fixture covers cancellation, request limits, and callback failures.

## Mixed-Workload Scheduling

The supervisor admits an invocation into an operational or analytical resource class, bounded by the caller’s configured allowance. The Linux supervisor may configure separate per-invocation CPU, memory, and process-count cgroup ceilings for the two classes. The analytical profile is optional and defaults to the operational profile. A client label selects only one of these trusted configured ceilings and cannot obtain unlimited priority or override budgets. Both classes retain snapshot isolation and the same permission model; read-only analytical grants are the default, not a mechanism to prohibit explicitly authorized writes. Pending uploads and prepared submissions have independent class limits: 256 operational and 64 analytical by default, configurable with `--max-pending-operational` and `--max-pending-analytical`; these limits bound the pre-START staging backlog. The supervisor also caps active START admissions by immutable sealed workload class: defaults are 64 operational and 8 analytical invocations, configurable with `--max-active-operational` and `--max-active-analytical`. Per-principal caps default to 16 operational and 2 analytical invocations, configured with `--max-active-operational-per-principal` and `--max-active-analytical-per-principal`; both global and per-principal limits must have capacity for START to proceed. Reservations count while START admission is in progress and while the worker remains active, and release their slot after durable completion or cleanup. At capacity, START leaves the sealed reservation prepared so it can be retried. The first retry assigns a bounded ticket; retries preserve ticket order among eligible requests, skipping a principal or class whose active quota is full. Tickets are removed by cancellation, expiry, or disconnect. This is retry-driven and does not hold a server thread waiting for a slot. Storage snapshot admission adds a shared analytical backstop of 8 active snapshots by default (`StorageManagerConfig::max_active_analytical_invocations`), configurable with `--max-storage-active-analytical-snapshots` and `--max-storage-active-snapshots`. The analytical storage cap must be at least the configured analytical START cap, and the total storage cap must cover the sum of operational and analytical START caps; the supervisor rejects inconsistent settings at startup. An analytical invocation rejected by that cap does not consume operational capacity; operational and trusted direct admissions can use the remaining global slots. The retry queue is bounded by the pending submission caps. These controls provide bounded admission fairness; they do not guarantee point-read, commit, cancellation, or reclamation latency under every system-wide resource failure.

Reserve queue capacity and progress for commits, redb commits, point reads, cancellation, and reclamation. Limit analytical queue depth, prefetch, CPU, output bytes, and snapshot age. Use scan-resistant cache admission so sequential scans do not evict the entire operational working set. Permit larger analytical budgets only through bounded admission configuration; never silently refresh their snapshots to relieve history pressure.

DDL/index builds and redb compaction/maintenance are separately budgeted maintenance work. Long analytical readers can retain old versions and schema definitions, so history retention and admission limits are part of performance policy, not optional cleanup.

## Performance Evidence

Measure point/range latency, update throughput, conflict rate, commit p50/p95/p99, redb bytes/commit, point-read latency, retained history, and memory-copy bytes. Add mixed workloads that measure operational latency while scans, joins, or maintenance run. No quantitative performance target is established until a repeatable benchmark and hardware/profile are recorded.

redb supplies the physical commit/recovery path. Measure its transaction/write amplification on representative operational workloads before considering another backend; never weaken durability or authorization checks for throughput.
