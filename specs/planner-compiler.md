# Optimizer and Client Compilation Boundary

## Responsibilities and Isolation

Implement the optimizer in Rust and transform structured query requests into logical and physical plans. TinyCC produces the submitted C query library in the client using the prebuilt C SDK; the server optimizer does not compile that program. The executor's [SQL library](sql-library.md) owns SQL text parsing and operator execution; the planner validates its structured input, resolves authorized schema/types, and performs optimization. Run in a process separate from both the executor and storage manager: optimizer complexity, malformed inputs, and resource exhaustion must not compromise storage memory.

The planner is not an authorization authority. A compromised planner must not be able to mint execution grants or cause storage to release unauthorized values. Treat its plans as untrusted structured input. All client-built query artifacts are untrusted native code regardless of compiler or SDK provenance.

## Pipeline

```text
client: user C source + prebuilt C SDK -> TinyCC compiler/linker -> query.so
executor: query.so -> SDK SQL API -> structured planning request
optimizer: validated request -> logical plan -> physical plan
executor: SDK interpreter executes plan -> user code consumes results
```

The prebuilt SDK executes physical plans with an interpreter initially. There is no server compilation backend in the baseline; adding one requires an explicit future design decision.

Inputs are bounded structured requests from the executor, typed parameters as needed for planning, authorized schema, scoped estimates, and execution constraints. A provisioned submission channel binds requests to the existing execution context; input cannot change its identity or grant. Outputs require explicit versioning and validation. Plans carry logical relation/schema references, never optimizer-connection storage handles; the executor resolves them again through its scoped storage channel.

The bounded structured request header is `u16 version=1`, `u8 statement`, and `u8 flags=0`. The SELECT statement (`statement=1`) uses a single-relation record: schema and relation identifiers (`u8 byte_length` plus ASCII identifier bytes), `u16 projection_count` and that many identifiers, `u32 predicate_length` and prefix-encoded predicate bytes (zero length means absent), then `u8 limit_present` (0 or 1) and an optional `u32 limit`. Identifiers use `[A-Za-z_][A-Za-z0-9_]{0,62}`. There must be 1–128 projections. The full record is at most 64 KiB and predicate bytes at most 16 KiB.

The DELETE statement (`statement=2`) uses a separate bounded record: schema and relation identifiers, followed by a nonzero `u32 predicate_length` and one prefix-encoded predicate. It has no projection or limit fields; WHERE is mandatory. The Rust decoder enforces the same 64 KiB request, 16 KiB predicate, 256-node, depth-32, 4,096-byte text/BYTEA literal, and identifier bounds as SELECT. `bind_delete_request` and its invocation-metadata variant resolve only an authorized stable relation, require a Boolean predicate root, and produce no executor handle. `optimize_delete_v1` lowers a bound DELETE to the canonical kind-2 `Scan -> Filter -> Delete` plan. The optimizer process accepts distinct `optimize_select` (`0x1203`), `optimize_delete` (`0x1205`), and `optimize_update` (`0x1206`) IPC operations, routes each bounded request through authorized planner metadata, and validates all three canonical plan kinds in its response codec. ABI v5's operation-selected callback submits the bounded DELETE request on `OptimizeDelete`; the C SDK encodes the parsed SQL v1 DELETE AST, independently decodes the plan, matches its predicate columns and parameter values against the AST, then re-resolves the relation through executor storage before acquiring a normal relation handle. The SDK evaluates the matched predicate over authorized full-scan batches, polls cancellation, and stages matching row handles through ordinary executor mutation IPC. The maintained confined acceptance exercises optimizer-backed DELETE and verifies the rows are absent before durable commit. Confined cancellation and injected-failure coverage for DELETE remain open.

The UPDATE statement (`statement=3`) uses schema and relation identifiers, a `u16 assignment_count` (1–64), then assignments in source order. Each assignment is a column identifier followed by kind `0` and a nonzero one-based `u32` parameter index, or kind `1` for NULL. A nonzero `u32 predicate_length` and one bounded prefix predicate follow; WHERE is mandatory. The Rust request decoder enforces the 64 KiB request, 16 KiB predicate, 256-node, depth-32, 4,096-byte text, 63-byte identifier, 64-assignment, and parameter-index bounds. Invocation-bound binding resolves assignment and predicate columns against authorized relation metadata, rejects unknown or duplicate target columns and NULL assigned to non-nullable columns, and requires a Boolean WHERE root. Binding does not confer write authority. The `optimize_update` process operation (`0x1206`) composes authorized relation lookup and canonical kind-3 plan output. The C SDK independently decodes and validates UPDATE assignments, predicate references, exact scan shape, target uniqueness, parameter bounds, and NULLability. `prdb_sdk_optimizer_encode_update_v1` serializes the parsed UPDATE AST into the bounded request, and `prdb_sdk_optimizer_submit_update_v1` submits it through ABI v5's operation-selected callback. `prdb_sdk_optimizer_validate_update_plan_with_parameters_v1` matches the returned predicate and source-order assignments against the AST, checks exact scalar type codes and NULLability, and re-resolves the plan relation through executor storage. `prdb_sdk_optimizer_execute_update_ast_v1` scans authorized full-shape batches, evaluates the AST predicate, collects row handles, closes the scan, and stages the verified parameter/NULL patches through ordinary executor mutation IPC. The confined `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` acceptance covers parameterized single-column and NULL assignments and multi-column value visibility through authenticated optimizer/executor processes and durable commit. Its default-deny case grants UPDATE on the table and target column but installs no applicable UPDATE row policy; the request reaches storage, receives an authorization rejection, and ends in a durable `QueryError` abort with the committed row unchanged. The TinyCC SDK suite also verifies cancellation cleanup, optimizer callback failure, stage-update failure, and target-capacity failure without publishing mutation counts on error. A real-redb transaction regression also stages two policy-authorized UPDATE patches from one snapshot and verifies one durable commit, one durable conflict, and the winning row value. Broader transaction conflict and policy acceptance remain open.

The composite join SELECT request (`statement=4`) uses the same version-1 four-byte request header, then schema, left-relation, and right-relation identifiers; `u16 projection_count` (1–128) followed by `(u8 relation_side, identifier)` records where side is 0 for left and 1 for right; `u8 join_key_count` (2–8) followed by left/right identifier pairs; and `u8 limit_present` plus an optional `u32 limit`. The decoder rejects invalid sides, out-of-range counts, malformed identifiers, truncated fields, and trailing bytes within the existing 64 KiB request cap. The invocation-bound binder resolves both names independently through authorized planner metadata, requires the same schema ID/version, binds projections and key sides to stable column IDs/ordinals, and rejects incompatible key types before planning. Decimal key scales must match; differing Decimal precision is allowed. The optimizer process routes operation `optimize_join_select` (`0x1207`) through two authorized plan-relation lookups with distinct request IDs in a namespace disjoint from direct planner SDK calls. It returns plan v1 kind 4: common schema identity, two relation name/ID/epoch references, each side's unique ordinal-sorted scan-column shape, ordered side-qualified projections, 2–8 bound equality-key pairs, and an optional limit. Rust and the TinyCC C SDK independently validate both scan shapes, projection/key membership, relation/schema identity, key type compatibility, collection bounds, version, and trailing bytes. The C SDK serializes the parsed alias-aware v19 INNER JOIN AST to statement 4 and submits it with operation `0x1207` through ABI v5. It also checks the returned schema/relation names, projection sides/order/types, composite keys, and LIMIT against the parsed and bound AST. Before execution, it re-resolves both relation references through executor storage and compares stable IDs, epochs, and every scanned column definition. The optimizer-backed v19 SDK entry point then executes the matching bounded join operators only after all checks succeed. The two-key aliased join passes through the confined ABI v5 SQL artifact acceptance, result relay, and durable commit. This remains the unfiltered request subset; planning/execution measurements remain open.

The filtered aliased-join request uses statement 12 and the same common join prefix and optional LIMIT as statement 4, followed by one filter side (`0` left, `1` right), a filter column identifier, and an expression tag: `0` is a comparison operator (`0` equals, `1` not-equal, `2` less, `3` less-or-equal, `4` greater, `5` greater-or-equal) plus a one-based parameter index bounded to 256; `1` is IS NULL; `2` is IS NOT NULL. The invocation-bound binder resolves the filter column against the selected authorized relation. Plan kind 12 retains all kind-4 records and appends the side, full bound filter-column record, and expression metadata after LIMIT. Each side's scan shape includes its projections, join keys, and filter column, sorted by ordinal. Rust produces and validates this request/plan pair. The TinyCC SDK independently encodes statement 12 from the parsed v20 AST, decodes kind 12, and matches join identity, projections, keys, LIMIT, filter side and column, comparison, parameter index, and parameter type against the v20 AST and binding. It also re-resolves both relation identities and complete scan shapes through executor storage, including the filtered column. The optimizer-backed runner completes all validation before executing the bounded v20 join; its four additional preflight executor requests reduce the scan ceiling from 119 to 117 pages. The maintained confined SQL artifact exercises parameterized statement-12/kind-12 execution through result relay and durable commit.

SQL-10 adds plan kind 17 for the existing v8/v16/v19/v20 join ASTs; kinds 4 and 12 and their request formats remain unchanged. Kind 17 retains the canonical kind-4 join fields (schema/relation identities, sorted scan shapes, projections, equality keys, and LIMIT), includes the existing kind-12 filter fields when planning a filtered v20 AST, and appends an index-strategy record: outer side (`0` left, `1` right), inner side, stable inner index ID[16], and the complete bound leading-key column record. The optimizer may emit it only when the inner index's first key column equals one bound join-key component and that key has an invocation-authorized path whose indexed cells are statically readable and unconditionally allowed. Probe values may use any scalar type accepted by the versioned index-range value codec and ordered SQL index encoder: Boolean, SMALLINT, INTEGER, BIGINT, DECIMAL, TEXT, VARCHAR, BYTEA, UUID, DATE, and TIMESTAMPTZ. Variable-length values remain subject to existing IPC request and row-size limits. The C SDK matches every added field to the parsed join and the authorized planner relation descriptions, then re-resolves both relation identities and scan shapes through executor storage before opening the outer scan. For each non-NULL outer key, the runner submits the existing `ScanIndexRange` request with identical inclusive lower and upper bounds, the checked index ID, and the complete inner relation column-ID list. Storage revalidates the index/table/key relationship, pinned snapshot and overlay, authorization, and existing per-request candidate/byte bounds. It returns only bounded sanitized inner rows, without row handles or index-existence/match-count metadata. For join requests, the optimizer requests an authorized population estimate for each relation under the shared 16-estimate allowance, capped at 16,384 rows per relation. If either exact population is zero or both are at most four, it retains hash join. Exactly one known 1–4-row input may use the small side as outer when the opposite relation has an eligible leading-key index. When both known populations exceed four, an eligible indexed nested-loop path may use the smaller side as outer if it has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash join. Five-run confined 4×128 and 8×128 high-fanout profiles and the 64×64 medium profile are measured locally; this bounded population-skew rule is not a fanout estimate or general cost model. A single known 1–4-row input may orient an indexed nested-loop join even when the other estimate is unknown. Other unknown estimates preserve the deterministic right-index-preferred/left-fallback choice. Estimates remain advisory and never affect authorization. This is a bounded, measured heuristic, not general cost-based planning: five-run 17×2,048 and 17×4,096 mixed-load profiles select indexed nested-loop and validate all 17 results at and below the configured population cap. The 17×4,097 profile obtains exact authorized population and pair-cardinality estimates, selects kind 17, and returns all 17 results. These profiles do not compare hash because the SDK hash materialization limit is 128 rows. Join population estimates above 16,384, predicate selectivity, and broader workload/hardware comparisons remain open. No eligible path retains the current bounded or spill hash plan. The existing 256-request executor ceiling and cancellation/deadline checks are shared across all outer pages and index probes; SDK and Rust plan decoders reject wrong orientations, non-leading keys, unapproved index IDs, incompatible types, trailing bytes, or a kind-17 plan for an ineligible AST. A composite index may use a consecutive leading prefix of two to eight columns when each indexed column is paired with a join equality. The optimizer selects the longest such prefix; an unmatched index-column gap terminates it. Prefix lengths of two or more use additive plan kind 18, retaining the canonical join and optional kind-12 filter fields before an index strategy record containing the outer/inner sides, stable index ID, prefix count, and complete bound column records in index order. The SDK matches each prefix column to exactly one inner join key and its paired outer key, then re-resolves both relation shapes before execution. For every outer row with no NULL prefix component, the runner submits all prefix values in index order through executor `ScanIndexPrefix` operation `0x1116`; NULL in any join key prevents a match and skips that probe. Storage validates the complete prefix against the pinned index schema, key readability and unconditional cell policy, reconciles snapshot and private writes, and returns only authorized sanitized rows. Extra join equalities remain residual comparisons. Unavailable, malformed, cancelled, or over-budget prefix requests follow the existing fail-closed index-runner contract; no partial rows are returned.

The 17-row moderate-skew cardinality gate also has two confined nonuniform fanout profiles. When one outer key matches 16 indexed rows and the other 16 outer keys are unmatched, the exact 16-pair estimate selects kind 17 and indexed execution returns the same 16 rows as hash. When that key matches all 128 indexed rows, the exact 128-pair estimate selects kind-4 hash and validates all 128 result rows. Five fresh-database runs for each profile overlap 192 operational reads and commits each. These are host-local hot-key observations, not generalized cost-based evidence. Paired five-run confined 17×119 profiles at the exact seven-to-one population ratio check the fanout boundary: 68 matching pairs (four per outer row) selected kind-17 indexed nested-loop; 69 pairs selected kind-4 hash. Both matched the hash result and overlapped 192 operational reads and commits per run. At 68 pairs, median run-level p50s were 250.3 ms indexed versus 292.3 ms hash. These results apply to the local fixture only.

The first grouped optimizer subset is the single-key COUNT request (`statement=5`): schema, relation, group-key identifiers, then an optional `u32 LIMIT`. Rust binds the key to invocation-authorized metadata and returns kind 5 containing the stable relation reference and exact one-column scan shape. It supports `SELECT key, COUNT(*) FROM relation GROUP BY key [LIMIT n]`; WHERE, HAVING, ORDER BY, composite keys, and other aggregates are outside this request. The TinyCC SDK independently decodes kind 5, encodes this v4 AST shape, and submits it through ABI v5 operation `0x1208`. Before execution, the SDK matches relation/schema, projected and grouped key bindings, and LIMIT against the parsed statement, then re-resolves the relation and exact scan-column identity through executor storage. The optimizer-gated v4 runner executes only after those checks, using the authorized bounded scan and existing COUNT grouping kernel. The confined ABI v5 SQL fixture exercises this path through result relay and durable commit. Kind 5 remains unordered; single-key COUNT ordering is provided by the separate statement-8/kind-8 subset. Statement 10 separately plans single-key COUNT, MIN, MAX, SUM, and AVG. HAVING, composite grouped ordering with other aggregates, and analytical workload measurements remain open.

The composite COUNT request subset (`statement=6`, using the existing `OptimizeGroupCount` operation) adds two to eight projected/grouped keys and optional post-group LIMIT, with no WHERE, HAVING, or ORDER BY. Rust bounds and decodes the request, resolves every key through authorized relation metadata, rejects duplicate bound ordinals, preserves SQL key order, and returns canonical kind 6 with the exact unique ordinal-sorted scan shape. TinyCC encodes the v13 AST, independently decodes kind 6, checks every key against the parsed and authorized binding, and re-resolves the relation and exact scan shape through executor storage before calling the existing authorized composite grouping runner. The confined ABI v5 SQL fixture exercises two-key COUNT through operation `0x1208` and verifies the relayed SQLR rows through durable commit. Request bounds/trailing-byte, binding duplicate/order, canonical plan, process-channel, TinyCC decode/matching, and confined acceptance checks pass. Composite-group ordering and analytical workload measurements remain open.

The ordered SELECT request (`statement=7`, routed through `OptimizeSelect` `0x1203`) extends the explicit-projection single-relation form with the order-key identifier, a descending flag, and an optional `u32 LIMIT`. The Rust optimizer resolves the key through invocation-authorized metadata and emits canonical plan kind 7: stable schema/relation identity, the ordinal-sorted union of projected columns and the possibly hidden order key, source-order projections, key direction, and LIMIT. The C SDK independently decodes the plan, matches relation/projection/order/LIMIT to the SQL v3 AST, and re-resolves the relation and scan shape through executor storage before scanning. Execution is bounded to 128 rows and 1 MiB, stable-sorts by the authorized typed key, applies LIMIT after sorting, and polls cancellation before sorting and during publication. The maintained confined SQL artifact verifies descending hidden-key output through result relay and durable commit. This does not change the unordered semantics of statements 5 and 6; grouped ordering uses the separate statement-8/kind-8 request and plan described below. Composite-group sorting and analytical/mixed-workload measurements remain open.

Grouped COUNT sorting uses request statement 8 and plan kind 8 under the existing `OptimizeGroupCount` operation. The bounded request contains schema, relation, and one group-key identifier, then a sort-item count (1–2), followed by each item's source (`0` group key or `1` COUNT(*)), descending flag, and NULLS FIRST flag, then the optional LIMIT. Repeated sort sources, invalid flags, extra bytes, WHERE, HAVING, composite grouping, and aggregates other than COUNT(*) are rejected. The authorized binder resolves the group key and emits kind 8 with the stable relation reference, exact one-column scan shape, group key, the ordered sort items, and optional LIMIT. The TinyCC SDK independently checks the plan against the parsed v12 AST and authorized binding, re-resolves executor identity, and only then runs the bounded grouped COUNT operator. Sorting is stable, applies NULL placement and direction per item, and applies LIMIT after sorting under the existing 128-group/1 MiB materialization budget. Statement 5/kind 5 and statement 6/kind 6 retain their existing unordered meanings. Confined acceptance verifies ordered SQLR output through result relay and durable commit. Composite-group sorting and analytical/mixed-workload measurements remain open.

Composite grouped COUNT sorting uses request statement 9 and plan kind 9 under `OptimizeGroupCount`. The request encodes schema/relation, two to eight group-key identifiers in SQL order, one to nine unique ORDER BY sources selected from those keys or COUNT(*), each source's group-key index when applicable, direction, NULL placement, and optional LIMIT. WHERE, HAVING, other aggregates, repeated or unselected sort sources, malformed flags, and trailing bytes are rejected. The kind-9 plan carries the stable relation reference, exact ordinal-sorted group-key scan shape, group keys in SQL order, sort sources in SQL order, and LIMIT. The TinyCC SDK independently matches the plan to the parsed v15 AST and authorized binding, re-resolves executor identity, then invokes the bounded v15 grouped sort runner. It retains stable lexicographic ties, NULL placement/direction per item, and LIMIT-after-sort behavior under the existing 128-group/1 MiB cap. Statement 6/kind 6 remains unordered. Confined acceptance verifies exact SQLR output through result relay and durable commit.

Single-key aggregate planning uses request statement 10 and plan kind 10 under `OptimizeGroupCount`. It accepts one group key and exactly one selected COUNT(*), COUNT(column), MIN, MAX, SUM, or AVG aggregate, with optional LIMIT. Aggregate tags are 1 for COUNT(*), 2 for MIN, 3 for MAX, 4 for SUM, 5 for AVG, and 6 for COUNT(column); tags 2–6 carry an aggregate-column identifier. The request rejects WHERE, HAVING, ORDER BY, other projections, invalid aggregate/argument combinations, and trailing bytes. The authorized binder validates group and aggregate columns and their SQL result type constraints; COUNT(column) accepts any supported scalar input, while SUM and AVG remain numeric-only. The kind-10 plan carries the stable relation reference, the group key, aggregate kind, optional aggregate argument, exact unique ordinal-sorted scan shape, and LIMIT. TinyCC independently matches SQL and binding to the plan, re-resolves executor identity, and invokes the bounded v24 grouping runner for COUNT(column) only after validation. The runner's 128-row and 1 MiB materialization limits and established NULL, overflow, and Decimal semantics remain in force.

Ordered single-key aggregate planning uses request statement 11 and plan kind 11 under `OptimizeGroupCount`. It accepts the same six aggregate kinds and at most two distinct ORDER BY sources from the group key and selected aggregate, with independent direction and NULL placement, and optional LIMIT. It rejects WHERE, HAVING, invalid or repeated sort sources, extra projections, invalid aggregate arguments, and trailing bytes. The plan includes the exact ordinal-sorted scan union of the group key and aggregate argument plus ordered sort metadata. The TinyCC SDK matches the SQL and authorized binding, re-resolves executor identity, and invokes the bounded grouping/sorting runner. Sorting remains stable and bounded by the existing 128-group/1 MiB cap; LIMIT follows sorting.

Composite grouped aggregate planning uses request statement 13 and plan kind 13 under `OptimizeGroupCount`. It accepts the v13 two-to-eight-key grouping shape with one COUNT(*), COUNT(column), MIN, MAX, SUM, or AVG aggregate and optional LIMIT; WHERE, HAVING, and ORDER BY remain unsupported in this request subset. The request carries group keys in SQL projection order and an optional aggregate argument. The authorized binder rejects duplicate key ordinals, enforces numeric arguments for SUM/AVG, and emits a scan union containing all group keys and the aggregate argument, sorted by relation ordinal. TinyCC independently decodes and matches kind 13 to the SQL AST and authorized binding, re-resolves executor identity, and invokes the bounded grouping runner.

Filtered composite aggregates use separate request statement 15 and plan kind 15 under the same operation, preserving statement 13's wire format. The request supports the six aggregate kinds, adds one required bounded Boolean WHERE tree before optional LIMIT, and includes direct-column `IS NULL` and `IS NOT NULL` nodes. Binding resolves every predicate and aggregate column against the invocation's authorized relation; planning places a Filter before the composite aggregate and scans the sorted union of grouping keys, the aggregate argument, and predicate columns. The executor applies the filter before grouping and LIMIT, preserves redacted required inputs as evaluation errors, and rejects a plan whose filter, grouping, or scan union does not match the submitted SQL and authorized shape.

Predicate node tags are `0x00` NULL; `0x01` Boolean followed by 0 or 1; `0x02` signed big-endian i64; `0x03` UTF-8 text with a big-endian u16 byte length (at most 4,096 bytes); `0x04` signed big-endian i32 DATE day count (days since 1970-01-01, in the supported DATE range); `0x05` UUID followed by its 16 canonical bytes; `0x06` signed big-endian i64 TIMESTAMPTZ microseconds since epoch, restricted to the supported timestamp range; `0x07` BYTEA followed by a big-endian u16 byte length and up to 4,096 raw bytes; `0x08` signed big-endian i128 DECIMAL coefficient, interpreted at the compared column's declared scale and required to fit its precision; `0x10` column identifier; `0x20` comparison followed by operator byte (0 equal, 1 not-equal, 2 less, 3 less-or-equal, 4 greater, 5 greater-or-equal) and two child nodes; `0x30` AND and `0x31` OR followed by a child count (2–16) and those child nodes; `0x32` NOT followed by one child; `0x40` IS NULL and `0x41` IS NOT NULL followed by one column node. Null tests accept only a direct column child. Predicates are bounded to 256 nodes and depth 32. Unknown tags, invalid values, truncation, and trailing bytes are rejected. The decoders check structure and resource bounds; the binder resolves relation/column names, infers expression types, and produces a canonical plan, while storage remains responsible for authorization and writes. Unsupported literal types and statement kinds without a defined request record are rejected in v1.

The in-process v1 binder's `bind_select_request_via_metadata` entry point resolves the request's exact qualified name through `PlannerMetadataConnection` on the admitted invocation before binding. A missing description and a description whose relation name does not match the requested name produce the same `RelationUnavailable` result. It binds the request to pinned schema ID/version, table ID/write epoch, and column IDs/ordinals/types/nullability; duplicate or malformed catalog metadata fails closed. Comparisons require matching known scalar types (or a NULL operand), and Boolean operators require Boolean expressions. The bound result retains the resolved schema/relation names plus stable catalog identities. Planner IPC `describe_plan_relation` (`0x1204`) returns authorized unique paths followed by an optional `0x5201` marker and bounded non-unique range paths. Both groups contain only stable index IDs and ordered key-column IDs whose full keys are statically readable and unconditionally allowed in the pinned projection; ordinary discovery still omits index details. Point hints can use only the unique group; range hints may use either group. This metadata selects a candidate and grants no authority. Executor IPC `resolve_plan_relation` (`0x1105`) returns the same authorized stable relation identity without path metadata or a handle. The executor-side endpoint lets the SQL library re-resolve a decoded plan against the same invocation snapshot before obtaining a scan capability.

The initial plan builder, `plan_select_v1`, lowers this bound SELECT to a linear `Scan -> Filter? -> Project -> Limit?` pipeline. The scan column set is the unique ordinal-sorted union of projected and predicate columns; projection order and duplicates remain intact. Every relation and column reference carries stable catalog IDs, schema version, and table write epoch, never a planner handle or permission. `validate_plan_v1` independently checks pipeline order, reference membership, Boolean filter types, duplicate/missing columns, and predicate bounds.

The mutation-plan format defines canonical DELETE plan v1 with kind 2 and `Scan -> Filter -> Delete` (node tags 1, 2, 5), and UPDATE plan v1 with kind 3 and `Scan -> Filter -> Update` (node tags 1, 2, 6). DELETE carries the unique ordinal-sorted predicate scan shape and its Boolean predicate. UPDATE carries the unique ordinal-sorted union of assignment targets and predicate references, a Boolean predicate, then 1–64 assignments in source order. Each UPDATE assignment contains a complete bound column record and a fixed value record: kind 0 plus a nonzero one-based parameter index, or kind 1 plus a zero parameter index for NULL. The Rust plan validators check relation identity fields, scan and predicate references, Boolean result type, assignment uniqueness, parameter bounds, NULLability, and predicate budgets. The C SDK independently checks UPDATE predicate and assignment structure, exact scan shape, assignment uniqueness, parameter bounds, and NULLability before relation validation. Plans carry no row handles, permissions, or write grants. The DELETE path includes bounded request/binding, canonical plan construction, optimizer-process IPC, independent C decoding, AST matching, executor relation re-resolution, authorized scan, ordinary stage-delete execution, and confined durable acceptance. The UPDATE path includes bounded request/binding, canonical plan construction, optimizer-process IPC, independent C decoding and AST assignment/predicate checks, executor relation re-resolution, authorized scan, ordinary stage-update execution, bounded failure handling, and confined parameterized/NULL/multi-column acceptance. Confined failure injection and broader transaction conflict/policy acceptance remain open.

`encode_plan_v1` and `decode_plan_v1` implement the canonical version-1 SELECT plan payload (maximum 64 KiB). Its header is `u16 version=1`, `u8 kind=1` (SELECT), and `u8 reserved=0`, followed by schema name (`u8 length` and ASCII identifier), schema ID[16], schema version `u64`, relation name (`u8 length` and identifier), relation ID[16], table write epoch `u64`, and a `u8` node count (2–4). Node tags are `1` Scan (`u16` scan-column count and full column records), `2` Filter (one prefix predicate), `3` Project (`u16` projection count and full column records), and `4` Limit (`u32` row count). A column record is ID[16], ordinal `u32`, scalar type code `u8`, type parameters[4], and nullable `u8`. Type codes 1–11 and parameters match the IPC relation-description encoding. Scan columns are limited to 256 and projections to 128. Filter predicates use the request v1 node tags, except a column node carries its bound column ID[16] rather than a name. The Rust decoder resolves those IDs only against the preceding scan shape and runs the independent plan validator. `optimizer_service::optimize_select_v1` composes request binding, conservative lowering, and canonical plan encoding against an invocation-bound `PlannerMetadataConnection`; a real-redb test checks the result against pinned catalog identities. The `optimize_select` (`0x1203`), `optimize_delete` (`0x1205`), and `optimize_update` (`0x1206`) IPC operations and `OptimizerSubmission` role have generated constants and allowlists. The `prdb-optimizer` executable serves all three operations in a separate process, requests stable authorized relation metadata through `describe_plan_relation` (`0x1204`), and returns a validated kind-1, kind-2, or kind-3 plan or non-disclosing status. The supervisor launcher starts the optimizer beside the executor in the invocation cgroup, gives it separate submission and planner Unix sockets, and serves both planner streams concurrently with the executor's planner stream. The optimizer receives its own Landlock policy and seccomp filter. ABI v4 exposes a fixed-operation executor callback for bounded SELECT submissions; ABI v5 adds an operation-selected callback for bounded SELECT/DELETE/UPDATE submissions under the same trusted role allowlist. The C SDK's `prdb_sdk_optimizer_encode_select_v1` serializes an explicit-column single-relation SQL v2 AST, a caller-supplied schema identifier, and optional LIMIT into request v1, with no WHERE tree. `prdb_sdk_optimizer_encode_select_with_parameters_v1` additionally serializes supported parameterized comparisons, direct-column IS [NOT] NULL tests, and Boolean AND/OR/NOT trees using the request v1 bounded prefix format. It supports Boolean, INTEGER, BIGINT, DATE, UUID, TIMESTAMPTZ, BYTEA (up to 4,096 bytes), TEXT, and NULL parameter values; other unsupported forms stay on the established SQL execution path. A DECIMAL coefficient parameter inherits scale only from a compared DECIMAL column; cross-type coercion is not performed. `prdb_sdk_optimizer_decode_plan_v1` validates the `Scan -> Project -> optional Limit` subset. `prdb_sdk_optimizer_decode_plan_with_filter_v1` validates the complete v1 pipeline, including its bounded predicate tree, scanned column references, scalar compatibility, and Boolean root. Both reject malformed identities, types, order, references, lengths, and trailing bytes. Plan names and the validated prefix predicate borrow the complete payload. `prdb_sdk_optimizer_validate_executor_relation_v1` independently decodes a plan, asks executor storage to re-resolve it with `resolve_plan_relation` (`0x1105`), and compares stable identities and scanned columns. `prdb_sdk_optimizer_acquire_plan_relation_v1` obtains a normal executor relation handle only after that validation and checks its relation ID/name. `prdb_sdk_optimizer_open_plan_scan_v1` opens a full scan from the checked handle and skips cursor creation for `LIMIT 0`. The plan batch consumer evaluates the validated Filter prefix tree against scanned cells with SQL three-valued comparisons before projection; false and UNKNOWN rows do not count toward LIMIT. The bounded runner polls cancellation between pages, caps scan execution at 125 pages so plan comparison, cancellation, batch, setup and cursor-close calls fit the 256-request executor stream budget, honors LIMIT, and closes early cursors. The SQL SDK path submits parsed SELECT ASTs over ABI v4 and verifies returned relation, projections, LIMIT, Filter operators, predicate columns, and parameter values against the AST and executor-authorized metadata before executing. The parameterized bridge supports bounded comparisons, direct-column IS [NOT] NULL tests, and Boolean AND/OR/NOT with Boolean, INTEGER, DATE, UUID, TIMESTAMPTZ, BYTEA, DECIMAL, TEXT, and NULL parameters; unsupported forms return to the established SQL path. `prdb_sdk_optimizer_execute_select_ast_to_result_v1` and its parameterized counterpart write each projected row as a provisional SQLR v1 record through the host result callback.

An optional SELECT plan suffix `0xa1` carries a unique-index point-access hint: nonzero index ID[16], the complete bound key-column record, and one scalar predicate node for its Boolean, INTEGER, DATE, UUID, TIMESTAMPTZ, BYTEA, DECIMAL, or TEXT equality value. Rust emits this suffix only when the invocation's authorized metadata lists a single-column unique path and the bound root filter is exactly equality between that key and a same-typed literal. Rust decoding rechecks the hint against the scan shape and filter. The TinyCC decoder accepts the suffix only on SELECT, checks the index ID, key-column membership and scalar type, and requires the hint key/value to equal the filter's root equality. The SQL AST validator already requires that filter to match the parsed AST and parameters. The SDK then submits a bounded `ProbeUniqueIndex` request using the checked executor handle and all relation column IDs in ordinal order, so the sanitized probe row has the same shape expected by the existing filter/projection runner. `match` is consumed through the existing filter/projection/limit path, `no_match` returns zero rows, and `unavailable` or a too-small probe response falls back to a full authorized scan. Probe results contain sanitized cells and an opaque row handle. Cancellation is checked after a definitive probe result; fallback scans retain their normal cancellation checks and reserve one executor request in their page budget for the probe. Storage remains authoritative for path availability, key visibility, and the probe result.

An optional SELECT plan suffix `0xa2` carries a bounded leading-key range hint: nonzero index ID[16], the complete bound key-column record, then lower and upper bound flags (0 absent, 1 inclusive, 2 exclusive), each followed when present by one same-typed Boolean, INTEGER, DATE, UUID, TIMESTAMPTZ, BYTEA, DECIMAL, or TEXT literal. At least one bound is required. For an exact root equality comparison, both bounds carry the same inclusive literal. The planner uses this path for an authorized non-unique leading key or when an equality cannot use a single-column unique probe, such as a prefix of a composite unique path. An eligible single-column unique path uses the unique point probe. The planner emits a one-sided hint for an exact root `<`, `<=`, `>`, or `>=` comparison, or a two-sided hint for an exact two-term `AND` of one lower and one upper comparison on the same key; the lower and upper terms may appear in either order, and a literal may appear on either side of its comparison. It does not infer a range from `!=`, OR, extra conjunction terms, duplicate-direction bounds, or different key columns. The selected key must be the first column of an authorized unique or non-unique path. Both Rust and TinyCC decoders match the hint exactly to the root filter and scan shape. The SDK submits `ScanIndexRange` with all relation column IDs in ordinal order after executor relation validation. The result contains sanitized cells without row handles, so the SELECT runner keeps any internal adaptation private and exposes only filtered/projected results. A definitive bounded result uses the existing predicate/projection/LIMIT path. An unavailable path or result that exceeds the requested candidate/byte bound falls back to a full authorized scan; malformed wire data fails closed. Cancellation is checked after a definitive result, and fallback reserves one executor request in its page budget. The planner receives only paths whose indexed cells are statically readable and unconditionally allowed. Storage returns `unavailable` before scanning for matching keys when any indexed key column is not unconditionally readable in the invocation's projection, so an explicit range request yields the same response for matching and absent hidden keys. Storage remains authoritative for path availability and row/cell authorization.

## Storage and Statistics Access

Use a dedicated planning channel for authorized schema, logical access paths, and bounded estimation requests. This is a richer interface than the worker scan API but grants no broader data authority. The storage-owned [statistics service](statistics-service.md) performs collection and policy-aware estimation; the optimizer consumes results and compares candidate plans.

Request cardinality, authorized output size, selectivity, and eventually distinct-count/correlation estimates as supported. Each estimate identifies its population and uncertainty. A readable-cell estimate cannot substitute for an estimate over every visible row. An estimate never proves a query is authorized.

The planner cannot request unrestricted refresh jobs, access raw global catalogs, or submit native estimation callbacks. Each planner stream has a cumulative allowance of 16 storage estimate requests; once exhausted, storage returns `Unknown` and planning may continue with fixed heuristics. This estimate allowance is separate from the existing 256-request planner stream cap and the invocation deadline. Exhaustion of the overall planning budget, cancellation, or deadline expiry terminates planning. The supervisor checks cancellation and deadline at optimizer-planner request boundaries as well as while channels are idle, so a request arriving as the deadline expires cannot return a successful late estimate. Treat all returned metadata as potentially disclosed through plans, diagnostics, and executor output.

For ordinary single-table SELECT, the optimizer opts into a small-population probe by appending `52 03 01` to its planner relation request; storage returns a count only for populations of 0–4 after reading at most five row keys. Join planning requests a bounded authorized population estimate with marker `52 07` followed by a big-endian `u16` maximum of 16,384 rows. Storage reads at most 16,385 row keys, never decodes row values, and returns a count only when the complete authorized population is at most the requested maximum. Larger populations, value-dependent row policies, oversized private overlays, unsupported metadata, and exhausted allowance produce `Unknown` with no count. An exact count is appended as marker `52 04` followed by a `u64` big-endian count. Exact zero also carries the empty-view marker `52 02 01`, which lets single-table SELECT emit its independently validated no-scan hint. Exact populations of one through four rows select a sequential scan over an otherwise selected point or range path; larger or unknown populations retain the indexed path. For joins, exact zero or two known populations of at most four retain hash join. Exactly one known 1–4-row input may become the outer side of an eligible indexed nested-loop join. When both known populations exceed four, the optimizer may choose indexed nested-loop only when the smaller input has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash join. For moderate skew where the smaller side has 9–16 rows and the opposite side is at least eight times larger, or has 17–18 rows and the opposite side is at least seven times larger, storage may additionally return an exact authorized join-pair count through planner-only `EstimateScan` marker `52 08`; response marker `52 09` carries the big-endian count, with the standard unknown response for unsupported cases. This estimate requires both populations to be no larger than 16,384, value-independent row visibility, statically readable join-key cells, and a bounded one-to-eight-column composite key. It includes the pinned snapshot and private overlay. The optimizer uses indexed nested-loop only when the count is at most four output pairs per outer row; high fanout retains hash. Five-run confined 9×128 mixed-load profiles selected indexed nested-loop and measured it faster at one and four matches per outer row; a five-match profile selected hash in every run. Five confined 18×126 mixed-load runs at fanout one also selected indexed nested-loop, matched hash output, and overlapped 192 operational reads and commits each; median run-level p50 was 273.9 ms indexed versus 305.3 ms hash. Additional five-run 18×126 profiles select indexed nested-loop at exactly 72 pairs (four per outer; median run-level p50 259.8 ms indexed (247.1–309.9 ms range) versus 307.9 ms hash (299.0–338.0 ms range)) and hash at 73 pairs (348.5 ms median run-level p50; 327.1–361.7 ms range). Every run validates result equivalence and overlaps 192 operational reads and commits. These are host-local boundary checks, not general cost evidence. This is a bounded heuristic, not a general cost model. The measurements are host-specific and are not deployment performance targets. Other unknown estimates preserve the deterministic index fallback. This remains bounded planning rather than general cost-based planning. Five fresh-database runs with 11 timed iterations each found median-of-run p50 latencies (point/range/scan, ms) of 0.085/0.092/0.020 at 1 row and 0.085/0.093/0.049 at 4 rows. At 8 rows the medians were 0.087/0.093/0.089, and at 16 rows they were 0.088/0.096/0.168. One run measured the row-count probe itself at 0.012–0.026 ms across 1–4,097 row tables; this excludes planner relation resolution and projection loading. The four-row cutoff is conservative across both access types. These profiles are host-specific and do not measure end-to-end SQL latency. Estimates use the same 16-request allowance and remain advisory: they neither authorize execution nor relax executor validation. Ordered SELECT and other operations do not request a population estimate or spend allowance. When empty proof is present, the optimizer may append plan suffix `a3` to the canonical kind-1 SELECT plan. Rust and TinyCC validate it as a standalone empty-view hint, mutually exclusive with point/range access hints. The SDK still matches the physical plan against parsed SQL and re-resolves the relation through executor storage before checking cancellation and returning zero rows without opening a scan. The hint carries no permission and cannot be used for DML or other plan kinds. Without an exact estimate, ordinary planning and authorized scan fallback continue.

A repeated near-cutoff profile took five fresh-database runs, each with eleven samples, at total populations of 6, 7, 9, 11, and 13 rows. Median-of-run scan-plus-filter p50 values were 0.070, 0.080, 0.100, 0.120, and 0.142 ms; corresponding unique-point p50 values were 0.086, 0.085, 0.086, 0.086, and 0.090 ms. The direct storage API crossover for this one-match workload lies between seven and nine rows, but at seven rows the scan advantage is only about five microseconds, before planner/setup cost. The four-row cutoff is retained as the conservative choice. This profile is from one Linux x86_64 host and is not an end-to-end SQL or target-hardware result.

For a filtered ordinary unordered single-table SELECT, the optimizer also sends the bound predicate and qualified relation through the planner-only `EstimateScan` operation. Storage re-resolves the relation in the invocation context and evaluates only the supported predicate subset against at most 16,384 authorized rows whose referenced cells are all readable. Exact `(visible_rows, matching_rows)` results share the planner's 16-estimate allowance and per-estimate candidate budget. `matching_rows == 0` adds the existing `a3` empty-view hint. For an exact nonzero estimate, populations of one through four remove point or range hints and retain the Filter for a sequential scan. For larger populations, the optimizer removes a range hint when at least half of the visible rows match; it retains the Filter node. A unique point probe remains unchanged because its result cardinality is bounded to one row. The half-selectivity cutoff is a conservative heuristic from a local 130-row TEXT range-versus-scan profile: ranges matching 43% were faster than scans, at 49% the paths were near a crossover, and at 62% scans were faster. Unknown estimates retain the ordinary access choice. This bounded choice does not compare general plan costs and does not alter ordered SELECT, DML, joins, or aggregates; join planning uses only the separate row-population probes described above. The SDK continues to match the physical plan to parsed SQL and resolve the relation through executor storage before it skips the scan.

Additional direct-storage TEXT profiles support the access-path-only crossover locally: at 514 rows, five-run median-of-run p50s were 4.966 ms range versus 5.746 ms scan at 43% matches, 5.769 versus 5.565 ms at 49%, and 7.626 versus 6.037 ms at 62%. At 2,050 rows and 43% matches, five runs measured 21.579 ms range versus 25.323 ms scan. The exact predicate estimate now has a bounded index-entry count path when a fresh exact committed population, empty private overlay, all-rows-visible policy, and readable first-key index prove the result. At 2,052 rows and 882 matches, five fresh-database profiles had a median of run-level estimate p50s of 1.537 ms (1.494–1.599 ms), compared with the earlier full-row estimate's 26.103 ms. The index path counts at most 1,024 locators and 16 MiB of encoded keys; unsupported, untrusted, or oversized cases use the bounded row estimator. These direct-storage timings exclude planner IPC and SQL execution, so accounting for estimate acquisition in end-to-end plan cost remains open.

## Catalog and DDL Boundaries

Use only authorized catalog names/types and logical access paths from the pinned schema. Administrative DDL bypasses query optimization and goes to the validated control path; the optimizer cannot create tables, indexes, users, or policies. Plans bind stable catalog IDs and schema epochs. A published index is an optional storage access path, never a bypass for row/cell policies or version visibility.

Metadata binding also supports the fixed virtual relations in [metadata discovery](metadata-discovery.md). Their estimates and scans use filtered metadata only. The optimizer cannot inspect raw catalog records, physical roots, live cross-user registries, or privileged expression definitions. Cache validity follows [data dictionary](data-dictionary.md), including checks independent of notification delivery.

## Concurrent and Writable Plans

Produce read and mutation plans for the initial SQL subset. Plans contain logical targets and supported expressions, never permissions or commit decisions. Storage checks every staged mutation and commit independently. Plan input and estimates use the invocation snapshot plus its current private writes, identified by a transaction-local write generation. Replan/re-estimate after generation changes; no stale plan estimate can establish authorization.

Use bounded optimizer work across invocations. The current implementation starts one isolated optimizer process per admitted invocation and processes one submission at a time: the optimizer waits for each planner metadata response and returns that plan before reading the next submission. It therefore has no shared in-memory planner queue; pending START work is bounded by staging limits, and concurrent optimizer process count is bounded by class and per-principal active START limits. Each optimizer connection is also capped at 256 requests, while each planner stream separately caps requests and storage estimates. A single invocation initially has one active planning/statement stream. Internal statistics requests must hold storage-owned snapshot pins until completion even if the executor exits. Do not let planner completion race transaction closure or change the invocation snapshot.

## Workload Priorities

Follow [workload profile](workload-profile.md): prioritize point/range access and predictable operational latency on the row store. The analytical follow-on chooses bounded join/group/sort plans over authorized batches and scoped estimates. Avoid unbounded optimization effort for small transactions. Planner estimates cannot authorize hidden-key index probes or hidden-data aggregation. Resource class and budgets are supplied by admission, not enlarged by plan output.

## Optimization Constraints

Optimize the authorized view. Never push a hidden-value predicate, user function, or native callback ahead of authorization. Storage must independently validate any requested pushdown. Error behavior for redacted inputs is part of semantics and must be preserved by rewrites.

Global histograms, samples, counts, and private-data-derived cost estimates are unavailable to the planner. Use scoped authorized-view summaries or conservative heuristics. Shared plan caches must not cross permission boundaries or reveal protected metadata. Historical estimates must remain valid for the current authorization and snapshot; staleness is not solely a performance issue.

## Native Artifacts and Budgets

User query artifacts are compiled in the client and loaded only in confined executors. The [SDK specification](client-sdk.md) defines packaging and version checks. Keep native ABI and IPC versions separate. Native SQL-plan generation by the server is outside the baseline and would require a separate design decision.

Bound server planning independently from execution and statistics estimation. Client compilation has its own latency and resource profile. A planning failure returns a bounded error and releases temporary resources; it must not fall back to executing user code inside storage.

## Validation and Limits

Test malformed queries, resource exhaustion, invalid output, unauthorized metadata requests, estimation probes, heuristic fallback, and rewrites involving redacted inputs. Compare SDK SQL execution with reference results on authorized data. Verify that changing only inaccessible data does not change released estimate content for a fixed authorized view.

Isolation protects data boundaries, not semantic correctness. Whether generated plans are trusted for correct results or require additional validation remains a separate research decision.
