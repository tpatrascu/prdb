# Schema Definition Language

## Scope and Execution

This document defines proposed SQL-like schema DDL, not an implemented parser or PostgreSQL compatibility promise. Users and roles are defined in [identity DDL](ddl-identity.md); row/cell rules are defined in [permission DDL](ddl-permissions.md).

DDL runs through a separately authenticated administrative SDK/control channel. The client may parse text, but storage independently parses or validates a bounded structured definition and checks administrative privileges. Query executors cannot call this channel or execute DDL inside their invocation transaction. Definitions in the SDK confer no authority.

Administrative row/index rewrite ceilings and request/work budgets in this specification are trusted maintenance-profile defaults, not immutable product limits. Validate and configure them separately from query profiles; a schema operation that exceeds its active budget must fail atomically without partial publication. Identifier, scalar-width, and catalog/ABI field constraints remain fixed-format limits unless a versioned format change explicitly extends them.

Each administrative submission contains one statement or an explicit atomic batch of DDL statements; it cannot mix user native execution or DML. Catalog changes, identity changes, and permissions share storage's durable commit ordering. Administrative requests have IDs, budgets, cancellation, and outcome lookup, just like transaction finalization.

## Names, Schemas, and Types

Initially one database per storage-manager instance, containing named schemas. `CREATE DATABASE`, federation, and cross-database references are future extensions.

`CREATE SCHEMA` is available through the v1 `schemas.create` authenticated control operation for normalized lowercase ASCII names of at most 128 bytes, with an existing user or role assigned as owner. The caller must have inherited database-scoped `CREATE_SCHEMA` or be a database administrator. Creation publishes the schema record, owned object record, audit event, and operation outcome in one commit. `ALTER SCHEMA ... RENAME TO ...` is available through `schemas.rename`; the schema owner (including inherited membership in an owning role), an inherited schema-scoped `ALTER` grantee, or a database administrator may rename a non-system schema. The stable schema ID and contents remain unchanged; final schema-name uniqueness is checked in the serialized writer. `DROP SCHEMA ... RESTRICT` is available through `schemas.drop`; the schema owner, an inherited schema-scoped `ALTER` grantee, or a database administrator may drop an empty schema. The authenticated SQL convenience also accepts `DROP SCHEMA IF EXISTS name RESTRICT`. A resolved schema follows the ordinary owner/ALTER/database-admin authorization and emptiness checks. An unresolved schema is a successful no-op only after database-admin authority is confirmed; no DDL mutation or outcome is created for that no-op, and other failures are not suppressed. `schemas.set_owner` transfers a non-system schema to a live user or role; the current owner, an inherited schema-scoped `ALTER` grantee, or a database administrator may request the change. A schema owner may create tables and manage the schema but receives no table data privileges. The owner object and version change atomically; schema contents remain unchanged. System schemas and schemas with child objects or remaining catalog dependencies are rejected by drop. Storage checks emptiness again in the serialized write transaction before atomically deleting the schema and owned object records. The authenticated SQL convenience accepts `ALTER SCHEMA name OWNER TO owner_name|USER owner_name|ROLE owner_name`; an owner or effective schema-scoped ALTER grantee resolves the destination name through a target-scoped lookup that does not enumerate identities, then storage rechecks mutation authority. The control operations accept structured arguments rather than SQL text; quoted mixed-case names remain unsupported.

The authenticated `prdb-client admin-sql` convenience accepts `CREATE SCHEMA [IF NOT EXISTS] name` to assign ownership to the authenticated principal, `CREATE SCHEMA name AUTHORIZATION 'uuid'` with a hexadecimal UUID owner (optional standard hyphens), or a name-resolved `AUTHORIZATION owner_name` clause. Typed `AUTHORIZATION USER owner_name` and `AUTHORIZATION ROLE owner_name` forms are also accepted. Name forms resolve the live identity through authenticated metadata before invoking `schemas.create`; an untyped name uses the globally unique principal-name index and the matching identity-management authority. Omitted ownership is resolved by the server to the authenticated actor, and storage independently validates the owner and caller authority. If `IF NOT EXISTS` resolves an existing schema, only a database administrator receives a successful no-op; no DDL outcome is created. Otherwise creation uses the normal `schemas.create` authorization and atomic publication path.

The storage manager's initial `create_table` path accepts a structured schema ID, normalized table name, and 1–4096 ordered columns. This 4096-column ceiling is the current implementation envelope, not the intended product maximum: the trusted maintenance/schema profile must make the admitted per-relation column budget configurable within the validated catalog, identifier, codec, and metadata envelopes. Raising it beyond those envelopes requires a compatible versioned extension. The illustrative ERP/CRM workload includes master relations with 80–250 declared columns, so acceptance must cover wide schemas and projections over them even when a small fixture remains the correctness default. Each column has a normalized name, one built-in scalar type, nullability, optional UUID generated-identity mode, and optional typed literal, NULL, or `CURRENT_PRINCIPAL_ID` default. Defaults are stored as immutable catalog expressions and evaluated by the existing insert path. Generated UUID identity cannot also have a default. The `tables.create` operation may also include an ordered, distinct list of non-nullable column names for a PRIMARY KEY. The table, columns, defaults, primary-key constraint, owned unique index, dependencies, audit event, and outcome publish atomically. It requires inherited `CREATE` on the schema, schema ownership (including inherited membership in an owning role), or database-administrator membership; duplicate table names reject. `CREATE TABLE IF NOT EXISTS` is an authenticated SQL convenience: absent tables use that same create path, while a resolved existing table is a successful no-op only for a database administrator and creates no DDL outcome. The form does not compare or reconcile the existing definition; non-administrators cannot use it to test for a hidden relation. New tables receive no data grants. Built-in system schemas are reserved. The authenticated `tables.create` control operation exposes this structured path. `AdminClient::execute_create_table_sql` is a client-side convenience over that operation for the limited SQL form documented below; the wire protocol carries typed structured arguments.

`ALTER TABLE ... ADD COLUMN` is available through `tables.add_column` with a table ID and one column definition. The table owner (including inherited membership in an owning role) or a database administrator may add a column to a non-system table. The new column is appended, receives no implicit grants, and cannot be a generated identity. A NOT NULL column requires a valid typed literal default; a nullable column may omit the default, which backfills NULL. `CURRENT_PRINCIPAL_ID` is rejected because a backfill must use one immutable value for all existing rows. The literal is recorded as both the initial insert default and immutable add-column default. Storage advances schema version and write epoch, rewrites every persisted tuple while preserving row IDs, and updates index definitions and row locators atomically under the table DDL fence. The rewrite is limited to 65,536 rows and 64 MiB of combined old and new tuple payloads; larger changes abort without publication. Existing snapshots retain the previous schema and rows.

`ALTER TABLE ... OWNER TO ...` is available through `tables.set_owner` with a table ID and the destination owner ID. The current table owner, a principal with effective `ALTER` on the table or its schema, or a database administrator may transfer a non-system table to a live user or role. The table object's owner and object version change atomically with the table write epoch; tuple schema version, rows, indexes, and grants remain unchanged. Ownership gives the new owner table-level DDL authority, but grants no SELECT/INSERT/UPDATE/DELETE privileges. Existing owners and authorized roles may still transfer ownership while they retain authority.

For authenticated SQL `ALTER TABLE ... OWNER TO USER|ROLE name`, an owner or effective table/schema `ALTER` grantee may resolve the destination identity name through a table-scoped control lookup. The lookup returns no identity for absent names or callers without target ALTER authority. It reveals only the matching identity ID; the typed owner-transfer mutation independently validates the destination and rechecks the actor's authority.

`DROP TABLE ... RESTRICT` is available through `tables.drop`. The table owner (including inherited membership in an owning role), a principal with effective `ALTER` on the table or its schema, or a database administrator may request it. Built-in system schemas cannot be dropped through this operation. Incoming catalog dependencies reject the drop. In one authorized commit, storage removes the table, owned columns, constraints, indexes, policies, default/check/policy expressions, corresponding grants and dependency edges, row data, and physical index entries, and permanently reserves the table ID in family 17. Cleanup is bounded by 65,536 rows, 65,536 index entries, and 64 MiB combined row tuple payload plus physical index key and locator bytes per commit; larger drops fail without changing the catalog or data. Storage rechecks incoming dependencies in the serialized DDL path, and the normal catalog conflict checks protect the discovered delete set and reservation. The authenticated SQL convenience also accepts `DROP TABLE IF EXISTS schema.table RESTRICT`. If the target resolves, it follows the ordinary table-drop authorization and dependency checks. If the schema or table cannot be resolved, the client first verifies database-administrator authority through the authenticated runtime metadata operation; only an administrator receives a successful no-op. This restriction is necessary because an absent table has no table owner whose authority can be checked. Non-administrators receive an error, and no DDL mutation or outcome is created for the no-op. Other failures, including RESTRICT dependency failures for a present table, are never suppressed.

`ALTER TABLE ... DROP COLUMN ... RESTRICT` is available through `tables.drop_column` with table and column IDs. The table owner (including inherited membership in an owning role) or a database administrator may request it; built-in system schemas are rejected. Constraints, expressions, indexes, and policies that reference the column block the operation. Storage removes the column's own default expression, dependent grant records, and dependency edges, compacts surviving column ordinals, increments schema version and write epoch, and rewrites persisted tuples and surviving index keys in one fenced commit. The row scan is bounded by 65,536 rows and 64 MiB of combined old and rewritten tuple payloads; larger drops fail without publication. Existing rows retain their surviving values and row identities.

`ALTER TABLE ... RENAME TO ...` is available through `tables.rename` using a table ID and normalized new name. The table owner (including inherited membership in an owning role), a principal with effective `ALTER` on the table or its schema, or a database administrator may rename a non-system table. Name uniqueness within the schema is checked in the serialized final catalog. The stable table ID and tuple schema version do not change; storage increments the table write epoch and object version so stale writers are rejected while existing row tuples and index keys remain valid.

```sql
CREATE SCHEMA app AUTHORIZATION app_owner;
ALTER SCHEMA app RENAME TO application;
ALTER SCHEMA application OWNER TO app_owner;
DROP SCHEMA application RESTRICT;
```

Unquoted identifiers fold to lowercase; double-quoted identifiers preserve case. Require schema-qualified names in administrative definitions and stored dependencies. Resolve client unqualified names against an explicit admitted default schema, never an uncontrolled search path. Catalog record layouts, indexes, and dependencies are defined in [data dictionary](data-dictionary.md). Object and column identities are stable catalog IDs; renames do not retarget dependencies. New objects never reuse a dropped object's identity.

Initial scalar types: `BOOLEAN`, `SMALLINT`, `INTEGER`, `BIGINT`, `DECIMAL(p,s)` with `1 <= p <= 38` and `0 <= s <= p`, `TEXT`, `VARCHAR(n)`, `BYTEA`, `UUID`, `DATE`, and `TIMESTAMP WITH TIME ZONE`. Integers are signed with checked overflow. Decimal is exact; implicit lossy conversions fail. Text is valid UTF-8 with a deterministic binary collation initially; `VARCHAR(n)` limits Unicode scalar count. Timestamps normalize to UTC at microsecond precision. [redb storage](redb-storage.md) defines storage scalar encodings and supported DATE/TIMESTAMPTZ ranges; tuple encoding and SQL SDK value/parameter validation enforce those ranges, while storage continues to validate independently. Arrays, JSON, enums, custom types, and locale collations are deferred.

## Tables, Defaults, and Constraints

CHECK and policy expressions also accept SQL Boolean tests `boolean_expression IS [NOT] TRUE`, `FALSE`, or `UNKNOWN` in CREATE TABLE, ALTER CHECK, and policy SQL. The operand may be a BOOLEAN column, a parenthesized Boolean expression, or a Boolean policy expression where allowed; other scalar types reject during binding. `IS TRUE` and `IS FALSE` return false for NULL, `IS UNKNOWN` is equivalent to `IS NULL`, and each `IS NOT` form negates the corresponding two-valued test. The client lowers these forms to existing EIR1 Boolean, equality, and null-test nodes; there is no new stored expression encoding.

For SQL name binding, an effective schema-scoped `CREATE` grantee may resolve the schema name needed by `CREATE TABLE` even without schema `USAGE`. This control metadata read reveals no relation names or columns; table creation still goes through the typed operation, which independently checks the caller's current `CREATE` authority.
The authenticated `AdminClient::execute_create_table_sql` convenience method accepts a restricted SQL form: schema-qualified `CREATE TABLE` with one or more columns, supported scalar types (including bounded `DECIMAL(p,s)` and `VARCHAR(n)`), optional `NOT NULL`, typed `DEFAULT` modifiers, `UUID GENERATED ALWAYS AS IDENTITY`, and optional column-level `PRIMARY KEY`, `UNIQUE`, `[CONSTRAINT name] CHECK (expression)`, or `REFERENCES schema.table (column)` plus final table-level `PRIMARY KEY (column, ...)`, `UNIQUE (column, ...)`, `[CONSTRAINT name] CHECK (expression)`, and `FOREIGN KEY (columns...) REFERENCES schema.table (columns...)` constraints. At most one PRIMARY KEY is accepted; multiple distinct UNIQUE, CHECK, and FOREIGN KEY definitions are supported. Column-level PRIMARY KEY and UNIQUE are equivalent to one-column table-level constraints; a column-level primary key implies NOT NULL, and duplicate key definitions reject. Column-level CHECK uses the same Boolean expression grammar but may reference only its declared column; table-level CHECK can reference multiple columns. Identity implies NOT NULL and excludes DEFAULT. A primary key implies NOT NULL for its columns; primary and unique constraints receive owned unique indexes, and table, columns, constraints, indexes, CHECK expressions, FK dependencies, and referenced-table write epochs publish in the same atomic operation. UNIQUE permits nullable columns, with NULL tuples remaining distinct. Unquoted identifiers use the normalized lowercase ASCII profile and are limited to 128 bytes. It resolves the schema on the same control connection and uses the typed `tables.create` PREPARE/START operation. Omitted nullability means nullable. `DEFAULT` accepts typed boolean, signed integer, exact DECIMAL, quoted text/VARCHAR, `X'hex'` BYTEA, quoted UUID, engine-epoch DATE/TIMESTAMPTZ integer, SQL NULL, or UUID `CURRENT_PRINCIPAL_ID()` literals. Decimal rescaling is exact and precision overflow rejects. CREATE TABLE CHECK accepts Boolean column references, `IS [NOT] NULL` on supported scalar expressions, `NOT`, `AND`, `OR`, parentheses, and comparisons using `=`, `!=`, `<>`, `<`, `<=`, `>`, and `>=`, plus `IN`/`NOT IN` with 1–64 supported scalar expressions as values on any supported scalar expression and `BETWEEN`/`NOT BETWEEN` with two supported scalar expressions as bounds on any supported scalar expression. `IS [NOT] DISTINCT FROM` accepts any supported scalar expression on each side, including expressions that evaluate to NULL. Literal operands bind to the tested expression type, and these predicates preserve SQL null semantics. Scalar expressions also accept integer `+`, binary `-`, `*`, `/`, `%`, and unary `-`; `*`, `/`, and `%` share multiplicative precedence, above addition and subtraction. Unary `-` binds more tightly and accepts a supported integer scalar expression. Binary operands must resolve to the same SMALLINT, INTEGER, or BIGINT type. NULL propagates through arithmetic. Overflow and modulo by zero fail closed during row validation. The signed minimum modulo `-1` also fails closed because the remainder operation overflows. DECIMAL arithmetic remains unsupported. Integer `/` truncates toward zero; division by zero and signed minimum divided by `-1` fail closed during row validation. Unary negation overflow also fails closed for the minimum signed integer. The EIR1 envelope remains readable at versions 1–4 and writes version 5 for unary negation; existing catalog expression metadata remains at its original version. Comparisons bind supported scalar expressions on both sides; literals use the opposite operand type and support boolean, signed integer, exact DECIMAL, quoted text/VARCHAR/UUID, `X'hex'` BYTEA, engine-epoch DATE/TIMESTAMPTZ integers, and SQL NULL. Mismatched scalar types and lossy DECIMAL rescaling are rejected. A CREATE TABLE foreign key may reference an existing schema-qualified table’s visible PRIMARY KEY or UNIQUE constraint, or a PRIMARY KEY/UNIQUE declared in the same CREATE TABLE. It must use the same ordered key columns and exact source/target scalar types; external targets require REFERENCES authority on the target table or columns. A self-referencing FK targets the table's same-statement key, creates its dependency and physical index metadata atomically with the table, and relies on the caller's CREATE authority for that table instead of a pre-existing REFERENCES grant. Column-level REFERENCES creates a one-column foreign key and follows the same target-key and authority rules. Named PRIMARY KEY, UNIQUE, CHECK, and FOREIGN KEY constraints are supported in column or table form where applicable, reject duplicate names across one CREATE TABLE statement, and retain their names in the catalog. Any explicitly named constraint can be resolved through authenticated metadata and dropped by name; generated IDs remain available for unnamed constraints. Quoted identifiers and multiple statements remain unsupported in this CREATE TABLE SQL path. The same authenticated `admin-sql` command accepts `CREATE SCHEMA name AUTHORIZATION 'uuid'` with an explicit hexadecimal UUID owner and maps it to `schemas.create`. The query-library SQL dispatcher continues to reject all DDL. The authenticated `admin-sql` path supports `ALTER TABLE schema.table ADD COLUMN name type [NOT NULL] [DEFAULT literal]` for one appended column, with the same typed scalar/default rules as CREATE TABLE except `CURRENT_PRINCIPAL_ID()` is rejected for backfill. It resolves the table over authenticated metadata and calls `tables.add_column`; storage performs bounded row/index/locator rewrites under the table DDL fence. It also supports `ALTER TABLE schema.table DROP COLUMN column RESTRICT`, resolving the column through authenticated metadata before invoking `tables.drop_column`; storage rejects dependencies and performs the bounded tuple/index rewrite atomically. The path supports `ALTER TABLE schema.table RENAME COLUMN old_name TO new_name`, resolving the column through authenticated metadata before invoking `tables.rename_column`; storage preserves its stable identity and atomically advances its object version and table write epoch. The path also supports `ALTER TABLE schema.table ALTER COLUMN column SET NOT NULL` and `DROP NOT NULL`, resolving column names through authenticated metadata before invoking `tables.alter_column_nullability`; the storage path remains responsible for validating existing rows and advancing write epochs. `ALTER COLUMN ... SET DEFAULT literal` and `DROP DEFAULT` resolve the declared type and nullability through authenticated metadata, bind one typed default literal, and invoke `tables.set_column_default` or `tables.drop_column_default`. Existing rows are not rewritten; storage rejects identical or absent default changes and advances the table write epoch. The same path supports `ALTER TABLE schema.table ADD [CONSTRAINT name] CHECK (expression)` with Boolean column references, `IS [NOT] NULL` on supported scalar expressions, `NOT`, `AND`, `OR`, parentheses, and typed comparisons using `=`, `!=`, `<>`, `<`, `<=`, `>`, and `>=`, `IN`/`NOT IN` with 1–64 supported scalar expressions as values on any supported scalar expression, `BETWEEN`/`NOT BETWEEN` with two supported scalar expressions as bounds on any supported scalar expression, and `IS [NOT] DISTINCT FROM` over any supported scalar expression on each side, including SQL NULL. These CHECK expressions also accept same-type SMALLINT, INTEGER, and BIGINT `+`, binary `-`, `*`, `/`, `%`, and unary `-` arithmetic; `*`, `/`, and `%` share multiplicative precedence, NULL propagates, and overflow, division/modulo by zero, or signed minimum divided/modulo by `-1` fails closed; negating a signed minimum also fails closed. Literal operands bind to the tested expression type, and these predicates preserve SQL null semantics. Comparisons bind against visible column types and accept the typed scalar literal forms documented above, including SQL NULL. It resolves every referenced column through control metadata and binds names to stable column IDs and ordinals before sending EIR1 through `constraints.create_check`. A supplied name is normalized lowercase ASCII, limited to 128 bytes, unique within the table's constraint objects, retained in the catalog object, and only displaces the generated name on this CHECK object. `DROP CONSTRAINT name` resolves and drops any explicitly named PRIMARY KEY, UNIQUE, CHECK, or FOREIGN KEY through authenticated constraint metadata; generated IDs remain supported for unnamed constraints. `DROP CONSTRAINT IF EXISTS` accepts either target form and suppresses only an unresolved target for a database administrator. Duplicate-name validation follows table DDL authorization and returns a durable ABORTED outcome on conflict. Expressions outside this bounded row-local language remain unsupported.

The bounded ALTER TABLE foreign-key form is `ADD [CONSTRAINT name] FOREIGN KEY (source_columns...) REFERENCES target_schema.target_table (target_columns...)`. Addition resolves both relations and columns through authenticated metadata and requires the referenced ordered columns to match a visible PRIMARY KEY or UNIQUE constraint. An optional normalized constraint name is sent with operation version 2; version 1 remains valid for unnamed requests. The authorized commit checks table-local constraint-name uniqueness after ALTER and REFERENCES authorization. The typed foreign-key operation and storage validate authority, column compatibility, existing rows, and dependency publication across both tables. `DROP CONSTRAINT 'generated-id'` accepts the generated ID of a PRIMARY KEY, UNIQUE, CHECK, or FOREIGN KEY constraint only after confirming that the ID belongs to the selected source table; it dispatches the matching typed drop operation. `DROP CONSTRAINT IF EXISTS 'generated-id'` suppresses an unresolved constraint only for a database administrator. Explicitly named PRIMARY KEY, UNIQUE, CHECK, and FOREIGN KEY constraints can instead be dropped by normalized name through SQL metadata resolution; unnamed constraints remain addressable by their generated ID. Administrative constraint metadata includes the catalog object name alongside the stable ID and kind.

```sql
CREATE TABLE app.employees (
    id UUID GENERATED ALWAYS AS IDENTITY,
    department_id UUID NOT NULL,
    manager_id UUID NOT NULL,
    name TEXT NOT NULL,
    salary DECIMAL(12,2),
    active BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT salary_nonnegative CHECK (salary >= 0),
    PRIMARY KEY (id)
);
```

`UUID GENERATED ALWAYS AS IDENTITY` is this engine's extension: storage allocates an opaque non-sequential ID, rejects explicit overrides, and checks collisions. Every table has a stable internal identity even when its SQL primary key is user-supplied. No global sequence values are exposed by default.

Catalog-backed executor INSERT materializes generated identities only from DEFAULT, rejects caller-supplied identity values, and checks UUID collisions against the serialized final table state at commit. Updates reject patches to generated identity columns. The lower-level materialized-row helper remains a trusted internal boundary.

Supported constraints:

| Definition | Semantics |
| --- | --- |
| `NOT NULL` | Reject a null value. |
| `PRIMARY KEY (a, b)` | At most one per table; all fields non-null and the tuple unique. |
| `UNIQUE (a, b)` | Enforce tuple uniqueness; rows with any null key field do not conflict initially. |
| `CHECK (expression)` | Bounded deterministic row-local expression; false fails, true or SQL unknown passes. Use `NOT NULL` separately. |
| `FOREIGN KEY (...) REFERENCES schema.table (...)` | Referenced fields must name a primary/unique key in the same order and have identical built-in scalar types, including declared parameters. `MATCH SIMPLE`: any null referencing field exempts that row. |

Constraints operate on full storage values, not redacted projections. Only built-in typed expressions are allowed; no native functions, subqueries, or external callbacks. Defaults are typed literals or fixed trusted built-ins, initially generated identity and `CURRENT_PRINCIPAL_ID()`. Defaults are applied before creation policies and constraints, but do not bypass field/row permissions. `CURRENT_PRINCIPAL_ID()` is a server value, never a parameter chosen by the query.

For `CHECK`, evaluate the trusted, schema-bound, deterministic row-local expression over the complete proposed tuple. Accept TRUE and SQL UNKNOWN; reject FALSE. Evaluation is bounded and type/runtime errors abort the invocation. CHECK additions validate all existing rows before publication, within the row and byte limits in [permission DDL](ddl-permissions.md). A CHECK definition or any schema inputs used to bind it must be included in the transaction's guarded catalog dependencies.

Primary, unique, and foreign-key constraints are part of the initial schema design. Defining a foreign key requires source-table ALTER/creation authority and REFERENCES authority on an existing target key. A foreign key in the same CREATE TABLE statement may instead reference a PRIMARY KEY or UNIQUE constraint declared by that statement; source-table creation authority covers this self-reference, and the table, generated FK target identity, dependency, and index metadata publish atomically. Foreign keys initially support only `ON UPDATE RESTRICT` and `ON DELETE RESTRICT`; cascading actions and deferrable constraints are deferred. User-defined native constraints remain forbidden. `StorageManager::create_foreign_key` accepts ordered source columns and a referenced PRIMARY KEY or UNIQUE constraint, generates the FK identity, and validates/publishes through the authorized FK DDL path. The authenticated ADMIN `foreign_keys.create` operation exposes this structured path. `StorageManager::drop_foreign_key` atomically removes and reserves the FK constraint ID while advancing both participating table epochs. CREATE TABLE SQL resolves external references through authenticated metadata, resolves self-references against keys declared in the same statement, and publishes new-table FK records, dependencies, and referenced-table write epochs in the same create commit. `AdminClient::execute_add_key_constraint_sql` accepts qualified `ALTER TABLE ... ADD [CONSTRAINT name] PRIMARY KEY (...)` and `ADD [CONSTRAINT name] UNIQUE (...)`; named forms use operation version 2, preserve version 1 for unnamed requests, persist optional names on the constraint object, and reject table-local name collisions after authority checks. `AdminClient::execute_add_foreign_key_sql` accepts optional `CONSTRAINT name` on its ADD FOREIGN KEY form and routes it through foreign_keys.create v2. These SQL binders resolve ordered column names through authenticated metadata and dispatch the existing authorized DDL operations. `StorageManager::create_unique_constraint` and authenticated ADMIN `constraints.create_unique` add a UNIQUE constraint with its owned, backfilled unique index; NULL tuples remain distinct. `StorageManager::create_primary_key` and authenticated ADMIN `constraints.create_primary_key` add a PRIMARY KEY and its owned unique index; all key columns must already be non-nullable. Both key creation paths validate and backfill existing rows under the table DDL fence. `StorageManager::commit_authorized_foreign_key_ddl` and `StorageManager::commit_authorized_constraint_ddl` remain trusted structured catalog entry points. The constraint route authorizes `NOT NULL`, CHECK, PRIMARY KEY, and UNIQUE add/drop through ownership or inherited ALTER. CHECK additions bind to the final table schema and validate existing rows before publication. These routes accept structured catalog changes from the separately authenticated administrative caller, not SQL text from an executor.

Stage-time checks can reject obvious failures early. Before committing, storage validates uniqueness and referential integrity against the latest committed state plus the transaction's final private changes under commit serialization. Creating a foreign key also validates all existing non-NULL child tuples against the referenced key set before publishing the constraint. Validate both child insert/update and parent delete/key-change directions, including concurrent transactions. Abort the whole invocation on violation. This protects these declared constraints but does not make general snapshot-isolated transactions serializable.

The initial reference-scan implementation bounds combined persisted and staged row visits across foreign-key validation to 65,536 per commit and the encoded comparison-key sets for one FK check to 16 MiB. Exceeding either limit aborts the whole invocation; implementations must not skip validation or partially commit to satisfy the budget. An indexed validation strategy may replace the reference scans while preserving the same final-state and concurrency guarantees.

Constraint outcomes can reveal that a hidden conflicting/referenced key exists. Do not return protected values or row identities in diagnostics; nevertheless this logical inference is an explicit limitation of exposing globally constrained writes. Definitions and grants must be reviewed with that implication; redaction cannot eliminate it.

## Alter and Drop

```sql
ALTER TABLE app.employees ADD COLUMN title TEXT;
ALTER TABLE app.employees ADD COLUMN IF NOT EXISTS title TEXT;
ALTER TABLE app.employees RENAME COLUMN title TO job_title;
ALTER TABLE app.employees ALTER COLUMN active SET DEFAULT TRUE;
ALTER TABLE app.employees ALTER COLUMN salary SET NOT NULL;
ALTER TABLE app.employees ADD UNIQUE (department_id, name);
ALTER TABLE app.employees DROP CONSTRAINT '01234567-89ab-cdef-0123-456789abcdef';
ALTER TABLE app.employees DROP COLUMN job_title RESTRICT;
ALTER TABLE app.employees RENAME TO staff;
ALTER TABLE app.staff OWNER TO app_owner;
TRUNCATE TABLE app.staff RESTRICT;
DROP TABLE app.staff RESTRICT;
```

Support nullable column addition, typed literal defaults, rename, default changes, `SET/DROP NOT NULL`, `SET/DROP DEFAULT`, constraint add/drop, ownership transfer, and restricted column/table drop. Adding a non-null field requires a valid literal default and validating existing rows. Existing rows acquire the add-column default as of that DDL change; later default changes affect future inserts only. Context-dependent defaults are not allowed for backfilling existing rows. General type-changing rewrites, computed columns, partitioning, temporary tables, user-created views, triggers, stored procedures, and explicit sequences are deferred. `TRUNCATE TABLE schema.table RESTRICT` is available through the authenticated control path and SQL convenience. It atomically removes all row records and physical index memberships while preserving table, column, constraint, policy, and index definitions and stable IDs. Any incoming foreign-key dependency rejects truncation, regardless of current child-row count. The operation is limited to 65,536 rows and 64 MiB combined row-record and index-key/locator bytes per commit; an over-limit request aborts without publication. It advances the table write epoch so stale writers conflict, and older snapshots retain the pre-truncate rows and index view. The table owner, effective table/schema `ALTER` grantee, or a database administrator may truncate. A bounded type-changing exception is `ALTER TABLE schema.table ALTER COLUMN column TYPE VARCHAR(n)`: it may widen an existing `VARCHAR(m)` only when `n > m`. This metadata-only change preserves the tuple schema version, stored values, stable column ID, dependent definitions, and index key bytes; it advances the table write epoch so stale writers abort. Index definitions remain at the same tuple schema version because the encoded key representation is unchanged. Existing values need no rewrite because they were valid under the smaller declared limit. Shrinking, cross-type conversion, `USING`, and same-width requests fail without publication. The operation requires table ownership, effective table/schema `ALTER`, or database-admin membership; commit-time authorization and version checks remain authoritative.

`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` is an authenticated SQL convenience. An absent column follows the ordinary typed `tables.add_column` path. A resolved existing column is a no-op only for a database administrator, after authority confirmation; the no-op creates no DDL outcome and does not compare or reconcile the requested definition. Other failures are not suppressed.

Changing nullability on an existing column is available through `tables.alter_column_nullability` with a table ID, column ID, and string `nullable` value (`"true"` or `"false"`). It preserves the tuple schema version because its encoded layout does not change; the table write epoch advances to invalidate stale writers. `SET NOT NULL` scans current persisted rows under the exclusive table fence and aborts with a constraint violation if any value is NULL. Validation is bounded to 65,536 rows and 64 MiB of row-record bytes per commit; larger tables fail without publication. `DROP NOT NULL` removes the matching internal constraint when present and marks the column nullable.

The authenticated `admin-sql` command accepts `ALTER TABLE schema.table ALTER COLUMN column SET NOT NULL` and `... DROP NOT NULL`. It resolves the table and column through authenticated metadata and submits the existing typed operation, which rechecks authorization and validates rows under the table DDL fence.

`ALTER TABLE ... RENAME COLUMN` is available through `tables.rename_column` with table ID, column ID, and normalized new name. The table owner (including inherited ownership through a role), a principal with effective `ALTER` on the table or its schema, or a database administrator may rename a column on a non-system table. The column ID, ordinal, type, nullability, defaults, dependencies, and tuple schema version remain unchanged; the table write epoch and column object version advance. The family 2 object name and family 6 column name update atomically, and table-local column-name uniqueness is checked against the serialized final catalog.

The authenticated `admin-sql` command also accepts `ALTER TABLE schema.table DROP COLUMN IF EXISTS column RESTRICT`. A resolved column follows the normal table-owner/database-administrator authorization, dependency checks, and bounded rewrite. An unresolved schema, table, or column is a successful no-op only after database-administrator authority is confirmed; the no-op creates no DDL outcome. Other failures, including a present column blocked by RESTRICT dependencies, are not suppressed.

`tables.set_column_default` sets or replaces a current insert default on a non-generated column. PREPARE supplies `{ "table_id": id, "column_id": id, "type": type, "default": { ... } }`; the default uses the same typed literal, `null`, or `current_principal_id` forms as `tables.create`. The table owner (including inherited ownership through a role) or a database administrator may change defaults on a non-system table. The default mask and declared scalar type are checked, including UUID-only `CURRENT_PRINCIPAL_ID`; existing rows are not rewritten. `tables.drop_column_default` removes the current default. Both operations atomically update the column's current-default expression reference and table write epoch, while preserving schema version and the immutable add-column default reference. Replaced or dropped expression objects and column dependency edges are removed in the same commit. Setting an identical default or dropping an absent default is rejected.

Default drop mode is `RESTRICT`: dependencies prevent removing an object still referenced elsewhere. Dropping a column is blocked by its policies, constraints, and indexes; when permitted, it atomically removes and reserves the column ID and any owned default-expression IDs. `DROP POLICY` reserves the removed policy and expression object IDs in the same transaction as its target, dependency, and table-epoch changes. Dropping a table removes its owned column/index/constraint/policy definitions atomically and reserves the table and every removed table-owned object ID in family 17, including columns, expressions, constraints, indexes, and policies; external references such as another table's foreign key still block the drop. Dropping an ordinary index also reserves its ID; dropping a PRIMARY KEY or UNIQUE constraint atomically removes and reserves both the constraint ID and its owned backing-index ID. Dropping a CHECK or NOT NULL constraint reserves the constraint ID and any owned expression ID. Dropping a schema requires it to be empty and atomically writes a family-17 permanent ID reservation with removal of its schema and object records. Recreating any retired ID is rejected. User and role IDs share the same reservation family; retirement of other object kinds remains open. No implicit cross-object cascade is supported. `IF EXISTS`/`IF NOT EXISTS` may suppress existence errors only after checking authority; they never reconcile incompatible definitions. For `DROP TABLE IF EXISTS`, `DROP SCHEMA IF EXISTS`, and `DROP INDEX IF EXISTS`, the absent-object no-op is database-administrator-only and creates no DDL outcome; a present object follows its regular authorization and RESTRICT checks. Adding a column grants no field privileges automatically.

## Indexes

```sql
CREATE INDEX employees_department ON app.employees USING BTREE (department_id, name);
CREATE UNIQUE INDEX employees_unique_name ON app.employees (department_id, name);
ALTER INDEX app.employees_department RENAME TO employees_by_department;
DROP INDEX app.employees_department RESTRICT;
DROP INDEX IF EXISTS app.employees_department RESTRICT;
REBUILD INDEX app.employees_department;
ALTER INDEX app.employees_department REBUILD USING BTREE NONUNIQUE (department_id, name);
```

Index names live in the table's schema. Initial indexes are B-trees on one or more plain columns, ascending with nulls last. `CREATE [UNIQUE] INDEX IF NOT EXISTS` creates an absent index through the regular typed operation; an existing logical index is a no-op only for a database administrator and creates no DDL outcome. The existing definition is not compared or reconciled. `ALTER INDEX schema.name RENAME TO new_name` updates only the logical catalog name and object version, preserves the stable index ID and physical memberships, and records the DDL audit/outcome atomically. The caller must have ordinary index DDL authority (table ownership, an inherited `INDEX` grant, or database-admin membership); the new name must be normalized and unique among objects in the schema. `REBUILD INDEX schema.name` resolves the logical index through authenticated metadata and republishes its existing definition and memberships through `indexes.rebuild`; it validates the complete membership set and advances the table write epoch, even when the definition is unchanged. `ALTER INDEX schema.name REBUILD [USING BTREE] {UNIQUE|NONUNIQUE} (column, ...)` resolves the index's owning table, binds a new ordered column set, and atomically rebuilds the index with the requested uniqueness profile. Storage validates the new definition against the current table and rows under the existing DDL fence. A unique index uses the same null/commit-validation semantics as `UNIQUE`. `DROP INDEX` atomically removes its catalog and physical memberships and reserves the stable ID in family 17. Primary/unique constraints own backing indexes; their indexes cannot be changed or dropped independently while required. Expression, partial, covering, full-text, custom access methods, and `CREATE INDEX CONCURRENTLY` are deferred.

For ordinary index creation, removal, and rebuild, the storage manager accepts an actor identity only from a trusted authenticated administrative caller, then independently verifies that the actor is an enabled user with table ownership, an inherited owner role, an `INDEX` grant, or membership in the reserved database-administrator role. The commit guards the actor, role-membership, grant, and table-owner records used by that decision so concurrent revocation or ownership changes abort stale DDL. Authenticated `admin-sql` metadata resolution exposes only the target relation, declared columns, and logical indexes needed by a table owner or inherited `INDEX` grantee, including when the principal has no schema `USAGE`; it grants no data access. This narrow route handles index-definition and matching index-object records; every other administrative action needs its own permission check before control-channel exposure.

An index is an internal access path, not an authorization boundary or raw data API. Entries must resolve to MVCC-visible row versions and be subject to identical row/cell checks as scans. An index-only read is allowed only if storage can enforce those checks and snapshot visibility. Index definitions/size/statistics are disclosed only through authorized catalog/optimizer surfaces.

## DDL Concurrency and Recovery

Use per-table/schema DDL fences plus the serialized redb writer for final publication. Initial table alterations, constraint validation, and index builds block affected-table write commits while building/validating; unrelated tables and pinned readers can continue. Do not hold the redb writer during a long scan; build against a pinned snapshot and revalidate before publishing. Acquire multiple DDL fences in a deterministic object-ID order and apply deadlines to waits.

The Rust `StorageManager` provides coordinated invocation and catalog-commit entry points that share one per-database fence manager. The manager provides shared guards for table writers and exclusive guards for DDL. It sorts and deduplicates multi-table requests, admits each request for all tables atomically, gives waiting DDL priority over new writers on affected tables, and releases guards through RAII. A timeout leaves no partial fence held. Raw storage commit helpers remain unfenced trusted primitives; runtime paths must use the coordinated entry points.

After taking a fence, capture the latest committed table version, build/validate privately, then atomically publish the catalog and physical changes. Foreign-key creation fences both referencing and referenced tables during validation/publication. A coordinated index build scans a pinned read snapshot, rechecks its row keys and versions under the serialized writer, and atomically publishes the complete index with its catalog record. A coordinated index rebuild derives old and new keys from the pinned rows, validates the complete existing forward membership set and matching row/reverse locators, checks uniqueness, and replaces changed memberships with the updated definition atomically. A rebuild request whose definition is unchanged still verifies and republishes the membership set, records audit/outcome, and advances the affected table write epoch. A coordinated index drop validates the complete forward membership set and matching row/reverse locators, then removes both membership directions with the catalog record in the same transaction. Index DDL is bounded to 65,536 scanned rows, 65,536 created, removed, or replaced memberships, and 64 MiB of accounted row/key data per commit; oversized operations fail without publication. Creating or rebuilding an index on a populated table cannot be combined with a schema change to that table in the same DDL operation. Every standalone index create, drop, or rebuild increments each affected table's write epoch in the same commit while preserving its tuple schema version. Transactions based on an older affected-table schema/write epoch must abort rather than commit incompatible writes after the fence is released. Uncommitted private writes are not included in a build or rebuild. An index becomes usable only after durable complete publication; failed builds and rebuilds leave the prior catalog and physical index state intact. Already-admitted transactions never acquire the new index just because it exists physically; catalog snapshot visibility still applies.

Old read snapshots retain compatible catalog definitions and physical versions until their pins drain, including after rename/drop. Stored row versions also retain the schema definitions and add-column defaults needed for decoding until rewritten/reclaimed. New snapshots see the new schema; plans/handles are never silently rebound. Retain retired tables/indexes until no snapshot can use them, or explicitly abort an invocation under retention pressure. Initially use a conservative table schema/write epoch for any relevant DDL change.

Physical key/value limits come from the pinned [redb API](redb-storage.md). Keep the logical column/scalar limits only after validating they fit that API. Index key ordering follows [key encoding](index-key-encoding.md), adapted to the chosen redb key type. Oversize values reject atomically; never truncate keys.

Policy and membership changes need epoch publication and write revalidation, not full-table scans. A policy change taking a policy-driving field into use also freezes that field for future query updates. Durable recovery must restore the catalog, constraints, index validity, and data at one committed state. Constraint creation and removal, and default-expression replacement or removal, publish their definitions, expressions, dependency edges, table write epochs, audit events, outcomes, and commit sequence atomically; recovery must expose either the complete pre-DDL state or the complete committed state.

## Discovery and Format Evolution

Built-in `information_schema` relations are fixed filtered storage interfaces defined in [metadata discovery](metadata-discovery.md), not user-created views. Reserve system namespaces against user DDL. Catalog bootstrap and storage-format upgrades are not ordinary ALTER statements; follow [catalog lifecycle](catalog-lifecycle.md). Diagnostic operational state is exposed separately from snapshot catalog discovery.

## Validation and References

Test duplicate definitions, dependency rejection, default/null semantics, simultaneous duplicate keys, both directions of foreign-key races, failed constraint validation, DDL versus pending writers, old snapshots after table, column, and constraint drops, crashes during index/table/constraint creation and key and foreign-key removal, table rename, ADD COLUMN and DROP COLUMN rewrites, DROP TABLE publication, and inaccessible catalog diagnostics.

Conventional syntax references: [PostgreSQL CREATE TABLE](https://www.postgresql.org/docs/current/sql-createtable.html) and [CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html). Engine-specific authorization and concurrency semantics above take precedence.
