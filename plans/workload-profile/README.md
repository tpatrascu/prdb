# Workloads, Integration and Release Evidence Plan

## Contract and Dependencies

Validate the [architecture](../../specs/architecture.md) and [operational/analytical workload](../../specs/workload-profile.md) across the [component roadmap](../README.md). Each component owns its local correctness suite; this plan owns cross-process vertical slices, scheduling evidence and release coverage. Add integration tests as interfaces appear, not after implementing every component.

## Decisions Before Implementation

Record supported hardware/kernel/filesystem/toolchain/redb profiles, deterministic workload datasets/seeds, resource classes/allowances, configurable workload-budget profiles, queue/age/memory/output defaults and benchmark methodology. Numeric ceilings in component plans are prototypes until validated at production-like scale; keep format invariants separate from configurable workload values. Set quantitative defaults only after repeatable measurements. Select scan-resistant cache/prefetch and maintenance policies supported by redb; do not implement a separate buffer manager or I/O subsystem.

For every bound touched by a roadmap increment, maintain a bound inventory with its classification (format invariant, implementation safety ceiling, or workload budget), scope, default, trusted configuration owner, validated minimum/maximum, exhaustion behavior, and independent cumulative/service limits. The inventory must include SQL-facing bounds such as `IN` list cardinality, LIMIT representation, scan/probe candidates, per-request batch sizes, materialized rows/bytes, and streamed result bytes, as well as planner, storage IPC, queue, admission, and maintenance bounds. A test that raises a profile must exercise the actual production configuration path and demonstrate that the same implementation accepts the higher value. If a fixed ABI, field, frame, data structure, or single-record size prevents the target workload, specify a compatible extension and migration path instead of treating the current ceiling as product capacity. Plans must not describe an implementation safety ceiling as a final product maximum. Use the illustrative ERP/CRM scale scenario in the workload spec as a baseline for test design, while recording that its population values are sizing examples rather than market-wide claims.

The bound inventory is a release deliverable, not just a documentation convention. The trusted supervisor/admission configuration owns workload class and profile selection; profiles are versioned, validated as complete vectors, and pinned to invocations. The optimizer, executor ABI, SDK dispatch, storage accounting, result relay, queue admission, and spill broker consume that same effective profile. Component plans must name their local accounting point and failure behavior, but may not introduce a second client-controlled override. Record defaults as current safe-start values until the profile propagation path and above-default evidence exist; a plan or test using the default does not establish that the corresponding limit is configurable in a running deployment.

For capacity evidence, exercise both wide relations and large outputs: the sizing model includes 250,000 customer/account rows with 80–250 declared columns, 5 million document headers, 25 million lines, 30 million activity/history rows, and 50 million inventory/ledger movements. Include projected rows around 1–8 KiB, queries returning tens to hundreds of MiB, and a configured multi-gigabyte streaming ceiling. Keep one-message/frame limits distinct from total streamed result budgets. Small fixture cardinalities establish correctness only; do not silently lower the production model to match an implementation array or an old benchmark.

## Integration Increments

| ID | Observable contract and evidence |
| --- | --- |
| WI-1 | Toolchain/profile and copied IPC fixtures work; real TinyCC constructors load only after fail-closed confinement. Missing features, role/version mismatch and crashes fail safely |
| WI-2 | Protected bootstrap plus real control administration creates two users and a table/policies. Different cell views survive hostile direct IPC attempts, forged handles and SDK bypass |
| WI-3 | Concurrent invocations read/stage writes, see own writes and preserve snapshots. Same-row conflicts abort wholly; disjoint writes commit; authority changes, constraints, recovery/status and retention safety use real redb |
| WI-4 | Real TCP helper uploads/seals/starts an immutable TinyCC artifact, sequential SDK SQL calls plan/execute, supervisor relays provisional output and storage confirms durable completion. Caught statement errors abort all writes |
| WI-5 | Disconnect/client/gateway/supervisor/storage failures around every commit transition reconcile by authenticated ID. Forged terminal bytes, incomplete frames or missing history never establish success/rollback; no automatic replay |
| WI-6 | Complete supported schema/identity/permission DDL and scalar/SQL matrix. Include unique/FK races, index publication crashes, bootstrap interruption, offline upgrade preservation and unsupported-format rejection |
| WI-7 | Under saturated analytics/output/planning/maintenance, bounded queues reserve progress for point reads, commit, cancellation and reclamation. Client class labels cannot exceed configured authority; memory/history pressure rejects or aborts explicitly |
| WI-8 | Required analytical SQL executes equijoins, grouping, COUNT/SUM/MIN/MAX/AVG, sorting/HAVING with precise null/redaction semantics and bounded hash/sort memory; no uncontrolled spill or privileged hidden-data aggregate |
| WI-9 | Opt-in external-memory sort/join/group work stays within invocation and service disk budgets, preserves authorized-view results, and cleans up after all terminal paths. Implement the versioned broker/profile across [workload](../../specs/workload-profile.md), [SQL](../../specs/sql-library.md), [sandbox](../../specs/linux-sandbox.md), and [supervisor](../../specs/supervisor.md); compare spilled results with the in-memory reference and measure disk/operational pressure. Spill is plaintext and isolated by access policy, not encrypted. |
| WI-10 | Trusted profiles can raise prototype query/estimate/result ceilings without changing semantics or exhausting host resources | Implement the trusted configuration owner and versioned profile selection first; define independent operational, analytical, planner and maintenance profiles and their inheritance/override rules. Validate each profile as a complete resource vector at startup or atomic reload, then pin its version and effective values to an invocation. Propagate the profile through supervisor admission, optimizer, executor host ABI, Rust/C IPC dispatch, storage work accounting, result relay and spill broker. Test the same binaries under defaults and at least one elevated profile against the illustrative ERP/CRM scale scenario in the workload spec (millions of master/document rows, tens of millions of line/history rows, wide tables and large streamed results), with mixed operational load. Record rows/bytes, result size, p50/p95/p99, peak memory, spill/disk and operational progress. |
| WI-11 | Every component exposes its effective bounds and rejects invalid profiles predictably | Maintain the machine-readable [cross-component bound inventory](BOUND_INVENTORY.csv): field/name, class (format invariant, implementation safety ceiling or workload budget), component, scope, default, trusted owner, supported envelope, accounting lifetime, exhaustion outcome, and implementation status. Treat the initial inventory as provisional until each owning component and code path is reconciled. Verify profile parsing, startup/reload validation, invocation pinning, per-request versus cumulative/service accounting, and explicit at/over-bound behavior. Fixed ABI/frame/field limits must be surfaced as non-configurable envelopes with a versioned extension path when insufficient. Elevated profiles must preserve authorization, cancellation, backpressure, statement atomicity and durable commit behavior. |

WI-2 and WI-3 jointly establish the first usable data milestone; a read-only slice is intermediate evidence. WI-6 is required for full initial scope and WI-8 for analytical support. General serializability, distributed execution, window/recursive SQL, secure remote transports, shared-memory transport and process reuse remain separate future work.

## Test and Benchmark Harness

Use maintained C unit executables for SDK parsing/ownership. Run query libraries and hostile fixtures only in the real sandbox harness. Integration uses real binaries, local Unix channels, TCP sockets, TinyCC artifacts and isolated redb directories; mocks are fault controls rather than persistence/isolation evidence. Deterministic barriers/deadlines cover both race orders; model/property/fuzz tests record seeds and turn minimized failures into regressions.

Measure SDK release build separately from cold/warm per-query compile/link, load, first result, execution and durable commit. Record point/range latency, write throughput, conflict rate, commit p50/p95/p99, redb bytes/commit, copy bytes, memory and retained history. Compare operational-only with simultaneous scans/joins/sorts, scoped estimates, index builds and supported maintenance. Measure sampling/estimation cost and plan quality independently; upstream benchmarks are not project results. This checkout is on NFS: run performance and other intensive tests with runtime data (database instances, query input/data files, spill files, logs and temporary files) under `$HOME/tmp/prdb-tests`, as described in [AGENTS.md](../../AGENTS.md#test-data-outside-the-nfs-checkout). Give each run its own `$PRDB_TEST_ROOT/runs/<name>` directory and set `TMPDIR` there. Leave Cargo and TinyCC compiler output in the established repository build directories; never place runtime test data in the checkout or its `target/` directory.

## Completion and Handoff

Maintain feature/spec-to-test coverage with real test paths, exact commands/profile/results and unverified gates. Run relevant component checks then the required workspace/release/target gates from AGENTS.md. Missing tools or skipped confinement are unresolved gates. Do not claim production/security audit readiness from prototype tests. First behavior: a repeatable confined-artifact launch harness with one successful fixture and constructor-time denial, after toolchain and sandbox prerequisites.
