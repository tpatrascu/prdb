# Optimizer Implementation Plan

## Contract and Dependencies

Implement the separate Rust [optimizer](../../specs/planner-compiler.md). It consumes structured requests and emits structured plans; client-side TinyCC compiles native artifacts. Depend on [IPC](../ipc-protocol/README.md), [metadata](../metadata-discovery/README.md), [statistics](../statistics-service/README.md) and shared formats with the [SQL interpreter](../sql-library/README.md).

## Decisions Before Implementation

Define bounded query/logical/physical IR, type/operator validation, stable object/schema references, plan compatibility and semantic validation scope. Clarify redaction/error ordering before permitting pushdown/reordering. Define planning budget separately from estimate allowance and invocation resources. Plans confer no permission or correctness guarantee for arbitrary user code.

## Increments

| OP-1 | Forged/malformed structured input, excessive nesting and unsupported types fail independently of the C parser | Implemented: bounded Rust request decoders reject malformed or excessive inputs; the supervisor launches one isolated `prdb-optimizer` process per invocation in the invocation cgroup with a separate Landlock policy and socket channel. The process handles submissions synchronously, enforces a 256-request connection cap, and waits for each matching planner response before advancing, so pending metadata naturally backpressures later submissions. Process-loop tests cover malformed input, request IDs, connection limits, and pending-metadata backpressure. Higher-concurrency saturation at configured admission limits and target-host measurements remain open |
| OP-2 | Hidden relation and nonexistent relation bind with non-disclosing behavior; planner cannot choose principal | Implemented: `bind_select_request_via_metadata` uses the invocation-bound planner connection and binds schema/table IDs, versions/epochs, and typed column references; missing or mismatched relation names share one error. The isolated optimizer obtains metadata only over its planner channel and emits the versioned canonical plan response; executor storage independently resolves relation identity before execution. Real-redb planner-stream, optimizer-process, and confined SDK acceptance cover these boundaries |
| OP-3 | Reference single-table read/write plans execute correctly through the SDK with independently resolved handles | Rust and C validation, ABI v4 SELECT submission, ABI v5 operation-selected optimizer submission, query-to-plan projection/LIMIT checks, identity checking, handle acquisition, bounded filtered/unfiltered scan execution, parameterized WHERE submission, and SQLR result emission are implemented. A confined default-deny case grants UPDATE on the table and target column but has no applicable UPDATE row policy; storage rejects staging and durably aborts without changing the row. A real-redb concurrency regression stages two authorized UPDATE patches from the same snapshot and verifies one durable commit and one durable conflict |
| OP-4 | Unknown estimate uses fixed heuristics while cancelled/expired planning terminates | Partial: ordinary single-table SELECT gets a bounded small-population probe under the shared 16-request allowance; it reads at most five row keys and returns a count only for populations of 0–4. Zero emits the independently validated no-scan hint; populations of 1–4 choose a sequential scan over point/range paths, a cutoff supported by repeated local measurements. Filtered ordinary unordered SELECT also requests a bounded predicate estimate through the planner-only IPC; an exact zero-match result emits the no-scan hint, while an exact nonzero estimate removes point/range hints when `visible_rows` is 1–4. For larger exact populations, range hints are removed when `matching_rows` is at least half of `visible_rows`; unique point probes remain. The filter stays in the plan, and unknown estimates preserve the prior access choice. Predicate estimates are exact for fully readable authorized populations up to 16,384 rows under the per-estimate candidate budget; nonzero plan selection uses the visible population for the four-row scan crossover. Storage cancellation/expiry tests and optimizer-process stream-loss coverage verify planning terminates without a fallback plan. Delegated-cgroup regressions launch the production optimizer binary through the real worker-channel multiplexer and hold its `EstimateScan` at the storage request boundary; owner cancellation and deadline expiry both produce durable ABORTED outcomes without a successful plan. A confined ABI v4 SQL acceptance now uploads through external TCP, observes `EstimateScan` in the full `RunningExecutor` lifecycle, commits one result, then issues an authenticated control-mode TCP CANCEL from a separate connection while the next estimate is pending and verifies the relayed terminal and durable outcome are ABORTED. Broader candidate comparison and target-host cost profiles remain open. The 256-request stream cap remains independent |
| OP-5 | Index/predicate rewrites preserve authorized-view results and redaction errors | Implemented: authorized unique point probes and leading-key range scans, including equality on non-unique leading keys, are independently validated by TinyCC, reauthorized by storage, and fall back to scans when unavailable or oversized. Storage regressions compare point/range results with the authorized reference scan; TinyCC regressions cover equality execution and unavailable/response-too-small fallback. The confined SQL acceptance uses five visible rows to avoid the small-scan choice, asserts exactly one `ScanIndexRange` request, and compares the returned rows with the authorized reference scan. A token-authenticated executor regression verifies explicit range requests on a hidden key return the same unavailable response for a matching and absent key, while an authorized exact range returns the sanitized reference row. A five-run local measurement compares the optimizer's complete confined SDK request/result callbacks with the reference SQL scan; broader dataset and gateway-relay profiles remain open. Estimates never establish permission |
| OP-6 | Mutation generation, policy/schema differences or missed invalidation prevent stale/cross-user cache reuse | Exact predicate estimates, bounded population probes, and exact column summaries may be reused only within one planner session and invocation. Keys include relation/schema identity and the complete request shape: predicate bytes plus candidate bound, population row bound, or ordered requested column IDs. The session pins principal, authorization and snapshot context, while an overlay generation invalidates all caches after every private mutation. Requests still consume the estimate allowance; unknown and cross-session results are not cached |
| OP-7 | Required join/group/sort plans match reference semantics within admitted memory/work | In progress: composite joins and COUNT(*) optimizer plans, including kind-8 single-key and kind-9 composite sorting, pass confined acceptance. Statement 10/kind 10 plans single-key COUNT/MIN/MAX/SUM/AVG; statement 11/kind 11 adds up to two sort expressions over those aggregates and the group key. Filtered aliased-join statement 12/kind 12 passes independent TinyCC validation, bounded optimizer-backed v20 execution, and confined result-relay acceptance. Five repeated local mixed-workload runs and a 30-second eight-worker confined mixed-load run are recorded in [workload progress](../workload-profile/PROGRESS.md); storage API-boundary bytes and worker cgroup memory are measured there. SQL operator allocation/copy accounting beyond those boundaries and target-hardware measurements remain open |

For SQL-10 join planning, the isolated optimizer opts into two bounded authorized population probes under the shared estimate allowance, each capped at 4,096 rows. Exactly one known 1–4-row input may become the outer side of an eligible indexed nested-loop join. When both known populations exceed four, the smaller side may drive indexed nested-loop if it has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash join. The skew rule is supported by five-run confined 4×128 and 8×128 profiles, while the 64×64 medium profile retains hash. A bounded exact pair estimate also permits low-fanout indexed nested-loop for outer inputs of 9–16 rows when the indexed input is at least eight times larger, plus the measured 17- and 18-row cases when the indexed input is at least seven times larger; five-run 9×128 fanout-one-through-five, 16×128, 17×128, exact-boundary 17×119, and 18×126 profiles support this cutoff locally; paired five-run 17×119 profiles verify that 68 pairs retains indexed nested-loop and 69 pairs selects hash. Higher fanout retains hash. A single known 1–4-row input may still orient the join when the opposite estimate is unknown. Index nested-loop keys accept every scalar type supported by the existing typed index-range IPC and ordered index codec; variable-length values remain request-size bounded. Composite indexes use the longest matching contiguous leading prefix of two to eight join keys through plan kind 18 and executor `ScanIndexPrefix`; confined acceptance verifies the selected plan and joined output during an operational saturation interval. Other unknown estimates retain the deterministic right-index-preferred/left-fallback choice. This remains a bounded measured heuristic. General cost comparison, join populations above 4,096, broader selectivity/fanout profiles and target-host join profiles remain open. Filtered single-table predicate estimates are independently bounded to 16,384 fully readable rows and share the per-estimate candidate budget.

## Acceptance and Handoff

Fuzz structured inputs and invalid plans, test restricted metadata/estimate requests over real channels, and compare SDK execution with reference results. Mutate only hidden data to test normalized released estimates/metadata; record timing/inference limits separately. Planner compromise must not grant broader data access. First behavior: a bounded independently validated single-table request and rejection of an unsupported node.
