# Optimizer Implementation Plan

## Contract and Dependencies

Implement the separate Rust [optimizer](../../specs/planner-compiler.md). It consumes structured requests and emits structured plans; client-side TinyCC compiles native artifacts. Depend on [IPC](../ipc-protocol/README.md), [metadata](../metadata-discovery/README.md), [statistics](../statistics-service/README.md) and shared formats with the [SQL interpreter](../sql-library/README.md).

## Decisions Before Implementation

Define bounded query/logical/physical IR, type/operator validation, stable object/schema references, plan compatibility and semantic validation scope. Clarify redaction/error ordering before permitting pushdown/reordering. Define planning budget separately from estimate allowance and invocation resources. Plans confer no permission or correctness guarantee for arbitrary user code.

| OP-4 | Unknown estimate uses fixed heuristics while cancelled/expired planning terminates | Partial: ordinary single-table SELECT gets a bounded small-population probe under the invocation-pinned estimate allowance (default 16; optional Analytical override; current maximum 4,096); it reads at most five row keys and returns a count only for populations of 0–4. Zero emits the independently validated no-scan hint; populations of 1–4 choose a sequential scan over point/range paths, a cutoff supported by repeated local measurements. Filtered ordinary unordered SELECT also requests a bounded predicate estimate through the planner-only IPC; an exact zero-match result emits the no-scan hint, while an exact nonzero estimate removes point/range hints when `visible_rows` is 1–4. For larger exact populations, range hints are removed when `matching_rows` is at least half of `visible_rows`; unique point probes remain. The filter stays in the plan, and unknown estimates preserve the prior access choice. Predicate estimates are exact for fully readable authorized populations up to the invocation-pinned per-estimate candidate limit (Operational default 16,384; optional Analytical override; current implementation maximum 1,048,576). A fresh full-population record plus an eligible readable leading index enables a bounded locator count for exact equality/range predicates; the estimator adjusts for bounded current-actor overlay writes by evaluating old and staged values, leaves unrelated rows undecoded, caps at 1,024 committed locators, 16 MiB of index keys, and 16 MiB of cumulative old/staged overlay payload bytes, and leaves query scan-work allowance untouched. Delegated-cgroup regressions launch the production optimizer binary through the real worker-channel multiplexer and hold its `EstimateScan` at the storage request boundary; owner cancellation and deadline expiry both produce durable ABORTED outcomes without a successful plan. A confined ABI v4 SQL acceptance now uploads through external TCP, observes `EstimateScan` in the full `RunningExecutor` lifecycle, commits one result, then issues an authenticated control-mode TCP CANCEL from a separate connection while the next estimate is pending and verifies the relayed terminal and durable outcome are ABORTED. For SQL-10 join planning, the isolated optimizer opts into two bounded authorized population estimates in one `estimate_scans` (`0x120a`) frame under the shared estimate allowance, each capped at 16,384 rows. Exactly one known 1–4-row input may become the outer side of an eligible indexed nested-loop join. When both known populations exceed four, the smaller side may drive indexed nested-loop if it has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash join. The skew rule is supported by five-run confined 4×128 and 8×128 profiles, while the 64×64 medium profile retains hash. A bounded exact pair estimate also permits low-fanout indexed nested-loop for outer inputs of 9–16 rows when the indexed input is at least eight times larger, plus the measured 17–19-row cases when the indexed input is at least seven times larger; five-run 9×128 fanout-one-through-five, 16×128, 17×128, exact-boundary 17×119, and 18×126 profiles support this cutoff locally; paired five-run 17×119 profiles verify that 68 pairs retains indexed nested-loop and 69 pairs selects hash. Five-run 19×133 profiles select indexed nested-loop and return all 19 pairs under 192 operational reads and commits; indexed median run-level p50 is 287.2 ms (264.8–298.2 ms range), with no hash comparison because the SDK hash join caps each input at 128 rows. Five-run 18×126 checks now validate the inclusive 72-pair limit (indexed nested-loop; median run-level p50 259.8 ms indexed (247.1–309.9 ms range) versus 307.9 ms hash (299.0–338.0 ms range)) and the 73-pair rejection (hash; 348.5 ms median (327.1–361.7 ms range)), with result equivalence and 192 overlapping operational reads and commits per run. For hash-compatible inputs (at most 128 rows per side), higher fanout retains hash. If an exact estimate shows that a hash input exceeds 128 rows, an eligible indexed path may run regardless of fanout when the outer input is at most 128 rows, the indexed relation population is at most 16,384 rows, and exact output is at most 16,384 pairs. The runner independently enforces its cumulative 16,384-candidate limit during probes. Five confined 19×133 runs at five matches per outer row selected kind 17, returned all 95 pairs, and overlapped 192 operational reads and commits per run; indexed median run-level p50 was 339.6 ms (280.1–404.1 ms range). Hash comparison is unavailable because the input exceeds its 128-row bound. This is bounded execution feasibility evidence, not a general high-fanout cost claim. A single known 1–4-row input may still orient the join when the opposite estimate is unknown. Index nested-loop keys accept every scalar type supported by the existing typed index-range IPC and ordered index codec; variable-length values remain request-size bounded. Composite indexes use the longest matching contiguous leading prefix of two to eight join keys through plan kind 18 and executor `ScanIndexPrefix`; confined acceptance verifies the selected plan and joined output during an operational saturation interval. Other unknown estimates retain the deterministic right-index-preferred/left-fallback choice. This remains a bounded measured heuristic. General cost comparison, join populations above 16,384, broader selectivity/fanout profiles and target-host join profiles remain open. Filtered single-table predicate estimates use the invocation-pinned candidate limit (default 16,384; current maximum 1,048,576) and require every referenced cell to be readable.

## Acceptance and Handoff

Fuzz structured inputs and invalid plans, test restricted metadata/estimate requests over real channels, and compare SDK execution with reference results. Mutate only hidden data to test normalized released estimates/metadata; record timing/inference limits separately. Planner compromise must not grant broader data access. First behavior: a bounded independently validated single-table request and rejection of an unsupported node.
