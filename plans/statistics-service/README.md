# Statistics Service Implementation Plan

## Contract and Dependencies

Implement [statistics](../../specs/statistics-service.md) as a trusted module within [storage](../storage-manager/README.md). Depend on [authorization](../authorization/README.md), [snapshots/overlays](../concurrency-mvcc/README.md), [dictionary validity](../data-dictionary/README.md) and planner-role [IPC](../ipc-protocol/README.md). A separate collector process and global statistics are not initial prerequisites.

## Initial Implemented Slice

The internal `InvocationTransaction::estimate_authorized_scan` API returns exact visible-row and requested-column VALUE/NULL/REDACTED counts from the pinned snapshot plus private overlay, or `Unknown` without partial counts. It scans at most 16,384 candidates per estimate and the planner metadata connection admits at most 16 estimates over its lifetime; exhaustion returns `Unknown` while leaving the invocation active. It returns exact results only for policy shapes with row inclusion independent of row values: literal policies can prove a full population or an empty population without scanning rows. Value-dependent policies and invalid contexts return `Unknown` before scanning. Ordinary unordered single-table SELECT can opt into a population probe capped at four rows, reading at most five row keys. Join planning can request up to 1,024 rows per relation, reading at most 1,025 row keys. Both probes avoid decoding row values and share the planner's estimate allowance. For joins, exact empty inputs and two known populations of at most four select hash join. Exactly one known 1–4-row side can be selected as outer when the opposite side has an eligible index. When both known populations exceed four, the smaller side may drive indexed nested-loop if it has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash. Five-run confined 4×128 and 8×128 profiles support these bounded population-skew cases, while 64×64 retains hash. For moderate skew, the optimizer now requests an exact authorized join-pair estimate when the smaller side has 9–16 rows and the other side is at least eight times larger. The estimate is capped at 1,024 rows per input and bounded to eight key components, 8 MiB decoded row data, and 4 KiB per encoded key. It requires value-independent row visibility and statically readable key cells; NULL keys do not match. The optimizer selects an eligible index only when estimated output is no more than four pairs per outer row; higher fanout keeps hash. Five-run confined 9×128 mixed-load profiles found indexed nested-loop about 39% faster at one match per outer row and 40% faster at four matches per outer row by median-of-run medians; at five matches per outer row, the optimizer selected hash in all five runs. Each run overlapped 192 operational reads and 192 commits. These measurements support this bounded crossover on this host only, not a general cost model or deployment target. Unknown and ineligible estimates preserve the existing heuristic. An exact empty SELECT population can produce the validated no-scan hint; exact populations 1–4 can select a sequential scan over an indexed path using the measured local cutoff. `planner_ipc` dispatches relation descriptions and estimates through connection-scoped kind-9 handles. The trusted transaction layer additionally supports exact predicate-match counts for authorized populations up to 16,384 rows when all referenced cells are readable; comparisons cover Boolean, integer, DATE, UUID, TIMESTAMPTZ, BYTEA, and text literals plus same-typed columns of Boolean, SMALLINT, INTEGER, BIGINT, DECIMAL, TEXT, VARCHAR, BYTEA, UUID, DATE, or TIMESTAMPTZ. DECIMAL precision and scale must match, and variable-width TEXT, VARCHAR, and BYTEA cells are limited to 4 KiB per value. DECIMAL literals and cross-type coercions remain unsupported by the optimizer request format. Redacted or unsupported predicates return `Unknown`. Planner estimates share the request allowance and session cache, with each successful private write invalidating cached estimates. Unknown values are not cached. The planner-only EstimateScan operation accepts bounded bound-predicate requests by qualified relation name and returns exact visible/matching counts or `Unknown`. Exact predicate results may be reused within their planner session when relation/schema, predicate, bound, snapshot, and private-write generation still match. For filtered ordinary unordered single-table SELECT, the optimizer uses exact zero matches for the no-scan hint. For nonzero results, it uses `visible_rows` to choose a sequential scan when the full authorized population is 1–4, and uses exact `matching_rows` to choose a sequential scan over a range path when at least half the authorized rows match. Unique point probes remain unchanged; `Unknown` preserves the ordinary plan. The SDK re-resolves the relation and checks cancellation before skipping an empty scan. The IPC role matrix denies estimate operations to executors and executor scan operations to planners. `SupervisorInvocation::serve_worker_channels` provisions the planner and executor storage streams concurrently and drains both before worker-exit observation. Estimate requests execute synchronously on their provisioned planner stream; there are no detached planner tasks. A separate bounded trusted collector writes a sequence-tagged global table population to the protected rebuildable stats table; the gateway maintenance loop schedules one catalog-cursor table refresh per configured interval, defaulting to 15 minutes in the supervisor. No collection operation is exposed to planner or executor IPC. Planner use of collected global counts, broader cost choices, additional statistics fields, and asynchronous estimate scheduling remain unimplemented.

## Decisions Before Further Implementation

The bounded trusted predicate contract reaches planner IPC and supports SELECT empty-result/access hints for exact authorized populations up to the 16,384-row estimate candidate budget. Join planning uses authorized population estimates capped at 1,024 rows per input. Exactly one known 1–4-row side may use an eligible opposite-side index. When both known populations exceed four, the smaller input may drive an eligible index when it has at most eight rows and the other side is at least 16 times larger; the measured 4×128 and 8×128 profiles support this skew rule, while 64×64 retains hash. A bounded exact join-pair estimate also gates index nested-loop for 9–16-row outers when the other input is at least eight times larger; estimates require statically readable key cells, value-independent row visibility, and remain within 1,024 rows per input. Five-run 9×128 mixed-load comparisons at one and four matches per outer row found indexed nested-loop faster than hash by median-of-run medians; five 16×128 runs also favored indexed nested-loop at one match per outer row. At five matches per outer row, the optimizer selected hash in every run. These results support the four-pairs-per-outer-row heuristic for the measured local profiles. Cost-based algorithm selection, populations above 1,024, and broader candidate comparison remain deferred. Exact predicate, population, and join-cardinality estimate reuse is scoped to one planner session and invalidated by every private write. Fix which logical access-path information is public; never release physical counts, global epochs/costs or raw samples indirectly.

## Increments

| ID | Observable test first | Minimum implementation and evidence |
| --- | --- | --- |
| ST-1 | Executor calling estimate/refresh and planner requesting unrestricted data are denied | Implemented at provisioned planner/executor streams: planner-only relation handles and estimate operations are dispatched under the planner role; executor streams reject `EstimateScan`, planner streams reject `OpenScan`, both emit no response and durably abort on cross-role requests. The fixed operation matrix is also tested independently |
| ST-2 | Scoped visible/readable/null/redacted populations match a reference authorized scan | The full summary, statically empty population, bounded exact population probe, and bounded trusted predicate-match estimator for 0–16,384 rows are implemented; optimizer uses estimates for SELECT access choices and join orientation, while general cost-based selectivity and broader policy-filtered estimates remain |
| ST-3 | Changing hidden values or adding invisible rows leaves normalized released estimates unchanged | Paired authorized-view comparisons verify unchanged visible rows and `Unknown` estimates across differing hidden candidate counts; real-redb regressions confirm changing only a redacted cell leaves exact predicate counts and sanitized populations unchanged, while adding invisible candidates under a value-dependent row policy continues to return `Unknown`. Timing/resource noninterference and broader estimate fields remain |
| ST-4 | Estimate-specific exhaustion returns unknown, but context cancellation/deadline drains and terminates | Verified for the synchronous estimate path: budget exhaustion returns `Unknown` without partial counts; cancellation/deadline terminate the estimate stream and worker without fallback, and supervisor finalization waits for provisioned channels to drain. No detached planner task queue is used |
| ST-5 | A private write or changed authorization context prevents stale summary reuse and cross-invocation leakage | Exact predicate results, bounded population probes, and exact column summaries are cached only within one planner session. Keys include relation/schema identity and their complete request shape: predicate bytes plus bound, population row bound, or ordered requested column IDs. The session pins authorization and snapshot context, and every private overlay mutation invalidates all caches by generation. Cache hits still consume the shared estimate allowance. Unknown and cross-session results are not cached |
| ST-6 | Later private collection is bounded, undisclosed and cannot starve commits | Implemented slice: one committed-snapshot row-population pass, capped at 16,384 rows with no partial result, one shared maintenance admission slot, `CPR1` source-sequence tagging in the protected `stats_v1` table, and no count in the public maintenance outcome. The gateway schedules one table per configured interval using a wrapping catalog cursor. A trusted freshness check reads the record and commit sequence from one snapshot; a fresh record skips redundant collection, while a stale/missing record is refreshed. Tests verify fresh/stale sequence handling, `Unknown` on overflow, clone-shared single admission, operational commit during collection, and cursor wrap. Richer statistics and planner consumption remain |

## Acceptance and Handoff

Use authorized-view reference fixtures with nulls/redactions and repeated chosen-predicate probes. A sample lacking redactions is not permission to execute an aggregate, and readable-only summaries never redefine SQL semantics. Record planning overhead/quality on selective policies and mixed workloads before richer sampling. Timing/cache noninterference is not established by normalized-content tests; estimate caches remain invocation- and planner-session-scoped.
