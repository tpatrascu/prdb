# Statistics Service Implementation Plan

## Contract and Dependencies

Implement [statistics](../../specs/statistics-service.md) as a trusted module within [storage](../storage-manager/README.md). Depend on [authorization](../authorization/README.md), [snapshots/overlays](../concurrency-mvcc/README.md), [dictionary validity](../data-dictionary/README.md) and planner-role [IPC](../ipc-protocol/README.md). A separate collector process and global statistics are not initial prerequisites.

## Initial Implemented Slice

The internal `InvocationTransaction::estimate_authorized_scan` API returns exact visible-row and requested-column VALUE/NULL/REDACTED counts from the pinned snapshot plus private overlay, or `Unknown` without partial counts. It scans at most 16,384 candidates per estimate and the planner metadata connection admits at most 16 estimates over its lifetime; exhaustion returns `Unknown` while leaving the invocation active. It returns exact results only for policy shapes with row inclusion independent of row values: literal policies can prove a full population or an empty population without scanning rows. Value-dependent policies and invalid contexts return `Unknown` before scanning. Ordinary unordered single-table SELECT can opt into a population probe capped at four rows, reading at most five row keys. Join planning can request up to 16,384 rows per relation, reading at most 16,385 row keys. Both probes avoid decoding row values and share the planner's estimate allowance. For joins, exact empty inputs and two known populations of at most four select hash join. Exactly one known 1–4-row side can be selected as outer when the opposite side has an eligible index. When both known populations exceed four, the smaller side may drive indexed nested-loop if it has at most eight rows and the indexed side is at least 16 times larger; other such joins retain hash. Five-run confined 4×128 and 8×128 profiles support these bounded population-skew cases, while 64×64 retains hash. For moderate skew, the optimizer requests an exact authorized join-pair estimate when the smaller side has 9–16 rows and the other side is at least eight times larger, or the outer side has 17–18 rows and the indexed side is at least seven times larger. The estimate is capped at 16,384 rows per input and bounded to eight key components, 8 MiB decoded row data, and 4 KiB per encoded key. It requires value-independent row visibility and statically readable key cells; NULL keys do not match. The optimizer selects an eligible index only when estimated output is no more than four pairs per outer row; higher fanout keeps hash. Five-run confined 9×128 mixed-load profiles from one through four matches per outer row favored indexed nested-loop: medians of run-level p50s were 180.1 ms at fanout one, 182.7 ms at fanout two, 181.5 ms at fanout three, and 183.7 ms at fanout four. At five matches per outer row, the optimizer selected hash in all five runs. Each run overlapped 192 operational reads and 192 commits. These measurements support this bounded crossover on this host only, not a general cost model or deployment target. Unknown and ineligible estimates preserve the existing heuristic. An exact empty SELECT population can produce the validated no-scan hint; exact populations 1–4 can select a sequential scan over an indexed path using the measured local cutoff. `planner_ipc` dispatches relation descriptions and estimates through connection-scoped kind-9 handles. The trusted transaction layer additionally supports exact predicate-match counts for authorized populations up to 16,384 rows when all referenced cells are readable; comparisons cover Boolean, integer, DECIMAL, DATE, UUID, TIMESTAMPTZ, BYTEA, and text literals plus same-typed columns of Boolean, SMALLINT, INTEGER, BIGINT, DECIMAL, TEXT, VARCHAR, BYTEA, UUID, DATE, or TIMESTAMPTZ. DECIMAL literals inherit the compared column scale and must fit its precision; column comparisons require matching precision and scale. Variable-width TEXT, VARCHAR, and BYTEA cells are limited to 4 KiB per value. cross-type coercions remain unsupported by the optimizer request format. Redacted or unsupported predicates return `Unknown`. Planner estimates share the request allowance and session cache, with each successful private write invalidating cached estimates. Unknown values are not cached. The planner-only EstimateScan operation accepts bounded bound-predicate requests by qualified relation name and returns exact visible/matching counts or `Unknown`. Exact predicate results may be reused within their planner session when relation/schema, predicate, bound, snapshot, and private-write generation still match. For filtered ordinary unordered single-table SELECT, the optimizer uses exact zero matches for the no-scan hint. For nonzero results, it uses `visible_rows` to choose a sequential scan when the full authorized population is 1–4, and uses exact `matching_rows` to choose a sequential scan over a range path when at least half the authorized rows match. Unique point probes remain unchanged; `Unknown` preserves the ordinary plan. The SDK re-resolves the relation and checks cancellation before skipping an empty scan. The IPC role matrix denies estimate operations to executors and executor scan operations to planners. `SupervisorInvocation::serve_worker_channels` provisions the planner and executor storage streams concurrently and drains both before worker-exit observation. Estimate requests execute synchronously on their provisioned planner stream; there are no detached planner tasks. A separate bounded trusted collector writes a sequence-tagged global table population to the protected rebuildable stats table; the gateway maintenance loop schedules one catalog-cursor table refresh per configured interval, defaulting to 15 minutes in the supervisor. No collection operation or raw stats record is exposed through planner or executor IPC. The trusted planner may reuse a fresh exact population record through its bounded estimate when the pinned snapshot and literal row policies prove the full committed population visible. It adjusts for bounded current-actor private inserts/deletes using row-key existence, keeps other actors' writes invisible, and falls back when more than 16,384 overlay row IDs or a storage validation failure prevents an exact adjustment; broader global-statistics use remains unimplemented. Broader cost choices, additional statistics fields, and asynchronous estimate scheduling also remain open.

Row-independent constant predicate estimates may reuse a fresh exact committed population count under the same pinned-snapshot, full-visible-policy, and request-bound conditions. The estimator adjusts for bounded current-actor overlay inserts/deletes using row-key existence, or falls back to the bounded row-key population probe; neither path decodes row values.

For exact single-column equality/range predicates, the predicate estimator counts committed index locators directly when a fresh committed population record, an all-rows-visible policy proof, and an unconditionally readable leading index key establish that the range count is exact. It adjusts the committed counts for bounded writes in the current actor's private overlay by evaluating each old and staged row value; other actors' writes remain invisible. It returns `(visible_rows, matching_rows)` without scanning unchanged rows, caps the index path at 1,024 locators, 16 MiB of encoded keys, and 16 MiB of cumulative old/staged overlay payload bytes, and leaves executor scan-work accounting untouched. Oversized overlays, malformed staged/old values, and other failed preconditions use the bounded row estimator. Five local 2,052-row TEXT profiles at 882 matches measured 1.537 ms median run-level estimate p50 (1.494–1.599 ms), versus 26.103 ms for the earlier full-row pass. Five fresh-database real `prdb-optimizer` profiles at 2,052 rows measured filtered equality request median-of-run p50 at 6.876 ms (6.686–7.069 ms), including optimizer execution and planner IPC after process launch; the underlying exact `EstimateScan` roundtrip measured 2.633 ms (2.512–2.714 ms). Process startup, full SQL latency, mixed operational load, and target-host cost remain unmeasured.

## Decisions Before Further Implementation

At the smallest moderate-skew boundary, five delegated-cgroup runs of the 9×72 shape (eight-to-one population ratio, 36 pairs, four per outer row) selected indexed nested-loop and matched hash output. Median of run-level p50s was 174.5 ms indexed (168.0–185.6 ms range) and 186.8 ms hash (172.7–200.8 ms range), with 192 operational reads and commits overlapping each run. This extends local evidence to the minimum ratio and inclusive fanout cutoff; it does not establish a general cost model or target-host performance.

The bounded trusted predicate contract reaches planner IPC and supports SELECT empty-result/access hints for exact authorized populations up to the 16,384-row estimate candidate budget. Join planning uses authorized population estimates capped at 16,384 rows per input. Exactly one known 1–4-row side may use an eligible opposite-side index. When both known populations exceed four, the smaller input may drive an eligible index when it has at most eight rows and the other side is at least 16 times larger; the measured 4×128 and 8×128 profiles support this skew rule, while 64×64 retains hash. A bounded exact join-pair estimate also gates index nested-loop for 9–16-row outers when the other input is at least eight times larger, plus the measured 17- and 18-row outer cases when the other input is at least seven times larger; estimates require statically readable key cells, value-independent row visibility, and remain within 16,384 rows per input, subject to the 8 MiB decoded-row budget. Five-run 9×128 mixed-load comparisons favored indexed nested-loop over hash at fanouts one through four (run-level median p50s 180.1, 182.7, 181.5, and 183.7 ms), while all five fanout-five runs selected hash. Five 16×128 and 17×128 runs and the exact 17×119 ratio-boundary runs also favored indexed nested-loop at fanout one. Five 18×126 runs at fanout one selected indexed nested-loop, matched hash results, and overlapped 192 operational reads and commits; median run-level p50 was 273.9 ms indexed versus 305.3 ms hash. Five-run 18×126 profiles also check the inclusive 72-pair limit (indexed nested-loop; median run-level p50 259.8 ms indexed (247.1–309.9 ms range) versus 307.9 ms hash (299.0–338.0 ms range)) and the 73-pair rejection (hash; 348.5 ms median (327.1–361.7 ms range)), with result equivalence and 192 overlapping operational reads and commits per run. Paired five-run 17×119 profiles at the exact seven-to-one population ratio verified both sides of the four-pairs-per-outer cutoff. At 68 pairs, every run selected indexed nested-loop and matched hash output; median run-level p50s were 250.3 ms indexed versus 292.3 ms hash. At 69 pairs, every run selected hash and returned all 69 matching rows. Each run overlapped 192 operational reads and commits. Five fresh-database 17×2,048 mixed-load runs selected kind-17 indexed nested-loop, returned all 17 expected pairs, and completed 192 operational reads and 192 commits per run; the median of per-run p50 indexed latencies was 280.3 ms (273.1–310.6 ms range). Five 17×4,096 runs passed the exact population-estimate cap end to end, with kind-17 plans and 17 expected pairs; the median of per-run p50 indexed latencies was 308.1 ms (297.1–342.0 ms range). A delegated 17×4,097 acceptance now receives exact authorized population and pair-cardinality estimates, selects kind 17, returns all 17 pairs, and overlaps 192 operational reads and commits. This is one correctness run, not a latency profile. These large-input profiles record no hash timing because the SDK hash join materializes at most 128 rows. These results support the bounded rules only for the measured local profiles. Cost-based algorithm selection, populations above 16,384, and broader candidate comparison remain deferred. Exact predicate, population, and join-cardinality estimate reuse is scoped to one planner session and invalidated by every private write. Fix which logical access-path information is public; never release physical counts, global epochs/costs or raw samples indirectly.

Five fresh-database confined 17×128 mixed-load runs covered a hot-key fanout on both sides of the existing threshold. With one outer key matching 16 indexed rows and the other 16 outer keys unmatched, the exact 16-pair estimate selected indexed nested-loop and matched hash; median-of-run p50 was 257.8 ms indexed and 299.1 ms hash. When that hot key matched all 128 inner rows, the exact 128-pair estimate selected hash in every run; median-of-run p50 was 341.9 ms. Each run overlapped 192 operational reads and commits. These are two nonuniform distributions, not a general cost model.

## Increments

| ID | Observable test first | Minimum implementation and evidence |
| --- | --- | --- |
| ST-1 | Executor calling estimate/refresh and planner requesting unrestricted data are denied | Implemented at provisioned planner/executor streams: planner-only relation handles and estimate operations are dispatched under the planner role; executor streams reject `EstimateScan`, planner streams reject `OpenScan`, both emit no response and durably abort on cross-role requests. The fixed operation matrix is also tested independently |
| ST-2 | Scoped visible/readable/null/redacted populations match a reference authorized scan | The full summary, statically empty population, bounded exact population probe, and bounded trusted predicate-match estimator for 0–16,384 rows are implemented; optimizer uses estimates for SELECT access choices and join orientation, while general cost-based selectivity and broader policy-filtered estimates remain |
| ST-3 | Changing hidden values or adding invisible rows leaves normalized released estimates unchanged | Paired authorized-view comparisons verify unchanged visible rows and `Unknown` estimates across differing hidden candidate counts; real-redb regressions confirm changing only a redacted cell leaves exact predicate counts and sanitized populations unchanged, while adding invisible candidates under a value-dependent row policy continues to return `Unknown`. Timing/resource noninterference and broader estimate fields remain |
| ST-4 | Estimate-specific exhaustion returns unknown, but context cancellation/deadline drains and terminates | Verified for the synchronous estimate path: budget exhaustion returns `Unknown` without partial counts; cancellation/deadline terminate the estimate stream and worker without fallback, and supervisor finalization waits for provisioned channels to drain. No detached planner task queue is used |
| ST-5 | A private write or changed authorization context prevents stale summary reuse and cross-invocation leakage | Exact predicate results, bounded population probes, exact join-cardinality estimates, and exact column summaries are cached only within one planner session. Keys include relation/schema identity and their complete request shape: predicate bytes plus bound, paired join keys plus population bound, population row bound, or ordered requested column IDs. The session pins authorization and snapshot context, and every private overlay mutation invalidates all caches by generation. Cache hits still consume the shared estimate allowance. Unknown and cross-session results are not cached |
| ST-6 | Later private collection is bounded, undisclosed and cannot starve commits | Implemented slice: one committed-snapshot row-population pass, capped at 16,384 rows with no partial result, one shared maintenance admission slot, `CPR1` source-sequence tagging in the protected `stats_v1` table, and no count in the public maintenance outcome. The gateway schedules one table per configured interval using a wrapping catalog cursor. A trusted freshness check reads the record and commit sequence from one snapshot; a fresh record skips redundant collection, while a stale/missing record is refreshed. A committed table drop removes its population record atomically; rejected drops preserve it. Tests verify fresh/stale sequence handling, `Unknown` on overflow, clone-shared single admission, operational commit during collection, cursor wrap, and drop cleanup. A planner estimate reuses a fresh exact count for the full committed view on the same pinned snapshot, then adjusts for bounded current-actor overlay inserts/deletes using row-key existence; stale or unsupported cases fall back to the bounded estimate. Richer statistics and broader global-statistics consumption remain |

## Acceptance and Handoff

Use authorized-view reference fixtures with nulls/redactions and repeated chosen-predicate probes. A sample lacking redactions is not permission to execute an aggregate, and readable-only summaries never redefine SQL semantics. Record planning overhead/quality on selective policies and mixed workloads before richer sampling. Timing/cache noninterference is not established by normalized-content tests; estimate caches remain invocation- and planner-session-scoped.
