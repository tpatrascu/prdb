# Sandboxed SQL v3 integration tests

The sandbox acceptance tests in `engine/tests/commit.rs` are enabled in the normal workspace suite and must run under the delegated service described below. The `sandboxed_v3_sql_error_latches_failure_and_durably_aborts_after_partial_output` test runs the maintained TinyCC artifact through authenticated staging, the configured cgroup/Landlock executor launch path, result relay, and storage terminal decision. The artifact writes provisional bytes, catches an unsupported SQL statement error, and returns success. The test requires the v3 host latch to turn that caught error into a worker failure, then checks that storage confirms ABORTED before the gateway terminal frame follows the provisional result frame.

The same confined SQL DML acceptance seeds `analytics_pressure_records` with 128 distinct 8,192-byte text keys and executes grouped `COUNT(*)` through the bounded v4 SDK runner. This is exactly 1 MiB of copied group-key data. The callback validates every key byte and all 128 groups; its first callback relays a marker while the four operational workers continue reads and commits. Five delegated-cgroup repetitions sampled the live analytics cgroup and compared baseline and concurrent operational latency. These are local comparative measurements, not a configured performance target or allocator-level copy measurement.

The first grouped-result marker also starts an online index backfill over a separate 1,024-row table with 8 KiB keys. The artifact relays a second marker as grouping resumes; the acceptance checks that index creation finishes after that point while the confined worker remains active. Four operational workers continue reads and commits. Five delegated-cgroup repetitions passed. The measured concurrent commit p99 median was 739.894 ms versus 18.483 ms at baseline on this host; this identifies a local tail-latency cost, not a target. The index table is separate from the SQL transaction's guarded relations.

The `sandboxed_v3_shared_sql_library_resolves_loads_and_durably_aborts_on_sql_error` acceptance uses the same SQL-error fixture linked dynamically against a test SDK release containing a hostile constructor. It derives PMF1 from the query ELF, resolves the installed release through `SdkLibraryRepository` during START, stages the pinned library beside query.so, and executes the SQL callback only in the confined executor. The durable ABORTED outcome proves the SDK dependency loaded and ran under Landlock/seccomp; query and SDK constructors cannot write outside the private scratch directory. An absent release or bad digest fails before admission. The test proves that the repository pin remains held through worker teardown.

The `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` acceptance installs the test SDK into a temporary instance repository and submits a query-only package containing the query, manifest, scope, and parameters. The server resolves and pins the exact SDK release at START; the confined executor loads the staged dependency and completes the SQL transaction. No SDK library bytes are included in the package or query upload.

Set `PRDB_TEST_COUNT_COLUMN_ONLY=1` to isolate the v24 `COUNT(decimal_value)` relay case in this acceptance. It runs through the SQL statement dispatcher against three Decimal groups and verifies the exact SQLR records: counts 3, 1, and 0 in ordered output, including the all-NULL group. The invocation still runs inside the normal delegated-cgroup executor path and must commit durably.

Set `PRDB_TEST_COUNT_BIGINT_ONLY=1` to isolate the optimizer-backed v24 `COUNT(bigint_value)` relay case. It uses the same authorized three groups with a nullable BIGINT input, filters through `bigint_value IS NULL OR bigint_value IS NOT NULL`, and verifies the exact ordered SQLR counts `3, 1, 0` before requiring a durable commit. The extra input column has its own dependency epoch, grant, and cell-allow policy.

The aggregate `A` invocation also calls the general SQL dispatcher with v23 compound HAVING: `SUM(decimal_value) IS NULL AND COUNT(*) IS NOT NULL AND COUNT(*) >= 1`, followed by ordering and LIMIT. Only the committed all-NULL group `(3,11)` survives, and the gateway checks its exact SQLR row with a NULL DECIMAL(38,2) sum before the durable COMMITTED outcome. The primary hidden-count dispatch query additionally requires both COUNT(*) and SUM to be non-NULL, preserving its existing exact `4.50` result.

The aggregate `A` invocation also exercises v24 through the same dispatcher. A typed Decimal WHERE parameter keeps NULL rows and excludes amounts below `1.25` before grouping. Compound HAVING keeps the all-NULL groups and the two-row group. ORDER BY with NULLS LAST and LIMIT 1 selects right_key `9` and exact DECIMAL(38,2) SUM `3.50`. The gateway verifies the two-column SQLR frame and durable COMMITTED result.

The same v24 query uses its valid Decimal parameter in both WHERE and HAVING. A separate invocation changes only the declared scale from 2 to 1 while all operand cells are visible. The fixture catches the resulting dispatcher error and returns success. The gateway must receive exactly one ABORTED terminal frame and storage must confirm the durable abort.

The same acceptance installs a restrictive cell policy on the Decimal aggregate input. Separate invocations check an optimizer-backed aggregate, an optimizer-backed WHERE NULL test, and a v23 compound HAVING NULL test. The HAVING case uses COUNT(*) IS NULL to exclude every group, but required redacted SUM input must still trigger an evaluation error before callbacks. The C fixture catches that error and returns success. The host latch forces an abort, and the gateway receives only the terminal frame. Storage confirms durable ABORTED for all three invocations.

The `sandboxed_shared_sql_missing_dependency_aborts_inside_executor` acceptance links a second query against the same SDK release and a test-only `libprdb_missing.so.1`, then omits that library from the staged directory and runtime profile. The confined dynamic loader rejects the query before its entry point or either constructor runs; the supervisor records durable ABORTED. The fixture is built only to test this failure path and is never executed outside the sandbox.

The `sandboxed_direct_executor_ipc_rejects_forged_relation_handle` acceptance loads `sql-v3-forged-relation-handle.so` only in the confined executor. The native query skips the SDK and submits OPEN SCAN and STAGE INSERT through the executor callback with a valid wire-shaped but never-issued relation handle. Storage rejects both requests before returning row data or staging a write; no result frame is emitted, and the invocation is durably ABORTED.

The `sandboxed_direct_executor_ipc_rejects_forged_row_handle_mutation` acceptance submits both STAGE DELETE and a validly encoded STAGE UPDATE through the callback, each with a valid wire-shaped but never-issued row handle. Storage rejects both before staging a write, no result frame is emitted, and the invocation is durably ABORTED.

The `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` acceptance configures the storage analytical admission cap to eight and starts the primary SQL worker plus seven cancellation SQL workers, all marked analytical, alongside 64 operational threads. All 72 test threads start behind a barrier. The operational threads each open a token-authenticated invocation; a second barrier holds the first 64 admitted contexts before any begins its authorized point read, scan, or durable commit, and the test asserts that the peak concurrent admission count reached 64. Sixty threads complete one transaction each; four threads continue authorized point reads and scans, then scan a separate two-column pressure table, apply a catalog-authorized row update, and commit. At the primary query's resumed-group marker, the fixture keeps its analytical process alive for 31 seconds while the acceptance measures a 30-second interval. During that interval the test requires at least four operational commits and verifies all eight storage invocation statuses remain Active. Each cancellation fixture submits an optimizer-backed UPDATE; its executor callback reports readiness at the first cancellation check after the authorized scan opens, then polls at a bounded 100-ms interval for the real cancellation response. Only after all seven report ready and the measured interval completes does a ninth START from a separate principal run; storage must reject it specifically with `AdmissionLimitExceeded`. The test-local staging caps are set to eight per principal and nine globally so the ninth START reaches storage for that assertion. The SDKs must close their cancelled scans, stage no UPDATE rows, latch statement failure, and return `CANCELLED` with an update count of zero. The acceptance confirms each cancellation result stream and durable ABORTED outcome, while checking the primary cancellation reaches the SDK poll within two seconds. It samples `memory.current` and `memory.peak` for all eight analytical worker cgroups and checks each peak against the configured 256 MiB worker limit. This covers eight simultaneous confined analytics workers and 30 seconds of concurrent operational row updates on the local cgroup/Landlock path. The run does not measure retained database file growth or physical reclamation and does not set target-hardware or latency targets.

The analytical acceptance's separate `A` invocation first runs `SELECT group_key, SUM(measure) ... ORDER BY SUM(measure) DESC NULLS LAST, group_key ASC NULLS FIRST` over the 128-row pressure table. The query forms 64 two-row groups with 8,172-byte text keys and checks every byte, exact BIGINT sums, sort metadata, and all 64 SQLR records through the gateway relay. Its 32-KiB batch lets each page carry multiple large rows, staying beneath the v12 runner's 124-page ceiling while preserving the 128-row and 1-MiB materialization bounds. Set `PRDB_TEST_ORDERED_ANALYTICAL_ONLY=1` to run this ordered query alone in the same confined test before the longer primary workload; the normal acceptance runs it in `A` before the composite aggregate matrix. A follow-on `B` invocation runs optimizer-backed composite SUM, MIN, MAX, and AVG over BIGINT and SMALLINT measure columns in a four-column table with its own executor request budget. The aggregate principal has row and per-column cell SELECT policies for all four columns. The BIGINT measure in the first group has one NULL across two visible rows; all four BIGINT aggregate results ignore it while retaining a matching-row count of two. SMALLINT SUM widens to BIGINT, MIN/MAX retain SMALLINT, and AVG uses DECIMAL(38,6). It also performs the generated UUID `DEFAULT` insert, which keeps that write out of the primary fixture's exhausted scan-work budget; its narrow requested scope covers the BIGINT read and identity-table insert.

The same acceptance covers optimizer scan choices against reference SQL in one confined executor. A nonunique `records_id_range` index is available after the query transaction inserts and updates its one visible row; the filtered equality SELECT has an exact one-row predicate estimate, so the fixture asserts one `OPEN_SCAN`, no `SCAN_INDEX_RANGE`, and equality with a direct authorized SQL execution. The five-row `grouped_records` range query remains above the four-row cutoff, asserts one `SCAN_INDEX_RANGE`, and compares duplicate-preserving results with the reference SQL scan. A separate 1,024-row table has an indexed key repeated eight times per value; the fixture queries key 3, whose eight rows occupy positions 24–31, with a 32-row page bound. It checks all eight values from both the optimizer and reference scan and records their elapsed times. A 128-row probe caused `ScanBudgetExceeded` at a later optimizer operation in this cumulative invocation, so the accepted comparison is bounded to 32 candidates. The equality and range tests use distinct table populations because the bounded predicate estimator returns exact results only when the full visible population is at most four.

The same acceptance also exercises bounded result backpressure. With parameter `O`, the confined TinyCC fixture writes 256 maximum-sized 16-KiB chunks (4 MiB total). The gateway-side reader delays 2 ms per chunk while four operational workers perform 64 authorized reads and commits and outcome maintenance prunes a bounded batch containing eight expired outcomes. The test verifies every chunk and terminal frame, requires the supervisor relay itself to take at least 200 ms, and confirms all operational operations finish. This drives the bounded result queue against a slow consumer without running the artifact outside the sandbox.

It starts a second 4-MiB output invocation and requests owner cancellation 30 ms into the slow relay. The terminal must report ABORTED within two seconds after cancellation; already-relayed result frames remain provisional. This covers cancellation racing with successful worker exit and terminal storage error handling through the real executor and gateway sockets. The maintenance overlap covers outcome pruning; index builds and redb compaction are not part of this acceptance.

A third 4-MiB output invocation crosses the real TCP gateway with its 150-ms idle/write deadline. The TCP client sends START and then does not read result frames. Constrained loopback send capacity forces the TCP write deadline to expire; the gateway closes the Unix service stream, the confined supervisor relay fails and reaps the worker, and an owner-scoped storage lookup must report durable ABORTED. The terminal frame may be lost with the timed-out connection, so the assertion relies on storage outcome rather than delivery.

The `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` test uses `engine/tests/fixtures/sql_v3_write_read.c` to run a sequence of SDK calls over one sandboxed executor connection. The fixture exports v3 through v5 entry points; ABI v5 adds optimizer-backed UPDATE while retaining the v4 optimizer SELECT path. It creates the nullable `records` table, a generated-UUID `identity_records` table, a two-column `grouped_records` table, a separate `decimal_grouped_records` table with two INTEGER keys and DECIMAL(4,2) values, and a distinct `linked_records` table. It seeds `(left_key,right_key)` rows `(1,7)`, `(1,7)`, and `(2,9)` plus Decimal values `1.00`, `NULL`, `1.00`, `1.25`, and `2.25` across the two groups. The query principal receives SELECT grants and allow policies for the Decimal table and its columns, and the invocation scope includes the additional relation. It also grants SELECT on the other required tables and columns plus INSERT on `identity_records`, adds an INSERT allow policy for that table, and includes those rights in the invocation's requested scope. The artifact inserts NULL into `records`, verifies the row in a following SELECT/UPDATE scan, updates it to 42, verifies that value in a following SELECT, then groups by `id` with `MIN(id)`, `SUM(id)`, and `AVG(id)`. It routes the AVG query through optimizer request statement 10 and plan kind 10, validates the v7 AST and authorized binding, re-resolves executor identity, and invokes the bounded v7 grouping runner before checking the established DECIMAL(38,6) SQLR output. It also routes a v12 grouped AVG query through request statement 11 and plan kind 11, matching two sort expressions (AVG descending NULLS LAST, then group key ascending NULLS FIRST), LIMIT, and the authorized binding before re-resolving executor identity and invoking the bounded v12 sorter; the acceptance checks both ordered DECIMAL(38,6) SQLR frames byte-for-byte. It routes v12 grouped `COUNT(*) ORDER BY COUNT(*) DESC NULLS LAST, id ASC NULLS LAST` through the optimizer's kind-5 grouping-plan validation, then the SDK's bounded grouped-sort runner, and writes its result as SQLR. The optimizer request validates the group key, relation identity, executor shape, and LIMIT; ORDER BY stays in the SDK and this composition accepts no WHERE or HAVING. It runs v13 grouped `COUNT(*)` on the two authorized key columns through the kind-13 composite aggregate optimizer wrapper, validating the optimizer plan and re-resolved relation identity before the authorized scan. It then runs v15 with parameterized composite HAVING, v17 with literal composite HAVING, and v18 with `(COUNT(*) >= 2 OR COUNT(*) = 3) AND NOT COUNT(*) < 2`; all composite queries use `ORDER BY right_key DESC NULLS LAST, COUNT(*) DESC, left_key ASC NULLS LAST`. The fixture runs `MIN(decimal_value) <= 1.00e0 ORDER BY left_key ASC LIMIT 1`, validates MIN HAVING at input DECIMAL(4,2) precision and scale, and checks the single `(1,7,1.00)` SQLR frame byte-for-byte. It then calls `prdb_sdk_sql_run_statement_v1` with a v22 composite SUM query containing `HAVING COUNT(*) >= 2 AND SUM(decimal_value) >= 4.50e0`; only `(2,9,4.50)` reaches the callback, and the acceptance checks the relayed SQLR frame byte-for-byte. The acceptance checks each emitted composite-group SQLR frame byte-for-byte. Parser, binder, and runner unit fixtures retain the v21 numeric COUNT and Decimal MAX coverage; the confined artifact stays within the invocation request budget. It next runs a v8 `INNER JOIN` across the linked relations through `prdb_sdk_sql_run_statement_v1`, independent planner descriptions, and sequential authorized executor scans, then checks the exact relayed SQLR row; this is followed by the two-key v19 aliased join across `grouped_records AS g` and `linked_records AS l` through ABI v5 optimizer submission, plan-to-AST validation, executor-side stable-identity re-resolution, and bounded join execution. It then runs a v19 self-join of `linked_records AS a` and `linked_records AS b`, followed by a parameterized v20 qualified-WHERE join dispatched through `prdb_sdk_sql_run_statement_v1`; it filters before LIMIT and writes the selected columns as SQLR. The v5 artifact also submits that filtered join as statement 12, validates kind 12 against the v20 AST and parameter, re-resolves both executor relation identities, and returns the same bounded `(1, 42)` result. The test checks each v20 frame byte-for-byte. The artifact then submits `SELECT right_key FROM grouped_records ORDER BY left_key DESC LIMIT 2` through the optimizer-backed kind-7 path and the confined executor; the gateway relay must receive exact one-column SQLR frames containing `9` then `7`, proving that the order key may be hidden from projection and LIMIT follows sorting. The v4 entry point parses and submits `SELECT id FROM records WHERE id = $1 LIMIT 1` through the optimizer process, independently validates the filtered plan and authorized relation shape, and checks the returned integer row is 42. After the multi-row INSERT, the v5 entry submits `UPDATE records SET id = $2 WHERE id = $1` through the isolated optimizer, validates the assignments against the SQL AST and executor metadata, stages the patches through executor IPC, then confirms both rows read back as 43. The artifact then deletes the `records` row and confirms a final SELECT returns no row. After receiving all provisional SQL results, the test closes the gateway before terminal delivery, requires the terminal frame write to fail, and checks that storage retained COMMITTED. Its restricted-principal query follows the normal terminal path. This exercises SQL parsing/binding, optimizer and executor IPC, DEFAULT-to-storage UUID generation, private-write visibility across SELECT/UPDATE/DELETE, filtered plan execution, grouped aggregation and composite multi-key ordering, optimizer-backed two-relation authorized JOIN execution with aliases and composite keys, self-join execution, ordered SELECT and grouped aggregate plan matching and execution, SQLR encoding in the confined artifact, result relay, and storage commit through the real invocation path, including lost-terminal recovery.

The `authenticated_metadata_and_admin_lifecycle_cross_gateway_and_supervisor_processes` process test also runs in the normal suite. Set `PRDB_TEST_RESTRICTED_METADATA_QUERY_ARTIFACT` to the built `sql-v3-restricted-metadata.so` to exercise its restricted metadata branch; it packages the artifact for the test principal, uploads and starts it through `SubmissionClient`, and verifies filtered SQL results and committed STATUS through the external gateway and supervisor processes.

Build the artifacts, SDK release, and installable release profile:

```sh
nix develop --no-update-lock-file -c make -f engine/sdk/Makefile release-profile
```

Create an external runtime-data directory for each test run; leave compiler output in the existing repository `target/` directories:

```sh
export PRDB_TEST_ROOT="$HOME/tmp/prdb-tests"
export PRDB_TEST_RUN_DIR="$PRDB_TEST_ROOT/runs/r$(date +%s)"
mkdir -p "$PRDB_TEST_ROOT/t" "$PRDB_TEST_RUN_DIR/data"
if [ ! -e "$HOME/t" ] && [ ! -L "$HOME/t" ]; then ln -s "$PRDB_TEST_ROOT/t" "$HOME/t"; fi
test "$(readlink -f "$HOME/t")" = "$(readlink -f "$PRDB_TEST_ROOT/t")"
export TMPDIR="$HOME/t"
```

Run `release-profile` after changing the SDK or query fixtures. The process tests use `PRDB_TEST_INSTALLED_SDK_RELEASE_DIR`, which points into `target/release-profile/`; rebuilding only the SDK release leaves that test input stale. Query binaries and SDK libraries are compiler outputs and stay under the established repository `target/` paths. Use `$PRDB_TEST_RUN_DIR` for runtime query/data files, databases, spill files, logs, and temporary directories.

This builds `sql-v3-caught-error.so`, `sql-v3-shared-library.so`, `sql-v3-missing-dependency.so`, `sql-v3-network-constructor.so`, `sql-v3-write-read.so`, and `sql-v3-restricted-metadata.so`, plus the regular and hostile-constructor `libprdb_sql.so.1` releases and their metadata. These are untrusted native libraries and query artifacts and must only be loaded through the sandboxed executor tests.

Run the full workspace test suite inside a delegated `systemd --user` unit. A direct `cargo test` from a desktop application scope is not a useful preflight: that scope may omit the `cpu` controller even when the host mount is writable. The repository launcher moves its process into a child cgroup, enables the delegated controllers on the unit cgroup, and exports the absolute parent path for the test.

Configure these environment variables in the shell command run by the unit:

- `PRDB_TEST_ROOT`: scratch root, normally `$HOME/tmp/prdb-tests`; create it before running the service.
- `PRDB_TEST_RUN_DIR`: unique run directory below `$PRDB_TEST_ROOT/runs/` for scratch data and logs.
- `TMPDIR`: set to `$PRDB_TEST_RUN_DIR/tmp` so Rust temporary directories and test databases stay outside the checkout.
- `PRDB_TEST_CGROUP_PARENT`: an existing cgroup v2 parent delegated with enabled `cpu`, `memory`, and `pids` controllers.
- `PRDB_TEST_QUERY_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-caught-error.so`.
- `PRDB_TEST_SHARED_SQL_QUERY_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-shared-library.so`.
- `PRDB_TEST_SHARED_SQL_LOAD_FAILURE_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-missing-dependency.so`.
- `PRDB_TEST_EXTRA_ALLOWED_DEPENDENCY`: set to `libprdb_missing.so.1` for the missing-dependency fixture so manifest admission succeeds and the confined loader observes the missing runtime file.
- `PRDB_TEST_SDK_RELEASE_DIR`: absolute path to the test release directory containing the hostile SDK constructor, normally `$PWD/target/sdk-v1/hostile-sdk/releases/linux-x86_64/x86_64-v1/nixos-x86_64-glibc-2.42/sdk-1-abis1,2,3,4,5,6` for the pinned release profile.
- `PRDB_TEST_INSTALLED_SDK_RELEASE_DIR`: absolute path to the normal SDK release in `$PWD/target/release-profile`; process tests install these artifacts into a temporary instance repository.
- `PRDB_TEST_WRITE_READ_QUERY_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-write-read.so`.
- `PRDB_TEST_ORDERED_ANALYTICAL_ONLY`: optionally set to `1` to isolate the high-cardinality ordered SUM branch of the confined write/read acceptance.
- `PRDB_TEST_FILTERED_COMPOSITE_ONLY`: optionally set to `1` to isolate the filtered ordered composite aggregate branch. It submits `SUM(decimal_value)` grouped by two keys with `WHERE left_key = $1 AND (decimal_value IS NULL OR decimal_value IS NOT NULL)`, compound `HAVING SUM(decimal_value) IS NOT NULL AND COUNT(*) >= 1`, and three `ORDER BY` items. It binds `$1` to `1`, verifies the null-test branches retain the two rows in `(1,7)`, checks sort metadata, and relays the exact DECIMAL(38,2) sum `1.00` through the gateway before commit. This exercises optimizer statement 16 / plan kind 16.
- `PRDB_TEST_COUNT_COLUMN_ONLY`: optionally set to `1` to isolate the confined v24 `COUNT(column)` SQLR relay case. It checks non-NULL counting and zero for an all-NULL group through the dispatcher and gateway.
- `PRDB_TEST_COUNT_BIGINT_ONLY`: optionally set to `1` to isolate optimizer-backed `COUNT(bigint_value)` over a nullable BIGINT input through the confined executor, gateway SQLR relay, and durable commit.
- `PRDB_TEST_RESTRICTED_METADATA_QUERY_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-restricted-metadata.so`, used by the restricted-principal metadata acceptance.
- `PRDB_TEST_NETWORK_CONSTRUCTOR_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-network-constructor.so`.
- `PRDB_TEST_FORGED_HANDLE_QUERY_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-forged-relation-handle.so`.
- `PRDB_TEST_FORGED_ROW_HANDLE_QUERY_ARTIFACT`: absolute path to `$PRDB_TEST_RUN_DIR/queries/sql-v3-forged-row-handle.so`.
- `PRDB_TEST_RUNTIME_READ_EXECUTE`: platform-separated absolute paths for the pinned dynamic loader, libc, and other executor runtime dependencies.
- `PRDB_TEST_RUNTIME_READ_ONLY`: platform-separated absolute paths for runtime configuration files the dynamic loader needs, such as its loader cache when applicable. Set it to an empty string when the selected runtime has no read-only files; do not use absent paths as placeholders.

The `sandboxed_v3_sql_dml_sequence_is_visible_and_commits` test has focused ABI v6 spill modes selected by one environment variable: `PRDB_TEST_SPILL_QUOTA_ONLY`, `PRDB_TEST_SPILL_ONLY`, `PRDB_TEST_SPILL_LIMIT_ONLY`, `PRDB_TEST_SPILL_DISABLED_ONLY`, `PRDB_TEST_SPILL_SORT_ONLY`, `PRDB_TEST_SPILL_DECIMAL_ONLY`, `PRDB_TEST_SPILL_REDACTED_ONLY`, `PRDB_TEST_SPILL_JOIN_ONLY`, `PRDB_TEST_SPILL_JOIN_DECIMAL_ONLY`, `PRDB_TEST_SPILL_JOIN_FILTERED_ONLY`, `PRDB_TEST_SPILL_JOIN_PARAMETER_ONLY`, `PRDB_TEST_SPILL_JOIN_BIGINT_ONLY`, `PRDB_TEST_SPILL_JOIN_OVERSIZE_ONLY`, `PRDB_TEST_SPILL_JOIN_TEXT_ONLY`, `PRDB_TEST_SPILL_CRASH_ONLY`, or `PRDB_TEST_SPILL_PRESSURE_ONLY`. The enabled modes open a real `SpillBroker` under a private temporary scratch parent. Spill GROUP BY inserts two NULL keys and checks one `(NULL,2)` SQLR group; the LIMIT mode checks the first two sorted groups after aggregation; integer ORDER BY checks NULL-first descending output; Decimal ORDER BY checks NULL-first Decimal ordering and exact SQLR encodings; the REDACTED mode applies a restrictive cell policy to the Decimal JOIN sort key and requires a durable abort with no SQLR rows. The broker's response cap is smaller than the append payload, confirming response and request limits are independent. Each mode must run through the delegated cgroup wrapper with the SDK release and runtime variables above. # Spill filesystem smoke probe

PRDB_TEST_SPILL_FILESYSTEM_ROOT=/absolute/path/on/mount \
