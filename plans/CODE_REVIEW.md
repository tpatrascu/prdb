# Code review progress

This file tracks review and repair evidence separately from implementation milestones. The scope is the current uncommitted Rust engine, tests, and related specification changes; this is an in-progress review, not a production readiness assessment.

## Findings fixed

- Transaction finalization could reject an invalid index removal without a durable aborted outcome. Invalid removals now fail during staging, and other definitive commit-validation failures record an abort; storage errors remain uncertain and are not converted into an abort decision. Regression tests first failed on the old behavior and now pass.
- Removing a newly staged row discarded its staged index entries without releasing their byte budget. Accounting is now recomputed after removal; a regression test first failed with `IndexOverlayLimitExceeded` and now passes.
- Follow-up review of sequential index changes found that the missing-removal fix also rejected removing a newly staged addition. Staging now cancels that addition, frees its byte budget, and continues to reject a truly missing membership. A real-redb regression first failed with `InvalidIndex` and now confirms only the final key is published.
- Catalog commits validated only changed constraints, so deleting an expression used by an unchanged CHECK could commit and leave a dangling definition. Catalog changes to a table, column, expression, constraint, or index now stream and validate the final constraint set against the final catalog, capped at 65,536 records. A real-redb regression failed before the fix (`Ok(2)`), now rejects the orphaning deletion without publication, and permits deleting the expression, constraint, and table together. This is not complete validation of the entire catalog graph.
- The table-schema loader cached a fully parameterized scalar by type ID, incorrectly reusing the first VARCHAR length or DECIMAL precision/scale for later columns and skipping validation of their parameters. It now caches the guarded type record and decodes each column's parameters independently. A real-redb regression first showed the duplicate parameters, then passed for distinct lengths/scales and rejection of an invalid later column; it also exercises tuple encoding with the loaded schema.
- The catalog-default insert helper accepted a caller-supplied UUID as a generated identity and exempted it from field INSERT checks. A regression first demonstrated acceptance. Until storage-owned generation and collision checks exist, this helper rejects all tables with generated columns, for explicit and DEFAULT inputs, and records ABORTED; the low-level materialized-row helper remains trusted-only.
- The catalog authority loader accepted a disabled user or a role as the invocation principal. It now denies both while still allowing inherited non-login roles. A real-redb regression first reproduced acceptance; it also checks that disabling a previously loaded user causes a pending write to conflict. This is not credential authentication or complete admission.
- CHECK reference validation decoded the expression envelope without comparing its embedded logical key to the lookup key. A valid envelope stored under a different expression ID therefore allowed a catalog commit despite corruption. Validation now uses the shared key-checking decoder; a corruption-injection regression first observed an incorrect successful commit and now confirms rejection without advancing the sequence.
- A standalone principal update could restore an old authority epoch after a membership or grant change, reproducing the principal bytes guarded by a stale reader. Catalog publication now validates principal records and requires every changed existing principal record to strictly advance its epoch. A regression first reproduced the rollback (`Ok(3)`); a separate phantom-membership test verifies the rollback is rejected and the stale write conflicts. Principal deletion/recreation and complete ID non-reuse still require lifecycle enforcement.
- Table schema and write epochs had the same standalone-rollback gap after a column or policy change. Existing table records now require nondecreasing values in both domains and an advance in at least one domain whenever the record changes. A regression first reproduced a schema-version rollback, and now exercises rejection of rollback in both domains while a pinned writer conflicts. Table ID non-reuse after deletion remains unimplemented.
- Membership graph validation applied its 4,096-edge limit while processing submitted writes in order. An addition listed before a compensating removal therefore rejected a valid final graph. Removals are now applied first, and a real-redb test at the limit exercises both write orders and rejects a genuinely oversized final graph. The regression failed with `InvalidCatalog` before the fix.
- Policy-target validation bounded only the existing target set; staged additions could publish 4,097 targets. The final set is now bounded after removals and additions, independently of write order. A low-level real-redb boundary fixture first observed the oversized commit succeed and now verifies rejection and a valid replacement at the limit. It does not establish complete policy-target referential integrity.
- The low-level transaction delete path accepted a second delete of a snapshot row already deleted in its overlay, contradicting own-write visibility. It now returns `NotFound` and aborts; a real-redb regression first failed on the duplicate delete and now verifies durable ABORTED and preservation of the original row.
- ENG1 structural decoding accepted nonzero logical version numbers as intended, but transaction admission and publication failed to reject unsupported catalog, expression, or built-in-semantics versions. These paths and aborted-outcome publication now check the supported version tuple (1, 1, 1) without writing to an unsupported database. A real-redb regression failed at admission before the fix and covers all three version fields plus a version change after a snapshot is opened.
